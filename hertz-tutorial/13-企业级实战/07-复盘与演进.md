# 07-复盘与演进
> 一句话定位：上线只是开始，用复盘、容量评估与技术债管理，把 mall-lite 从“能跑”推向“能长期跑”。

## 本篇目标

- 用统一模板做无责复盘，把故障转成可验收的改进项
- 读懂压测报告，快速定位 DB 连接池、Redis 热 key、Kafka 积压与 GC 瓶颈
- 掌握容量评估公式，给出有依据的副本数、连接池与分区数
- 建立技术债清单与优先级，规划分库分表、CQRS、多活等演进路线
- 固化团队协作规范，并重新评估“是否真的需要微服务”

## 一、复盘模板

固定六段，缺一段就不算复盘：目标、结果、问题、根因、改进、沉淀。以一次大促事故为例：

| 段落 | 内容 |
| --- | --- |
| 目标 | 下单 P99 ≤ 300ms，错误率 < 0.1% |
| 结果 | 20:00 起 P99 升至 1.8s，错误率 6%，持续 12 分钟 |
| 问题 | 库存服务 DB 连接池耗尽，预扣超时拖垮订单线程 |
| 根因 | 大促前只扩了 Pod，未扩连接池；重试放大流量 |
| 改进 | 连接池按“实例数 × 并发”重算；写操作禁止无幂等重试；补连接池水位告警 |
| 沉淀 | 容量评审加入“依赖连接数”检查项，压测脚本纳入发布门禁 |

根因分析用 5 Whys，追到“机制缺失”为止，不要停在“某人忘了”。复盘对事不对人，行动项必须有负责人、截止时间和验收标准；没有验收标准的改进等于没改。可直接套用下面的记录格式：

```markdown
## 事故复盘：订单预扣超时（2026-11-20）
- 影响：20:00–20:12，下单失败率 6%，影响约 1.2 万用户
- 时间线：20:00 告警 → 20:03 定位连接池 → 20:07 扩容 → 20:12 恢复
- 根因：连接池 50 未随副本调整；客户端重试把流量放大 3 倍
- 改进：池大小纳入容量评审（@后端，11-30）
        写接口禁用无幂等重试（@架构，11-27）
- 验收：3 倍峰值下 pool_wait < 5ms，重试流量为 0
```

行动项另起一张表跟踪，避免“会上热烈、会后失忆”：

| 改进项 | Owner | 截止 | 状态 | 验收证据 |
| --- | --- | --- | --- | --- |
| 连接池容量评审 | 后端 | 11-30 | 进行中 | 评审记录 + 压测报告 |
| 重试策略改造 | 架构 | 11-27 | 待开始 | 回归用例通过 |

## 二、压测报告解读

先看曲线形状：吞吐上升而 P99 突然拐头的位置就是拐点，之后加并发只会加延迟和错误。

| 症状 | 大概率瓶颈 | 验证方式 | 处置 |
| --- | --- | --- | --- |
| 应用 CPU 不高，P99 锯齿上升 | DB 连接池排队 | `pool_wait`、`SHOW PROCESSLIST` | 扩池、缩短事务、读写分离 |
| 单个接口 QPS 上不去，Redis CPU 高 | 热 key | `redis-cli --hotkeys`、单 key 延迟 | 本地缓存、key 分桶、批量合并 |
| 消费延迟持续增长 | Kafka 积压 | consumer lag、消费耗时 | 扩分区/消费者、批量提交 |
| P99 周期性尖刺，CPU 曲线锯齿 | GC | `GODEBUG=gctrace=1`、pprof | 降分配、调 GOGC、对象复用 |
| 网关先饱和 | JSON 序列化/TLS | pprof CPU、连接数 | 调 worker、keep-alive、换序列化 |

一份能用的报告至少包含五项，缺一项结论都不可信：

- 压测模型：读写比、热点 SKU 占比、数据量级与用户分布
- 环境规格：副本数、CPU/内存、DB/Redis 规格与网络拓扑
- 拐点数据：QPS—延迟曲线、拐点位置、对应错误率
- 瓶颈证据：火焰图、慢查询、连接池等待、GC 日志
- 结论建议：扩什么、扩多少、还差哪些前置条件

只给一个“最大 QPS 5000”的数字，没有拐点与错误率，等于没测。还要警惕三种误判：全走缓存导致 DB 压力被低估、单机压测忽略网关限流、短时间压测没跑到连接池稳定态。

## 三、容量评估方法

```text
单实例安全 QPS = 压测拐点 × 0.6
所需实例数     = ceil(峰值 QPS / 单实例安全 QPS × (1 + 冗余系数 0.5))
DB 连接总数    = 实例数 × 单实例池大小 ≤ max_connections × 0.6
Redis 内存     = key 数 × 平均 value 大小 × 1.5（副本/碎片）
Kafka 分区数   = max(目标吞吐 / 单分区吞吐, 消费者实例数)
```

以 mall-lite 为例，把公式落成一张可核对的表：

| 资源 | 计算 | 结论 |
| --- | --- | --- |
| 应用实例 | 2000 ÷ 780 × 1.5 | 4 个 product 实例 |
| DB 连接 | 4 × 50 | 200，低于 500 × 0.6 |
| Redis 内存 | 500 万 key × 2KB × 1.5 | 约 15GB，留一倍余量 |
| Kafka 分区 | max(2000/500, 6 消费者) | 6 分区 |

订单表按 3 年 5000 万行规划，超过 2000 万行进入分表评估。容量评估每季度复跑一次，大促前按 3 倍峰值做专项；扩容后要复测，确认瓶颈没有转移到 DB 或 Redis。

## 四、技术债清单与优先级

| 债务 | 影响 | 成本 | 优先级 |
| --- | --- | --- | --- |
| 三个服务共享一个 pkg 模块，改动连带发版 | 发布耦合 | 中 | P1 |
| 缺契约测试，IDL 改动靠人肉核对 | 联调故障 | 低 | P0 |
| 缓存一致性只靠“删 key” | 偶发脏读 | 中 | P2 |
| Outbox 单表无归档，查询变慢 | 投递延迟 | 低 | P2 |
| 订单查询仍走主库深分页 | DB 压力 | 中 | P1 |
| 告警噪音多，值班疲劳 | 真故障被淹没 | 低 | P0 |

排序规则：P0 正确性/安全，P1 稳定性与发布效率，P2 性能，P3 体验。每个迭代固定留 20% 容量还债，债务项必须写“不还的后果”，否则永远排不上。需要量化时用下面的打分：

```text
优先级分 = 影响面(1-5) × 发生频率(1-5) × 不修复风险(1-5) ÷ 修复成本(1-5)
≥ 20 本迭代做；10–19 排入下两个迭代；< 10 观察并记录
```

示例：缺契约测试得分 `4 × 4 × 5 ÷ 2 = 40`，立即做；Outbox 归档得分 `2 × 2 × 3 ÷ 2 = 6`，先观察。

## 五、演进路线

```mermaid
flowchart LR
  A[单库 + 单服务] --> B[读写分离 + 缓存]
  B --> C[分库分表]
  C --> D[CQRS + 事件驱动]
  D --> E[多活]
```

- **读写分离**：主从延迟可接受、读多写少时做；写完立即读强制走主库，延迟监控纳入告警
- **分库分表**：单表 > 2000 万行或写入到顶再做；`user_id` 分片，`order_no` 内置分片位，避免全库扫描
- **CQRS**：查询模型通过 Kafka 同步到 ES，列表/搜索与交易库解耦；接受最终一致并给出延迟 SLA
- **事件驱动**：Outbox 升级为 schema registry + 事件版本，消费者可回放；先统一事件契约再谈流处理
- **多活**：按单元化切流量，先做同城双活，再做异地；数据同步、冲突解决与成本要提前算清

| 阶段 | 触发条件 | 关键动作 | 验证指标 |
| --- | --- | --- | --- |
| 读写分离 | 读 QPS 持续超单主 60% | 加只读副本、写后读主 | 主从延迟 < 100ms |
| 分库分表 | 单表 > 2000 万行或写入到顶 | 以 user_id 分片、订单号埋分片位 | 跨分片查询为 0 |
| CQRS | 列表/搜索拖慢交易库 | Kafka 同步到 ES，查询双读 | 同步延迟 < 3s |
| 事件驱动 | 消费者超过 5 个、事件契约混乱 | Schema Registry + 版本化事件 | 事件可回放 |
| 多活 | 单地域 RTO 不达标 | 单元化 + 双向同步 | 切流演练 10 分钟内 |

每一步都要有触发条件，而不是“别人都做了”。mall-lite 当前停留在第二阶段，订单量到千万级再启动分表。

## 六、团队协作规范

- **IDL 单一事实来源**：只改 `idl/*.thrift`，生成代码随 PR 提交；字段只增不改序号，破坏性变更升版本
- **Code Review 清单**：context 与超时、错误是否被吞、幂等键、SQL 是否走索引、N+1、日志脱敏、单测覆盖失败路径、配置是否有默认值
- **接口文档**：由 IDL 生成，变更写 CHANGELOG；废弃字段标注 `deprecated` 与下线时间
- **值班手册**：告警分级、看板入口、常见故障剧本（库存不足、MQ 积压、DB 连接满）、升级路径与回滚命令
- **发布纪律**：周五下午不发布，灰度观察 30 分钟，回滚演练每季度一次

接口变更走固定流程，避免“改完才发现调用方崩了”：

1. 提 PR 只改 `idl/*.thrift`，附兼容性说明（新增/废弃/删除）
2. CI 生成代码并跑契约测试，失败即阻断合并
3. 先发布服务端（兼容新旧字段），确认无报错后再让调用方切换
4. 废弃字段观察两个迭代，确认无流量后删除，并在 CHANGELOG 标注

## 七、从单体到微服务的再评估

拆分前先问五个问题：是否有独立扩缩容需求？发布节奏是否互相阻塞？故障是否需要隔离？是否有明确的团队 ownership？是否具备观测、CI 与自动化运维？五个里少于三个“是”，优先做模块化单体。

| 评估项 | 拆分的信号 | 不拆的信号 |
| --- | --- | --- |
| 扩缩容 | 读写/计算曲线差异 > 3 倍 | 各模块压力接近 |
| 发布节奏 | 一天多次 vs 一周一次 | 同一批人同一节奏 |
| 故障隔离 | 一个模块拖垮全站 | 故障面本来就共享 DB |
| 团队边界 | 3 个以上小组各自负责 | 一个小组 8 人以内 |
| 基础设施 | 有观测、CI、灰度、值班 | 还在手工发布 |

微服务的代价是真实的：网络不可靠、分布式事务、链路变长、排障成本上升。mall-lite 拆成三个服务，是因为商品读与订单写的扩缩容曲线完全不同，且库存需要独立保护；如果只是 CRUD 后台，单体加模块边界更划算。架构没有终点，只有与当前规模和团队匹配的选择。

## 常见坑

1. **复盘变成追责会**：没人说真话，根因永远停在“操作失误”；坚持无责与机制改进。
2. **只看平均延迟**：平均值掩盖长尾，用户感知的是 P99；所有 SLO 用分位。
3. **压测数据太理想**：全走缓存、无热点、无锁冲突，结论不可用；压测模型要贴近真实分布。
4. **容量只算应用**：忽略 DB 连接、Redis 内存、Kafka 分区，扩容后瓶颈立刻转移。
5. **技术债只记不做**：清单变成许愿池；每项必须有 owner、截止时间与验收标准。
6. **为微服务而微服务**：团队与观测能力没跟上，拆完只是把单体故障变成分布式故障。

## 小结

- 复盘六段式 + 5 Whys，行动项必须可验收，否则只是故事会
- 压测看拐点与错误率，按“症状 → 证据 → 处置”定位四类典型瓶颈
- 容量用公式算，实例、连接、内存、分区要一起匹配，留 50% 冗余
- 技术债按正确性 > 稳定性 > 性能 > 体验排序，每迭代固定还 20%
- 演进由触发条件驱动；微服务是手段，匹配团队与规模才是目的

## 练习

1. 用本文模板复盘一次你经历过的线上问题，写出至少三条带 owner 和截止时间的改进项。
2. 按容量公式为 mall-lite 做一份 3 倍大促评估：实例数、DB 连接、Redis 内存、Kafka 分区。
3. 给当前项目列 10 条技术债，用“影响 × 成本”排序，并说明下个迭代先还哪三条。
