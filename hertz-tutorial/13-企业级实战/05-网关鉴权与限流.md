# 05-网关鉴权与限流
> 一句话定位：把网关做成唯一入口——认证、限流、透传、防重放、灰度与兜底全部在这里收口。

## 本篇目标

- 用路由分组做版本管理与 BFF 聚合，保持对外契约稳定
- 写可复用的 JWT 中间件：校验、黑名单、白名单、身份注入
- 把用户上下文从 HTTP header 透传到 Kitex metainfo
- 用本地令牌桶 + Redis 滑动窗口做双层限流，支持 IP/用户维度
- 补齐 CORS、访问日志、panic 兜底、防重放与灰度路由

- 已读 [02-用户服务Hertz与Kitex落地](02-用户服务Hertz与Kitex落地.md)，掌握 JWT 签发
- Hertz 中间件与路由分组：[03-基本特性/05-中间件](../03-基本特性/05-中间件.md)
- 限流算法与 Redis：[10-Redis缓存最佳实践/03-分布式锁与限流实践](../10-Redis/03-分布式锁与限流实践.md)

## 一、路由聚合与版本管理

```go
h := server.Default(server.WithHostPorts(":8080"))
h.Use(mw.AccessLog(), mw.Recovery(), mw.CORS())

v1 := h.Group("/api/v1")
v1.POST("/auth/register", gw.Register)   // 白名单
v1.POST("/auth/login", gw.Login)
v1.POST("/auth/refresh", gw.Refresh)
v1.GET("/products", gw.ListProducts)
v1.GET("/products/:id", gw.GetProduct)

auth := v1.Group("", mw.JWT(secret, rdb), mw.RateLimit(rl))
auth.GET("/users/me", gw.Me)
auth.POST("/orders", gw.CreateOrder)     // 需 Idempotency-Key
auth.GET("/orders/:id", gw.GetOrder)
auth.GET("/orders/stream", gw.OrderStream) // SSE
```

版本只放在路径里（`/api/v1`），破坏性变更开 `/api/v2`，旧版本至少保留两个迭代并在响应头加 `Deprecation`。BFF 聚合放在网关：订单详情由 order-service 返回订单、再并发调 product-service 补商品标题，网关合并后一次返回，前端少一次往返。`/auth/refresh` 不走 JWT 中间件，校验 refresh 的 `typ` 与 jti 后轮换双令牌，旧 access 立即进黑名单。

## 二、JWT 中间件

```go
func JWT(secret []byte, rdb *redis.Client) app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		raw := strings.TrimPrefix(string(c.GetHeader("Authorization")), "Bearer ")
		if raw == "" {
			response.Fail(c, 401, errcode.Unauthorized, "未登录")
			c.Abort()
			return
		}
		claims, err := jwtx.Parse(raw, secret) // 内部固定 HS256
		if err != nil || claims.Type != "access" {
			response.Fail(c, 401, errcode.TokenInvalid, "登录已失效")
			c.Abort()
			return
		}
		if n, _ := rdb.Exists(ctx, "jwt:block:"+claims.ID).Result(); n > 0 {
			response.Fail(c, 401, errcode.TokenRevoked, "令牌已注销")
			c.Abort()
			return
		}
		c.Set("uid", claims.UserID)
		c.Next(ctx)
	}
}
```

白名单（注册、登录、商品浏览）通过路由分组天然隔离，不靠中间件里写 `if path == ...`。退出登录把 access 的 `jti` 写入 Redis 直到其过期，配合 refresh 轮换实现“立即下线”。

## 三、上下文透传：HTTP → Kitex

```go
uid, _ := c.Get("uid")
ctx = metainfo.WithValue(ctx, "uid", strconv.FormatInt(uid.(int64), 10))
ctx = metainfo.WithValue(ctx, "trace_id", string(c.GetHeader("X-Trace-Id")))
ctx = metainfo.WithValue(ctx, "request_id", string(c.GetHeader("X-Request-Id")))
resp, err := s.orderClient.CreateOrder(ctx, req)
```

Kitex 客户端需启用元信息透传（`transmeta.ClientTTHeaderHandler`，具体以所用版本为准，示例示意）；服务端用 `metainfo.GetValue(ctx, "uid")` 取回，**不信任请求体里的 user_id**。下游据此做鉴权与审计，避免“网关校验了，业务层却被伪造参数绕过”。

## 四、双层限流

本地令牌桶挡住瞬时突发，Redis 滑动窗口保证集群总量：

```lua
local key, now, window, limit = KEYS[1], tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
if redis.call('ZCARD', key) >= limit then return 0 end
redis.call('ZADD', key, now, ARGV[4])
redis.call('PEXPIRE', key, window)
return 1
```

```go
func RateLimit(rdb *redis.Client, cfg *config.RateLimit) app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		dim, limit := "ip:"+c.ClientIP(), cfg.IPLimit
		if v, ok := c.Get("uid"); ok {
			dim, limit = fmt.Sprintf("uid:%d", v.(int64)), cfg.UserLimit
		}
		if !localBucket.Allow(dim, limit) { // 单机粗筛
			c.Header("Retry-After", "1")
			response.Fail(c, 429, errcode.RateLimited, "请求过于频繁")
			c.Abort()
			return
		}
		ok, err := slideWindow(ctx, rdb, "rl:"+dim, time.Second, limit, time.Now().UnixNano())
		if err != nil || !ok { // Redis 故障时退化为本地限流，不整体拒绝
			if err != nil {
				logx.Ctx(ctx).Warnf("rate limit degrade: %v", err)
			} else {
				c.Header("Retry-After", "1")
				response.Fail(c, 429, errcode.RateLimited, "请求过于频繁")
				c.Abort()
				return
			}
		}
		c.Next(ctx)
	}
}
```

限额从 Nacos 动态下发：普通读 200/s/IP、登录 5/min/IP、下单 20/min/用户。`Retry-After` 让客户端知道何时重试，避免重试风暴。

## 五、黑名单

`bl:uid:{id}`、`bl:ip:{ip}` 存 Redis Set，带 TTL 自动解封；管理端接口写入，网关在 JWT 之后检查。黑名单只做“快速拒绝”，永久封禁仍要落 `users.status=0`，否则 Redis 丢数据就绕过。

## 六、CORS

```go
h.Use(cors.New(cors.Config{
	AllowOrigins:     []string{"https://mall.example.com"},
	AllowMethods:     []string{"GET", "POST", "PATCH", "DELETE", "OPTIONS"},
	AllowHeaders:     []string{"Authorization", "Content-Type", "Idempotency-Key", "X-Request-Id"},
	AllowCredentials: true,
	MaxAge:           12 * time.Hour,
}))
```

`AllowOrigins: ["*"]` 与 `AllowCredentials: true` 不能共存；预检请求不要经过 JWT 中间件，否则浏览器拿不到 204。

## 七、访问日志与 trace_id

```go
func AccessLog() app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		start := time.Now()
		c.Next(ctx)
		logx.Ctx(ctx).Info("access",
			"method", string(c.Method()), "path", string(c.Path()),
			"status", c.Response.StatusCode(), "cost_ms", time.Since(start).Milliseconds(),
			"ip", c.ClientIP(), "request_id", string(c.GetHeader("X-Request-Id")))
	}
}
```

`X-Request-Id` 只接受合法字符且长度 ≤ 64，否则重新生成；响应头回写同一个值。日志禁止记录 body、Authorization、Cookie；需要排障时记字段白名单。

## 八、统一响应与 panic 兜底

```go
func Recovery() app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		defer func() {
			if r := recover(); r != nil {
				logx.Ctx(ctx).Errorf("panic: %v\n%s", r, debug.Stack())
				response.Fail(c, 500, errcode.Internal, "系统繁忙")
				c.Abort()
			}
		}()
		c.Next(ctx)
	}
}
```

RPC 错误统一翻译：`BizError.code` 直接透出；`context.DeadlineExceeded` → 504/50001；连接失败或熔断 → 503/50002。网关永远返回 JSON 信封，不允许把 Kitex 原始错误串吐给前端。

## 九、防重放

写接口（尤其支付回调）要求 `X-Timestamp`、`X-Nonce`、`X-Sign`：时间戳与服务器偏差 ≤ 300 秒；nonce 用 `SETNX` 保存 5 分钟；签名 `HMAC-SHA256(secret, method+path+body+timestamp+nonce)`。任一项不满足返回 40003。TLS 防窃听，JWT 防身份伪造，防重放补上“旧请求重发”这一环。

## 十、灰度路由

```go
func pickGray(c *app.RequestContext, uid int64) bool {
	if string(c.GetHeader("X-Gray")) == "v2" {
		return true // 内部测试账号显式指定
	}
	return uid > 0 && uid%100 < atomic.LoadInt64(&grayRatio) // 按用户稳定分桶
}
```

按用户 ID 取模而不是随机，保证同一用户始终命中同一版本。灰度实例在 Nacos 打 `version=v2` 标签，网关用带标签的客户端调用；灰度实例不可用时回退稳定版并打点，绝不把请求挂死。比例从 Nacos 热更新，观察错误率与 P99 再放量。

## 常见坑

1. **在网关聚合里串行调三个服务**：延迟叠加；能并行的用 errgroup，且设总超时。
2. **信任 body 里的 user_id**：越权漏洞；身份只来自 token，下游从 metainfo 取。
3. **限流只做单机**：扩容后总量翻倍；必须 Redis 全局 + 本地粗筛两层。
4. **Redis 故障时全量拒绝**：一次缓存抖动打挂全站；限流应降级为本地桶。
5. **CORS 配 `*` 又带凭证**：浏览器直接拒绝；按域名白名单配置。
6. **panic 后连接未收尾**：网关必须 recover + Abort，否则响应可能半截写出。

## 小结

- 路由按 `/api/v1` 分组，鉴权接口与公开接口物理隔离，白名单不写在 if 里
- JWT 中间件固定算法、校验 typ、检查 jti 黑名单，身份注入 context
- 用户上下文经 metainfo 透传，下游不信任请求体身份字段
- 限流双层：本地桶抗突发、Redis 窗口管全局，故障时降级而非全拒
- 日志、trace_id、panic 兜底、防重放与灰度共同构成网关的“企业级下限”

## 练习

1. 给登录接口单独加 5 次/分钟/IP 的限流，并验证 Redis 宕机时降级为本地 20 次/秒。
2. 实现 `X-Sign` 校验中间件，写一个重放旧请求的测试，确认第二次返回 40003。
3. 用 Nacos 标签做灰度：10% 用户走 v2，要求灰度实例下线时请求自动回退且指标可观测。
