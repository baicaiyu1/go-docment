# 03-商品与库存服务
> 一句话定位：用条件更新 + Lua 预扣 + 流水对账三件套，把“不超卖”从口号变成可验证的工程实现。

## 本篇目标

- 设计 products / stocks / stock_logs 三张表，明确库存口径
- 用 `available >= n` 条件更新杜绝超卖，不依赖应用层判断
- 用 Redis Lua 做预扣，DB 事务做最终事实，失败可回补
- 用 request_id + 唯一索引实现幂等，流水表支持对账
- 落地商品详情缓存、价格快照与 Kitex 接口，给出压测关注点

## 前置知识

- 已读 [02-用户服务Hertz与Kitex落地](02-用户服务Hertz与Kitex落地.md)，熟悉 service/repository 分层
- GORM 事务与乐观锁：[09-MySQL与ORM最佳实践/03-事务-乐观锁-软删除](../09-MySQL与ORM/03-事务-乐观锁-软删除.md)
- Redis 缓存与 Lua：[10-Redis缓存最佳实践/02-缓存模式与三大经典问题](../10-Redis/02-缓存模式与三大经典问题.md)

## 一、三张表定口径

```sql
CREATE TABLE products (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  title VARCHAR(128) NOT NULL,
  price_cent INT NOT NULL COMMENT '展示价，单位分',
  status TINYINT NOT NULL DEFAULT 1 COMMENT '1 上架 0 下架',
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);

CREATE TABLE stocks (
  sku_id BIGINT UNSIGNED PRIMARY KEY,
  product_id BIGINT UNSIGNED NOT NULL,
  available INT NOT NULL DEFAULT 0,
  locked INT NOT NULL DEFAULT 0,
  version BIGINT NOT NULL DEFAULT 0,
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  KEY idx_product (product_id),
  CONSTRAINT ck_available CHECK (available >= 0)
);

CREATE TABLE stock_logs (
  id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
  request_id VARCHAR(64) NOT NULL,
  sku_id BIGINT UNSIGNED NOT NULL,
  delta INT NOT NULL COMMENT '扣减为负，回补为正',
  type VARCHAR(16) NOT NULL COMMENT 'deduct/restore',
  balance_after INT NOT NULL,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  UNIQUE KEY uk_request (request_id, type)
);
```

口径只有一句：`available + locked = 总库存`，下单扣 `available` 同时加 `locked`，支付后扣 `locked`，取消则反向回补。所有变更必须写 `stock_logs`，否则对账无据可依。

## 二、防超卖：一条 SQL 定胜负

```go
res := tx.WithContext(ctx).Model(&model.Stock{}).
	Where("sku_id = ? AND available >= ?", skuID, qty).
	UpdateColumns(map[string]any{
		"available": gorm.Expr("available - ?", qty),
		"locked":    gorm.Expr("locked + ?", qty),
	})
if res.Error != nil {
	return res.Error
}
if res.RowsAffected == 0 {
	return ErrStockNotEnough // 扣不到就是不够，绝不再查一次
}
```

`UPDATE ... WHERE available >= n` 在 InnoDB 行锁内完成读改写，天然串行化同一 SKU。**禁止**“先 SELECT 判断再 UPDATE”，那是在两把锁之间留了竞态窗口；`CHECK` 约束是最后一道保险，不是主逻辑。

## 三、Redis 预扣：把热点挡在 DB 前

`stock:{sku_id}` 存可用量，预热时从 DB 写入。Lua 保证“判断 + 扣减”原子：

```lua
local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then return -2 end          -- 未预热，回源 DB
if stock < tonumber(ARGV[1]) then return -1 end
return redis.call('DECRBY', KEYS[1], ARGV[1])
```

```go
var deductScript = redis.NewScript(luaDeduct)

n, err := deductScript.Run(ctx, s.rdb, []string{stockKey(skuID)}, qty).Int()
switch {
case errors.Is(err, redis.Nil), n == -2:
	// 缓存未命中：直接走 DB 条件更新，成功后 SETNX 回填
case n == -1:
	return ErrStockNotEnough
case err != nil:
	return fmt.Errorf("redis deduct: %w", err) // 降级走 DB，不阻断下单
}
```

Redis 只负责“谁先抢到”，DB 条件更新才是事实来源。DB 扣减失败或事务回滚时，必须 `INCRBY` 回补 Redis；回补失败写补偿任务，不能吞掉。Cluster 下给 key 加 hash tag（`stock:{sku:1001}`）保证同 SKU 落同一槽。

## 四、幂等：request_id 是唯一凭证

```go
reqKey := "stock:req:" + requestID
ok, err := s.rdb.SetNX(ctx, reqKey, "processing", 24*time.Hour).Result()
if err != nil {
	return fmt.Errorf("idempotent guard: %w", err)
}
if !ok {
	return s.loadPreviousResult(ctx, requestID) // 已处理，返回首次结果
}
```

三层防线：Redis `SETNX` 挡重复请求；`stock_logs` 的 `UNIQUE(request_id, type)` 挡并发穿透；命中唯一键时读取已有流水返回成功，而不是报错。Redis 故障时不能放行全部请求，应降级为“只靠 DB 唯一键”，并打点告警。

## 五、流水与对账

扣减事务里三件事必须同生共死：更新 `stocks`、插入 `stock_logs`、写 `Outbox`（若需发事件）。对账 SQL 每晚跑一次：

```sql
SELECT s.sku_id, s.available, s.locked, COALESCE(SUM(l.delta), 0) AS log_balance
FROM stocks s LEFT JOIN stock_logs l ON l.sku_id = s.sku_id
GROUP BY s.sku_id, s.available, s.locked
HAVING s.available + s.locked <> COALESCE(SUM(l.delta), 0);
```

有结果就告警并冻结该 SKU 的自动扣减，人工核对后再放开。对账还要比对 Redis 与 DB 的差值，允许“Redis 偏小”（预扣未落库），不允许“Redis 偏大”。

## 六、商品详情缓存

Cache-Aside + 空值缓存 + singleflight，防止热点 key 失效瞬间打穿：

```go
func (s *productService) Get(ctx context.Context, id int64) (*model.Product, error) {
	key := fmt.Sprintf("product:detail:%d", id)
	if b, err := s.rdb.Get(ctx, key).Bytes(); err == nil {
		if string(b) == "__nil__" {
			return nil, ErrProductNotFound
		}
		var p model.Product
		if json.Unmarshal(b, &p) == nil {
			return &p, nil
		}
	}
	v, err, _ := s.sf.Do(key, func() (any, error) {
		p, err := s.repo.FindByID(ctx, id)
		if err != nil {
			return nil, err
		}
		if p == nil {
			s.rdb.Set(ctx, key, "__nil__", 60*time.Second)
			return nil, ErrProductNotFound
		}
		b, _ := json.Marshal(p)
		s.rdb.Set(ctx, key, b, 10*time.Minute+time.Duration(rand.Intn(120))*time.Second)
		return p, nil
	})
	if err != nil {
		return nil, err
	}
	return v.(*model.Product), nil
}
```

详情页的“剩余库存”单独读 `stock:{sku}`，TTL 3~5 秒，允许展示层短暂滞后；**下单校验永远走 DB**，不能信缓存数字。改价或下架时删除 `product:detail:{id}`，不要 set。

## 七、价格快照

商品价格随时会变，订单必须记录下单瞬间的价格：`order_items.price_cent` 存快照，`product_id` 只做追溯。`GetProduct` 返回 `price_cent` 与 `version`；改价用 `WHERE version = ?` 乐观锁，版本冲突让运营重试。这样即使商品下架、改价，历史订单金额也不会漂移。

## 八、Kitex 接口定义

```thrift
struct Product { 1: i64 id, 2: string title, 3: i64 price_cent, 4: i32 available }
struct GetProductReq  { 1: i64 product_id }
struct DeductStockReq { 1: string request_id, 2: i64 sku_id, 3: i32 qty }
struct DeductStockResp { 1: bool success, 2: i32 remaining }
struct RestoreStockReq { 1: string request_id, 2: i64 sku_id, 3: i32 qty }
struct RestoreStockResp { 1: bool success }

service ProductService {
  Product GetProduct(1: GetProductReq req)
  DeductStockResp DeductStock(1: DeductStockReq req)
  RestoreStockResp RestoreStock(1: RestoreStockReq req)
}
```

`DeductStock` 的 `request_id` 由 order-service 生成并贯穿全链路；`RestoreStock` 幂等键用 `原request_id + restore`，取消与超时关单重复调用也只回补一次。

## 九、压测关注点

- **同一 SKU 行锁**：并发全打一个 SKU 时 DB 串行化，QPS 上限取决于单行更新耗时；用库存分桶（`stocks` 拆 N 行）或 Redis 预扣削峰
- **Redis 热 key**：单 key 写 QPS 有上限，观察 `redis_cmd_duration` 与慢查询，必要时本地批量合并
- **Lua 复杂度**：脚本保持 O(1)，禁止在脚本里遍历大集合
- **连接池**：库存事务短，但并发高，`MaxOpenConns` 与 DB CPU 要一起看
- **正确性验证**：压测后检查 `available + locked = 初始库存`、流水求和一致、无负库存

## 常见坑

1. **先查后改**：`SELECT available` 再 `UPDATE` 在并发下必然超卖；只认带条件的 `UPDATE`。
2. **Redis 扣了 DB 没扣**：异常路径忘记回补，缓存与 DB 永久偏差；补偿任务要按 request_id 可重放。
3. **幂等键放内存**：多实例部署后本地 map 失效，重复请求直接穿透；幂等必须落 Redis 或 DB。
4. **缓存存库存并用于下单**：页面数字滞后几秒可以接受，扣减依据必须是 DB。
5. **对账只看总数**：SKU 之间错账会互相抵消；必须按 SKU 分组比对。
6. **回补无上限**：重复回补把库存刷高；`RestoreStock` 必须校验原扣减流水存在且未回补。

## 小结

- 库存口径固定为 `available + locked`，任何变更都留流水
- 防超卖靠 `UPDATE ... WHERE available >= n`，影响行数为 0 即失败
- Redis Lua 只做预扣削峰，DB 事务是最终事实，失败要可回补
- 幂等三层：Redis SETNX、流水唯一键、结果可重放
- 缓存只服务展示，价格用快照，对账按 SKU 分组并驱动告警
