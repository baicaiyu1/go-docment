# 服务注册与发现总览
> 一句话定位：先把“注册、发现、健康检查、负载均衡”这条链路讲透，再谈 Hertz 的 registry 抽象与选型。
## 本篇目标
- 理解为什么微服务需要注册中心，以及完整调用流程
- 掌握 Hertz 的三个扩展接口：`Registry`、`Resolver`、`Loadbalancer`
- 知道 `registry.Info` 里哪些字段真正影响流量分配
- 能对照 Consul / Nacos / Etcd / Eureka / Polaris / ZooKeeper / ServiceComb 做选型
- 理解健康检查与服务上下线的关系
## 前置知识
- 已读 [03-基本特性/11-客户端Client](../03-基本特性/11-客户端Client.md)
- 了解 DNS 与反向代理的基本作用
- 知道什么是“实例”“节点”“权重”
## 一、为什么需要注册中心
没有注册中心时，调用方通常这样做：

```go
// 硬编码，扩容/迁移/宕机都要改代码发版
c.Get(ctx, nil, "http://10.0.0.12:8888/api/user")
```

问题显而易见：

| 问题 | 后果 |
| --- | --- |
| 地址硬编码 | 扩缩容必须改配置甚至改代码 |
| 无法感知宕机 | 请求持续打到坏节点 |
| 无法加权 | 新机器无法保护性上线 |
| 无元数据 | 无法按机房/版本/灰度路由 |

注册中心把“地址列表”变成一个可动态变化的服务目录：

```text
┌────────────┐   1.注册/心跳   ┌──────────────┐
│  Provider  │ ───────────────▶│   Registry   │
│ (Hertz 服务)│ ◀─── 4.推送/拉取 └──────┬───────┘
└─────┬──────┘                        │ 2.订阅
      │ 5.被调用                       │
      ▼                               ▼
┌────────────────────────────────────────────┐
│              Consumer (Hertz Client)        │
│  Resolver(发现) -> Loadbalancer(选节点) -> 调用 │
└────────────────────────────────────────────┘
```
## 二、完整流程拆解
1. **注册**：Provider 启动后把 `服务名 + IP:Port + 权重 + 标签` 写入注册中心
2. **订阅/发现**：Consumer 按服务名拉取实例列表，并监听变更
3. **健康检查**：注册中心通过心跳（TTL）或主动探测判断实例是否存活
4. **负载均衡**：Consumer 按权重/随机/一致性哈希挑选一个实例
5. **调用与重试**：连接失败或超时后换节点重试（需注意幂等）
6. **下线**：优雅退出时先摘除实例，再等待存量请求结束

Hertz 只负责第 4 步的一部分（默认加权随机），1/2/3/6 由 `hertz-contrib/registry` 的具体实现与你的运维流程负责。
## 三、Hertz 的三个扩展接口
### 3.1 服务注册：`Registry`
定义在 `pkg/app/server/registry`：

```go
type Registry interface {
	Register(info *Info) error
	Deregister(info *Info) error
}

type Info struct {
	ServiceName string
	Addr        net.Addr
	Weight      int
	Tags        map[string]string // 扩展信息，具体语义由实现决定
}
```

接入：

```go
import (
	"github.com/cloudwego/hertz/pkg/app/server"
	"github.com/cloudwego/hertz/pkg/app/server/registry"
	"github.com/cloudwego/hertz/pkg/common/utils"
)

h := server.Default(
	server.WithHostPorts("10.0.0.12:8888"),
	server.WithRegistry(r, &registry.Info{
		ServiceName: "order-service",
		Addr:        utils.NewNetAddr("tcp", "10.0.0.12:8888"),
		Weight:      10,
		Tags:        map[string]string{"version": "v1.2.0"},
	}),
)
```

关键点：`Addr` 必须是**其他机器能访问到的地址**。容器里常见错误是把 `127.0.0.1:8888` 注册进去，结果调用方永远连不上。
### 3.2 服务发现：`Resolver`
定义在 `pkg/app/client/discovery`：

```go
type Resolver interface {
	Target(ctx context.Context, target *TargetInfo) string
	Resolve(ctx context.Context, desc string) (Result, error)
	Name() string
}

type TargetInfo struct {
	Host string
	Tags map[string]string
}

type Result struct {
	CacheKey  string
	Instances []Instance
}
```

- `Target`：把用户传入的 host 归一化成缓存 key
- `Resolve`：真正去注册中心取实例列表
- `Name`：Hertz 用它缓存并复用 Resolver

接入（Discovery 中间件）：

```go
cli, _ := client.NewClient()
cli.Use(sd.Discovery(resolver))
```

官方注意事项：Resolver 会被复用，**实现必须并发安全**。
### 3.3 负载均衡：`Loadbalancer`
定义在 `pkg/app/client/loadbalance`：

```go
type Loadbalancer interface {
	Pick(discovery.Result) discovery.Instance
	Rebalance(discovery.Result)
	Delete(string)
	Name() string
}
```

Hertz 默认提供加权随机：

```go
import "github.com/cloudwego/hertz/pkg/app/client/loadbalance"

cli.Use(sd.Discovery(
	resolver,
	sd.WithLoadBalanceOptions(
		loadbalance.NewWeightedBalancer(),
		loadbalance.Options{
			RefreshInterval: 5 * time.Second,
			ExpireInterval:  30 * time.Second,
		},
	),
))
```

`RefreshInterval` 控制发现结果刷新节奏，`ExpireInterval` 控制空闲 balancer 的回收，二者都影响“实例变更多久生效”。
## 四、常见实现对比
| 注册中心 | 一致性模型 | 健康检查 | 控制台/生态 | 适合场景 |
| --- | --- | --- | --- | --- |
| **Consul** | Raft 强一致 | TTL、TCP、HTTP、gRPC | 自带 KV/UI/多数据中心 | 中小团队、混合云、需要 KV |
| **Nacos** | AP/CP 可切换 | 心跳、临时/持久实例 | 配置中心 + 注册一体，中文生态好 | 国内主流、Spring Cloud 体系 |
| **Etcd** | Raft 强一致 | 租约 TTL | 轻量、K8s 底座 | 已有 K8s/Etcd 基础设施 |
| **Eureka** | AP | 客户端心跳 | Spring Cloud Netflix 老体系 | 存量 Java 微服务 |
| **Polaris** | 多集群 | 心跳/探测 | 腾讯系，治理能力强 | 需要流量治理、灰度 |
| **ZooKeeper** | ZAB 强一致 | 临时节点 | 老牌、运维复杂 | 存量 Dubbo/ZK 体系 |
| **ServiceComb** | 依赖服务中心 | 心跳 | 华为系 | 已有 ServiceComb 平台 |

补充：社区还提供 Redis 作为轻量注册中心，适合小规模或临时场景，不建议承载核心交易流量。
## 五、选型建议
按团队现状做决策，而不是按“哪个最流行”：

1. **已经在用 Nacos 做配置中心** → 直接复用 Nacos，减少一套中间件
2. **K8s 原生体系，服务发现走 Service/DNS** → 可以不用独立注册中心；需要权重/灰度时再引入 Polaris 或 Nacos
3. **多数据中心、需要 KV** → Consul 更合适
4. **已有 Etcd 集群、追求轻量** → Etcd + Hertz registry
5. **Java/Spring Cloud 存量** → Eureka 或 Nacos，优先 Nacos（Eureka 2.x 已停止演进）
6. **强治理诉求（熔断、灰度、路由规则）** → Polaris / Nacos + Sentinel，而不是只靠注册中心

无论选哪个，都要额外确认：

- 是否有官方维护的 `hertz-contrib/registry` 适配
- 该适配最近一次提交时间与 Hertz 版本兼容性
- 是否支持你要用的健康检查方式
- 控制台能否看到实例与权重
## 六、健康检查与上下线
三种常见模式：

| 模式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 客户端心跳 | Provider 定期上报 | 实现简单 | 网络抖动易误判 |
| 服务端 TTL | 注册中心等待续约 | 天然感知宕机 | 需要合理 TTL |
| 主动探测 | 注册中心调 `/health` | 能验证业务可用性 | 探测频率与成本 |

Hertz 服务的 `/health` 建议分两层：

```go
h.GET("/healthz", func(ctx context.Context, c *app.RequestContext) {
	c.String(200, "ok") // 存活探针：进程还在就返回 200
})

h.GET("/readyz", func(ctx context.Context, c *app.RequestContext) {
	if !dbReady() || !cacheReady() {
		c.String(503, "not ready")
		return
	}
	c.String(200, "ready")
})
```

优雅下线顺序：

1. 从注册中心 `Deregister`（或先把权重置 0）
2. 等待一个“发现刷新周期”（如 5~10 秒），让调用方更新列表
3. 停止接收新连接，等待存量请求完成
4. 进程退出

只做第 3 步不做第 1 步，是发布期间 5xx 抖动的最常见原因。
## 常见坑
1. **注册了 `127.0.0.1` 或容器内网 IP**：跨节点调用必然失败，注册地址必须是可达地址。
2. **权重填 0 以为“不接流量”**：不同实现的语义不同，有的会兜底选 0 权重实例；要下线请直接 Deregister。
3. **Resolver 非并发安全**：它会被复用并并发调用，map 读写不加锁会直接 panic。
4. **认为注册成功就代表可用**：注册只代表“地址写进去了”，业务是否 ready 要靠 `/readyz`。
5. **发布时直接 kill 进程**：没有摘除等待期，调用方拿着旧列表打过来，出现尖峰 5xx。
6. **没有统一服务名规范**：`order-service`、`order_service`、`order` 混用，发现端永远查不到。
## 小结
- 注册中心解决的是“地址动态化 + 健康感知 + 权重治理”
- Hertz 把职责拆成 Registry、Resolver、Loadbalancer 三个可替换接口
- 默认加权随机够用，复杂路由需要自定义 Loadbalancer
- 选型优先看团队现有基础设施与治理诉求，而不是单纯比性能
- 发布稳定性取决于“摘除 → 等待 → 优雅退出”这条流程
## 练习
1. 画出你当前项目的服务调用图，标出哪些调用还是硬编码地址。
2. 用 `consul.NewConsulRegister` 与 `NewConsulResolver` 跑通一次注册+发现（注册中心可用 Docker 起）。
3. 自定义一个 Loadbalancer，实现“优先同机房，其次加权随机”。
4. 设计一个发布检查清单，确保摘除、等待、退出三步都覆盖。
