# 协议扩展与自定义协议
> 一句话定位：理解 Hertz “网络层—协议层—应用层”的分层，知道什么时候该写协议扩展、什么时候该用 Kitex。
## 本篇目标
- 理解 Hertz 分层架构中协议层的位置与职责
- 掌握 `protocol.Server`、`protocol.StreamServer`、`suite.Core`、`ServerFactory`
- 知道 `AddProtocol` 与 ALPN 协商 key 的对应关系
- 能读懂并改造一个最小自定义协议 server
- 判断“自定义协议 / HTTP / Kitex RPC”各自的适用边界
## 前置知识
- 已读 [03-基本特性/10-网络库Netpoll与标准库](../03-基本特性/10-网络库Netpoll与标准库.md)
- 了解 TCP 字节流、HTTP 报文格式
- 知道 TLS ALPN 的作用
## 一、Hertz 的分层
```text
┌─────────────────────────────────────┐
│ 应用层：路由 / 中间件 / Handler / Context │
├─────────────────────────────────────┤
│ 协议层：HTTP/1.1、HTTP/2、HTTP/3、自定义 │
├─────────────────────────────────────┤
│ 网络层：Netpoll / net 标准库 / 自定义     │
└─────────────────────────────────────┘
```

各层扩展点：

| 层 | 扩展接口 | 注册方式 |
| --- | --- | --- |
| 网络层 | `network.Conn` / `network.Dialer` | `server.WithTransport` / `client.WithDialer` |
| 协议层 | `protocol.Server` / `protocol.StreamServer` | `engine.AddProtocol` |
| 应用层 | `app.HandlerFunc` / 中间件 | `h.GET` / `h.Use` |

协议层是“把字节流解析成请求，并把响应写回字节流”的那一层。Hertz 默认已经内置了 HTTP/1.1，并按构建标签/配置支持 HTTP/2、HTTP/3（以官方文档与源码为准）。
## 二、HTTP/1.1、HTTP/2、HTTP/3 的差异
| 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
| --- | --- | --- | --- |
| 传输层 | TCP | TCP | QUIC（UDP） |
| 多路复用 | 无（靠多连接） | 有（Stream） | 有（Stream） |
| 头部压缩 | 无 | HPACK | QPACK |
| 典型协商 | 直接 | TLS ALPN `h2` | ALPN `h3` |
| Hertz 扩展接口 | `protocol.Server` | `protocol.Server` | `protocol.StreamServer` |

HTTP/2 与 HTTP/3 的协商依赖 TLS ALPN：客户端在 ClientHello 里带上协议列表，服务端选一个并在 ALPN 扩展里返回。Hertz 的 `AddProtocol(key, factory)` 中的 key 就是协商用的协议名。
## 三、协议扩展接口
### 3.1 字节流协议：`protocol.Server`
```go
type Server interface {
	Serve(c context.Context, conn network.Conn) error
}

type ServerFactory interface {
	New(core Core) (server protocol.Server, err error)
}
```
### 3.2 流式协议：`protocol.StreamServer`
```go
type StreamServer interface {
	Serve(c context.Context, conn network.StreamConn) error
}
```

HTTP/3 这类基于 QUIC Stream 的协议使用它，底层连接需实现 `network.StreamConn`。
### 3.3 与上层交互的核心：`suite.Core`
```go
type Core interface {
	IsRunning() bool
	GetCtxPool() *sync.Pool
	ServeHTTP(ctx context.Context, c *app.RequestContext)
	GetTracer() tracer.Controller
}
```

`Core` 是框架交给协议层的“应用层入口”：

- `GetCtxPool()`：复用 `RequestContext`，避免每请求分配
- `ServeHTTP()`：进入路由、中间件、Handler
- `GetTracer()`：让协议层也能触发埋点
## 四、最小自定义协议示例
下面基于官方示例做简化：只接受以 `GET` 开头的报文，其余直接拒绝。

```go
package main

import (
	"bytes"
	"context"

	"github.com/cloudwego/hertz/pkg/app"
	"github.com/cloudwego/hertz/pkg/app/server"
	"github.com/cloudwego/hertz/pkg/common/errors"
	"github.com/cloudwego/hertz/pkg/common/hlog"
	"github.com/cloudwego/hertz/pkg/network"
	"github.com/cloudwego/hertz/pkg/protocol"
	"github.com/cloudwego/hertz/pkg/protocol/suite"
)

type myServer struct {
	suite.Core
}

func (m *myServer) Serve(ctx context.Context, conn network.Conn) error {
	firstThree, _ := conn.Peek(3)
	if !bytes.Equal(firstThree, []byte("GET")) {
		return errors.NewPublic("not a GET method")
	}

	c := m.GetCtxPool().Get().(*app.RequestContext)
	defer func() {
		m.GetCtxPool().Put(c)
		conn.Skip(conn.Len())
		conn.Flush()
	}()

	// 解析：这里做了极简假设，真实协议需完整解析请求行与 header
	c.Request.SetMethod("GET")
	c.Request.SetRequestURI("/test")

	m.ServeHTTP(ctx, c) // 进入路由与业务逻辑

	conn.WriteBinary([]byte("HTTP/1.1 200 OK\r\n" +
		"Content-Type: text/plain; charset=utf-8\r\n" +
		"Content-Length: 2\r\n\r\nok"))
	return nil
}

type serverFactory struct{}

func (s *serverFactory) New(core suite.Core) (protocol.Server, error) {
	return &myServer{Core: core}, nil
}

func main() {
	h := server.New()
	h.GET("/test", func(ctx context.Context, c *app.RequestContext) {
		hlog.Info("in handler")
	})

	// key 与 ALPN 协议名一一对应；覆盖默认 HTTP/1.1 时同样用 "http/1.1"
	h.AddProtocol("http/1.1", &serverFactory{})
	h.Spin()
}
```

这个示例只演示机制，不是可上生产的 HTTP 解析器：真实实现要处理请求行、header 大小限制、chunked、keep-alive、超时、半包/粘包等。
## 五、ALPN 协商
典型流程：

```text
ClientHello (ALPN: h2, http/1.1)
        │
        ▼
Server 选择协议 -> ServerHello (ALPN: h2)
        │
        ▼
后续字节流交给 h2 协议 server 处理
```

Hertz 中注册：

```go
h.AddProtocol("h2", &http2Factory{})
```

要点：

- key 必须与 ALPN 名称一致，否则协商成功后找不到对应实现
- 未启用 TLS 时没有 ALPN，HTTP/1.1 直接按明文处理
- 想替换默认 HTTP/1.1 行为，注册 key `http/1.1` 会覆盖内置实现
## 六、什么时候真的需要自定义协议
先问三个问题：

1. **客户端能改吗？** 不能改就别自定义，兼容成本极高
2. **HTTP 真的不够吗？** 头部冗余、队头阻塞在 HTTP/2/3 下已大幅缓解
3. **收益能覆盖成本吗？** 自研协议意味着网关、抓包、压测、排障工具全部要重做

适合自定义协议的少数场景：

| 场景 | 说明 |
| --- | --- |
| 极低延迟的内部通信 | 二进制头 + 固定结构，减少解析开销 |
| 已有私有协议迁移 | 老系统使用自定义二进制协议，需在 Hertz 内兼容 |
| 特殊传输语义 | 长连接推送、自定义流控、私有加密帧 |
| 协议网关 | 在同一进程内同时服务多种协议 |

不适合：

- 公网 API（用 HTTP/JSON 或 gRPC）
- 只是“想少传几个 header”
- 团队没有协议解析与测试能力
## 七、和 Kitex RPC 的关系
| 维度 | Hertz | Kitex |
| --- | --- | --- |
| 定位 | HTTP 框架（网关、BFF、Web API） | 高性能 RPC 框架 |
| 协议 | HTTP/1.1、HTTP/2、HTTP/3 | Thrift、gRPC、Kitex Protobuf 等 |
| IDL | hz + Thrift/Protobuf 生成 HTTP 路由 | kitex + Thrift/Protobuf 生成 RPC |
| 典型组合 | 入口网关用 Hertz，内部服务用 Kitex | 内部服务间 RPC |

常见架构：

```text
Client → Hertz 网关（HTTP/JSON） → Kitex 服务（Thrift/gRPC） → DB
```

这时**不需要**给 Hertz 写自定义协议：网关负责 HTTP，RPC 交给 Kitex。只有当你必须在 Hertz 进程内直接讲 Kitex 的私有协议时，才涉及协议层扩展，而这通常不是推荐做法。
## 常见坑
1. **`AddProtocol` 的 key 与 ALPN 不一致**：协商成功但连接被错误实现处理，表现为请求乱码或直接断开。
2. **忘记归还 `RequestContext`**：不复用池会导致每请求分配，QPS 高时 GC 压力明显。
3. **自定义 server 不处理半包/粘包**：本地小报文正常，一上压测就解析错乱。
4. **没有设置读超时**：恶意/异常连接长期占用 goroutine，最终耗尽资源。
5. **覆盖了 `http/1.1` 却只实现部分语义**：keep-alive、chunked、100-continue 全部失效。
6. **以为 HTTP/2 只要换协议实现**：还需要 TLS 证书与 ALPN 配置，明文 h2c 场景要单独处理。
7. **把 RPC 需求硬塞进 Hertz 自定义协议**：不如直接用 Kitex，生态与治理能力差一个量级。
## 小结
- Hertz 的协议层是网络层与应用层之间的可替换实现
- 字节流用 `protocol.Server`，QUIC 流用 `protocol.StreamServer`，都通过 `Core` 进入业务
- `AddProtocol` 的 key 与 ALPN 协议名对应，可用于覆盖默认实现
- 自定义协议只在收益明确、客户端可控时使用
- HTTP 入口用 Hertz、内部 RPC 用 Kitex，是最常见也最省心的组合
