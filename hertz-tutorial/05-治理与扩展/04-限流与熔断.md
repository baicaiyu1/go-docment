# 限流与熔断
> 一句话定位：用限流保护自己、用熔断保护调用链，给出 Hertz 中可直接落地的实现与验证方法。
## 本篇目标
- 掌握令牌桶、漏桶、滑动窗口的差异与适用场景
- 写出可用的 Hertz 单机限流中间件
- 了解 `hertz-contrib/limiter` 自适应限流与 Sentinel 接入
- 理解熔断三态机与降级兜底
- 区分单机与集群限流，能用压测验证阈值
## 前置知识
- 已读 [03-基本特性/05-中间件](../03-基本特性/05-中间件.md)
- 了解 QPS、并发数、P99 与 Redis 基本命令
## 一、为什么两者要一起做
| 手段 | 保护对象 | 触发条件 | 表现 |
| --- | --- | --- | --- |
| 限流 | 自己 | 速率超阈值 | 快速拒绝 429 |
| 熔断 | 调用链 | 下游错误/超时率高 | 走降级 |
| 降级 | 用户体验 | 熔断或超时 | 缓存/默认值 |
| 重试 | 瞬时故障 | 网络抖动 | 可能放大流量 |

只限流不熔断，下游挂了线程仍被慢调用占满；只熔断不限流，突发流量照样打穿下游。
## 二、三种限流算法
### 令牌桶（最常用）
固定速率生成令牌，允许桶容量内的突发：
```bash
go get golang.org/x/time/rate
```
```go
limiter := rate.NewLimiter(rate.Limit(1000), 200) // 1000 QPS，突发 200
if !limiter.Allow() {
	// 拒绝
}
```
### 漏桶
以固定速率流出，输出平滑、不保留突发。实现上是一个带容量的 channel + 定时器，每 `interval` 取走一个；适合调用第三方或写队列，避免把下游打出尖峰。
### 滑动窗口
统计最近 N 秒的请求数，避免固定窗口“临界双倍”：
```go
type SlidingWindow struct {
	mu     sync.Mutex
	window time.Duration
	limit  int
	events []time.Time
}

func (s *SlidingWindow) Allow() bool {
	s.mu.Lock()
	defer s.mu.Unlock()

	cutoff := time.Now().Add(-s.window)
	i := 0
	for i < len(s.events) && s.events[i].Before(cutoff) {
		i++
	}
	s.events = s.events[i:]
	if len(s.events) >= s.limit {
		return false
	}
	s.events = append(s.events, time.Now())
	return true
}
```
| 算法 | 突发 | 复杂度 | 用途 |
| --- | --- | --- | --- |
| 令牌桶 | 有 | 低 | API 网关、业务接口 |
| 漏桶 | 无 | 中 | 调用第三方、写队列 |
| 滑动窗口 | 有（受窗口限制） | 中 | 精确 QPS |
| 固定窗口 | 有（临界问题） | 最低 | 粗粒度保护 |
## 三、Hertz 单机限流中间件
```go
func RateLimit(qps float64, burst int) app.HandlerFunc {
	limiter := rate.NewLimiter(rate.Limit(qps), burst)
	return func(ctx context.Context, c *app.RequestContext) {
		if !limiter.Allow() {
			c.Header("Retry-After", "1")
			c.AbortWithStatusJSON(429, utils.H{"code": 42900, "msg": "too many requests"})
			return
		}
		c.Next(ctx)
	}
}

h.Use(RateLimit(1000, 200))
```
按租户/路由限流时，用 `map[string]*rate.Limiter` 缓存；必须配 LRU/TTL 淘汰，否则 key 无限增长导致 OOM。注意限流器要在启动时创建并复用，不能每个请求新建。
## 四、自适应限流：hertz-contrib/limiter
```bash
go get github.com/hertz-contrib/limiter
```
```go
import "github.com/hertz-contrib/limiter"

h := server.Default()
h.Use(limiter.AdaptiveLimit())
```
它读取 CPU 负载动态判断：CPU 低于期望且并发未超历史峰值时放行；CPU 高于期望且并发超过历史峰值时拒绝。适合“拍不出固定 QPS”的服务，但依赖 Linux `/proc/stat`，Windows/macOS 本地可能不可用。
## 五、Sentinel 接入
```bash
go get github.com/hertz-contrib/opensergo
go get github.com/alibaba/sentinel-golang
```
规则初始化（示例示意，字段以 sentinel-golang 文档为准）：
```go
if err := sentinel.InitDefault(); err != nil {
	panic(err)
}
_, err := flow.LoadRules([]*flow.Rule{{
	Resource:               "GET:/api/order",
	Threshold:              500,
	TokenCalculateStrategy: flow.Direct,
	ControlBehavior:        flow.Reject,
}})
```
```go
h.Use(sentinelplugin.SentinelServerMiddleware(
	sentinelplugin.WithServerResourceExtractor(func(ctx context.Context, c *app.RequestContext) string {
		return fmt.Sprintf("%s:%s", c.Request.Method(), c.FullPath())
	}),
	sentinelplugin.WithServerBlockFallback(func(ctx context.Context, c *app.RequestContext) {
		c.AbortWithStatusJSON(429, map[string]interface{}{"code": 10222, "msg": "too many requests"})
	}),
))
```
Sentinel 的价值是规则可动态下发，并支持熔断、热点参数、系统自适应。只做固定 QPS 时，`x/time/rate` 更轻。
## 六、熔断与降级
```text
Closed --(错误率/慢调用超阈值)--> Open --(冷却期)--> Half-Open
  ▲                                                    │
  └────────────(探测成功)───────────────────────────────┘
                    (探测失败) --> Open
```
用 `sony/gobreaker` 示意：
```bash
go get github.com/sony/gobreaker
```
```go
var cb = gobreaker.NewCircuitBreaker(gobreaker.Settings{
	Name:        "user-service",
	MaxRequests: 5,
	Interval:    30 * time.Second,
	Timeout:     10 * time.Second,
	ReadyToTrip: func(c gobreaker.Counts) bool {
		return c.Requests >= 20 && float64(c.TotalFailures)/float64(c.Requests) > 0.5
	},
})

result, err := cb.Execute(func() (interface{}, error) {
	status, body, err := userClient.Get(ctx, nil, "http://user-service/user/42")
	if err != nil {
		return nil, err
	}
	if status != 200 {
		return nil, fmt.Errorf("status=%d body=%s", status, body)
	}
	return body, nil
})
if err != nil {
	c.JSON(200, map[string]interface{}{"user": nil, "degraded": true})
	return
}
c.JSON(200, result)
```
| 参数 | 建议 |
| --- | --- |
| 统计窗口 | 30s~1min |
| 最小请求数 | ≥20 |
| 错误率阈值 | 50% |
| 冷却时间 | 5s~30s |
| 探测请求数 | 3~10 |

熔断统计必须包含超时。只统计 5xx 不统计 deadline，会把“慢死”当成健康。
## 七、单机 vs 集群限流
| 维度 | 单机 | 集群 |
| --- | --- | --- |
| 阈值 | 每实例 QPS | 全服务总量 |
| 实现 | 本地内存 | Redis / Sentinel Token Server |
| 精度 | 高 | 受网络与时钟影响 |
| 成本 | 无 | 每请求一次 RTT |
| 适用 | 保护单实例 | 严格总量配额 |

Redis 令牌桶 Lua 关键片段：
```lua
-- KEYS[1]=key, ARGV[1]=rate, ARGV[2]=capacity, ARGV[3]=now_ms
local d = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(d[1]) or tonumber(ARGV[2])
local ts = tonumber(d[2]) or tonumber(ARGV[3])
tokens = math.min(tonumber(ARGV[2]),
  tokens + math.max(0, tonumber(ARGV[3]) - ts) / 1000 * tonumber(ARGV[1]))
local ok = 0
if tokens >= 1 then tokens = tokens - 1; ok = 1 end
redis.call('HMSET', KEYS[1], 'tokens', tokens, 'ts', ARGV[3])
redis.call('PEXPIRE', KEYS[1], 60000)
return ok
```
先单机兜底，确有全局配额需求再上集群，避免每条请求多一次 Redis 往返。
## 八、压测验证
1. 单实例压测找 P99 拐点
```bash
hey -z 60s -c 200 http://127.0.0.1:8888/api/order
```
```powershell
hey.exe -z 60s -c 200 http://127.0.0.1:8888/api/order
```
2. 取拐点的 70%~80% 作为单机阈值
3. 开限流后再压，确认超限请求快速 429、P99 不失控
4. 关闭下游，验证熔断在 N 秒内打开并走降级
5. 恢复下游，验证 Half-Open 自动恢复
## 常见坑
1. `rate.NewLimiter` 每个请求新建，等于没限流。
2. `Allow()` 放在 `c.Next()` 之后，先执行业务再判断，毫无作用。
3. 限流拒绝返回 200，监控与调用方都看不出异常。
4. 按 userId 建限流器不淘汰，内存无限增长直至 OOM。
5. 熔断只统计错误不统计超时，下游“慢死”时不触发。
6. 被限流后立即重试 3 次，等于把拒绝流量放大三倍。
7. 集群限流 key 没有过期时间，Redis 被历史 key 占满。
8. 只在网关限流，内网直连流量仍能打穿关键服务。
## 小结
- 令牌桶适合多数 API，漏桶适合匀速，滑动窗口适合精确 QPS
- 单机用 `x/time/rate`，注意复用与 key 淘汰
- 自适应限流与 Sentinel 适合规则动态化、系统级保护
- 熔断看“错误率 + 超时”，必须配降级
- 阈值由压测拐点决定，并用故障注入验证
