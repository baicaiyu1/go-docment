# 三方中间件生态
> 一句话定位：给 hertz-contrib 做一次“目录导览 + 质量分级 + 选型方法”，避免把 demo 级依赖带上生产。
## 本篇目标
- 了解 hertz-contrib 中常用中间件与扩展的分布
- 建立一套“能不能上生产”的评估清单
- 知道三方扩展与框架内置能力的边界
- 按规范自己写一个可复用的 Hertz 中间件
- 避开版本、并发、顺序、Abort 等常见坑
## 前置知识
- 已读 [03-基本特性/05-中间件](../03-基本特性/05-中间件.md)
- 会看 GitHub 的 commit、issue、release
- 了解 Go Modules 的版本管理
## 一、先明确“三方”的含义
官方对三方扩展的说明很直接：

> 第三方扩展由 CloudWeGo 社区开发者贡献与维护，不是 Hertz 内置能力，不由 Hertz 团队维护，请谨慎验证后使用。

因此：

- `github.com/cloudwego/hertz` 内的能力 = 框架内置，质量与兼容性有官方背书
- `github.com/hertz-contrib/*` = 社区维护，质量参差，需要自己评估
- 其它个人仓库 = 风险最高，必须读源码

## 三、社区质量分级
下面是一套可操作的分级标准（不是官方评级）：

| 等级 | 判据 | 使用建议 |
| --- | --- | --- |
| A | 有多个维护者、持续提交、有测试与示例、被广泛使用 | 可直接评估引入 |
| B | 单人维护但活跃、有测试、issue 响应及时 | 可用，锁定版本，准备 fork |
| C | 长期无提交、无测试、依赖老旧 | 仅 demo，生产慎用 |
| D | 无 README、无 license、无法编译 | 不使用 |

快速判断方法：

1. 看最近 12 个月是否有 commit / release
2. 看 issue 是否有维护者回复
3. 看 `go.mod` 是否锁定了很老的 Hertz 版本
4. 看是否有 `_test.go` 与 `example/`
5. 看 CI 状态与 license
## 四、评估一个三方扩展的清单
### 4.1 兼容性
- 依赖的 Hertz 版本是否与你的版本兼容（本教程基线 v0.10.6）
- 是否使用了已废弃 API（如旧的 `app.RequestContext` 方法）
- Go 版本要求是否与团队一致
### 4.2 正确性
- 中间件是否在所有分支都调用了 `c.Next(ctx)` 或 `c.Abort()`
- 是否把 `ctx` 换成 `context.Background()`
- 并发场景是否有锁、是否复用全局状态
- 错误路径是否吞掉了 error
### 4.3 安全性
- JWT 是否校验了 `alg`（防止 alg=none）
- CORS 是否允许了 `*` + credentials 的危险组合
- 是否打印了 Authorization/Cookie
- 依赖链是否有已知漏洞（`govulncheck`）
### 4.4 性能
- 是否每请求分配大对象
- 是否在热路径做正则/反射/JSON 序列化
- 是否有可配置的缓存
### 4.5 可维护性
- license 是否允许商用
- 是否容易 fork（代码量、耦合度）
- 是否有明确的版本标签

建议把上述检查写进团队的“依赖引入 PR 模板”，避免每次靠记忆。
## 五、自己写中间件的规范
### 5.1 标准签名
```go
func MyMiddleware(opts ...Option) app.HandlerFunc {
	return func(ctx context.Context, c *app.RequestContext) {
		// 前置逻辑
		c.Next(ctx)
		// 后置逻辑
	}
}
```
### 5.2 必须遵守的规则
| 规则 | 原因 |
| --- | --- |
| 用 `c.Next(ctx)` 而不是自己调用下一个 | 保证执行链正确 |
| 拒绝请求用 `c.Abort()` 或 `AbortWithStatusJSON` | 防止继续执行 |
| 不在中间件里吞 panic，交给统一 Recovery | 避免半截响应 |
| 不在热路径做重 IO | 直接拉高延迟 |
| 配置项用函数选项，不读全局变量 | 可测试、可复用 |
| 不修改 `c.Request` 的原始 URI 而不恢复 | 影响下游路由与日志 |
### 5.3 示例：带白名单的简易鉴权
```go
package middleware

import (
	"context"
	"strings"

	"github.com/cloudwego/hertz/pkg/app"
	"github.com/cloudwego/hertz/pkg/protocol/consts"
)

type AuthOption struct {
	SkipPaths []string
}

func Auth(opt AuthOption) app.HandlerFunc {
	skip := make(map[string]struct{}, len(opt.SkipPaths))
	for _, p := range opt.SkipPaths {
		skip[p] = struct{}{}
	}

	return func(ctx context.Context, c *app.RequestContext) {
		if _, ok := skip[string(c.Path())]; ok {
			c.Next(ctx)
			return
		}
		token := string(c.GetHeader("Authorization"))
		if !strings.HasPrefix(token, "Bearer ") {
			c.AbortWithStatusJSON(consts.StatusUnauthorized, map[string]string{"msg": "unauthorized"})
			return
		}
		// 校验 token，并把用户信息放入上下文
		c.Set("uid", "1001")
		c.Next(ctx)
	}
}
```
### 5.4 中间件顺序
推荐顺序（从外到内）：

```text
Recovery -> RequestID -> AccessLog -> CORS -> 限流 -> 鉴权 -> 业务
```

错误顺序的后果：

- 鉴权在日志之前：被拒绝的请求没有访问日志
- 限流在鉴权之前：未认证流量也能消耗配额（视场景而定）
- CORS 在最内层：预检请求被鉴权拦截
## 六、版本与依赖管理
```bash
go list -m -u all | grep hertz    # Linux/macOS
```

```powershell
go list -m -u all | Select-String hertz   # Windows
```

建议：

- `go.mod` 固定 Hertz 与扩展版本，不用 `@latest`
- 升级时一起升级 `hertz` 与 `hertz-contrib/*`，避免 API 错位
- 引入新依赖前跑 `govulncheck ./...`
- 对 B/C 级依赖，在 `pkg/` 里做一层薄封装，方便替换
## 常见坑
1. **CORS 配置 `AllowOrigins=["*"]` + `AllowCredentials=true`**：浏览器直接拒绝，且是常见安全误配。
2. **JWT 中间件不校验签名算法**：攻击者用 `alg=none` 伪造 token。
3. **Session 用内存存储上多副本**：登录态在 A 实例，请求打到 B 就掉线。
4. **pprof 暴露在公网端口**：`/debug/pprof` 可被用来打 CPU、读内存，必须内网或加鉴权。
5. **Swagger 在生产开启**：泄露全部接口与参数结构，至少加 Basic Auth。
6. **中间件里 `return` 前忘记 `Abort`**：后续 Handler 继续执行，出现“拒绝后仍写响应”。
7. **升级 hertz 不升级 contrib**：编译报错或运行时行为不一致。
8. **使用无 license 的仓库**：商用合规风险，法务过不了。
## 小结
- hertz-contrib 是社区生态，不是官方保证，必须自行评估
- 中间件选型看维护活跃度、测试、依赖、license 与安全实现
- 内置能力（静态资源、优雅退出、TLS）优先用内置，不要绕远路
- 自写中间件遵守 `Next/Abort` 语义与函数选项风格
- 版本锁定 + 薄封装，是控制三方风险最有效的手段
## 练习
1. 从 hertz-contrib 选 3 个你需要的中间件，按本清单打分并给出结论。
2. 给示例项目加 CORS + RequestID + AccessLog，调整顺序验证日志是否覆盖被拒请求。
3. 用 `govulncheck` 扫描项目，记录并处理高危项。
4. 把自己写的鉴权中间件补齐单元测试，覆盖跳过路径与非法 token。
