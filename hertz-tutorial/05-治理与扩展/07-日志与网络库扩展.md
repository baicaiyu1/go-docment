# 日志与网络库扩展
> 一句话定位：从“换一个 Logger”到“换掉网络库、劫持响应 Writer”，讲清 Hertz 底层扩展点与性能代价。
## 本篇目标
- 掌握 hlog 的 `FullLogger` 组合关系与自定义注入方式
- 能在不破坏框架日志的前提下包装/增强 Logger（加字段、脱敏、采样）
- 理解 `network.Conn`、`network.Dialer` 的职责与替换方式
- 掌握 Response Writer 劫持，实现 chunked、压缩、加密、审计
- 评估这些底层扩展对性能与可维护性的影响

## 一、hlog 扩展点回顾
`hlog` 定义了四个接口，合并为 `FullLogger`：

| 接口 | 职责 |
| --- | --- |
| `Logger` | `Info`、`Error` 等无格式化方法 |
| `FormatLogger` | `Infof`、`Errorf` 等格式化方法 |
| `CtxLogger` | 带 `context.Context` 的方法，用于关联 trace |
| `Control` | `SetLevel`、`SetOutput` |

注入入口只有一个：
```go
hlog.SetLogger(myLogger) // 参数类型是 hlog.FullLogger
```
这意味着：**要么实现全部方法，要么用嵌入的方式复用已有实现。**
## 二、自定义 Logger 的两种写法
### 2.1 嵌入已有实现（推荐）
只覆写需要增强的方法，其余委托给 zap/logrus：

```go
package logging

import (
	"context"
	"io"

	"github.com/cloudwego/hertz/pkg/common/hlog"
	hertzzap "github.com/hertz-contrib/logger/zap"
)

type Logger struct {
	hlog.FullLogger // 嵌入 zap 实现，自动获得全部方法
}

func New() *Logger {
	return &Logger{FullLogger: hertzzap.NewLogger()}
}

// 覆写：错误日志统一补充字段
func (l *Logger) CtxErrorf(ctx context.Context, format string, args ...interface{}) {
	l.FullLogger.CtxErrorf(ctx, "[error] "+format, args...)
}

// 覆写：输出重定向时同步给底层
func (l *Logger) SetOutput(w io.Writer) {
	l.FullLogger.SetOutput(w)
}
```

初始化：

```go
func init() {
	hlog.SetLogger(logging.New())
	hlog.SetLevel(hlog.LevelInfo) // 调用的是包装后的 SetLevel
}
```
嵌入的注意点：
- 外层方法集必须完整覆盖 `FullLogger`，否则编译报错
- 覆写方法里调用 `l.FullLogger.Xxx` 而不是 `l.Xxx`，避免递归
- 不要在外层再包一层普通函数给业务用，否则调用深度变化会影响文件名/行号
### 2.2 从零实现（了解即可）
需要实现 7 个无格式化方法、7 个格式化方法、7 个 Ctx 方法，以及 `SetLevel`/`SetOutput`，通常只在对接公司统一日志 SDK 时这么做。注意三点：写日志线程安全；`Fatal` 是否退进程要统一；`Ctx` 方法要能提取 trace_id 写入字段。
## 三、日志增强的三类需求
| 需求 | 做法 | 风险 |
| --- | --- | --- |
| 统一字段（service、env、host） | 在 Logger 初始化时绑定固定字段 | 字段名要与采集侧约定 |
| 脱敏 | 在写入前对参数做正则替换 | 正则性能，热路径慎用 |
| 采样 | 成功日志按比例丢弃 | 错误日志不能采样 |
| 多目标输出 | `io.MultiWriter(stdout, file)` | 文件轮转与并发写 |

推荐的组合：

```text
业务代码 -> hlog 全局函数 -> 自定义 Logger(嵌入 zap) -> zap core(JSON + 轮转) -> stdout/文件 -> 采集
```
## 四、网络库扩展
Hertz 默认集成 Netpoll 与 Go 标准库网络实现，可以按场景选择；也允许完全替换。
### 4.1 Server 侧接口
```go
type Conn interface {
	net.Conn
	Reader
	Writer
	SetReadTimeout(t time.Duration) error
}
```
`Reader` 的关键方法：

| 方法 | 用途 |
| --- | --- |
| `Peek(n)` | 预读 n 字节但不移动读指针（协议判断常用） |
| `Skip(n)` | 丢弃 n 字节 |
| `ReadBinary(n)` | 读取 n 字节并移动指针 |
| `Len()` | 当前可读字节数 |
| `Release()` | 释放读缓冲，必须在确认数据不再使用后调用 |
`Writer` 的关键方法：

| 方法 | 用途 |
| --- | --- |
| `Malloc(n)` | 申请写缓冲 |
| `WriteBinary(b)` | 写入并刷出 |
| `Flush()` | 真正发送到对端 |
### 4.2 Client 侧接口
```go
type Dialer interface {
	DialConnection(network, address string, timeout time.Duration, tlsConfig *tls.Config) (conn Conn, err error)
	DialTimeout(network, address string, timeout time.Duration, tlsConfig *tls.Config) (conn net.Conn, err error)
	AddTLS(conn Conn, tlsConfig *tls.Config) (Conn, error)
}
```
### 4.3 替换方式
```go
// Server
h := server.New(server.WithTransport(myTransport{}))

// Client
cli, _ := client.NewClient(client.WithDialer(myDialer{}))
```

什么时候替换网络库：已有自研 IO 框架想统一线程模型；需要特殊连接池、TLS 卸载、零拷贝；使用特定平台能力（如 io_uring）。不建议替换：只是“听说另一个库快 5%”，或团队无力维护连接生命周期、超时与半包处理。
## 五、Response Writer 扩展
### 5.1 为什么需要
Hertz 默认在 Handler 返回后统一写响应，无法在 Handler 内立即刷新分块。SSE、大文件流式输出、边算边发等场景需要控制写时机。
### 5.2 接口
```go
type ExtWriter interface {
	io.Writer
	Flush() error
	Finalize() error // 框架释放 writer 前调用，必须可重复调用
}
```
劫持：

```go
h.GET("/stream", func(ctx context.Context, c *app.RequestContext) {
	c.Response.HijackWriter(myWriter)
	// 后续 c.Write / c.Flush 走你的实现
})
```
### 5.3 内置 ChunkedBodyWriter
```go
import (
	"fmt"
	"strings"
	"time"

	"github.com/cloudwego/hertz/pkg/protocol/http1/resp"
)

h.GET("/flush/chunk", func(ctx context.Context, c *app.RequestContext) {
	c.Response.HijackWriter(resp.NewChunkedBodyWriter(&c.Response, c.GetWriter()))
	for i := 0; i < 10; i++ {
		c.Write([]byte(fmt.Sprintf("chunk %d: %s", i, strings.Repeat("hi~", i))))
		c.Flush()
		time.Sleep(200 * time.Millisecond)
	}
})
```
验证：
```bash
curl -N --location localhost:8888/flush/chunk
```
```powershell
curl.exe -N --location http://localhost:8888/flush/chunk
```
### 5.4 压缩 / 加密 / 审计的思路
| 能力 | 实现位置 | 思路 |
| --- | --- | --- |
| Gzip 压缩 | Writer 包装 | 写入前压缩，`Finalize` 时 flush 压缩器并写 trailer |
| 国密/自定义加密 | Writer 包装 | 分块加密，注意块边界与认证标签 |
| 响应审计 | Writer 包装 | 旁路记录字节数与摘要，不要阻塞写路径 |
| 限速 | Writer 包装 | 按令牌桶控制 `Flush` 节奏 |

骨架示意：

```go
type auditWriter struct {
	inner   network.ExtWriter // 以实际接口类型为准
	written int64
}

func (w *auditWriter) Write(p []byte) (int, error) {
	n, err := w.inner.Write(p)
	w.written += int64(n)
	return n, err
}

func (w *auditWriter) Flush() error { return w.inner.Flush() }

func (w *auditWriter) Finalize() error {
	// 记录审计信息；失败不能影响主流程
	hlog.Infof("response bytes=%d", w.written)
	return w.inner.Finalize()
}
```
压缩与加密会改变 `Content-Length`，必须改用 chunked 或先算好长度；同时要正确设置 `Content-Encoding`，否则客户端无法解码。
## 六、性能影响
| 扩展 | 典型开销 | 建议 |
| --- | --- | --- |
| 自定义 Logger | 每条日志一次函数调用 + 序列化 | 热路径避免 Debug 级别字符串拼接 |
| MultiWriter | 双倍 IO | 生产只写 stdout，由采集侧落盘 |
| 替换网络库 | 取决于实现 | 必须做同机压测对比 |
| Writer 劫持 | 每块一次额外拷贝 | 块大小 ≥4KB，避免小包 |
| 响应加密 | CPU 明显上升 | 评估是否下沉到网关/硬件 |
| 审计旁路 | 少量内存与日志 IO | 异步批量上报，禁止同步写远端 |

一条经验：**底层扩展的收益要用 P99 与 CPU 使用率衡量，而不是只看吞吐。** 劫持 Writer 后如果每 10 字节 Flush 一次，吞吐可能不降，但系统调用次数会暴涨。
## 常见坑
1. **自定义 Logger 只实现了部分接口**：`SetLogger` 编译失败，或运行时 panic。
2. **覆写方法里调用自身**：`func (l *Logger) Info(...) { l.Info(...) }` 无限递归。
3. **换了 Logger 但没设级别**：默认级别可能过滤掉你需要的信息，启动时统一配置。
4. **Writer 的 `Finalize` 不可重入**：框架可能多次调用，重复 flush/close 会 panic。
5. **劫持 Writer 后仍用 `c.JSON`**：两套写路径混用，响应体错乱或 header 冲突。
6. **压缩后忘改 `Content-Length`**：客户端按旧长度读取，表现为响应截断。
7. **审计 Writer 里同步写远端**：直接把写响应延迟放大数倍。
## 小结
- 自定义 Logger 优先“嵌入 + 覆写”，避免从零实现 20 多个方法
- 网络库扩展的核心是 `Conn`/`Dialer`，替换前先量化收益
- Response Writer 劫持用于流式、压缩、加密、审计等“写时控制”
- 所有底层扩展都要关注 `Finalize` 语义、错误处理与性能
- 能用应用层中间件解决的，不要动协议层与网络层
