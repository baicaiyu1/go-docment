# 05-高可用部署与运维
> 一句话定位：从单机 Redis 走向主从、哨兵、Cluster，并用指标、备份与容量规划把「高可用」落到可验证的运维动作。
## 本篇目标
- 理解主从复制、哨兵、Cluster 三种形态的故障切换原理与代价
- 说清 Cluster 的 slot 机制与多 key、事务、Lua 的限制
- 在 RDB 与 AOF 之间做取舍，明确可接受的数据丢失窗口
- 会算内存容量，会看关键监控指标
- 能完成一次「备份 → 故障 → 恢复」演练
- 用 docker compose 在本地拉起三节点集群
## 前置知识
- 已读 [01-go-redis接入与连接池](01-go-redis接入与连接池.md)
- 了解 Redis 单机启动与 `redis.conf` 基本配置
- 会使用 Docker 与 Docker Compose
## 一、主从复制
```bash
redis-server --port 6380 --replicaof 127.0.0.1 6379
```
```powershell
redis-server --port 6380 --replicaof 127.0.0.1 6379
```
复制流程：从节点 `REPLICAOF` 后先做一次全量（`PSYNC` → 主节点 `BGSAVE` 生成 RDB + 缓冲增量），之后持续接收命令流。要点：
- 复制是**异步**的，`master_repl_offset - slave_repl_offset` 就是从节点的落后字节数
- 主节点写入成功不代表从节点已收到，宕机切换可能丢最后一段写
- 从节点默认 `replica-read-only yes`，可承接读流量，但要注意读到旧数据
- `min-replicas-to-write` + `min-replicas-max-lag` 可以让主节点在从节点失联时拒绝写入，降低丢数据风险
## 二、哨兵：自动故障转移
```ini
# sentinel.conf
port 26379
sentinel monitor mallmaster 127.0.0.1 6379 2
sentinel down-after-milliseconds mallmaster 5000
sentinel failover-timeout mallmaster 60000
sentinel parallel-syncs mallmaster 1
```
```bash
redis-server sentinel.conf --sentinel
```
```powershell
redis-server sentinel.conf --sentinel
```
哨兵集群（通常 3 个）负责监控、主观/客观下线判定、选主与通知客户端。客户端通过 `NewFailoverClient` 询问哨兵当前主节点地址。注意：
- 哨兵数量建议 ≥3 且为奇数，`quorum` 设为 `n/2+1`
- 切换过程中有秒级不可用窗口，客户端要配合重试与超时
- 哨兵不解决容量问题，只是高可用
## 三、Cluster：分片与限制
Cluster 把 key 通过 `CRC16(key) % 16384` 映射到 16384 个 slot，每个主节点负责一部分 slot，从节点做副本。最少 3 主 3 从。
```bash
redis-cli --cluster create 127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 \
  --cluster-replicas 0
redis-cli --cluster check 127.0.0.1:7001
```
```powershell
redis-cli --cluster create 127.0.0.1:7001 127.0.0.1:7002 127.0.0.1:7003 --cluster-replicas 0
redis-cli --cluster check 127.0.0.1:7001
```
| 限制 | 表现 | 应对 |
| --- | --- | --- |
| 多 key 命令跨 slot | `CROSSSLOT Keys in request don't hash to the same slot` | 用 hash tag `{user:1}:cart` |
| 事务跨 slot | `EXECABORT`/`CROSSSLOT` | 同 tag，或拆分事务 |
| Lua 跨 slot | 直接报错 | 脚本中所有 KEYS 同 tag |
| 不支持 `SELECT DB` | 只能 DB 0 | 用 key 前缀隔离环境 |
| `KEYS`/`SCAN` 只作用于当前节点 | 结果不完整 | 遍历所有主节点 |
| 扩容需迁移 slot | 迁移期间部分请求 MOVED/ASK | 客户端需支持重定向（go-redis 已内置） |
hash tag 规则：只对 `{}` 内的内容做哈希，因此 `{sku:1001}:stock` 与 `{sku:1001}:locked` 必在同一 slot。
## 四、持久化：RDB 与 AOF
| 方案 | 原理 | 优点 | 缺点 | 丢失窗口 |
| --- | --- | --- | --- | --- |
| RDB | 定时 fork 生成快照 | 文件小、恢复快 | 崩溃丢最后一次快照后的数据 | 取决于 `save`，可能几分钟 |
| AOF | 追加写命令日志 | 丢数据少、可读 | 文件大、恢复慢、有写放大 | `everysec` 最多约 1 秒 |
| 混合 | AOF 重写时用 RDB 前导 | 恢复快 + 丢得少 | 配置稍复杂 | 约 1 秒 |
```ini
appendonly yes
appendfsync everysec          # always 最安全但极慢；no 交给 OS，可能丢 30 秒
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
save 900 1
save 300 10
```
取舍建议：纯缓存可以只开 RDB 甚至不持久化；订单事件、库存快照这类「丢了要赔钱」的数据，开 AOF `everysec` + 主从 + 定期备份，并且**关键数据仍要以 MySQL 为准**。
## 五、容量评估与内存规划
粗略估算公式：
```text
总内存 = 数据量 × (1 + 碎片率) + 副本数 × 从节点开销 + 预留 buffer
单 key 开销 ≈ 50~100 字节（dict entry + redisObject + SDS 头）
```
| 数据 | 规模 | 单条估算 | 合计 |
| --- | --- | --- | --- |
| 商品详情 JSON | 100 万 | 2KB | 2GB |
| 购物车 Hash | 50 万用户 × 20 字段 | 约 1.5KB | 0.75GB |
| 销量榜 ZSet | 100 万成员 | 约 80 字节 | 80MB |
| 分布式锁/限流 | 10 万 | 约 100 字节 | 10MB |
规划原则：`maxmemory` 设为物理内存的 70% 左右；`mem_fragmentation_ratio` 长期大于 1.5 要排查大 Key 频繁分配；从节点与备份 fork 需要额外内存，`used_memory_rss` 可能达到 2 倍。
## 六、关键监控指标
| 指标 | 命令/来源 | 告警建议 |
| --- | --- | --- |
| 命中率 | `keyspace_hits/(hits+misses)` | 低于 80% 关注，低于 60% 告警 |
| 内存使用 | `used_memory` / `maxmemory` | 超过 80% 预警 |
| 内存碎片 | `mem_fragmentation_ratio` | >1.5 或 <1 关注 |
| 连接数 | `connected_clients` | 超过 `maxclients` 80% 告警 |
| 被淘汰 key | `evicted_keys` | 持续增长说明容量不足或 TTL 不合理 |
| 过期 key | `expired_keys` | 突增可能是大量 key 同时过期 |
| 慢日志 | `SLOWLOG GET 10` | `slowlog-log-slower-than 10000`（10ms） |
| 主从延迟 | `master_repl_offset - slave_repl_offset` | 超过几 MB 或 `master_link_status:down` 告警 |
| fork 耗时 | `latest_fork_usec` | 超过 200ms 关注，影响主线程 |
```bash
redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|mem_fragmentation_ratio"
redis-cli INFO stats | grep -E "keyspace_hits|keyspace_misses|evicted_keys"
redis-cli INFO replication | grep -E "role|master_link_status|slave_repl_offset"
redis-cli SLOWLOG GET 10
```
```powershell
redis-cli INFO memory | Select-String "used_memory_human|maxmemory_human|mem_fragmentation_ratio"
redis-cli INFO stats | Select-String "keyspace_hits|keyspace_misses|evicted_keys"
redis-cli INFO replication | Select-String "role|master_link_status|slave_repl_offset"
redis-cli SLOWLOG GET 10
```
生产建议接 `redis_exporter` + Prometheus + Grafana，避免靠人登录执行 `INFO`。
## 七、备份与恢复演练
```bash
redis-cli BGSAVE
redis-cli --rdb ./backup-20261123.rdb
redis-cli CONFIG GET dir
```
```powershell
redis-cli BGSAVE
redis-cli --rdb ./backup-20261123.rdb
redis-cli CONFIG GET dir
```
恢复流程（必须在隔离环境演练）：
1. 停掉目标实例，确认 `dir` 与 `dbfilename`
2. 用备份文件替换 `dump.rdb`（AOF 开启时同时处理 `appendonly.aof`）
3. 启动实例，`DBSIZE` 与抽样 key 校验数据完整性
4. 校验业务：商品详情可读、库存 key 存在、锁 key 无残留脏值
没有演练过的备份等于没有备份；至少每季度做一次「从备份拉起一个实例 + 业务验收」。
## 八、docker compose 三节点示例
```yaml
services:
  redis-1:
    image: redis:7
    command: ["redis-server", "--cluster-enabled", "yes",
              "--cluster-config-file", "nodes.conf", "--appendonly", "yes"]
    ports: ["7001:6379", "17001:16379"]
  redis-2:
    image: redis:7
    command: ["redis-server", "--cluster-enabled", "yes",
              "--cluster-config-file", "nodes.conf", "--appendonly", "yes"]
    ports: ["7002:6379", "17002:16379"]
  redis-3:
    image: redis:7
    command: ["redis-server", "--cluster-enabled", "yes",
              "--cluster-config-file", "nodes.conf", "--appendonly", "yes"]
    ports: ["7003:6379", "17003:16379"]
```
```bash
docker compose up -d
docker compose exec redis-1 redis-cli --cluster create redis-1:6379 redis-2:6379 redis-3:6379 --cluster-replicas 0
docker compose exec redis-1 redis-cli -c -p 6379 cluster info
```
```powershell
docker compose up -d
docker compose exec redis-1 redis-cli --cluster create redis-1:6379 redis-2:6379 redis-3:6379 --cluster-replicas 0
docker compose exec redis-1 redis-cli -c -p 6379 cluster info
```
注意：宿主机通过映射端口访问时，客户端会收到指向容器内网 IP 的 `MOVED`，导致连不上。本地验证建议：
- 用 `docker compose exec` 在容器网络内执行命令；或
- 给每个节点加 `--cluster-announce-ip 127.0.0.1 --cluster-announce-port 7001` 这类参数；或
- 直接在 WSL/Linux 上用三个本地端口启动（最省事）
客户端侧只需配置 3 个种子地址，go-redis 会自动跟随重定向并刷新拓扑。
## 常见坑
1. **以为主从切换不丢数据**：异步复制下最后一段写必然可能丢，核心数据必须以 MySQL 为准。
2. **Cluster 里用 `MGET`/`SINTER` 不带 hash tag**：线上直接 `CROSSSLOT`。
3. **AOF `appendfsync no` 还宣称不丢数据**：OS 缓冲可能丢 30 秒。
4. **`maxmemory` 不设或设成物理内存 100%**：触发 OOM Killer，Redis 被系统杀掉。
5. **只监控 `used_memory` 不看 `evicted_keys`**：缓存已经在大面积被淘汰，业务命中率暴跌却无人知。
6. **哨兵只部署一个**：单点，主节点挂了没人能投票切换。
7. **备份只备份 RDB 不校验**：文件损坏、AOF 不完整，故障时才发现恢复不了。
8. **扩容 Cluster 时监控盲区**：迁移 slot 期间延迟上升，误判为业务代码问题。
## 小结
- 主从解决读扩展与副本，哨兵解决自动切换，Cluster 解决容量，三者叠加但都不保证强一致
- Cluster 的一切限制都源自 slot：多 key、事务、Lua 都要同 tag
- 持久化按数据价值选：纯缓存可只开 RDB，关键数据 AOF `everysec` + 备份
- 运维的核心是「指标 + 演练」：命中率、内存、连接、evicted、主从延迟必须进看板
- 备份不演练等于没有备份
## 练习
1. 按本文 compose 拉起三节点 Cluster，用 `redis-cli -c` 写入 1000 个 key，观察 `cluster slots` 的分布。
2. 故意写一个跨 slot 的 `MGET`，记录报错信息，再用 hash tag 改写使其成功。
3. 分别开启 AOF `always`/`everysec`，用 `redis-benchmark -t set` 对比 QPS 差异。
4. 模拟主节点宕机（`docker compose stop redis-1`），观察哨兵/Cluster 的切换时间与客户端表现。
