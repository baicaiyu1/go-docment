# 02-缓存模式与三大经典问题
> 一句话定位：以商品详情缓存为样板，讲清 Cache-Aside 的正确写法，以及穿透、击穿、雪崩、一致性这四道送命题。
## 本篇目标
- 说清 Cache-Aside / Read-Through / Write-Through / Write-Behind 的差异与边界
- 用 TTL 随机抖动避免同一时刻集体失效
- 分别用布隆过滤器、singleflight、多级缓存解决穿透、击穿、雪崩
- 掌握「先更库再删缓存 + 延迟双删 + binlog 订阅」的取舍
- 建立缓存预热与 Redis 故障时的降级兜底

## 一、四种缓存模式
| 模式 | 读路径 | 写路径 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- | --- | --- |
| Cache-Aside | 先缓存，未命中回源并回填 | 更新 DB 后删缓存 | 简单、可控 | 应用自己管一致性 | 90% 业务 |
| Read-Through | 缓存层代理回源 | 同上 | 业务代码干净 | 需要缓存框架支持 | 中间件封装完善时 |
| Write-Through | 先缓存，未命中回源 | 同时写缓存与 DB（同步） | 缓存始终较新 | 写延迟高、写放大 | 读多写少且强依赖缓存 |
| Write-Behind | 先缓存，未命中回源 | 只写缓存，异步刷 DB | 写极快、可合并 | 宕机丢数据、实现复杂 | 计数、点赞、浏览数 |

Go 生态没有成熟统一的 Read-Through 框架，实际项目里 Read-Through 通常表现为「在 repository 层封装一个 `GetOrLoad(ctx, key, loader)`」。Write-Behind 则往往借助 Kafka 异步落库（第 11 章）。
### Cache-Aside 标准写法
```go
type ProductRepo struct {
	rdb redis.UniversalClient
	db  *gorm.DB
	sf  singleflight.Group
}

func (r *ProductRepo) Detail(ctx context.Context, id int64) (*Product, error) {
	key := fmt.Sprintf("mall:prod:product:detail:%d", id)
	if p, ok := r.getCache(ctx, key); ok {
		if p == nil {
			return nil, ErrProductNotFound // 命中的是空值标记
		}
		return p, nil
	}
	v, err, _ := r.sf.Do(key, func() (any, error) {
		return r.loadFromDBAndFill(ctx, id, key)
	})
	if err != nil {
		return nil, err
	}
	p, _ := v.(*Product)
	if p == nil {
		return nil, ErrProductNotFound
	}
	return p, nil
}

func (r *ProductRepo) getCache(ctx context.Context, key string) (*Product, bool) {
	raw, err := r.rdb.Get(ctx, key).Bytes()
	if err != nil {
		if !errors.Is(err, redis.Nil) {
			r.metrics.CacheError.Inc() // Redis 故障：降级直查 DB
		}
		return nil, false
	}
	if string(raw) == "1" { // 空值标记
		return nil, true
	}
	p, err := decodeProduct(raw)
	if err != nil {
		return nil, false
	}
	return p, true
}
```
回填时一定带 TTL，且用「删缓存」而不是「改缓存」来响应写请求。
## 二、TTL 必须加随机抖动
如果 10 万个商品详情都在 0 点批量预热、统一 30 分钟过期，30 分钟后它们会在同一秒集体失效，DB 瞬间被打穿——这就是雪崩的一个变种。
```go
func jitterTTL(base time.Duration) time.Duration {
	// 在 [base, base*1.2) 之间随机
	delta := base / 5
	return base + time.Duration(rand.Int63n(int64(delta)))
}
```
| 场景 | 建议 TTL |
| --- | --- |
| 商品详情（变化慢） | 10~30 分钟 + 抖动 |
| 库存展示（变化快） | 5~30 秒，或干脆不缓存，只缓存「有货/无货」 |
| 空值标记 | 30~60 秒，短 TTL 防止数据刚创建却长期不可见 |
| 用户会话 | 与 token 有效期一致 |
## 三、缓存穿透：查不存在的数据
攻击者用 `id=-1`、随机 UUID 疯狂请求，缓存永远不命中，全部打到 MySQL。
**方案一：空值缓存（短 TTL）**
```go
func (r *ProductRepo) loadFromDBAndFill(ctx context.Context, id int64, key string) (any, error) {
	var p Product
	err := r.db.WithContext(ctx).First(&p, id).Error
	switch {
	case errors.Is(err, gorm.ErrRecordNotFound):
		// 缓存空值，60 秒内同一 id 不再回源
		_ = r.rdb.Set(ctx, key, "1", 60*time.Second).Err()
		return nil, ErrProductNotFound
	case err != nil:
		return nil, err
	}
	body, _ := json.Marshal(&p)
	_ = r.rdb.Set(ctx, key, body, jitterTTL(30*time.Minute)).Err()
	return &p, nil
}
```
**方案二：布隆过滤器前置拦截**
```bash
redis-cli BF.RESERVE mall:prod:product:bloom 0.01 10000000
redis-cli BF.ADD mall:prod:product:bloom 1001
redis-cli BF.EXISTS mall:prod:product:bloom 1001
```
```powershell
redis-cli BF.RESERVE mall:prod:product:bloom 0.01 10000000
redis-cli BF.ADD mall:prod:product:bloom 1001
redis-cli BF.EXISTS mall:prod:product:bloom 1001
```
命中判定为「不存在」时直接返回 404；判定「存在」仍有误判率，需要继续查缓存/DB。布隆过滤器需要 RedisBloom 模块（Redis Stack 自带），删除商品时无法从布隆过滤器里移除，通常用定期重建解决。
## 四、缓存击穿：单个热点 key 失效
某爆款商品缓存过期的瞬间，上万请求同时回源。`singleflight` 能让同一 key 只有一个请求真正回源：
```go
func (r *ProductRepo) DetailSafe(ctx context.Context, id int64) (*Product, error) {
	key := fmt.Sprintf("mall:prod:product:detail:%d", id)
	ch := r.sf.DoChan(key, func() (any, error) {
		return r.loadFromDBAndFill(context.WithoutCancel(ctx), id, key)
	})
	select {
	case <-ctx.Done():
		return nil, ctx.Err() // 客户端已断开，不再等
	case res := <-ch:
		if res.Err != nil {
			return nil, res.Err
		}
		p, _ := res.Val.(*Product)
		if p == nil {
			return nil, ErrProductNotFound
		}
		return p, nil
	}
}
```
- `DoChan` 配合 `select` 才能尊重请求超时；直接用 `Do` 会被慢请求拖住
- 回源要用 `context.WithoutCancel`（Go 1.21+）或独立超时 context，避免第一个请求被取消导致所有等待者失败
- 跨进程还需要分布式互斥锁（见 [03-分布式锁与限流实践](03-分布式锁与限流实践.md)），或用逻辑过期方案：value 里存 `expireAt`，逻辑过期后由单个协程异步重建，其余请求先返回旧值
## 五、缓存雪崩：大面积同时失效
| 手段 | 说明 |
| --- | --- |
| TTL 抖动 | 避免同时过期，成本最低 |
| 多级缓存 | 进程内 local cache（bigcache/ristretto）+ Redis，Redis 挂了还有本地兜底 |
| 熔断降级 | Redis 错误率超阈值时切到「直查 DB + 限流」，保护 DB |
| 预热 | 发布后/大促前批量回填热点 key，避免冷启动全量击穿 |
| 限流 | 回源路径加并发信号量，宁可返回兜底页也不要打挂 DB |

```go
var dbGuard = make(chan struct{}, 50) // 最多 50 个并发回源

func (r *ProductRepo) loadWithGuard(ctx context.Context, id int64) (*Product, error) {
	select {
	case dbGuard <- struct{}{}:
		defer func() { <-dbGuard }()
	case <-ctx.Done():
		return nil, ctx.Err()
	}
	key := fmt.Sprintf("mall:prod:product:detail:%d", id)
	return r.loadFromDBAndFill(ctx, id, key)
}
```
## 六、缓存与 MySQL 的一致性
先给结论：**缓存与数据库不追求强一致，只追求「最终一致 + 不一致窗口足够短」**。订单、库存扣减这类强一致场景请以 DB 为准，不要拿缓存当账本。
### 推荐：先更库，再删缓存
```go
func (r *ProductRepo) UpdatePrice(ctx context.Context, id, price int64) error {
	key := fmt.Sprintf("mall:prod:product:detail:%d", id)
	if err := r.db.WithContext(ctx).Model(&Product{}).
		Where("id = ?", id).Update("price", price).Error; err != nil {
		return err
	}
	return r.rdb.Del(ctx, key).Err()
}
```
为什么是删而不是改：并发「先查后写缓存」的两个请求可能把旧值覆盖新值，删除则让下一次读自然回源。
### 延迟双删
更新 DB → 删缓存 → 延迟 500ms 再删一次，用来清理「更新前读到旧值、更新后才回填」的脏数据：
```go
time.AfterFunc(500*time.Millisecond, func() {
	bg, cancel := context.WithTimeout(context.Background(), time.Second)
	defer cancel()
	_ = r.rdb.Del(bg, key).Err()
})
```
延迟时间要大于一次「读 DB + 回填缓存」的耗时，只能降低概率，不能根除。
### binlog 订阅（最终方案）
用 Canal / Debezium 订阅 MySQL binlog，把变更统一投递到消息队列，由消费者删除缓存。业务代码零侵入、顺序可靠，适合表结构稳定、缓存 key 规则明确的核心表。代价是引入额外组件与延迟（通常几十到几百毫秒）。
## 七、预热与降级兜底
```go
// 启动时预热 TOP 1000 热销商品
func WarmUp(ctx context.Context, r *ProductRepo) error {
	ids, err := r.topHotIDs(ctx, 1000)
	if err != nil {
		return err
	}
	for _, id := range ids {
		if _, err := r.Detail(context.WithoutCancel(ctx), id); err != nil {
			log.Printf("warmup product %d: %v", id, err)
		}
	}
	return nil
}
```
降级兜底要写进代码而不是应急预案：
- Redis 超时/错误 → 直查 DB，同时上报 `cache_error_total`
- DB 压力过大 → 返回本地缓存旧值或「稍后再试」兜底页
- 详情页可接受「价格可能延迟」时，明确在产品上标注，避免用户投诉
## 常见坑
1. **更新时改缓存而不是删缓存**：并发写会把旧值写回去，问题极难复现。
2. **先删缓存再更新 DB**：删除后、更新前的读请求会把旧值回填，脏数据窗口更长。
3. **空值不设短 TTL**：一次误缓存「不存在」会让新上架商品一小时不可见。
4. **所有 key 同一 TTL、同一时刻预热**：整点集体失效，DB 直接被雪崩。
5. **用 `singleflight.Do` 不处理 context**：首请求超时取消，所有等待者一起失败。
6. **把缓存当唯一数据源**：Redis 主从切换丢数据后，订单/库存直接错乱，必须 DB 为准。
7. **一致性方案层层叠加**：既延迟双删又 binlog 又定时全量刷新，维护成本爆炸，选一种即可。
## 小结
- Cache-Aside 是默认选择：读回填、写删缓存、TTL 加抖动
- 穿透靠布隆过滤器 + 空值短缓存，击穿靠 singleflight + 逻辑过期，雪崩靠抖动 + 多级 + 限流
- 一致性优先「先更库再删缓存」，需要更稳再上 binlog 订阅
- 缓存不是账本，核心交易链路永远以 MySQL 为准
