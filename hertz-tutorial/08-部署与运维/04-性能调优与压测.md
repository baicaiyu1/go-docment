# 性能调优与压测
> 一句话定位：用可复现的压测和 pprof 证据调优，而不是靠“感觉”改参数、拍脑袋扩容。

## 本篇目标

- 选对压测工具，建立 QPS / P99 / 错误率 / GC 的指标体系
- 掌握 netpoll 与标准库 net 的对比方法，理解 GOGC/GOMAXPROCS/GOMEMLIMIT
- 接入 pprof，能定位 CPU、内存、goroutine 问题
- 用连接池、超时与容量公式给出可执行的调优结论

## 前置知识

- 已读 [08-部署与运维/03-Kubernetes部署与健康检查](03-Kubernetes部署与健康检查.md)
- 了解 HTTP 长连接、连接池、GC 与 `go tool pprof` 的基本用法

## 一、压测工具选型

| 工具 | 特点 | 典型参数 |
| --- | --- | --- |
| `wrk` | C 实现、高并发、支持 Lua | `-t4 -c400 -d60s --latency` |
| `hey` | Go 实现、简单、支持固定 QPS | `-z 60s -c 200 -q 500` |
| `vegeta` | 固定速率、报告清晰、可出图 | `-rate=1000 -duration=60s` |
| `fortio` | HTTP/gRPC、自带 UI 与直方图 | `-c 200 -qps 1000` |

安装（bash 与 PowerShell 命令相同）：`go install github.com/rakyll/hey@latest`、`go install github.com/tsenart/vegeta@latest`。`wrk` 用系统包管理器或源码编译。

## 二、压测环境与指标

- 压测机与被测服务分开、同可用区；客户端不要成为瓶颈（CPU、文件描述符、端口耗尽）
- 固定版本、固定配置、固定数据集；先预热 30 秒，再取 3 轮的稳定值
- 看分位数而非平均值：**QPS、P50/P90/P99、错误率、CPU、内存、GC 次数、goroutine 数**
- 先定义 SLO（如 P99 < 100ms、错误率 < 0.1%），再判断是否达标

```bash
ulimit -n 65535
sysctl -w net.ipv4.ip_local_port_range="10000 65000"
```

```powershell
netsh int ipv4 show dynamicport tcp
```

## 三、基准压测命令

```bash
hey -z 60s -c 200 -m GET http://127.0.0.1:8888/api/users/1
wrk -t4 -c400 -d60s --latency http://127.0.0.1:8888/api/users/1
```

```powershell
hey -z 60s -c 200 -m GET http://127.0.0.1:8888/api/users/1
wrk -t4 -c400 -d60s --latency http://127.0.0.1:8888/api/users/1
```

固定速率并生成报告：

```bash
"GET http://127.0.0.1:8888/api/users/1" > targets.txt
vegeta attack -rate=1000 -duration=60s -targets=targets.txt -output result.bin
vegeta report -type=text result.bin
```

```powershell
"GET http://127.0.0.1:8888/api/users/1" | Set-Content targets.txt
vegeta attack -rate=1000 -duration=60s -targets=targets.txt -output result.bin
vegeta report -type=text result.bin
```

压测必须带真实鉴权头与典型 body，否则测出来的是“空 handler 的上限”。

## 四、netpoll 与标准库 net 对比

Hertz 默认使用 netpoll（事件驱动，海量长连接下开销更低）。切换到标准库 net 只需要换 Transporter：

```go
import "github.com/cloudwego/hertz/pkg/network/standard"

h := server.New(
	server.WithHostPorts(":8888"),
	server.WithTransport(standard.NewTransporter), // 默认是 netpoll
)
```

对比方法：同一份代码用环境变量选择 Transporter，分别构建、同机同参数各压 3 轮：

```go
opts := []config.Option{server.WithHostPorts(":8888")}
if os.Getenv("HERTZ_TRANSPORT") == "net" {
	opts = append(opts, server.WithTransport(standard.NewTransporter))
}
h := server.New(opts...)
```

高并发短连接通常 netpoll 更稳；需要依赖标准库 `net` 特性的中间件时再用标准实现。结论必须来自自家业务压测，不能照搬博客数字。

## 五、GOGC、GOMAXPROCS 与 GOMEMLIMIT

```bash
GOGC=200 GOMEMLIMIT=400MiB GOMAXPROCS=4 ./bin/userapi
```

```powershell
$env:GOGC = "200"; $env:GOMEMLIMIT = "400MiB"; $env:GOMAXPROCS = "4"
.\bin\userapi.exe
```

- `GOGC=100` 是默认值；调到 200 会减少 GC 次数但增加内存，延迟敏感型服务可小步试
- `GOMEMLIMIT` 给 GC 一个软上限，建议设为容器内存 limit 的 70%~80%，防止 OOMKilled
- Go 1.25 已支持按 cgroup 感知 CPU；仍建议显式核对 `GOMAXPROCS` 与 `limits.cpu` 一致
- 不要用 `GOGC=off` 跑在线 API；那是批处理场景的优化

## 六、pprof：拿证据再调优

接入 `hertz-contrib/pprof`：

```go
import "github.com/hertz-contrib/pprof"

pprof.Register(h) // 暴露 /debug/pprof/
```

只在内网端口或带鉴权的前缀下开启，绝不能暴露公网。

```bash
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/profile?seconds=30"
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/heap"
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/goroutine?debug=1"
```

```powershell
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/profile?seconds=30"
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/heap"
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/goroutine?debug=1"
```

解读要点：

- CPU：看 `top` 的 `flat`（自身耗时）与 `cum`（含调用链），`list 函数名` 定位到行
- 内存：`inuse_space` 看当前占用，`alloc_space` 看累计分配；后者高说明分配频繁，不是泄漏
- goroutine：数量持续上涨且不回落，通常是 channel/锁/HTTP 连接未释放
- block/mutex：需要先开 `runtime.SetBlockProfileRate` / `SetMutexProfileFraction`，否则采样不到

## 七、连接池与超时

```go
db.SetMaxOpenConns(50)
db.SetMaxIdleConns(20)
db.SetConnMaxLifetime(30 * time.Minute)
db.SetConnMaxIdleTime(5 * time.Minute)

c, _ := client.NewClient(
	client.WithMaxConnsPerHost(200),
	client.WithMaxIdleConnDuration(60*time.Second),
	client.WithDialTimeout(500*time.Millisecond),
	client.WithClientReadTimeout(2*time.Second),
)
```

```go
server.New(
	server.WithReadTimeout(5*time.Second),
	server.WithWriteTimeout(10*time.Second),
	server.WithIdleTimeout(60*time.Second),
	server.WithMaxRequestBodySize(8<<20),
)
```

起始值建议：DB 连接池 `maxOpen = QPS × 平均耗时(s) × 2`，并保证 `副本数 × maxOpen < DB max_connections × 0.8`；HTTP 客户端池上限不小于单实例峰值并发；所有超时必须显式设置，杜绝 0（无限等待）。

## 八、常见性能反模式

1. **同步日志刷盘**：每个请求 `Write + Sync`，QPS 被磁盘 IO 锁死；日志写 stdout 交给采集，或使用异步/批量/采样
2. **JSON 大对象**：返回全量字段、嵌套大 map；分页 + 固定 struct，Hertz 默认 sonic 已足够快
3. **锁竞争**：全局 `sync.Mutex` 保护大 map；改分片锁、读多写少用 `sync.Map` 或原子操作
4. **热路径重复创建**：每请求 `client.NewClient`、`regexp.Compile`、`time.NewTicker`；全部提到包级复用
5. **无超时**：下游变慢拖满连接池，故障从单接口扩散到全站；dial/read/write/total 都要设
6. **打印完整请求/响应体**：内存与 IO 双放大，还可能泄露敏感信息

## 九、容量评估

```text
副本数 = ceil(峰值QPS × 冗余系数 / (单实例QPS × 目标利用率))
```

示例：单实例压测 3000 QPS，峰值 20000 QPS，冗余 1.3，目标利用率 0.6：`ceil(20000×1.3/(3000×0.6)) = 15` 个副本。再校验内存：单实例常驻 200 MB + 并发×每请求内存，按 70% 水位反推 limit。

容量确认必须跑 120% 峰值、持续 30 分钟，观察 P99、GC、OOM 与下游瓶颈；只测 1 分钟峰值会漏掉连接泄漏与 GC 抖动。

## 常见坑

1. **压测机与被测服务同机**：CPU 互相抢，数据完全失真。
2. **只看平均延迟**：平均 20ms 但 P99 800ms，用户照样超时。
3. **不预热、不固定版本**：第一轮冷启动、依赖缓存差异让结果无法对比。
4. **用 `-race` 构建做压测**：性能下降数倍，测出的上限没有意义。
5. **pprof 暴露公网**：既泄露内存数据，也可能被恶意触发高开销采样。
6. **GOMAXPROCS 按物理核数设置**：容器 limit 2 核却开 16 个 P，调度开销反而变大。

## 小结

- 压测要固定环境、固定版本、固定数据，关注 QPS、P99、错误率与资源指标
- netpoll 与标准库 net 要用自家业务对比，不迷信单一结论
- pprof 先定位再调参；GOGC/GOMEMLIMIT/GOMAXPROCS 要结合容器 limit
- 连接池与超时是稳定性底线，容量按公式计算并用 120% 峰值压测验证

## 练习

1. 用 hey 与 vegeta 各压一次同一接口，对比 QPS 与 P99 差异并解释。
2. 采集 30 秒 CPU profile，找出一个可优化点并给出修改前后的压测数据。
3. 按本文公式为你的服务估算副本数与 DB 连接池上限，并检查是否超过数据库容量。
