# 测试与基准测试

> 测试不是「有空再补」的附属品，而是 Go 工程的一等公民：`go test` 一条命令就能跑单测、子测试、基准与覆盖率。

## 本篇目标

- 写出符合 Go 规范的测试文件，理解 `TestXxx(t *testing.T)` 的命名与包约定
- 用表驱动测试与 `t.Run` 组织多组用例，输出清晰的失败信息
- 用 `httptest` 测试 HTTP 处理器，不启动真实端口
- 写基准测试并用 `-benchmem` 观察内存分配，知道如何避免编译器优化干扰
- 使用覆盖率与 testify 断言库，建立「测试 → 覆盖率 → CI」的闭环

## 一、测试文件的基本规则

- 文件名必须以 `_test.go` 结尾，否则 `go test` 不会识别
- 测试函数必须是 `func TestXxx(t *testing.T)`，`Xxx` 首字母大写
- 测试文件与被测代码放在**同一个包**（可直接访问未导出标识符），或放在 `xxx_test` 包（只测公开 API）
- 测试文件不参与 `go build`，不会打进二进制

先写一个被测函数与对应测试：

```go
// calc.go
package calc

func Divide(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("除数不能为 0")
	}
	return a / b, nil
}
```

```go
// calc_test.go
package calc

func TestDivide(t *testing.T) {
	got, err := Divide(10, 2)
	if err != nil {
		t.Fatalf("unexpected error: %v", err)
	}
	if got != 5 {
		t.Errorf("Divide(10,2) = %d, want 5", got)
	}
}
```

```powershell
go test ./...
go test -v ./...
```

```bash
go test ./...
go test -v ./...
```

`t.Errorf` 记录失败并继续执行；`t.Fatalf` 记录失败并立即终止当前测试函数。断言前置条件用 `Fatalf`，多个独立检查用 `Errorf`。

## 二、表驱动测试与 t.Run

真实业务分支多，逐个写函数既冗长又难维护。表驱动是 Go 的标准做法：

```go
func TestDivideTable(t *testing.T) {
	tests := []struct {
		name    string
		a, b    int
		want    int
		wantErr bool
	}{
		{name: "正常除法", a: 10, b: 2, want: 5},
		{name: "整除为零", a: 0, b: 5, want: 0},
		{name: "除数为零", a: 1, b: 0, wantErr: true},
		{name: "负数", a: -9, b: 3, want: -3},
	}

	for _, tt := range tests {
		t.Run(tt.name, func(t *testing.T) {
			got, err := Divide(tt.a, tt.b)
			if tt.wantErr {
				if err == nil {
					t.Fatalf("expected error, got nil")
				}
				return
			}
			if err != nil {
				t.Fatalf("unexpected error: %v", err)
			}
			if got != tt.want {
				t.Errorf("Divide(%d,%d) = %d, want %d", tt.a, tt.b, got, tt.want)
			}
		})
	}
}
```

优点：新增用例只加一行，不复制测试逻辑；`t.Run` 生成子测试，失败时能定位到具体用例名；可以只跑某个子测试：`go test -run 'TestDivideTable/除数为零'`。

Go 1.22 起循环变量每轮独立，**不需要再写 `tt := tt`**。看到老代码里的这行，知道是历史遗留即可。

## 三、测试辅助：t.Helper、t.Cleanup、t.TempDir

- `t.Helper()`：让失败行号指向真正的调用位置，否则日志全指向辅助函数
- `t.Cleanup()`：注册清理函数，比 `defer` 更适合在辅助函数中注册
- `t.TempDir()`：创建自动清理的临时目录，适合文件相关测试
- `t.Setenv()`：设置环境变量并在测试后自动恢复

## 四、测试 HTTP 处理器

不需要真的监听端口，`httptest` 可以构造请求与捕获响应：

```go
func healthz(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte("ok"))
}

func TestHealthz(t *testing.T) {
	req := httptest.NewRequest(http.MethodGet, "/healthz", nil)
	rec := httptest.NewRecorder()

	healthz(rec, req)

	if rec.Code != http.StatusOK {
		t.Fatalf("status = %d, want 200", rec.Code)
	}
	if got := rec.Body.String(); got != "ok" {
		t.Errorf("body = %q, want %q", got, "ok")
	}
}
```

要点：`httptest.NewRequest` 不会真的走网络；`httptest.NewRecorder` 捕获状态码、头与 body；测试中间件时，把 `middleware(handler)` 的结果当作被测对象即可。

## 五、基准测试

基准函数以 `Benchmark` 开头，接收 `*testing.B`：

```go
var sink int

func BenchmarkDivide(b *testing.B) {
	b.ReportAllocs()
	for i := 0; i < b.N; i++ {
		sink, _ = Divide(100, 3)
	}
}
```

```powershell
go test -bench=. -benchmem ./...
```

```bash
go test -bench=. -benchmem ./...
```

输出形如 `BenchmarkDivide-8 1000000000 0.30 ns/op 0 B/op 0 allocs/op`。

- `b.N` 由框架自动调整，直到运行时间足够稳定
- `b.ReportAllocs()` 或 `-benchmem` 报告内存分配
- `sink` 是包级变量，防止编译器把循环优化掉
- 初始化耗时用 `b.ResetTimer()` 排除

## 六、覆盖率与 testify

```powershell
go test -cover ./...
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```

```bash
go test -cover ./...
go test -coverprofile=coverage.out ./...
go tool cover -html=coverage.out
```

`-cover` 输出每个包的语句覆盖率，`go tool cover -html` 会在浏览器里逐行标记「覆盖 / 未覆盖」。注意：覆盖率**不等于**质量，100% 覆盖也可能全是无效断言；关注「核心业务分支是否覆盖」，不要为了数字写无意义测试。

标准库断言够用，但比较冗长。testify 提供 `assert` 与 `require`：

```go
func TestUser(t *testing.T) {
	u := NewUser(1, "alice")
	require.NotNil(t, u) // 失败立即终止
	assert.Equal(t, "alice", u.Name)
	assert.Empty(t, u.Email)
}
```

安装：`go get github.com/stretchr/testify@v1.10.0`。

区别：`require` 断言失败调用 `t.FailNow()`，用于「不满足就无法继续」的前置条件；`assert` 失败记录错误但继续执行，用于独立的多项检查。团队规范建议：**外部依赖、初始化、取指针后用 `require`，其余用 `assert`**。

## 七、常用参数与 CI 实践

| 参数 | 作用 |
| --- | --- |
| `-run` | 按正则筛选测试 |
| `-count=1` | 禁用缓存，强制重跑 |
| `-race` | 开启数据竞争检测 |
| `-shuffle=on` | 打乱测试顺序，暴露顺序依赖 |
| `-timeout=30s` | 超时保护，防止测试挂死 |

CI 里的典型命令是 `go vet ./... && go test -race -shuffle=on -count=1 -timeout=60s ./...`。`-race` 会显著变慢，但对并发代码是必须的；`-count=1` 避免「上次跑过了」的假绿。

## 常见坑

1. **测试文件命名错误**：`calc_test.go.txt` 或 `calcTest.go` 都不会被识别，必须 `_test.go`。
2. **测试依赖执行顺序**：Go 不保证测试顺序，用 `-shuffle=on` 尽早暴露。
3. **在测试里 `os.Exit`**：会直接终止测试进程，其他测试全被跳过，用 `t.Fatal`。
4. **用 `time.Sleep` 等待异步结果**：不稳定，改用 channel 通知或带超时的轮询。
5. **基准测试没有使用结果**：编译器可能优化掉整个循环，用包级 `sink` 接收。
6. **测试真实数据库/网络**：单元测试应可离线运行，外部依赖用接口 mock 或 `httptest`。

## 小结

`_test.go` + `TestXxx` + 表驱动 + `t.Run` 是 Go 测试的标准骨架；`httptest` 让 HTTP 处理器可测；`-bench` 量化性能；覆盖率与 testify 提升可读性。到这里，`01-Go语言基础` 全部结束，接下来进入 [02-Hertz入门/01-Hertz是什么-架构与性能](../02-Hertz入门/01-Hertz是什么-架构与性能.md)，你会带着完整的 Go 基础去看框架设计。
