# 学习计划与时间估算

> 一句话定位：按依赖关系重排 100 篇教程的学习顺序，并给出可执行的学时预算、里程碑验收标准与企业级达标判定。

---

## 本篇目标

- 明确「目录编号顺序」与「推荐学习顺序」的差异，避免学到一半卡住
- 拿到每一篇的阅读与动手学时，能排出自己的周计划
- 用里程碑验收代替"看完了"，确保每一步真的会
- 理性判断：学完本教程离企业级还差什么

## 前置知识

无。本文是全局规划，随时可回看。

## 一、先回答：目录顺序对吗？

**不完全对。** 大方向正确（基础 → 框架 → 数据 → 微服务 → 实战），但存在 5 处会导致"接不上"的地方：

| # | 问题 | 后果 | 修正 |
| --- | --- | --- | --- |
| 1 | 04 可观测性 排在 05 Prometheus 之前 | 04/03 埋点会引用尚未讲的指标暴露方式 | 先看 05/05，再回看 04/03 |
| 2 | 05 治理与扩展 排在 12 Kitex 之前 | 没有 RPC 服务时学"服务注册发现"只能死记概念 | 05/01-02 只做概念速览，实操放到 12/05 |
| 3 | 07 工程化 排在 09-11 数据层之前 | 分层示例里 repository 层没有 MySQL/Redis 可落 | 07 移到 09-11 之后 |
| 4 | 08 部署与运维 整体排在数据层之前 | 09-11 要用 Docker 起 MySQL/Redis/Kafka，但 K8s、压测此时学太早 | 08/01-02 提前，08/03-04 后置到实战之后 |
| 5 | 06 hz 进阶 的 Thrift 与 12 Kitex 的 Thrift 同名不同物 | 容易误以为是一套东西 | 06 只学 hz 的 HTTP IDL；RPC IDL 留到 12/02 |

> 为什么不直接改目录编号？因为 100 个文档里有大量相对链接，改编号会产生上百处断链。用「推荐学习顺序」覆盖编号顺序更稳，链接也不会坏。

## 六、学完能达到企业级标准吗？

**知识框架：能。工程能力：还差一截，需要额外补三样东西。**

### 你已经具备的（学完本教程）

- 能独立设计并实现一个 Hertz + Kitex 的分层微服务
- 会用 MySQL/Redis/Kafka 解决缓存、异步、最终一致性问题
- 会接 Nacos 注册配置、Prometheus 监控、OTel 链路
- 会写 Dockerfile、K8s 部署清单、灰度与回滚流程
- 知道幂等、超时预算、熔断降级、对账补偿这些企业级关键词的真正含义

### 还差的（教程无法替代）

| 缺口 | 为什么教程给不了 | 怎么补 |
| --- | --- | --- |
| 真实生产排障 | 线上问题是长尾的：连接泄漏、GC 抖动、网络分区、脏数据 | 实习/工作，或自己压测+故意注入故障 |
| 代码评审经验 | 看别人代码、被别人挑毛病，才知道什么叫"可维护" | 参与开源项目 PR、找同侪 review |
| 容量与成本 | 真实 QPS、机器规格、预算约束下做取舍 | 自己买台云主机做压测与成本核算 |
| 安全 | OAuth2/OIDC、越权、注入、密钥轮换、等保 | 专项学习 + 安全扫描工具实践 |
| 分布式理论深度 | CAP/BASE、一致性哈希、Raft、分库分表实操 | 读《数据密集型应用系统设计》 |
| 组织协作 | 需求评审、排期、跨团队接口对齐、值班 | 只能在工作里练 |

### 结论

- **面试/求职**：这套教程的知识密度足够覆盖 Go 后端初中级岗位的八股与项目追问，前提是 mall-lite 你要能讲清楚每个设计取舍。
- **直接上手企业项目**：能干活，但仍需要 3-6 个月的真实项目磨合。
- **"完全掌握"的定义**：不是看完 313 小时，而是能**不看教程从零复现 mall-lite，并能解释每个选择的代价**。做到这一点，才算跨过企业级门槛。

### 建议的额外补充（教程之外，按需）

1. 分布式理论：CAP、BASE、一致性哈希、Raft（1-2 周）
2. 安全专项：OAuth2/OIDC、JWT 最佳实践、OWASP Top 10（1 周）
3. 分库分表实操：ShardingSphere 或 TiDB 入门（1 周）
4. 服务网格与云原生：Istio 概念、K8s Operator（选学）
5. 英语阅读：官方 issue / RFC / 源码注释（长期）

## 七、学习建议

1. **按第二节的 16 步走，不要按目录编号硬啃。**
2. **每篇的"动手"环节不能省**——Hertz 的很多行为（中间件顺序、绑定失败、优雅退出）只看文字学不会。
3. **每完成一个里程碑，用验收标准自测**，不达标就回炉。
4. **13 章要真做**：哪怕简化，也要自己把下单链路跑一遍，这是整本书的收敛点。
5. **遇到 API 疑问以官方文档为准**：本教程个别第三方库的写法标注了"示例示意"，版本升级后可能变化。
6. **别追求一次看懂**：第一遍跑通，第二遍看原理，第三遍做优化，是正常节奏。
