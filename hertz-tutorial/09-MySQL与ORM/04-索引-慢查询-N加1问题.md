# 04-索引-慢查询-N加1问题
> 一句话定位：先把 SQL 看明白，再谈优化；索引、EXPLAIN、慢日志和 N+1，是数据层性能的四把手术刀。

## 一、B+ 树与两种索引

InnoDB 的主键索引是**聚簇索引**，叶子节点直接存整行；二级索引叶子存“索引列 + 主键”，查非索引列要**回表**。B+ 树的特点是：

- 所有数据在叶子节点，且按 key 有序，范围查询与排序友好
- 树高三到四层，一次查询通常 3~4 次页读取
- 联合索引按定义顺序逐列排序，所以有**最左前缀**限制
- 索引不是越多越好：每个索引都增加写放大、磁盘与优化器选择成本

## 二、联合索引、最左前缀与覆盖索引

为 mall-lite 的订单列表建联合索引：

```sql
ALTER TABLE orders
  ADD INDEX idx_orders_user_status_created (user_id, status, created_at);
```

它能服务这些查询（按最左前缀连续命中）：

```sql
SELECT id, order_no FROM orders WHERE user_id = 42;
SELECT id, order_no FROM orders WHERE user_id = 42 AND status = 1;
SELECT id, order_no FROM orders
 WHERE user_id = 42 AND status = 1 ORDER BY created_at DESC LIMIT 20;
```

下面这些**不能**充分利用该索引：只查 `status`、只查 `created_at`、`WHERE status = 1 AND created_at > ?`。不是因为索引没用，而是缺少最左列 `user_id`。

**覆盖索引**：查询列全在索引里，无需回表。给上面的索引补上 `order_no`：

```sql
ALTER TABLE orders DROP INDEX idx_orders_user_status_created;
ALTER TABLE orders
  ADD INDEX idx_orders_user_status_created (user_id, status, created_at, order_no);
```

```sql
EXPLAIN SELECT user_id, status, order_no FROM orders
 WHERE user_id = 42 AND status = 1; -- Extra: Using index
```

用 `SELECT *` 会直接破坏覆盖索引，这是最简单的优化点之一。

## 三、区分度与前缀索引

区分度 = `COUNT(DISTINCT col) / COUNT(*)`。接近 1 适合建索引；性别、状态这类低区分度列单独建索引意义不大，应放在联合索引的非首列或配合其他条件。

```sql
SELECT COUNT(DISTINCT user_id) / COUNT(*) AS user_sel,
       COUNT(DISTINCT status)  / COUNT(*) AS status_sel
FROM orders;
```

长字符串（URL、邮箱、商品名）可用前缀索引控制体积：

```sql
ALTER TABLE products ADD INDEX idx_products_name_prefix (name(12));
```

代价：前缀索引**不能覆盖**完整列，也不能用于 `ORDER BY name` 的完全排序；前缀长度要保证区分度足够（可对比 `LEFT(name,12)` 与完整列的 distinct 数）。

## 四、索引失效的常见写法

```sql
-- 失效：对索引列做函数
SELECT * FROM orders WHERE DATE(created_at) = '2026-01-01';
-- 改写：范围查询
SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';

-- 失效：隐式类型转换（phone 是 varchar）
SELECT * FROM users WHERE phone = 13800138000;
-- 改写：
SELECT * FROM users WHERE phone = '13800138000';

-- 失效：前导模糊
SELECT * FROM products WHERE name LIKE '%耳机%';
-- 只能前缀模糊走索引；全文检索交给 ES/全文索引
SELECT * FROM products WHERE name LIKE '耳机%';
```

其他高频原因：`OR` 连接了无索引列、`!=`/`NOT IN`、联合索引跳过最左列、`ORDER BY` 与索引顺序不一致、两表 JOIN 的字符集/排序规则不一致、对索引列使用 `+ - * /`。

## 五、EXPLAIN 关键字段

```sql
EXPLAIN SELECT id, order_no FROM orders
 WHERE user_id = 42 AND status = 1 ORDER BY created_at DESC LIMIT 20;
```

| 字段 | 关注点 |
| --- | --- |
| `type` | 从好到差：`const` > `eq_ref` > `ref` > `range` > `index` > `ALL` |
| `possible_keys` / `key` | 优化器考虑过什么、最终用了什么；`key` 为 `NULL` 即未走索引 |
| `key_len` | 联合索引用到了几列，可判断最左前缀是否生效 |
| `rows` | 预估扫描行数，越大越危险 |
| `filtered` | 扫描后剩余比例，低说明大量无效扫描 |
| `Extra` | `Using index` 覆盖索引；`Using index condition` 索引下推；`Using filesort`/`Using temporary` 需警惕 |

`type=ALL` 且 `rows` 很大，基本可以判定全表扫描；`type=index` 是全索引扫描，也不等于走对了索引。

## 六、慢查询日志与 Top SQL

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.2;   -- 200ms
SET PERSIST slow_query_log = ON;    -- 重启后仍生效
SHOW VARIABLES LIKE 'slow_query_log_file';
```

查看并分析：

```bash
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query_log_file';"
pt-query-digest /var/lib/mysql/mysql-slow.log > slow_report.txt
```

```powershell
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query_log_file';"
pt-query-digest C:\mysql\data\mysql-slow.log > slow_report.txt
```

Windows 上没有 `pt-query-digest` 时用 WSL/Docker 跑 Percona Toolkit；没有工具时先按 `Query_time` 排序人工看。报告重点：**总耗时占比、执行次数、平均/最大耗时、扫描行数**。次数多且单次不慢的 SQL，往往比偶发超慢 SQL 更值得优化。

## 七、GORM 中消灭 N+1

反例：先查 100 个订单，再循环查明细，共 101 条 SQL：

```go
var orders []Order
db.WithContext(ctx).Where("user_id = ?", uid).Find(&orders)
for i := range orders {
	db.WithContext(ctx).Where("order_id = ?", orders[i].ID).Find(&orders[i].Items) // N+1
}
```

三种正解：

```go
// 1) Preload：1 + N 张关联表，无重复行
db.WithContext(ctx).Preload("Items").Preload("Items.Product").
	Where("user_id = ?", uid).Find(&orders)

// 2) 批量 IN：先收集主键，一次查回
var items []OrderItem
db.WithContext(ctx).Where("order_id IN ?", orderIDs).Find(&items)

// 3) Joins + Select：用子表条件筛父表，只取需要的列
type OrderRow struct {
	OrderNo  string
	Nickname string
}
var rows []OrderRow
db.WithContext(ctx).Table("orders").
	Select("orders.order_no, users.nickname").
	Joins("JOIN users ON users.id = orders.user_id").
	Where("orders.status = ?", 1).Scan(&rows)
```

选择原则：取聚合根用 `Preload`；只需要关联字段用 `Joins + Select`；ID 列表已知用批量 `IN`。无论哪种，都要用日志确认 SQL 条数，而不是凭感觉。

## 八、深分页、count 与大表

**深分页**：`OFFSET 1000000` 要先扫描并丢弃 100 万行，越翻越慢。改用游标（keyset pagination）：

```go
// 慢
db.WithContext(ctx).Order("id").Offset(1000000).Limit(20).Find(&orders)
// 快：where id > 上一页最后一个 id
db.WithContext(ctx).Where("id > ?", lastID).Order("id").Limit(20).Find(&orders)
```

要求排序字段有索引且唯一（通常是主键）；按 `created_at` 翻页时要加 `id` 作为第二排序键避免重复。

**count(*)**：InnoDB 需要扫描最小的二级索引，大表上仍可能很慢。优化手段：缩小 `WHERE` 范围、用覆盖索引、维护计数表（下单/取消时增减）、接受 `SHOW TABLE STATUS` 的估算值。**不要**对多表 JOIN 后的结果做 `COUNT(*)`，先聚合再计数。

**大字段与大表**：商品详情、富文本、图片 base64 拆到 `product_details` 纵表；超过千万行的订单按时间分区或归档到 `orders_history`；写多读少的日志表定期 `DELETE ... LIMIT` 分批清理，避免一次删太多造成长事务与主从延迟。

## 常见坑

1. **联合索引按“区分度最高”排序**：忽略查询模式，导致最左前缀永远用不上。
2. **对索引列做函数或运算**：`DATE(created_at)`、`price * 2` 都让索引失效。
3. **隐式类型转换**：`varchar` 列用数字比较，既全表扫描又可能查出错误结果。
4. **`LIKE '%关键词'`**：前导模糊必然全表扫描，搜索需求应交给全文索引或 ES。
5. **`SELECT *`**：破坏覆盖索引，还把大字段一起读回内存。
6. **大 `OFFSET` 深分页**：页数越深越慢，必须改游标。
7. **只看 `key` 不看 `rows`/`Extra`**：走了索引但扫描百万行，依然是慢 SQL。
8. **盲目加索引**：写放大、锁范围变大、优化器选错索引，删除比新增更安全。

## 小结

- 联合索引要按查询模式设计，遵守最左前缀；覆盖索引能省掉回表
- 索引失效多来自函数、隐式转换、前导模糊与联合索引跳列
- `EXPLAIN` 看 `type/key/rows/Extra`，慢日志按总耗时占比排优先级
- N+1 用 Preload、批量 IN、Joins + Select 三种方式解决
- 深分页用游标，count 用计数表或缩小范围，大表拆分归档
