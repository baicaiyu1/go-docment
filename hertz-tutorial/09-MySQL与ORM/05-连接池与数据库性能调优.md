# 05-连接池与数据库性能调优
> 一句话定位：数据库性能的上限，往往不是 SQL 慢，而是连接池配错、超时没预算、读写分离读到了旧数据。

## 本篇目标

- 搞懂 `sql.DB` 四个参数的含义，并按 QPS 与 MySQL 配置算出合理值
- 识别连接池耗尽的现象，用 `db.Stats`、Prometheus、pprof 定位
- 把 `context` 超时从 Hertz/Kitex 一路传到 GORM
- 掌握 dbresolver 读写分离、批量写入、prepared statement 与事务大小控制

## 前置知识

- 已读 [09-MySQL与ORM/04-索引-慢查询-N加1问题](04-索引-慢查询-N加1问题.md)
- 了解 `database/sql` 连接池、`context` 取消与主从复制
- 知道 Hertz 的 `ReadTimeout`、Kitex 的 `WithTimeout`

## 一、`sql.DB` 与四个参数

GORM 的 `*gorm.DB` 底层就是一个 `*sql.DB` 连接池，**不是单个连接**：

```go
sqlDB, _ := db.DB()
sqlDB.SetMaxOpenConns(50)                  // 最大打开连接数（含使用中+空闲）
sqlDB.SetMaxIdleConns(20)                  // 最大空闲连接数
sqlDB.SetConnMaxLifetime(30 * time.Minute) // 连接最长存活时间
sqlDB.SetConnMaxIdleTime(5 * time.Minute)  // 空闲多久后关闭
```

| 参数 | 作用 | 配错的后果 |
| --- | --- | --- |
| `MaxOpenConns` | 并发上限 | 太小请求排队；太大打爆 MySQL |
| `MaxIdleConns` | 热连接保留 | 默认只有 2，频繁建连/断连 |
| `ConnMaxLifetime` | 强制换连接 | 为 0 时连接永久存活，遇到主从切换/重启报错 |
| `ConnMaxIdleTime` | 回收空闲连接 | 空闲连接长期占用 MySQL 名额 |

`MaxIdleConns` 建议等于或略小于 `MaxOpenConns`，避免“用一下关一下”的抖动。

## 二、按 QPS 与 MySQL 容量算连接数

```text
单实例 maxOpen ≈ ceil(单实例QPS × 平均DB耗时(s) × 2)
总连接数 = 副本数 × maxOpen + 其他服务连接 + 运维预留
总连接数 ≤ MySQL max_connections × 0.8
ConnMaxLifetime < wait_timeout（MySQL 默认 28800s，但代理/LB 常见 60s）
```

示例：单实例 2000 QPS、平均 DB 耗时 5ms，则并发约 10，乘 2 得 `maxOpen=20`；8 个副本共 160，MySQL `max_connections=1000`，留足余量。若单实例 500 QPS、平均 50ms，则并发 25，`maxOpen` 至少要 50。

估算时逐项核对：

- 峰值 QPS 用压测值，不用日均值
- 平均 DB 耗时看 P50，不要用 P99 放大整体
- 单实例并发 = QPS × 耗时（秒）
- `maxOpen` = 并发 × 2，给突发留余量
- 总连接 = 副本数 × `maxOpen` + 其他服务 + 运维预留
- 总连接不超过 `max_connections` 的 80%

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'wait_timeout';
SHOW STATUS LIKE 'Threads_connected';
```

扩容副本前先做乘法：副本数翻倍，数据库连接数也翻倍，这是最常见的“扩容把数据库打挂”原因。

## 三、连接池耗尽：现象与排查

典型现象：

- 接口 P99 突然抬升，日志出现 `context deadline exceeded` 或 `i/o timeout`
- `SHOW PROCESSLIST` 大量 `Sleep` 或 `Waiting for table metadata lock`
- MySQL 报 `Too many connections`
- pprof goroutine 大量卡在 `database/sql.(*DB).conn`

先看池内指标：

```go
stats := sqlDB.Stats()
log.Printf("open=%d inuse=%d idle=%d waitCount=%d waitDuration=%s maxOpen=%d",
	stats.OpenConnections, stats.InUse, stats.Idle,
	stats.WaitCount, stats.WaitDuration, stats.MaxOpenConnections)
```

`WaitCount` 持续增长、`WaitDuration` 变大，说明请求在等连接，而不是 SQL 慢。接入 Prometheus：

```go
prometheus.MustRegister(collectors.NewDBStatsCollector(sqlDB, "mysql_master"))
```

需要看 goroutine 栈时：

```bash
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/goroutine?debug=1"
```

```powershell
go tool pprof -http=:8080 "http://127.0.0.1:8888/debug/pprof/goroutine?debug=1"
```

常见根因：事务里做 RPC/发 MQ、循环里逐条查库（N+1）、`MaxOpenConns` 小于实际并发、慢 SQL 占住连接不释放。GORM 的 `Warn` 日志会打印超过 `SlowThreshold` 的 SQL，先确认有没有慢查询把连接占满。**连接池不是限流器**，入口该限流还是要限流。

## 四、context 超时：把预算传下去

```go
ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond)
defer cancel()
err := db.WithContext(ctx).Where("user_id = ?", uid).Find(&orders).Error
```

`WithContext` 会把取消/超时传给驱动，查询被 cancel 后连接会尽快归还。典型预算（按链路逐层递减）：

| 层级 | 预算 | 说明 |
| --- | --- | --- |
| Hertz 网关 | 800ms | 对外承诺的 P99 |
| Kitex RPC | 400ms | 网关到 order-service |
| MySQL 查询 | 200ms | 单次查询上限 |
| Redis | 50ms | 缓存读写 |

每层预留 10%~20% 余量，不要把超时都设成一样长；否则下游超时了，上游还在傻等。Hertz handler 里用 `c.Request.Context()`，Kitex 服务里用 RPC 传入的 `ctx`，一路传到 repository。

## 五、读写分离：dbresolver 与主从延迟

```go
import "gorm.io/plugin/dbresolver"

err := db.Use(dbresolver.Register(dbresolver.Config{
	Sources:  []gorm.Dialector{mysql.Open(masterDSN)},
	Replicas: []gorm.Dialector{mysql.Open(replicaDSN)},
	Policy:   dbresolver.RandomPolicy{},
}).SetMaxOpenConns(50).SetMaxIdleConns(20).SetConnMaxIdleTime(5 * time.Minute))
```

默认读走从库、写走主库；需要强制读主库时显式声明：

```go
db.Clauses(dbresolver.Write).Where("id = ?", orderID).First(&order)
db.Clauses(dbresolver.Read).Where("id = ?", orderID).First(&order)
```

主从延迟的应对：

- **写后立即读**（下单后跳订单详情）强制走主库，或读自己的缓存
- 对延迟敏感的列表页，可接受“短时间旧数据”的才走从库
- 监控 `Seconds_Behind_Source`（`SHOW REPLICA STATUS`），延迟超过阈值自动切主库
- 不要把强一致事务拆到从库执行

## 六、分库分表的时机

先问三个问题：单表是否超过 2000 万~5000 万行？写入 QPS 是否已接近单机上限？DDL/备份窗口是否不可接受？如果都没有，优先做**索引优化、归档、读写分离、升级硬件**。

确需拆分时：

- 垂直拆分：大字段、日志、历史订单拆到独立表/库
- 水平分片：按 `user_id` 取模或范围，保证同一用户的数据在同一分片
- 中间件：ShardingSphere-Proxy、Vitess；或应用层分片（自研路由）
- NewSQL：TiDB 等，适合不想自研路由但能接受运维成本

分片键一旦选错，跨分片 JOIN、分页、事务都会变成灾难，必须在上线前压测验证。

## 七、批量写入、Prepared Statement 与事务大小

```go
// 批量插入：每批 500~1000 行，避免单条 SQL 过大
db.WithContext(ctx).CreateInBatches(&orders, 500)

// 幂等写入：唯一键冲突时更新指定列
db.Clauses(clause.OnConflict{
	Columns:   []clause.Column{{Name: "sku"}},
	DoUpdates: clause.AssignmentColumns([]string{"price", "updated_at"}),
}).Create(&products)
```

Prepared Statement 在 `gorm.Open` 时开启 `PrepareStmt: true`，可复用解析计划、降低 SQL 解析开销；但要注意连接重建后语句需要重新准备，DDL 变更后应滚动重启。

事务大小控制：单事务 500~1000 行或 1~2 秒内提交；超大事务会导致 undo/binlog 膨胀、锁等待、主从延迟。批量任务拆成多个小事务，并记录断点以便重跑。

## 常见坑

1. **只设 `MaxOpenConns` 不设 `MaxIdleConns`**：默认空闲连接只有 2，流量抖动时反复建连。
2. **`ConnMaxLifetime=0`**：连接永久存活，MySQL 重启、主从切换、代理 60s 空闲断连后报 `invalid connection`。
3. **连接数不乘副本数**：扩容后总连接超过 `max_connections`，新 Pod 全部启动失败。
4. **事务里做 RPC/MQ 或循环查库**：连接被长期占用，池很快耗尽。
5. **忘记 `WithContext`**：客户端断开后查询继续跑，白白占用连接与 CPU。
6. **读写分离后写后立即读**：从库延迟导致“刚下的单查不到”，必须强制读主库或读缓存。
7. **把连接池当限流**：入口不限流，池满后所有请求一起超时，故障面更大。
8. **`PrepareStmt` 与频繁 DDL/连接重建混用**：出现预编译语句失效，需滚动重启验证。

## 小结

- `sql.DB` 是连接池，四个参数要按 QPS、副本数与 MySQL 容量一起算
- 池耗尽先看 `db.Stats` 的 `WaitCount/WaitDuration` 与 goroutine 栈，再谈加连接
- 超时预算从网关到 DB 逐层递减，`WithContext` 必须贯穿全链路
- 读写分离要处理主从延迟，强一致读显式走主库
- 批量写分批、事务短小、prepared statement 按需开启

## 练习

1. 按你的服务 QPS 与平均 DB 耗时计算 `maxOpen`，再乘以副本数校验是否超过 MySQL 容量。
2. 用 `go tool pprof` 抓一次高并发下的 goroutine 栈，找出等待连接的位置。
3. 为订单详情接口配置 dbresolver，并实现“下单后 3 秒内强制读主库”的策略。
