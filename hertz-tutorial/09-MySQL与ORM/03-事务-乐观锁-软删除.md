# 03-事务-乐观锁-软删除
> 一句话定位：事务管边界、锁管并发、软删除管历史，三者错一个，订单和库存就会对不上。

- 理解 MySQL 默认 RR 隔离级别与死锁排查路径

## 一、事务的三种写法

**推荐：`db.Transaction`**，回调返回 error 自动回滚，正常返回自动提交：

```go
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	return tx.Model(&Stock{}).Where("product_id = ?", pid).
		Update("available", gorm.Expr("available - ?", qty)).Error
})
```

**需要精细控制：手动 Begin/Commit**。用命名返回值 + `defer` 保证异常路径一定回滚：

```go
func createOrder(ctx context.Context, db *gorm.DB, o *Order) (err error) {
	tx := db.WithContext(ctx).Begin()
	if tx.Error != nil {
		return tx.Error
	}
	defer func() {
		if r := recover(); r != nil {
			tx.Rollback()
			panic(r)
		}
		if err != nil {
			tx.Rollback() // Commit 成功后 err 为 nil，不会重复回滚
		}
	}()
	if err = tx.Create(o).Error; err != nil {
		return err
	}
	if err = tx.Create(&o.Items).Error; err != nil {
		return err
	}
	return tx.Commit().Error
}
```

**嵌套事务**：GORM 默认用 `SAVEPOINT` 实现，内层失败只回滚到保存点，外层仍可决定继续或回滚：

```go
db.Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	// 内层失败不必然回滚外层；需要“全有或全无”时仍返回 err
	return tx.Transaction(func(tx2 *gorm.DB) error {
		return tx2.Create(&order.Items).Error
	})
})
```

不想要 SavePoint 语义时用 `db.Session(&gorm.Session{DisableNestedTransaction: true})`，让内层 `Transaction` 退化为直接使用外层连接。不要在事务里启动 goroutine 复用 `tx`，`*gorm.DB` 不是并发安全的。

## 二、事务边界：不要跨网络调用

一个事务应该只包含**本地数据库操作**。下面这些都必须放到事务外：

- 调用 Kitex 的 `product-service` 预扣库存（跨进程，可能超时/重试）
- 发送 Kafka 订单事件（可能阻塞、重试、重复）
- 调用支付网关、短信、对象存储
- 读写 Redis（除非是同一业务语义的锁，且要单独评估）

原因很直接：网络调用耗时不可控，事务会长时间持有行锁与连接，轻则连接池耗尽，重则锁等待雪崩。正确做法是**本地事务 + 事件表（outbox）**：

```go
// 本地事务只做两件事：写订单、写 outbox
err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	if err := tx.Create(&order).Error; err != nil {
		return err
	}
	return tx.Create(&Outbox{EventType: "order.created", Payload: payload}).Error
})
// 提交成功后由独立消费者读取 outbox 投递 Kafka；RPC 预扣库存放在事务之前或之后做补偿
```

## 三、隔离级别与死锁

MySQL InnoDB 默认 `REPEATABLE READ`（RR）。RR 下普通 `SELECT` 是**快照读**，`SELECT ... FOR UPDATE` 与 `UPDATE` 是**当前读**：

```sql
SHOW VARIABLES LIKE 'transaction_isolation';
SELECT @@transaction_isolation;
```

- 快照读在事务第一次读时建立 Read View，之后看不到其他事务的新提交
- 当前读会加锁并读最新版本；RR 还会加间隙锁，降低并发、增加死锁概率
- 高并发扣减场景可评估 `READ COMMITTED`，但要确认 binlog 为 `ROW`：

```go
err := db.Transaction(func(tx *gorm.DB) error {
	// ...
	return nil
}, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
```

死锁排查三板斧：

```sql
SHOW ENGINE INNODB STATUS\G          -- 看 LATEST DETECTED DEADLOCK
SHOW VARIABLES LIKE 'innodb_print_all_deadlocks';
SET PERSIST innodb_print_all_deadlocks = ON;
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
```

治理思路：**固定加锁顺序**（都按 `product_id` 升序）、缩短事务、确保 `WHERE` 走索引（否则锁全表/大量间隙）、对死锁错误码 `1213` 做有限重试。

## 四、乐观锁：version 字段

适合**冲突不频繁**的库存扣减、配置更新。核心是 `UPDATE ... WHERE id=? AND version=?`，用 `RowsAffected` 判断是否抢到：

```go
func deductStock(ctx context.Context, db *gorm.DB, pid uint64, qty int64) error {
	for i := 0; i < 3; i++ { // 冲突重试
		var s Stock
		if err := db.WithContext(ctx).Where("product_id = ?", pid).First(&s).Error; err != nil {
			return err
		}
		if s.Available < qty {
			return ErrStockNotEnough
		}
		res := db.WithContext(ctx).Model(&Stock{}).
			Where("product_id = ? AND version = ? AND available >= ?", pid, s.Version, qty).
			Updates(map[string]interface{}{
				"available": gorm.Expr("available - ?", qty),
				"version":   gorm.Expr("version + 1"),
			})
		if res.Error != nil {
			return res.Error
		}
		if res.RowsAffected == 1 {
			return nil
		}
	}
	return ErrConflict
}
```

注意两点：`available >= ?` 与 version 条件同时命中时 `RowsAffected=0` 可能表示“库存不足”或“版本冲突”，需要重新查询区分；重试要有上限并加退避，避免活锁。

## 五、悲观锁：SELECT ... FOR UPDATE

适合**冲突频繁、必须一次成功**的场景，例如同一订单的重复支付回调。用 `clause.Locking`：

```go
import "gorm.io/gorm/clause"

err := db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
	var s Stock
	if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
		Where("product_id = ?", pid).First(&s).Error; err != nil {
		return err
	}
	if s.Available < qty {
		return ErrStockNotEnough
	}
	return tx.Model(&Stock{}).Where("product_id = ?", pid).
		Update("available", gorm.Expr("available - ?", qty)).Error
}, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
```

`FOR UPDATE` 会阻塞其他写事务，必须满足：条件列有索引、事务尽量短、加锁顺序一致。并发量高时优先乐观锁或 Redis 预扣，不要把数据库行锁当万能锁。

## 六、软删除与唯一索引冲突

`gorm.DeletedAt` 会让查询自动追加 `deleted_at IS NULL`。但 `users.email` 若是普通唯一索引，软删除后这一行仍在表里，**同一邮箱无法重新注册**。

方案 A（推荐）：`deleted_at` 改为 `BIGINT NOT NULL DEFAULT 0`，与业务唯一键组成复合唯一索引：

执行前先把历史 `DATETIME` 值转换为毫秒时间戳（或新增 `deleted_ts` 列再切换），否则类型变更会截断已有数据：

```sql
ALTER TABLE users
  MODIFY deleted_at BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0未删除，其余为删除时间戳(ms)',
  DROP INDEX uk_users_email,
  ADD UNIQUE KEY uk_users_email_del (email, deleted_at);
```

模型改用 `gorm.io/plugin/soft_delete`，活跃行 `deleted_at=0`，删除时写入毫秒时间戳（同时从 `BaseModel` 移除 `gorm.DeletedAt`，避免同名列冲突）：

```go
import "gorm.io/plugin/soft_delete"

type User struct {
	ID        uint64                `gorm:"primaryKey"`
	Email     string                `gorm:"uniqueIndex:uk_users_email_del,priority:1"`
	DeletedAt soft_delete.DeletedAt `gorm:"softDelete:milli;uniqueIndex:uk_users_email_del,priority:2"`
}
```

方案 B：逻辑删除标记用主键填充（`deleted_at = id`），保证每条删除行唯一；方案 C：历史数据归档到 `users_archive`，活跃表只留未删除行。

**不要**天真地给 `gorm.DeletedAt` 加 `(email, deleted_at)` 复合唯一索引：MySQL 唯一索引把多个 `NULL` 视为互不相等，两条 `deleted_at IS NULL` 的活跃行仍能插入。恢复删除用 `db.Unscoped().Model(&u).Update("deleted_at", 0)`。

## 常见坑

1. **`defer tx.Rollback()` 无条件执行**：Commit 后 Rollback 返回 `sql.ErrTxDone`，日志里全是噪音；应按命名 `err` 判断。
2. **事务内调 Kitex/Kafka**：下游抖动把数据库连接和行锁一起拖死，故障从下游扩散到整条链路。
3. **手动事务 panic 未回滚**：没写 `defer rollback` 时，连接与锁会一直挂到超时。
4. **RR 下“读不到刚提交的数据”**：先快照读再判断，看到的是旧版本，误以为丢更新。
5. **乐观锁只看 `Error` 不看 `RowsAffected`**：冲突被当成成功，库存少扣。
6. **软删除 + 唯一索引**：删除后无法重建同邮箱用户，或复合索引含 `NULL` 根本不起作用。
7. **大事务批量更新**：一次改几十万行，binlog 膨胀、主从延迟、锁等待超时。
8. **在 goroutine 里复用 `tx`**：`*gorm.DB` 非并发安全，随机报错或串事务。

## 小结

- 优先 `db.Transaction`；手动事务用命名返回值 + `defer` 回滚
- 嵌套事务默认是 SavePoint 语义，清楚“内层失败是否要拖垮外层”
- 事务只包本地数据库操作，跨服务用 outbox + 异步补偿
- 冲突少用乐观锁并检查 `RowsAffected`，冲突多用悲观锁但必须短事务
- 软删除要配复合唯一索引或归档表，别让 `NULL` 骗了你
