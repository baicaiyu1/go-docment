# 03-版本演进与选型

> 一句话定位：理清 Hertz、hz、Kitex 的版本关系与升级路径，并用选型矩阵回答“什么时候该用这套栈、什么时候不该用”。

## 本篇目标

- 了解 Hertz 的演进主线与 0.10 系列的关键变化。
- 掌握 hz 与 Hertz 的版本匹配、Kitex 的版本节奏与升级步骤。
- 用四张矩阵完成 Web 框架、ORM、消息队列、注册中心的选型。
- 明确本套技术栈的边界，知道哪些场景应该换方案。

- 已读完 [Hertz 是什么与设计理念](../02-Hertz入门/01-Hertz是什么-架构与性能.md) 与 [Kitex 快速入门与 IDL](../12-微服务与Kitex/02-Kitex快速入门与IDL.md)。
- 了解 SemVer（主版本.次版本.修订号）与 Go Modules 的基本用法。

## 一、Hertz 版本演进

Hertz 遵循语义化版本：主版本号表示不兼容变更，次版本号表示向下兼容的新能力，修订号表示修复与小优化。版本与能力的对应是归纳，细节以 [GitHub Releases](https://github.com/cloudwego/hertz/releases) 为准。

| 阶段 | 代表能力 | 对使用者的影响 |
| --- | --- | --- |
| 0.1 ~ 0.3 | 核心路由、中间件、Context、绑定、hz 雏形 | 能写服务，但生态与治理能力有限 |
| 0.4 ~ 0.6 | 可观测性、TLS/HTTP2、客户端、适配器 | 开始可用于生产，仍需自建治理 |
| 0.7 ~ 0.9 | hz 注解与模板、治理扩展、性能与稳定性 | 代码生成与团队协作方式成熟 |
| 0.10 | SSE 独立包、HTTP Handler 适配、竞态检测、退出修复 | 长连接、标准库迁移与稳定性增强 |

### 0.10 变化要点

- **SSE 独立包**：新增 `protocol/sse`，支持 `SetLastEventID`、取消流，客户端按流式读取而不是超时。
- **HertzHandler**：`adaptor` 新增面向 `http.Handler` 的适配，标准库组件接入更顺。
- **请求竞态检测**：服务端增加请求竞态检测能力，帮助发现跨 goroutine 复用 Context 的问题。
- **退出与校验修复**：`Shutdown` 正确检查 `ExitWaitTimeout`；自定义 validator 优先于默认校验器。
- **平台收敛**：netpoll 与 sonic 仅在 Linux/Darwin 的 amd64/arm64 启用，其他平台自动回退。

本教程基线为 Hertz v0.10.6，属于 0.10 系列的修订版本，建议锁定具体补丁版本，不要只写 `@latest`。

## 二、hz 与 Hertz 的版本匹配

| Hertz | hz | 说明 |
| --- | --- | --- |
| v0.10.x | v0.9.x（基线 v0.9.8） | 0.10.0 发布时同步更新 hz 工具，新项目按此组合 |
| v0.9.x | v0.8.x ~ v0.9.x | 老项目升级前先看生成代码差异 |
| v0.8.x 及以下 | 对应年代版本 | 建议先升 Hertz 再升 hz |

实践建议：

- 用 Makefile 或 `tools.go` 固定 hz 版本，例如 `go install github.com/cloudwego/hertz/cmd/hz@v0.9.8`，避免“同事生成的代码与我不同”。
- thriftgo、protoc、protoc-gen-go 同样要锁版本；IDL 生成链路是团队一致性的源头。
- 升级 hz 后先在小项目跑 `hz update`，用 `git diff` 审查生成物再推广。

## 三、Kitex 版本演进简述

Kitex 同样遵循语义化版本，0.x 阶段迭代较快。演进主线可以概括为：

| 阶段 | 代表能力 | 对使用者的影响 |
| --- | --- | --- |
| 早期 0.x | Thrift RPC、代码生成、连接池 | 高性能 RPC 底座 |
| 中期 0.x | 泛化调用、Protobuf、服务治理、超时重试 | 微服务治理能力补齐 |
| 近期 0.x（v0.13+） | 流式、服务网格、可观测与多协议 | 与 Hertz、Nacos、OTel 组合更顺 |

本教程基线为 Kitex v0.13+。Kitex 与生成代码、`kitex-contrib` 扩展存在版本耦合，升级时要同时看 `go.mod`、IDL 生成器与注册中心适配库。

## 四、升级步骤

```bash
# 1. 改 go.mod（或直接 go get 指定版本）
go get github.com/cloudwego/hertz@v0.10.6
go get github.com/cloudwego/kitex@latest

# 2. 整理依赖
go mod tidy

# 3. 编译与静态检查
go build ./...
go vet ./...

# 4. 单测与集成测试
go test ./... -race
```

升级检查清单：

- [ ] 读 Release Notes，标出破坏性变更与弃用项。
- [ ] 对齐 hz/thriftgo/protoc 版本，重新生成并审查 diff。
- [ ] 编译、单测、`-race` 全绿。
- [ ] 跑核心链路回归与压测，对比 P99、内存、错误率。
- [ ] 灰度发布，保留回滚版本与数据库兼容方案。

## 五、技术选型矩阵

### 1. Web 框架：Hertz vs Gin vs FastHTTP

| 维度 | Hertz | Gin | FastHTTP |
| --- | --- | --- | --- |
| 网络模型 | Linux 默认 netpoll，事件循环 | `net/http`，goroutine-per-conn | goroutine-per-conn，零拷贝 |
| 路由/中间件 | 内置完整 | 内置完整 | 需第三方路由，中间件自组 |
| 生态 | CloudWeGo + hertz-contrib | 最大，教程与中间件最多 | 偏底层，库较少 |
| 可观测/治理 | 官方扩展齐全 | 社区方案多，需自行拼装 | 基本靠自己 |
| 适合场景 | 高并发微服务、网关、需要治理 | 通用业务、快速交付、团队熟悉 | 追求极致吞吐、能接受自建 |

### 2. ORM：GORM vs ent vs sqlx

| 维度 | GORM | ent | sqlx |
| --- | --- | --- | --- |
| 抽象层级 | 高，约定优于配置 | 高，Schema as Code | 低，贴近 SQL |
| 学习曲线 | 低 | 中 | 低（会 SQL 即可） |
| 复杂关系 | 够用，复杂查询需手写 | 强，图结构友好 | 手写 JOIN |
| 迁移 | `AutoMigrate` 方便但不可控 | 内置 Schema 迁移 | 自管 SQL 脚本 |
| 适合场景 | 业务 CRUD、快速迭代 | 关系复杂、强类型团队 | 复杂 SQL、性能敏感 |

### 3. 消息队列：Kafka vs RocketMQ vs RabbitMQ

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 模型 | 分区日志，拉模式 | 主题队列，支持事务/延迟 | AMQP，推模式 |
| 吞吐 | 最高 | 高 | 中 |
| 延迟消息 | 需自建 | 原生支持 | 插件支持 |
| 顺序 | 分区内有序 | 队列内有序 | 队列内有序 |
| 适合场景 | 日志、埋点、大数据管道 | 电商交易、事务消息 | 业务解耦、路由灵活 |

### 4. 注册中心：Nacos vs Consul vs Etcd

| 维度 | Nacos | Consul | Etcd |
| --- | --- | --- | --- |
| 核心能力 | 注册发现 + 配置中心 | 注册发现 + 健康检查 + KV | 强一致 KV |
| 语言生态 | Java/Go 都友好 | Go 生态好 | Kubernetes 底座 |
| 运维成本 | 中 | 中 | 低（但需自己封装发现） |
| 适合场景 | 国内微服务、配置一体 | 多语言、服务网格 | K8s、基础设施 |

## 六、什么场景不该用本套栈

- 团队完全基于 `net/http` 生态、没有性能瓶颈：Gin 更稳，迁移收益低。
- 单体小工具、Serverless、冷启动敏感：标准库或轻量框架更合适。
- 需要大量现成企业中间件与低学习成本：Gin 的生态更成熟。
- 强一致金融核心、复杂分布式事务：Outbox/Saga/TCC 只是入门，需专业中间件与审计。
- 没有 K8s、监控、日志与值班体系却强上微服务：先把单体与可观测做好。
- Windows 作为生产环境：Hertz 会回退标准库，性能优势不明显。
- 必须使用 HTTP/3/QUIC：先确认 Hertz 与网关的支持情况，再决定是否引入。
- 团队无力维护 Nacos、Kafka、Redis 集群：优先托管服务或简化架构。

## 使用建议

- 选型先看团队与运维能力，再看 benchmark；没有维护能力的“高性能”是负债。
- 锁定版本、锁定工具链、锁定升级流程，比追新更重要。
- 迁移与升级都按“编译 → 单测 → 回归 → 灰度 → 回滚预案”执行。

## 小结

- Hertz 0.10 的重点是 SSE、标准库适配、竞态检测与稳定性修复；生产应锁定补丁版本。
- hz 与 Hertz、Kitex 与生成器/扩展都存在版本耦合，升级要成组进行。
- 四张矩阵分别回答 Web、ORM、MQ、注册中心的取舍；边界比功能更重要。
- 学习路线从语言到实战再到迁移收尾，最终产出是一套可维护的工程方法。
