# 跨服务链路追踪与日志串联

> 一句话定位：让一次下单在 Hertz、Kitex、MySQL、Kafka 之间留下同一条 trace_id，慢在哪一跳一眼可见。

## 本篇目标

- 在 Hertz 与 Kitex 两侧统一接入 OpenTelemetry
- 理解 `traceparent` 的透传条件与 metainfo 的定位差异
- 用 metainfo 传递 uid / tenant_id 等业务上下文
- 让 hlog / klog 的每条日志都带 trace_id、span_id
- 设计采样策略，并用一条真实慢链路完成排查
- 建立结构化、脱敏、限长的日志规范

## 一、先分清两种上下文

| 上下文 | 载体 | 内容 | 谁消费 |
| --- | --- | --- | --- |
| 追踪上下文 | W3C `traceparent` / OTel SpanContext | trace_id、span_id、采样标记 | 链路系统、日志 |
| 业务上下文 | Kitex metainfo（TTHeader） | uid、tenant_id、灰度标签 | 业务代码、鉴权、路由 |

两者不能混：把 uid 塞进 trace 属性会污染链路维度；把 trace_id 当业务参数传给下游，也无法自动串联 span。

## 二、Hertz 侧接入

```go
import (
    "github.com/hertz-contrib/obs-opentelemetry/provider"
    hertztracing "github.com/hertz-contrib/obs-opentelemetry/tracing"
)

p := provider.NewOpenTelemetryProvider(
    provider.WithServiceName("hertz-gateway"),
    provider.WithExportEndpoint("otel-collector:4317"),
    provider.WithInsecure(),
)
defer p.Shutdown(context.Background())

tracer, cfg := hertztracing.NewServerTracer()
h := server.Default(tracer)
h.Use(hertztracing.ServerMiddleware(cfg))

cli, _ := client.NewClient()
cli.Use(hertztracing.ClientMiddleware())
```

`tracer` 是 server 选项，负责创建入口 span；`ServerMiddleware` 补充路由、状态码等属性。只加其中一个，链路会缺头或缺尾。

## 三、Kitex 侧接入

Kitex 用 Suite 一次性接入，服务端和客户端分开：

```go
import (
    "github.com/kitex-contrib/obs-opentelemetry/provider"
    kitextracing "github.com/kitex-contrib/obs-opentelemetry/tracing"
)

p := provider.NewOpenTelemetryProvider(
    provider.WithServiceName("user-service"),
    provider.WithExportEndpoint("otel-collector:4317"),
    provider.WithInsecure(),
)
defer p.Shutdown(context.Background())

svr := userservice.NewServer(
    new(UserServiceImpl),
    server.WithSuite(kitextracing.NewServerSuite()),
    // 其他选项...
)

cli, err := userservice.NewClient("user-service",
    client.WithSuite(kitextracing.NewClientSuite()),
    client.WithResolver(res),
)
```

同一个进程如果既是服务端又是客户端（如 order-service 调 product-service），两个 Suite 都要加。Kitex 的 Suite 会自动从 ctx 提取上游 span，并在调用下游时注入，**前提是传的是同一个 ctx**。

## 四、traceparent 如何跨进程

```text
浏览器/App
  │  traceparent: 00-<trace_id>-<span_id>-01
  ▼
Hertz 网关（提取，创建 server span）
  │  Kitex TTHeader 中透传 trace 信息
  ▼
order-service（提取，创建 server span）
  │  Kitex 调用
  ▼
product-service（提取，创建 server span）
```

三个必须同时成立的条件：

1. 两端都接了 OTel，且传播格式一致（默认 W3C）
2. 调用时传递请求 ctx，不能 `context.Background()`
3. 中间件顺序正确：追踪中间件在业务中间件之前

经过 Kafka 时框架不会自动透传，必须手动注入/提取：

```go
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/propagation"
    "github.com/segmentio/kafka-go"
)

// 生产端
carrier := propagation.MapCarrier{}
otel.GetTextMapPropagator().Inject(ctx, carrier)
msg := kafka.Message{
    Topic: "order.created",
    Value: payload,
    Headers: []kafka.Header{
        {Key: "traceparent", Value: []byte(carrier.Get("traceparent"))},
    },
}

// 消费端
ctx = otel.GetTextMapPropagator().Extract(context.Background(),
    propagation.MapCarrier{"traceparent": string(msg.Headers[0].Value)})
```

## 五、metainfo 传递业务上下文

metainfo 走 TTHeader，Kitex 默认传输协议即可透传：

```go
import "github.com/bytedance/gopkg/cloud/metainfo"

// 网关入口：从 JWT 解析后写入 ctx
ctx = metainfo.WithValue(ctx, "uid", "42")
ctx = metainfo.WithValue(ctx, "tenant_id", "t-01")
ctx = metainfo.WithValue(ctx, "gray", "v2")

// Kitex 服务端：直接读取
uid, ok := metainfo.GetValue(ctx, "uid")
```

注意：metainfo 是**透传，不是鉴权**。下游仍要校验 uid 是否合法，不能因为“上游传了”就信任。若切换到 PurePayload 等不携带 header 的协议，metainfo 会丢失，必须显式配置 meta handler（以官方文档为准）。

## 六、日志注入 trace_id / span_id

用 OTel 的 SpanContext 取 ID，不依赖框架私有字段：

```go
import "go.opentelemetry.io/otel/trace"

func TraceIDs(ctx context.Context) (string, string) {
    sc := trace.SpanContextFromContext(ctx)
    if !sc.IsValid() {
        return "", ""
    }
    return sc.TraceID().String(), sc.SpanID().String()
}

func logOrder(ctx context.Context, orderID string, uid int64) {
    tid, sid := TraceIDs(ctx)
    klog.CtxInfof(ctx, "order_created order_id=%s uid=%d trace_id=%s span_id=%s",
        orderID, uid, tid, sid)
}
```

Hertz 侧把 `klog` 换成 `hlog.CtxInfof`，同样传请求 ctx。网关的 AccessLog 里也加上 trace_id，客户端报障时用响应头里的 `X-Trace-ID` 就能直接定位。

## 七、采样策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| AlwaysSample | 全量 | 开发、低流量核心链路 |
| TraceIDRatioBased | 按比例 | 生产常态，1%~10% |
| ParentBased | 跟随上游 | 微服务下游，避免断链 |
| 尾部采样 | Collector 按错误/慢请求保留 | 既要低成本又不漏异常 |

```go
// import sdktrace "go.opentelemetry.io/otel/sdk/trace"
provider.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.05)))
```

推荐组合：网关 5% 头部采样 + Collector 尾部采样（错误全留、P99 慢请求全留）。**不要在中途服务单独提高采样率**，否则会出现“下游有 span、上游没有”的孤儿链路。

## 八、一次慢下单的排查示例

用户反馈下单 2s，网关日志只有一条 trace_id，打开 Jaeger 后看到：

| Span | 耗时 | 说明 |
| --- | --- | --- |
| `POST /api/v1/orders`（Hertz） | 1960ms | 入口 |
| `CreateOrder`（order-service） | 1900ms | 含下游 |
| `DeductStock`（product-service） | 1500ms | 异常点 |
| `SELECT stock ...`（MySQL） | 1420ms | 缺索引 |

结论：不是网络问题，是 `stock` 表按 `sku_id` 查询没走索引。加索引后该 span 降到 8ms，整条链路恢复到 120ms。

排查顺序固定为：**先看最深的慢 span，再看该 span 的属性（db.statement、peer.service），最后回到代码**。日志按 trace_id 聚合，能把同一请求的网关、订单、库存日志拼在一起。

## 九、日志规范

| 规范 | 做法 | 反例 |
| --- | --- | --- |
| 结构化 | 固定字段：trace_id、span_id、uid、order_id、cost_ms | 拼一整句自然语言 |
| 脱敏 | 手机号、身份证、token、密码统一打码 | 原样打印 JWT |
| 限长 | body 截断到 4KB | 打印整个商品详情 |
| 错误带原因 | `err=%v` + 业务码 | 只写“失败” |
| 不重复 | 入口记一次结果，中间层不重复刷 | 每层都打完整请求 |
| 采样 | 成功按比例，错误全量 | 1 万 QPS 每请求 3 条 Info |

日志字段名要全链路统一，否则 Loki/ES 里聚合不出来。禁止把整个 struct `%+v` 打进日志，既慢又容易泄露。

## 常见坑

1. **客户端用 `context.Background()` 调下游**：trace 断成两条，日志对不上。
2. **Kitex 只加了 ServerSuite 没加 ClientSuite**：服务端有 span，调下游那一段消失。
3. **metainfo 用了不携带 header 的协议**：uid 全空，灰度与鉴权失效。
4. **日志用 `hlog.Infof` 而不是 `CtxInfof`**：trace_id 永远是空的。
5. **两端采样率不一致**：上游采了、下游没采，链路缺段。
6. **Kafka 消费端没 extract**：异步链路全部变成新的孤立 trace。
7. **把 trace_id 当业务主键**：重建 trace 或重试后对不上，业务幂等应使用自己的幂等键。

## 小结

- trace 上下文用 W3C `traceparent`，业务上下文用 metainfo，两者职责不同
- Hertz 用 tracer + ServerMiddleware，Kitex 用 ServerSuite / ClientSuite
- 串联的前提是传请求 ctx、格式一致、两端都接入
- 日志从 SpanContext 取 trace_id / span_id，Hertz 用 hlog，Kitex 用 klog
- 采样用 ParentBased + 比例，异常链路交给尾部采样兜底

## 练习

1. 给 mall-lite 三个服务接入 OTel，验证 Jaeger 中是一条完整链路。
2. 在 Kafka 生产/消费两端手动注入 traceparent，验证异步链路可串联。
3. 用 metainfo 传递 tenant_id，在库存服务中按租户打印日志。
4. 人为给 `stock` 表去掉索引，按本文顺序定位慢 span。
