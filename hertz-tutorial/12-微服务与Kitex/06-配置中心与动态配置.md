# 配置中心与动态配置

> 一句话定位：把“改配置要重启”变成“发布一次、全量生效、可回滚”，同时守住敏感配置与启动顺序两条底线。

## 本篇目标

- 说清哪些配置该进配置中心、哪些不该
- 用 Nacos Config 完成启动加载与变更监听
- 设计可校验、有默认值、可热更新的配置结构体
- 接入 `kitex-contrib/config-nacos` 管理超时、重试、限流等治理策略
- 实现日志级别、限流阈值、灰度开关的热更新
- 建立密钥管理、发布回滚与启动顺序的规范

## 一、为什么需要配置中心

| 痛点 | 本地配置文件 | 配置中心 |
| --- | --- | --- |
| 改一个阈值 | 改文件 + 重启 + 发版 | 控制台发布，秒级生效 |
| 多实例一致 | 每台机器一份，容易漂移 | 统一 DataId，天然一致 |
| 审计与回滚 | 靠 Git，回滚要重新发布 | 历史版本一键回滚 |
| 密钥 | 容易进 Git | 可加密、可权限控制 |

边界：**代码逻辑、表结构、大体积静态资源不进配置中心**，只放“运行时可变、且变更后不需要重新编译”的参数。

## 二、Nacos Config 起步

```go
sc := []constant.ServerConfig{*constant.NewServerConfig("127.0.0.1", 8848)}
cc := constant.ClientConfig{
    NamespaceId: "mall-lite-prod", TimeoutMs: 5000,
    NotLoadCacheAtStart: true,
    LogDir: "./nacos/log", CacheDir: "./nacos/cache", LogLevel: "warn",
}
cfgCli, err := clients.NewConfigClient(
    vo.NacosClientParam{ClientConfig: &cc, ServerConfigs: sc},
)
```

```go
content, err := cfgCli.GetConfig(vo.ConfigParam{
    DataId: "user-service.yaml", Group: "mall-lite",
})

err = cfgCli.ListenConfig(vo.ConfigParam{
    DataId: "user-service.yaml", Group: "mall-lite",
    OnChange: func(namespace, group, dataId, data string) {
        if err := holder.Reload([]byte(data)); err != nil {
            klog.Errorf("reload %s failed: %v", dataId, err)
        }
    },
})
```

Windows 下 `LogDir` / `CacheDir` 不要写 `/tmp`，用 `./nacos/log` 或 `D:\logs\nacos`。

## 三、配置结构体、默认值与校验

```go
type Config struct {
    Server    Server    `yaml:"server"`
    DB        DB        `yaml:"db"`
    Redis     Redis     `yaml:"redis"`
    Log       Log       `yaml:"log"`
    RateLimit RateLimit `yaml:"rate_limit"`
    Canary    Canary    `yaml:"canary"`
}

type RateLimit struct {
    GatewayQPS int `yaml:"gateway_qps"`
    OrderQPS   int `yaml:"order_qps"`
}

func (c *Config) Validate() error {
    if c.Server.Addr == "" {
        return errors.New("server.addr is required")
    }
    if c.DB.DSN == "" {
        return errors.New("db.dsn is required")
    }
    if c.RateLimit.GatewayQPS < 0 {
        return errors.New("rate_limit.gateway_qps must be >= 0")
    }
    return nil
}
```

规则：**必填项启动校验失败直接退出；可选项给默认值**。不要用零值表达“没配置”——`0` 到底是关掉限流还是忘了配，事后没人说得清。

## 四、热更新的安全姿势

不要在回调里直接改全局变量，用 `atomic.Pointer` 整份替换：

```go
type Holder struct{ p atomic.Pointer[Config] }

func (h *Holder) Get() *Config { return h.p.Load() }

func (h *Holder) Reload(b []byte) error {
    next := &Config{}
    if err := yaml.Unmarshal(b, next); err != nil {
        return err
    }
    if err := next.Validate(); err != nil {
        return err
    }
    h.p.Store(next) // 指针替换，读侧无锁
    return nil
}
```

业务侧每次用到配置时 `cfg := holder.Get()`，读到的始终是同一份快照。

| 配置 | 能否热更新 | 说明 |
| --- | --- | --- |
| 日志级别 | 能 | `hlog.SetLevel` |
| 限流阈值 | 能 | 原子变量 / 限流器 Reload |
| 业务开关 | 能 | `atomic.Bool` |
| 连接池大小 | 视实现 | 多数需要重建连接池 |

## 五、kitex-contrib/config-nacos 治理配置

业务配置之外，Kitex 的**治理策略**（超时、重试、限流、熔断）也交给 Nacos：

```go
nacosClient, err := nacos.NewClient(nacos.Options{
    Address: "127.0.0.1", Port: 8848,
    NamespaceID: "mall-lite-prod", Group: "mall-lite",
})
if err != nil {
    klog.Fatal(err)
}

svr := userservice.NewServer(
    new(UserServiceImpl),
    server.WithServerBasicInfo(&rpcinfo.EndpointBasicInfo{ServiceName: "user-service"}),
    server.WithSuite(nacosserver.NewSuite("user-service", nacosClient)),
)
```

客户端用 `config-nacos/client.NewSuite(serverName, clientName, nacosClient, configLog)`，`configLog` 用于自定义回调（示例示意，类型以 README 为准）。

| 侧 | 默认 DataId 格式 | 示例 |
| --- | --- | --- |
| 服务端 | `{{.ServerServiceName}}.{{.Category}}` | `user-service.rpc_timeout` |
| 客户端 | `{{.ClientServiceName}}.{{.ServerServiceName}}.{{.Category}}` | `hertz-gateway.user-service.retry` |

```json
// user-service.rpc_timeout
{
  "*": { "conn_timeout_ms": 100, "rpc_timeout_ms": 3000 },
  "GetUser": { "conn_timeout_ms": 50, "rpc_timeout_ms": 300 }
}
```

治理配置只影响框架行为，**不替代业务配置**；两类 DataId 分开管理，避免一次发布同时改业务与治理。

## 六、Hertz 侧配置加载

Hertz 没有内置配置中心绑定，采用“启动时拉取 + 监听热更新 + 注入 server 选项”：

```go
func main() {
    cfg, err := loadRemote("hertz-gateway.yaml") // 内部走 Nacos GetConfig
    if err != nil {
        log.Fatal(err)
    }
    h := server.Default(
        server.WithHostPorts(cfg.Server.Addr),
        server.WithReadTimeout(cfg.Server.ReadTimeout),
    )
    h.Use(rateLimitMW(cfgHolder))
    h.Spin()
}
```

热更新只影响中间件读取的快照；`WithHostPorts` 这类启动参数变了必须重启，因此在配置里标注 `requires_restart: true`。

## 七、灰度开关设计

三种粒度：全局开关（紧急止血）、比例灰度（按 `hash(uid) % 100 < percent`）、白名单（内部账号先验证）。

```go
func inCanary(cfg *Config, uid int64) bool {
    for _, id := range cfg.Canary.UIDs {
        if id == uid {
            return true
        }
    }
    return int(uid%100) < cfg.Canary.Percent
}
```

开关必须**可快速关闭**，默认值永远是“旧逻辑”；上线前先验证开关能生效，再放量。

## 八、敏感配置与密钥

| 方式 | 适用 | 注意 |
| --- | --- | --- |
| K8s Secret + 环境变量 | 数据库密码、JWT 密钥 | 镜像不落盘，日志不打印 |
| Nacos 加密配置 | 中小团队 | 依赖加密插件与密钥管理 |

三条底线：配置中心权限按环境隔离；日志打印配置时统一脱敏；密钥轮换要有流程，不能靠改代码。

## 九、发布流程、回滚与启动顺序

```text
修改配置 → CI 校验（YAML 解析 + Validate）→ 灰度 Group/实例 → 观察指标
        → 全量发布 → 记录变更单（谁、何时、改了什么）
```

回滚：Nacos 控制台选择历史版本一键回滚；回滚后确认监听回调已刷新，而不是只看控制台显示。

启动顺序固定为：**拉取配置 → 初始化日志 → 连接 MySQL → 连接 Redis → 注册中心 → 启动服务**。

配置中心不可用时的策略要明确：核心配置缺失 → 启动失败（fail fast）；非核心配置 → 读本地快照兜底并告警。最忌讳“静默使用零值配置”把服务带进生产。

## 常见坑

1. **DataId / Group 写错**：`GetConfig` 返回空字符串，服务用零值启动。
2. **监听回调里直接写全局变量**：并发读写导致 data race，配置“偶尔不生效”。
3. **配置中心挂了服务就起不来**：没做本地快照与降级策略。
4. **热更新了连接池大小**：代码只在启动时读一次，改了等于没改。
5. **密钥进 Git 或明文放 Nacos**：一次仓库泄露全线失守。
6. **重复注册监听**：每次请求都 `ListenConfig`，goroutine 与连接持续增长。

## 小结

- 配置中心解决“运行时可变参数”的分发、审计与回滚，不是代码仓库
- Nacos Config = `GetConfig` + `ListenConfig`，配合 `atomic.Pointer` 做无锁热更新
- 必填项启动校验，可选项给默认值，禁止用零值表达“未配置”
- 密钥走 Secret/KMS，发布先灰度，回滚要验证监听已生效
