# 17-正向代理与反向代理
> 客户端出网走正向代理，服务入口做反向代理：Hertz 内置前者，后者交给 hertz-contrib/reverseproxy。

## 本篇目标

- 用 Hertz Client 的 `SetProxy` 访问 HTTP/HTTPS 正向代理。
- 理解 HTTP CONNECT 隧道的原理与 Hertz 在服务端实现它的边界。
- 用 `hertz-contrib/reverseproxy` 搭建反向代理，定制请求与响应。
- 掌握 `X-Forwarded-For` 的正确处理与信任边界。
- 知道 WebSocket 代理、超时与重试的注意事项。

## 前置知识

- 理解正向代理与反向代理的区别：前者代表客户端，后者代表服务端。
- 了解 HTTP 代理的两种形式：普通请求转发与 `CONNECT` 隧道。
- 已读 03-基本特性/11，能创建并配置 Hertz Client。

## 1. 正向代理：客户端侧

Hertz Client 内置正向代理能力，API 在 `protocol` 包：

```go
// Proxy 根据请求决定代理 URI
type Proxy func(*protocol.Request) (*protocol.URI, error)

// 固定代理地址
func ProxyURI(fixedURI *protocol.URI) Proxy

// 为 Client 设置代理
func (c *Client) SetProxy(p protocol.Proxy)
```

### 1.1 HTTP 代理

```go
proxyURI := protocol.ParseURI("http://user:pass@127.0.0.1:3128")

c, err := client.NewClient(
	client.WithDialer(standard.NewDialer()), // HTTPS 目标或需要 TLS 时必须
)
if err != nil {
	log.Fatal(err)
}
c.SetProxy(protocol.ProxyURI(proxyURI))

status, body, err := c.Get(context.Background(), nil, "http://example.com/")
log.Printf("status=%d body=%s err=%v", status, body, err)
```

代理地址支持 `http://user:password@host:port` 形式，Hertz 会自动生成 `Proxy-Authorization`。

### 1.2 HTTPS 与证书

访问 HTTPS 目标时，先走 `CONNECT` 建立隧道，再在隧道内做 TLS 握手。Hertz Client 需要：

```go
c, err := client.NewClient(
	client.WithTLSConfig(&tls.Config{InsecureSkipVerify: true}), // 仅演示，生产禁止
	client.WithDialer(standard.NewDialer()),                     // netpoll 不支持 TLS
)
```

如果代理本身是 HTTPS（`https://proxy:443`），同样需要标准库拨号器与正确的 TLS 配置。

### 1.3 服务端实现 CONNECT 的边界

`CONNECT` 的语义是：客户端请求代理建立到 `host:port` 的 TCP 隧道，之后双方只转发字节流。实现它需要**接管底层连接**（Hijack），把 HTTP 解析器让位给裸 TCP。

Hertz 路由可以注册 CONNECT 方法：

```go
h.Handle(consts.MethodConnect, "/", func(ctx context.Context, c *app.RequestContext) {
	// 这里需要自行完成：解析 target、Dial、双向 io.Copy、关闭连接
	// 核心库没有 net/http 那样现成的 http.Hijacker 抽象
})
```

但 Hertz 核心并未提供类似 `http.Hijacker` 的开箱即用能力，自己实现要处理连接生命周期、半关闭、超时与并发。生产环境的正向代理建议直接使用 Nginx、Squid、Envoy 等成熟组件；Hertz 更适合做**反向代理**或代理的管控面。若确有需求，可参考 `hertz-contrib/reverseproxy` 的 WebSocket 实现来理解连接接管方式，具体以官方文档与源码为准。

## 2. 反向代理：hertz-contrib/reverseproxy

Hertz 核心不内置反向代理，官方扩展是 `github.com/hertz-contrib/reverseproxy`：

```bash
go get github.com/hertz-contrib/reverseproxy
```

核心构造函数：

```go
func NewSingleHostReverseProxy(target string, opts ...config.Option) (*reverseProxy, error)
```

它提供 `ServeHTTP(ctx, c)` 方法，可直接注册为 Hertz Handler，也可在中间件里调用。

### 2.1 最小示例

```go
h := server.Default(server.WithHostPorts(":8080"))

proxy, err := reverseproxy.NewSingleHostReverseProxy("http://127.0.0.1:9000")
if err != nil {
	panic(err)
}

// 所有方法、/api 前缀的请求统一转发到后端
h.Any("/api/*any", proxy.ServeHTTP)
h.Spin()
```

> `NewSingleHostReverseProxy` **不会重写 Host 请求头**。很多后端按 Host 做虚拟主机路由，需要自定义 Director 显式设置。

### 2.2 定制请求：Director

```go
proxy.SetDirector(func(req *protocol.Request) {
	// 改写目标 Host（保留原始路径）
	req.Header.SetHost("backend.internal")
	// 追加统一的内部标记
	req.Header.Set("X-Proxy-By", "hertz-gateway")
})
```

Director 在转发前执行，只能访问 `*protocol.Request`，拿不到 `app.RequestContext`。需要在 Director 里使用的数据，应在前置中间件写入 Header。

### 2.3 定制响应与错误处理

```go
proxy.SetModifyResponse(func(resp *protocol.Response) error {
	resp.Header.Set("X-Cache", "miss")
	return nil
})

proxy.SetErrorHandler(func(c *app.RequestContext, err error) {
	c.JSON(502, utils.H{"error": "bad gateway"})
})
```

注意：反向代理会**重置响应头**，在调用 `proxy.ServeHTTP` 之前给 `c.Response` 设置的 Header 可能被覆盖，应放在 `SetModifyResponse` 里。

### 2.4 共享 Client、超时与重试

`NewSingleHostReverseProxy` 未传 Client 配置时会使用默认全局 Client。生产中建议显式注入一个配置好的 Hertz Client：

```go
cli, err := client.NewClient(
	client.WithDialer(standard.NewDialer()), // 后端为 HTTPS 时必须
	client.WithDialTimeout(500*time.Millisecond),
	client.WithClientReadTimeout(3*time.Second),
	client.WithMaxConnsPerHost(512),
	client.WithRetryConfig(retry.WithMaxAttemptTimes(2)),
)
if err != nil {
	panic(err)
}

proxy, err := reverseproxy.NewSingleHostReverseProxy("https://backend.internal")
if err != nil {
	panic(err)
}
proxy.SetClient(cli)
```

重试只应覆盖幂等方法；对 POST 转发开启重试前，确认后端支持幂等键。

## 3. X-Forwarded-For 与信任边界

代理必须把真实客户端 IP 传给后端，但 `X-Forwarded-For` 可以被客户端伪造。推荐做法：

```go
h.Use(func(ctx context.Context, c *app.RequestContext) {
	ip := c.ClientIP()
	if prior := c.Request.Header.Get("X-Forwarded-For"); prior != "" {
		// 只有确认来源是可信代理时才追加
		c.Request.Header.Set("X-Forwarded-For", prior+", "+ip)
	} else {
		c.Request.Header.Set("X-Forwarded-For", ip)
	}
	c.Request.Header.Set("X-Real-IP", ip)
	c.Next(ctx)
})
```

信任原则：

- 在边缘网关**覆盖**而不是追加客户端传来的 XFF；
- 内层代理只信任来自已知代理网段的 XFF；
- 后端取"最右侧的可信 IP"，不要直接取第一个；
- `c.ClientIP()` 的解析规则可通过 `c.SetClientIPFunc` 定制，默认逻辑要结合部署拓扑确认。

## 4. 负载均衡雏形

`NewSingleHostReverseProxy` 面向单个目标。多实例时可以复用多个 proxy 的 Handler 做轮询：

```go
targets := []string{"http://10.0.0.1:9000", "http://10.0.0.2:9000", "http://10.0.0.3:9000"}
var handlers []app.HandlerFunc
for _, t := range targets {
	p, _ := reverseproxy.NewSingleHostReverseProxy(t) // 错误处理略
	handlers = append(handlers, p.ServeHTTP)
}

var counter uint64
h.GET("/api/*any", func(ctx context.Context, c *app.RequestContext) {
	i := atomic.AddUint64(&counter, 1) % uint64(len(handlers))
	handlers[i](ctx, c)
})
```

这只是最小轮询，没有健康检查、权重、一致性哈希。生产环境应结合服务发现扩展（discovery）与专门网关，避免在业务进程里手写负载均衡。

## 5. WebSocket 代理

WebSocket 需要 Upgrade 与连接接管，普通反向代理不适用。`reverseproxy` 提供了专用入口：

```go
h.GET("/ws", reverseproxy.NewWSReverseProxy("ws://backend:9000").ServeHTTP)
```

可配置项包括 `WithDirector`、`WithDialer`、`WithUpgrader`（默认使用 Hertz 的 WebSocket upgrader）。

## 常见坑

1. **Host 头没改**：`NewSingleHostReverseProxy` 不重写 Host，后端虚拟主机匹配失败；在 Director 里 `req.Header.SetHost(...)`。
2. **在代理前设置响应头**：代理会重置响应头，必须用 `SetModifyResponse`。
3. **HTTPS 后端没切标准库**：netpoll 不支持 TLS，需给 Client 配 `standard.NewDialer()`。
4. **用普通反向代理转发 WebSocket**：Upgrade 失败，必须用 `NewWSReverseProxy`。
5. **无条件信任 XFF**：客户端可伪造，边缘必须覆盖，内层只信任可信代理网段。
6. **代理指向自己形成环路**：target 与当前服务同地址会无限递归，直到耗尽连接。

## 小结

- Hertz Client 通过 `SetProxy(protocol.ProxyURI(uri))` 支持正向代理，HTTPS 需标准库拨号器。
- HTTP CONNECT 需要接管底层 TCP，Hertz 核心不提供开箱能力，生产正代理由专用组件承担。
- 反向代理用 `hertz-contrib/reverseproxy`，通过 Director / ModifyResponse / ErrorHandler 定制。
- XFF 必须配合信任边界；WebSocket 用 `NewWSReverseProxy`，负载均衡只是雏形，生产应依赖网关与服务发现。
