# 14-适配器与标准库互操作
> 用 `adaptor.HertzHandler` 把 net/http 生态搬进 Hertz，也看清兼容层背后的性能代价与边界。

## 本篇目标

- 理解 Hertz 与 `net/http` 两套模型的差异，知道适配的方向性。
- 用 `adaptor.HertzHandler` 接入 `http.Handler`、静态文件、pprof、Prometheus。
- 了解 `GetCompatRequest` / `GetCompatResponseWriter` 的用途与弃用状态。
- 明确 Hertz 的 `ServeHTTP` 为什么不能直接当 `http.Handler` 用。
- 能评估适配层的性能损耗并决定是否放在热路径。

## 前置知识

- 熟悉 `net/http` 的 `http.Handler`、`http.ResponseWriter`、`http.Request`。
- 了解 Hertz 的 `app.HandlerFunc` 签名：`func(context.Context, *app.RequestContext)`。
- 已读 03-基本特性/04，知道 `c.Response` 与 `c.GetResponse()` 的区别。

## 1. 两套模型的核心差异

| 维度 | net/http | Hertz |
| --- | --- | --- |
| Handler 签名 | `func(http.ResponseWriter, *http.Request)` | `func(context.Context, *app.RequestContext)` |
| 请求对象 | `*http.Request` | `c.Request`（`protocol.Request`） |
| 响应写入 | `http.ResponseWriter` | `c.Response` / `c.Write` / `c.JSON` |
| Body | `io.ReadCloser` | 字节或流，`c.Request.Body()` |
| 复用 | 每请求分配 | Context / Request / Response 池化 |

两套模型没有继承关系，所谓"适配"本质是**做一次对象转换与数据拷贝**。因此：

- Hertz Handler 调 net/http Handler：用 `adaptor.HertzHandler`；
- net/http 调 Hertz Handler：核心库没有官方反向适配，需要社区组件或自行封装（以官方文档为准）。

特别注意：Hertz 的 `Engine.ServeHTTP(ctx context.Context, c *app.RequestContext)` **不是** `http.Handler` 的 `ServeHTTP(w, r)`，不能直接注册到 `http.Server`。

## 2. 推荐方式：adaptor.HertzHandler

`github.com/cloudwego/hertz/pkg/common/adaptor` 提供了当前推荐的适配入口：

```go
func HertzHandler(h http.Handler) app.HandlerFunc
```

它会把 Hertz 请求转换成 `*http.Request`，把 `http.ResponseWriter` 的写入同步到 Hertz 响应，从而让标准库 Handler 直接跑在 Hertz 路由上。

### 2.1 接入普通 http.Handler

```go
package main

import (
	"net/http"

	"github.com/cloudwego/hertz/pkg/app/server"
	"github.com/cloudwego/hertz/pkg/common/adaptor"
)

func main() {
	h := server.Default(server.WithHostPorts(":8080"))

	hello := http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("X-From", "net/http")
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("hello from http.Handler"))
	})

	// 关键：把 http.Handler 转成 Hertz Handler
	h.GET("/hello", adaptor.HertzHandler(hello))
	h.Spin()
}
```

### 2.2 静态文件与 embed.FS

标准库 `http.FileServer` 可以直接复用：

```go
import (
	"embed"
	"net/http"

	"github.com/cloudwego/hertz/pkg/common/adaptor"
)

//go:embed static/*
var staticFiles embed.FS

func registerStatic(h *server.Hertz) {
	fs := http.FileServer(http.FS(staticFiles))
	// StripPrefix 去掉路由前缀，FileServer 才能找到正确路径
	h.GET("/static/*filepath", adaptor.HertzHandler(http.StripPrefix("/static/", fs)))
	h.HEAD("/static/*filepath", adaptor.HertzHandler(http.StripPrefix("/static/", fs)))
}
```

### 2.3 接入 pprof

pprof 的处理器本质是 `http.Handler`，导入副作用包后可以直接挂 `http.DefaultServeMux`：

```go
import (
	"net/http"
	_ "net/http/pprof" // 注册 /debug/pprof/* 到 DefaultServeMux

	"github.com/cloudwego/hertz/pkg/common/adaptor"
)

func registerPprof(h *server.Hertz) {
	h.GET("/debug/pprof/*any", adaptor.HertzHandler(http.DefaultServeMux))
}
```

生产环境务必给 pprof 加鉴权或只监听内网端口，不要裸奔在公网。

### 2.4 接入 Prometheus

```go
import (
	"github.com/prometheus/client_golang/prometheus/promhttp"
	"github.com/cloudwego/hertz/pkg/common/adaptor"
)

func registerMetrics(h *server.Hertz) {
	h.GET("/metrics", adaptor.HertzHandler(promhttp.Handler()))
}
```

`promhttp.Handler()` 返回的是 `http.Handler`，适配后即可被 Hertz 提供。Hertz 也有官方 Prometheus 扩展（`hertz-contrib/monitor-prometheus`），业务指标更推荐用它直接采集中间件数据。

## 3. 更底层的兼容 API（已弃用）

`adaptor` 还提供两个更细粒度的函数：

```go
// 从 Hertz 请求构造 *http.Request
func GetCompatRequest(req *protocol.Request) (*http.Request, error)

// 从 Hertz 响应构造 http.ResponseWriter
func GetCompatResponseWriter(resp *protocol.Response) http.ResponseWriter
```

用法：

```go
h.GET("/legacy", func(ctx context.Context, c *app.RequestContext) {
	req, err := adaptor.GetCompatRequest(&c.Request)
	if err != nil {
		c.String(400, "bad request")
		return
	}

	// 注意：必须传 &c.Response，不能传 c.GetResponse()（那是拷贝）
	rw := adaptor.GetCompatResponseWriter(&c.Response)
	legacyHandler(rw, req)
})
```

两者在官方文档中已标记为**弃用**，新代码应优先 `HertzHandler`。仅在需要拿到 `*http.Request` 做额外处理（如签名校验）时才考虑使用，并注意未来版本可能移除。

另一个实用函数是 `CopyToHertzRequest`：

```go
func CopyToHertzRequest(req *http.Request, hreq *protocol.Request) error
```

它把标准库请求的 URI、Host、Method、Protocol、Header 复制到 Hertz 请求，Body 以共享 Reader 的方式适配。适合"从 net/http 侧拿到请求，再交给 Hertz 处理"的场景。

## 4. 性能损耗在哪里

适配层不是零成本的：

- 需要构造 `*http.Request`，复制 Header、URL、Body 包装；
- `http.ResponseWriter` 的每次 `Write` 要同步到 Hertz 响应，可能触发额外拷贝；
- 无法完全复用 Hertz 的 Context 池化优势；
- 对 `Hijack`、`Flusher` 等接口的支持受适配实现限制。

因此建议：

- **热路径用原生 Hertz**，适配层只用于运维端点（pprof/metrics）、静态文件、第三方标准库组件；
- 不要在 QPS 核心接口上套一层 `http.Handler`；
- 压测时对比适配前后 P99，确认损耗可接受。

## 5. Hertz 反向挂到 net/http

有时需要把 Hertz 路由暴露给已有的 `http.Server`（例如与老系统共进程）。核心库没有提供 `http.Handler` 适配，原因是 `ServeHTTP` 签名不同且 Context 需要网络连接等状态。可选做法：

- 使用社区维护的适配器（如 `hertz-contrib/adapters`，具体包名与用法以仓库文档为准）；
- 或者保留两个独立端口，用网关统一入口，避免进程内互调。

不要尝试用 `http.HandlerFunc(h.Engine.ServeHTTP)` 强行转换，签名不匹配，编译就过不了。

## 常见坑

1. **把 `c.GetResponse()` 传给 `GetCompatResponseWriter`**：拿到的是响应拷贝，写入不会回传给客户端；必须用 `&c.Response`。
2. **在适配的 Handler 里改了 Header 却调用 `WriteHeader` 前没写 body**：某些实现要等 `Write` 才把 Header 刷到 Hertz 响应，改完 Header 记得写数据。
3. **继续使用已弃用的 `GetCompatRequest`**：未来版本可能移除，且性能不如 `HertzHandler`，新代码不要用。
4. **用 `adaptor.HertzHandler` 包裹整个业务路由**：热路径性能下降，且部分 Hertz 特性（如原生 Context 操作）不可用。
5. **忘记 `http.StripPrefix`**：`FileServer` 收到的路径带 `/static/` 前缀，导致 404。
6. **pprof / metrics 暴露公网**：信息泄露风险，必须加鉴权或只绑定内网地址。
7. **认为 Hertz Engine 实现了 `http.Handler`**：签名是 `(context.Context, *app.RequestContext)`，不能直接挂 `http.Server`。

## 小结

- 适配方向主要是 net/http → Hertz，核心入口是 `adaptor.HertzHandler`。
- 静态文件、pprof、Prometheus 等标准库生态可以低成本复用。
- `GetCompatRequest` / `GetCompatResponseWriter` 已弃用，只作了解。
- 适配有明确的性能代价，应限制在运维端点与非热路径。
- Hertz 反向作为 `http.Handler` 需要社区适配器，核心库不支持。

## 练习

1. 用 `adaptor.HertzHandler` 把一个标准库 `http.HandlerFunc` 挂到 `/hello`，并用 curl 验证响应头与 body。
2. 用 `embed.FS` + `http.FileServer` 提供静态目录，正确处理 `/static/` 前缀。
3. 挂载 pprof 与 Prometheus 端点，并给它们加一个简单的 Token 鉴权中间件。
4. 用 `GetCompatRequest` + `GetCompatResponseWriter` 实现同样的 `/legacy` 接口，对比与 `HertzHandler` 的代码差异。
5. 对同一接口分别用原生 Hertz 和 `HertzHandler` 压测，记录 QPS 与 P99 差异。
