# 优雅退出

> 一句话定位：优雅退出的目标是“停止接收新请求、等在途请求处理完、释放资源、再退出进程”，Hertz 用 `Spin` + 信号 + `WithExitWaitTime` + `OnShutdown` 钩子完成这套流程。

- 知道需要自己掌控生命周期时，如何用 `Run` + `Shutdown` 替代 `Spin`。

## 为什么需要优雅退出

进程收到终止信号时，如果直接 `os.Exit`：

- 正在处理的请求会被切断，客户端收到连接重置。
- 数据库事务可能只提交了一半。
- 日志、Trace 缓冲区里的数据丢失。
- 注册中心还没摘除实例，流量仍可能打进来。

优雅退出要同时解决三件事：

1. **停止接收新连接/新请求**。
2. **给在途请求留出完成时间**。
3. **按正确顺序释放资源**。

## Hertz 的信号处理

从 v0.9.6 起：

- 收到 `SIGTERM`、`SIGHUP`、`SIGINT` 都触发优雅退出。
- v0.9.6 之前，`SIGTERM` 会立即退出，只有 `SIGHUP` / `SIGINT` 才优雅退出。

所以在旧版本上，Kubernetes 发 `SIGTERM` 时进程会直接退出，这是升级时要特别注意的差异。

特殊需求可用 `h.SetCustomSignalWaiter` 覆盖默认实现：返回 `nil` 优雅退出，返回 `error` 立即退出，一般不要改。

## Spin 的退出流程

`h.Spin()` 大致执行以下步骤：

1. 把 Engine 状态置为 `closed`，不再接受新连接。
2. 非阻塞触发所有 `OnShutdown` 回调，并等待它们完成或超时。
3. 从注册中心注销当前实例。
4. 关闭网络库的信号监听。
5. 对关闭过程中的请求统一加上 `Connection: Close`。
6. 等待业务协程退出：
   - Netpoll：每 1 秒检查一次 active conn 是否为 0（该 1 秒 ticker 目前不可配置）。
   - Go 原生网络库：关闭监听，不再等待连接。
   - 总等待时间由 `ExitWaitTime` 控制，默认 5 秒。

超过 `ExitWaitTime` 仍未退出，进程会强制结束。因此它必须小于 Kubernetes 的 `terminationGracePeriodSeconds`。

```go
h := server.Default(
	server.WithHostPorts("0.0.0.0:8080"),
	server.WithExitWaitTime(10*time.Second),
)
```

## 注册 Shutdown 钩子

`Engine.OnShutdown` 的类型是 `[]func(context.Context)`，可以追加多个：

```go
h.Engine.OnShutdown = append(h.Engine.OnShutdown, func(ctx context.Context) {
	hlog.Info("flush trace buffer")
	// tracer.Flush(ctx)
})

h.Engine.OnShutdown = append(h.Engine.OnShutdown, func(ctx context.Context) {
	hlog.Info("close database")
	// db.Close()
})
```

注意：

- 所有钩子是**并发、非阻塞触发**的，顺序没有保证。
- 每个钩子都应尊重 `ctx` 的超时，不能无限阻塞。
- 需要严格顺序的资源释放，放在同一个钩子里按顺序写。
- 钩子执行时在途请求可能还在处理，数据库等资源应最后关闭。

## 资源释放顺序

推荐顺序：

```text
停止接收新请求
  → 等待在途请求完成
  → 刷新日志 / Trace
  → 关闭消息生产者、缓存、数据库
  → 注销服务发现（Hertz 内部已处理）
  → 进程退出
```

如果顺序反了，例如先关数据库，在途请求会大量报错，客户端收到 500。

## 完整示例

```go
package main

import (
	"context"
	"time"

	"github.com/cloudwego/hertz/pkg/app"
	"github.com/cloudwego/hertz/pkg/app/server"
	"github.com/cloudwego/hertz/pkg/common/hlog"
	"github.com/cloudwego/hertz/pkg/common/utils"
	"github.com/cloudwego/hertz/pkg/protocol/consts"
)

func main() {
	h := server.Default(
		server.WithHostPorts("0.0.0.0:8080"),
		server.WithExitWaitTime(10*time.Second),
	)

	h.Engine.OnShutdown = append(h.Engine.OnShutdown, func(ctx context.Context) {
		hlog.Info("[shutdown] close database")
		// 在这里 flush 日志、关闭 db、redis 等
	})

	h.GET("/slow", func(ctx context.Context, c *app.RequestContext) {
		select {
		case <-time.After(3 * time.Second):
			c.JSON(consts.StatusOK, utils.H{"ok": true})
		case <-ctx.Done():
			c.AbortWithStatusJSON(consts.StatusServiceUnavailable, utils.H{"code": 503})
		}
	})

	h.Spin()
}
```

验证步骤：

1. 启动服务。
2. 在另一个终端发起 `/slow` 请求。
3. 在服务终端按 `Ctrl+C`，观察日志：应先看到 `[shutdown]` 钩子，再看到在途请求完成，最后进程退出。

Windows PowerShell：

```powershell
go run .
# 另开一个窗口
curl.exe -i http://127.0.0.1:8080/slow
# 回到服务窗口按 Ctrl+C
```

Linux / macOS bash：

```bash
go run .
# 另开一个终端
curl -i http://127.0.0.1:8080/slow
# 回到服务终端按 Ctrl+C，或执行：
kill -TERM <服务PID>
```

## 手动控制：Run + Shutdown

需要自己接管信号、或在测试中控制生命周期时，用 `Run` + `Shutdown`：

```go
go func() {
	if err := h.Run(); err != nil {
		hlog.Errorf("server run: %v", err)
	}
}()

quit := make(chan os.Signal, 1)
signal.Notify(quit, syscall.SIGINT, syscall.SIGTERM)
<-quit

ctx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
if err := h.Shutdown(ctx); err != nil {
	hlog.Errorf("shutdown: %v", err)
}
```

注意不要同时使用 `Spin()` 和这套逻辑，否则两个信号消费者会重复调用 `Shutdown`。

## Kubernetes 配合

Kubernetes 删除 Pod 时的顺序：

1. Pod 进入 `Terminating`，从 Service Endpoints 中摘除。
2. 执行 `preStop` 钩子。
3. 向容器主进程发送 `SIGTERM`。
4. 等待 `terminationGracePeriodSeconds`。
5. 仍未退出则发送 `SIGKILL`。

推荐配置：

```yaml
spec:
  terminationGracePeriodSeconds: 30 # > preStop 5s + ExitWaitTime 10s + 缓冲
  containers:
    - name: user-service
      image: registry.example.com/user-service:v1.0.0
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 5"]
```

`preStop` 的 `sleep` 用于等待 Endpoints 摘除与负载均衡停止转发，避免新请求打进正在退出的实例。

## 常见坑

1. **用 `h.Run()` 却期待优雅退出**：`Run` 不处理信号，终止时直接中断。生产服务用 `Spin` 或自己实现 `Run + Shutdown`。
2. **`ExitWaitTime` 大于 K8s 宽限期**：还没等完就被 `SIGKILL`，优雅退出形同虚设。
3. **忘记 `preStop`**：Endpoints 摘除有延迟，退出瞬间仍有流量打进来。
4. **Shutdown 钩子里阻塞**：例如等待一个永远不会返回的连接，拖垮整个退出流程；钩子必须尊重 `ctx`。
5. **在钩子里依赖执行顺序**：多个钩子并发执行，顺序不确定；有依赖就写进同一个函数。
6. **先关数据库再等在途请求**：在途请求全部失败，应在请求排空后再释放资源。
7. **同时用 Spin 和自定义信号处理**：重复 Shutdown，日志与状态混乱。
8. **在 Windows 上按 `Stop-Process` 验证**：它更接近强制终止，不能代表 Linux 的 `SIGTERM` 行为。

## 小结

- 优雅退出 = 停止接收 + 排空在途 + 释放资源，Hertz 的 `Spin` 已封装主要流程。
- 用 `WithExitWaitTime` 控制等待上限，用 `OnShutdown` 注册资源释放钩子。
- K8s 下必须协调 `preStop`、`ExitWaitTime`、`terminationGracePeriodSeconds` 三者的时间。
- 需要自定义生命周期时用 `Run + Shutdown`，不要和 `Spin` 混用。
