# 项目分层与目录规范
> 一句话定位：把 hz 生成的“能跑”项目，演进成“能长期维护、能多人协作”的企业级目录结构。

## 本篇目标

- 看清 hz 默认布局里哪些是生成代码、哪些该由人维护
- 掌握一套可直接落地的分层：`cmd` / `internal` / `pkg` / `api`
- 明确各层边界、依赖方向与包命名规范
- 学会循环依赖排查、单仓多服务与 IDL 生成代码的摆放

## 前置知识

- 已读 [02-Hertz入门/04-项目结构与代码生成布局](../02-Hertz入门/04-项目结构与代码生成布局.md)，熟悉 Go Module 与导入路径
- 理解接口与依赖倒置（见 [01-Go语言基础/04-结构体-方法-接口](../01-Go语言基础/04-结构体-方法-接口.md)）

## 一、hz 默认布局回顾

执行 `hz new -module hertz_demo` 后得到的基础布局（Hertz v0.10.6 / hz v0.9.8）：

```text
.
├── biz
│   ├── handler/api/hello.go      # 生成骨架，补业务
│   ├── model/api/hello.go        # IDL 生成模型
│   ├── router/{api,register,router}.go  # 路由（生成）
│   └── service/hello.go          # 业务逻辑
├── main.go / router_gen.go       # 进程与路由入口
└── script/bootstrap.sh
```

三条铁律：生成的 `handler` / `router` / `model` 骨架不要手改；`service` 由人维护；每次 `hz update` 后都要 review diff。

## 二、企业级目标结构

```text
hertz_demo/
├── api/user/v1/user.proto      # IDL 契约
├── cmd/userapi/main.go         # 组合根：只做装配与启动
├── internal/
│   ├── handler/                # HTTP 适配：绑定、校验、错误映射
│   ├── service/                # 业务层（biz）：规则、事务边界
│   ├── repository/             # 数据访问：SQL / 缓存 / 外部存储
│   ├── model/                  # 持久化实体与领域对象
│   ├── router/                 # 路由与中间件装配
│   └── config/                 # 配置结构体与加载逻辑
├── pkg/                        # 可复用、无业务依赖
└── go.mod
```

| 目录 | 职责 | 允许依赖 | 禁止 |
| --- | --- | --- | --- |
| `cmd` | 加载配置、组装依赖、启停 | internal、pkg | 写业务逻辑 |
| `internal/handler` | 协议适配与参数校验 | service、model | 直接访问 DB/Redis |
| `internal/service` | 业务规则、事务、领域校验 | repository、model、pkg | 依赖 `app.RequestContext` |
| `internal/repository` | 屏蔽存储细节 | model、pkg | 返回 HTTP 状态码 |
| `internal/model` | 数据结构，无业务行为 | 仅标准库 | import 上层包 |
| `pkg` | 通用工具（重试、ID 生成） | 标准库/三方库 | import `internal` |
| `api` | IDL 契约，服务端与客户端共享 | 无 | 写业务实现 |

## 三、各层职责与代码骨架

model 只描述数据：

```go
package model

import "time"

type User struct {
	ID        int64
	Name      string
	CreatedAt time.Time
}
```

repository 定义接口并给出实现，接口定义在**消费方所在包**，service 只依赖接口：

```go
package repository

// import 省略：context、database/sql、errors、fmt、internal/model

type UserRepository interface {
	FindByID(ctx context.Context, id int64) (*model.User, error)
}

type mysqlUserRepo struct{ db *sql.DB }

func NewMySQLUserRepository(db *sql.DB) UserRepository { return &mysqlUserRepo{db: db} }

func (r *mysqlUserRepo) FindByID(ctx context.Context, id int64) (*model.User, error) {
	var u model.User
	err := r.db.QueryRowContext(ctx,
		`SELECT id, name, created_at FROM users WHERE id = ?`, id).
		Scan(&u.ID, &u.Name, &u.CreatedAt)
	if errors.Is(err, sql.ErrNoRows) { return nil, nil }
	if err != nil { return nil, fmt.Errorf("find user %d: %w", id, err) }
	return &u, nil
}
```

service（biz）承载业务规则，事务边界也在这里：

```go
package service

// import 省略：context、errors、fmt、internal/model、internal/repository

var ErrUserNotFound = errors.New("user not found")

type UserService interface {
	Get(ctx context.Context, id int64) (*model.User, error)
}

type userService struct{ repo repository.UserRepository }

func NewUserService(repo repository.UserRepository) UserService { return &userService{repo: repo} }

func (s *userService) Get(ctx context.Context, id int64) (*model.User, error) {
	if id <= 0 { return nil, fmt.Errorf("invalid user id: %d", id) }
	u, err := s.repo.FindByID(ctx, id)
	if err != nil { return nil, err }
	if u == nil { return nil, ErrUserNotFound }
	return u, nil
}
```

handler 只做协议转换，错误在这里映射成状态码：

```go
package handler

// import 省略：context/errors/strconv、hertz 的 app/utils/consts、internal/service

type UserHandler struct{ svc service.UserService }

func NewUserHandler(svc service.UserService) *UserHandler { return &UserHandler{svc: svc} }

func (h *UserHandler) Get(ctx context.Context, c *app.RequestContext) {
	id, err := strconv.ParseInt(c.Param("id"), 10, 64)
	if err != nil {
		c.JSON(consts.StatusBadRequest, utils.H{"code": 40001, "msg": "invalid id"})
		return
	}
	u, err := h.svc.Get(ctx, id)
	if errors.Is(err, service.ErrUserNotFound) {
		c.JSON(consts.StatusNotFound, utils.H{"code": 40401, "msg": "user not found"})
	} else if err != nil {
		c.JSON(consts.StatusInternalServerError, utils.H{"code": 50000, "msg": "internal error"})
	} else {
		c.JSON(consts.StatusOK, utils.H{"id": u.ID, "name": u.Name})
	}
}
```

handler 里出现 SQL、缓存 key、事务，就说明分层已经破了。

## 四、依赖方向规则

```text
handler ──▶ service ──▶ repository ──▶ model
   └── 只依赖接口（接口定义在消费方）
pkg 不依赖以上任何一层；api 不反向依赖 internal
```

- 箭头只能单向，反向依赖通过接口或事件解耦
- 事务边界放在 service，repository 只负责“执行语句”
- DTO 与实体分离：IDL 生成的模型不要直接当 ORM 实体
- 排查依赖边（bash 与 PowerShell 命令相同）：`go list -f '{{.ImportPath}} -> {{join .Imports " "}}' ./...`

出现循环依赖时 `go build ./...` 会直接报 `import cycle not allowed`，先拆接口再谈重构。

## 五、包命名规范

| 反例 | 正例 | 原因 |
| --- | --- | --- |
| `internal/user_service` | `internal/service` | 不用下划线，目录即包名 |
| `pkg/utils` / `pkg/common` | `pkg/retry` / `pkg/idgen` | 按能力命名，避免大杂烩 |
| `type IUserService interface` | `type UserService interface` | 接口不加 I 前缀 |
| `type UserRepositoryInterface` | `type UserRepository` | 名字不重复包语义 |

补充约定：单方法接口以 `-er` 结尾（`Reader`、`Notifier`）；对外类型要能脱离包名读懂；测试用黑盒包 `package handler_test`，只验证公开行为。

## 六、避免循环依赖

1. 接口下沉到消费方：service 依赖 `UserRepository` 接口，repository 不反向引用 service
2. 用 DTO 转换：handler 把 IDL 模型转成 service 入参
3. 组合根集中装配：只有 `cmd/*/main.go` 同时认识 db、repo、service、handler
4. 共享类型放最底层，`model` 不 import 任何 internal 子包；`pkg` 禁止 import `internal`

## 七、单仓多服务布局

```text
repo/
├── go.work
├── services/
│   ├── userapi/{cmd,internal,api}
│   └── orderapi/{cmd,internal,api}
├── pkg/                     # 独立 module，按 tag 发版
└── deploy/
```

`go.work` 用 `use ./services/...` 声明本地模块，只用于联调，**不要提交到生产构建流程**；共享库用独立 module + 语义化版本，生产环境禁止长期使用 `replace`。

## 八、IDL 与生成代码目录

| hz 默认产物 | 企业目录 | 是否手改 |
| --- | --- | --- |
| `biz/handler/api` | `internal/handler` | 生成骨架，业务自行实现 |
| `biz/service` | `internal/service` | 是 |
| `biz/model/api` | `internal/model` / `api/user/v1` | 否 |
| `biz/router` | `internal/router` | 否（`router.go` 除外） |
| `main.go` / `router_gen.go` | `cmd/userapi/main.go` | 迁移后手改 |

生成命令统一收敛到脚本，PowerShell 与 bash 完全相同：

```bash
hz new -module hertz_demo -idl api/user/v1/user.proto
hz update -idl api/user/v1/user.proto
```

若坚持 `cmd/internal` 布局，迁移后需修正 import；hz 也支持 `--customize_layout` 指定自定义模板，但模板维护成本高，先用“生成后 review + 脚本统一”更稳。

## 常见坑

1. **handler 直接写 SQL/缓存**：单测被迫连数据库，换存储时全站改 handler。
2. **model 当万能 DTO**：IDL 字段一改，实体、HTTP 响应、内部调用全部受影响。
3. **`pkg` 反向 import `internal`**：编译器直接拒绝；共享代码要下沉到 `pkg` 或 `model`。
4. **`hz update` 后不看 diff**：手写在生成文件里的逻辑被覆盖，线上行为悄悄变化。

## 小结

- hz 的 `biz` 只是起点，企业级要按“适配层 / 业务层 / 数据层 / 模型层”收敛
- 依赖方向单向：handler → service → repository → model，接口定义在消费方
- `cmd` 只做装配，`internal` 包住实现，`pkg` 放无业务依赖的复用代码
- 生成代码不可手改，流程要脚本化；规范的价值是让改动范围可预测、测试可隔离

## 练习

1. 用 `hz new` 建项目，按本文结构迁移到 `cmd/internal/pkg`，跑通 `go build ./...`。
2. 给 `UserService` 补 `List` 方法，要求 handler 不出现 SQL、repository 不出现 HTTP 错误码。
3. 故意让 `pkg` import `internal/model`，观察编译错误并给出两种修复方案。
