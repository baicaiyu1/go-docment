# 01-消息队列选型对比
> 一句话定位：先用业务约束筛掉不合适的 MQ，再谈吞吐与功能，避免「为了用 MQ 而用 MQ」。
## 本篇目标
- 用吞吐、延迟、顺序、事务、延迟消息、运维成本六个维度对比主流 MQ
- 了解 Kafka / RocketMQ / RabbitMQ / NSQ / Pulsar 的架构差异与 Go 客户端成熟度
- 能根据业务场景给出选型结论，而不是背参数表
- 识别「用 MQ 做 RPC」「用 MQ 代替任务队列」等反模式
- 明确 mall-lite 为什么选 Kafka 作为订单事件总线
## 前置知识
- 已读 [10-Redis/05](../10-Redis/05-高可用部署与运维.md)，理解中间件的可用性代价
- 了解「至少一次」「幂等」的基本概念
- 本地有 Docker，能拉起单节点 Kafka
## 一、先问三个问题
选型前先回答，而不是先看性能数字：
1. **消息能不能丢？** 订单、支付不能丢；日志、埋点可以丢。
2. **要不要严格顺序？** 同一订单的状态变更必须有序；通知类消息无所谓。
3. **团队谁来运维？** 有没有专职中间件团队，决定了能不能碰 Pulsar 这类重组件。
把这三个答案写进设计文档，后面的对比表只是佐证。
## 二、对比矩阵
| 维度 | Kafka | RocketMQ | RabbitMQ | NSQ | Pulsar |
| --- | --- | --- | --- | --- | --- |
| 吞吐 | 极高（十万~百万级/s） | 高（十万级/s） | 中（万级/s） | 中 | 高（分层存储更强） |
| 延迟 | 毫秒~几十毫秒（批量） | 毫秒级 | 微秒~毫秒级 | 毫秒级 | 毫秒级 |
| 顺序消息 | 分区内有序 | 队列内严格有序（可全局顺序） | 单队列有序 | 单 channel 有序 | 分区有序 |
| 事务消息 | 事务写（EOS，仅流处理） | 原生半消息事务 | 不支持（需业务实现） | 不支持 | 支持事务 |
| 延迟消息 | 不支持（需自建） | 原生延迟级别 | 插件/死信 + TTL | 不支持 | 支持 |
| 消息回溯 | 按 offset 任意回溯 | 按时间/offset 回溯 | 消费即删，难回溯 | 内存/磁盘短期 | 按时间回溯 |
| 运维复杂度 | 中（KRaft 后降低） | 中高（NameServer+Broker） | 低 | 低 | 高（BookKeeper+Broker） |
| Go 客户端 | 非常成熟 | 官方 v2 客户端 | 官方 amqp091-go | 官方 go-nsq | 官方 pulsar-client-go |
| 社区/生态 | 最大 | 国内最活跃 | 老牌稳定 | 小而稳 | 上升期 |
| 典型定位 | 日志、流处理、事件总线 | 业务消息、电商交易 | 复杂路由、任务分发 | 轻量内网消息 | 云原生多租户 |
> 表里的「吞吐」是数量级感受，真实数字取决于分区数、批量、压缩、磁盘与网络，必须用自己的消息体压测。
## 三、逐个点评
### Kafka：事件流的事实标准
- 架构：Topic 分 Partition，Partition 内有序，副本 + ISR 保证可用；消费组按分区分配
- 强项：顺序写磁盘、零拷贝、批量压缩，吞吐极高；按 offset 回溯，天然适合流处理
- 弱项：没有原生延迟消息与业务事务消息；分区数变更需要规划；运维要懂 rebalance 与 ISR
- 适合：订单事件总线、行为日志、CDC 下游、实时数仓
### RocketMQ：业务消息的国产主力
- 架构：NameServer 管路由，Broker 存消息，Topic 下分 Queue；支持同步/异步刷盘、主从
- 强项：事务消息、延迟消息、顺序消息、消息重试与死信都是原生能力，贴合电商交易
- 弱项：组件多、部署与调优门槛高于 RabbitMQ；Go 客户端功能比 Java 客户端少一些
- 适合：订单创建/支付回调/库存扣减等需要事务与延迟的业务链路
### RabbitMQ：路由能力最强
- 架构：Exchange（direct/topic/fanout/headers）+ Binding + Queue，路由规则灵活
- 强项：复杂路由、优先级队列、TTL + 死信、管理界面完善，上手快
- 弱项：堆积能力弱（消息在队列里影响性能），吞吐有限，不适合当大数据管道
- 适合：任务分发、通知、按规则路由到多个下游
### NSQ：轻量、无中心
- 架构：nsqd 存消息，nsqlookupd 做发现，消费者通过 HTTP/TCP 拉取
- 强项：部署极简、无 ZooKeeper、单机性能不错
- 弱项：生态小、无事务/延迟/严格顺序，消息保留时间短，社区更新慢
- 适合：内网轻量异步、日志转发、非核心通知
### Pulsar：存算分离的云原生方案
- 架构：Broker 无状态 + BookKeeper 存储 + 分层存储（可落对象存储）
- 强项：多租户、按时间回溯、跨地域复制、弹性扩缩容
- 弱项：组件多、运维复杂、团队学习成本高
- 适合：有平台团队、需要多租户与海量留存的中大型公司
## 四、Go 客户端生态
| MQ | 推荐库 | 备注 |
| --- | --- | --- |
| Kafka | `github.com/segmentio/kafka-go`、`github.com/IBM/sarama`、`github.com/confluentinc/confluent-kafka-go` | kafka-go 简单；sarama 功能全；confluent 基于 librdkafka，性能最好但要 cgo |
| RocketMQ | `github.com/apache/rocketmq-client-go/v2` | 官方维护，事务/顺序/延迟消息都有 |
| RabbitMQ | `github.com/rabbitmq/amqp091-go` | 官方维护，替代旧的 streadway/amqp |
| NSQ | `github.com/nsqio/go-nsq` | 官方维护 |
| Pulsar | `github.com/apache/pulsar-client-go` | 官方维护，纯 Go |
选库原则：优先官方或官方推荐的库；确认最近一年有提交；确认支持你要用的特性（事务、延迟、批量），不要只看 star。
## 五、选型建议
```text
消息能否丢？
├─ 能丢（日志/埋点） → Kafka（吞吐优先）
└─ 不能丢
   ├─ 需要事务消息/延迟消息/严格顺序 → RocketMQ
   ├─ 需要复杂路由/低延迟任务分发 → RabbitMQ
   └─ 数据量极大且要长期留存/多租户 → Pulsar（有平台团队时）
```
补充规则：
- 已经在用 Kafka 的团队，业务消息也优先 Kafka，少引入一套中间件比「更贴合」更重要
- 消息体大（>1MB）不要塞 MQ，传对象存储地址
- 消费能力跟不上时先看分区数，再看消费者并发，最后才考虑换 MQ
## 六、mall-lite 为什么选 Kafka
| 需求 | Kafka 是否满足 |
| --- | --- |
| 订单事件扇出到库存、通知、积分多个消费组 | 满足，消费组天然隔离 |
| 大促峰值写入 | 满足，批量 + 压缩 |
| 事件回放排查问题 | 满足，按 offset 回溯 |
| 订单 30 分钟未支付自动取消 | 不满足，需定时扫表或延迟 Topic 方案 |
| 本地事务 + 消息同时成功 | 不满足，需本地消息表（Outbox） |
因此 mall-lite 采用「Kafka 做事件总线 + 本地消息表保证可靠投递 + 定时任务处理延迟取消」。如果业务更偏交易、团队更熟 RocketMQ，把 Kafka 换成 RocketMQ 也能成立，第 03 篇给出对应实现。
```bash
docker run -d --name kafka -p 9092:9092 apache/kafka:3.9.0
```
```powershell
docker run -d --name kafka -p 9092:9092 apache/kafka:3.9.0
```
## 七、国内企业常见组合
| 组合 | 场景 | 说明 |
| --- | --- | --- |
| Kafka + RocketMQ | 电商/金融 | Kafka 做日志与数仓，RocketMQ 做交易消息 |
| Kafka 单栈 | 互联网中台 | 团队统一，业务消息也走 Kafka + Outbox |
| RabbitMQ + Kafka | 传统企业 | RabbitMQ 做任务分发，Kafka 做数据管道 |
| NSQ + Redis | 小团队 | 轻量异步，够用就好 |
## 八、反模式
1. **用 MQ 做 RPC**：发一条消息等回复，超时与错误处理极其别扭；同步调用请用 Kitex。
2. **用 MQ 代替任务队列**：任务需要「指定时间执行、失败重试、可视化重跑」，MQ 只能提供部分能力，应配合调度系统。
3. **一个 Topic 装所有业务**：无法独立扩缩容、无法按业务限流，排查问题时全链路互相干扰。
4. **把 MQ 当数据库**：消息有保留期，消费完即删，不能作为唯一数据源。
5. **消息体塞整个聚合根**：几 MB 的消息拖垮 broker，传 ID + 变更字段即可。
6. **没有死信与监控就上线**：出问题时消息静默丢失，只能靠用户投诉发现。
## 九、消息模型：推与拉
| 模型 | 代表 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 推（Push） | RabbitMQ、RocketMQ PushConsumer | 实时性好、客户端简单 | 消费能力不足时被压垮，需要 prefetch/流控 |
| 拉（Pull） | Kafka、NSQ、RocketMQ PullConsumer | 消费端自控速率，天然背压 | 空轮询浪费资源，需要长轮询 |
| 长轮询 | Kafka `fetch.max.wait.ms` | 兼顾实时与背压 | 参数不当会增加延迟 |

选型时要问：消费端能否承受「被推送」的速率？如果下游是脆弱的第三方接口，拉模型更容易做限流与暂停。

## 十、消息保留与回溯
- Kafka 按时间/大小保留（如 7 天），可按 offset 重新消费，适合排障与重建读模型
- RocketMQ 默认保留 72 小时，支持按时间回溯，超过后消息被删除
- RabbitMQ 消费即删，回溯能力弱，重要事件建议同时落库
- 需要「永久事件日志」时，Kafka + 分层存储（或 Pulsar）比传统 MQ 更合适

## 十一、上线前的验收清单
| 检查项 | 通过标准 |
| --- | --- |
| 消息能否丢 | 关键消息有 Outbox/事务消息，消费端幂等 |
| 顺序要求 | 明确哪些消息需要顺序，key 设计已评审 |
| 延迟需求 | 明确用延迟级别、扫表还是延迟 Topic |
| 容量 | 分区数、保留时间、磁盘容量经过估算与压测 |
| 监控 | lag、失败率、死信量、消费耗时都有看板与告警 |
| 运维 | 有扩容、降级、重放、切流的操作手册 |
| 演练 | 做过 Broker 宕机、消费者全挂、消息重放的演练 |

任何一项答不上来，都不要直接把 MQ 接进交易主链路；先在小流量业务上跑通，再逐步扩大。

## 常见坑
1. **只看吞吐不看延迟**：Kafka 批量参数调大后吞吐上升、P99 延迟也上升，交易链路可能无法接受。
2. **以为 Kafka 有延迟消息**：原生不支持，必须自己用扫表或延迟 Topic 实现。
3. **忽略 Go 客户端能力差异**：某些特性只有 Java 客户端支持，选型时要按语言验证。
4. **小团队上 Pulsar**：BookKeeper + Broker 的运维成本远超收益。
5. **用 RabbitMQ 堆百万消息**：堆积后内存与磁盘告警，消费速度进一步下降。
6. **不压测就定分区数**：分区数后期只能增不能减，重启与 rebalance 成本高。
## 小结
- 先按「能否丢、要不要顺序、谁运维」筛掉候选，再看功能矩阵
- Kafka 强在吞吐与回溯，RocketMQ 强在业务消息能力，RabbitMQ 强在路由
- Go 生态最稳的是 kafka-go / sarama、rocketmq-client-go/v2、amqp091-go
- mall-lite 用 Kafka 做事件总线，用 Outbox 与定时任务补足事务与延迟能力
- MQ 不是 RPC，也不是数据库，更不是任务调度器
