# 05-积压-死信-延迟消息与监控
> 一句话定位：把 MQ 上线后一定会遇到的积压、死信、延迟需求与监控告警，做成可操作的处置手册。
## 本篇目标
- 快速定位积压根因，并区分「扩容能解决」与「扩容解决不了」
- 建立死信队列的处理流程与人工干预入口
- 用 RocketMQ 延迟级别、Kafka 定时扫表 + 延迟 Topic 实现订单超时取消
- 搭建 lag、消费耗时、失败率、死信量四类监控与告警阈值
- 制定消息命名、schema 演进、大小限制与 trace 透传规范

## 一、积压的成因
| 根因 | 现象 | 判断方法 |
| --- | --- | --- |
| 流量突增 | 生产速率远大于消费速率 | 生产 TPS 与消费 TPS 曲线对比 |
| 消费变慢 | 单条处理耗时上升 | 消费耗时 P99、下游 RT |
| 分区太少 | 加消费者后 lag 不降 | 消费者数 > 分区数，多出的实例空闲 |
| 下游抖动 | DB/Redis/HTTP 超时增多 | 下游错误率与连接池指标 |
| 毒消息 | 同一 offset 反复重试 | 日志中同一 msgID 循环 |
| rebalance 频繁 | 消费反复暂停 | 组状态日志、RebalanceCount |
先看「生产 vs 消费」速率，再看单条耗时，最后看分区与 rebalance，顺序不要颠倒。
## 二、积压处置
| 手段 | 操作 | 适用 | 副作用 |
| --- | --- | --- | --- |
| 扩消费者 | 实例数 ≤ 分区数 | 消费 CPU/IO 未打满 | 超过分区数无效 |
| 扩分区 | 增加 Partition | 长期容量不足 | 同 key 路由变化，顺序受影响 |
| 批量消费 | 一次拉多条、批量写库 | DB 往返是瓶颈 | 单条失败回滚成本高 |
| 降级非核心 | 关闭通知/积分消费，优先库存 | 大促洪峰 | 功能暂时不可用 |
| 限流生产端 | 网关限流、暂停低优先级 Topic | 源头流量失控 | 影响业务写入 |
| 丢弃可丢消息 | 日志/埋点直接跳过 | 非核心数据 | 数据缺失 |
追积压时必须保持幂等与顺序：**不要为了速度跳过失败消息**，宁可把失败消息转死信并记录，也不要静默丢弃。
## 三、死信队列处理流程
```text
消费失败 → 有限重试（退避） → 仍失败 → 死信队列 → 告警 → 人工/工具重放
```
- Kafka：消费端捕获「不可重试错误」，直接投递 `mall.dlq.<topic>`，附带原 topic/partition/offset/异常信息
- RocketMQ：消费返回 `ConsumeRetryLater` 重试 16 次后自动进入 `%DLQ%<group>`
- RabbitMQ：`Nack(requeue=false)` 且队列配置 `x-dead-letter-exchange`
死信消息必须包含：原始消息体、消息 ID、失败原因、失败次数、首次失败时间。处理入口至少提供「查看、单条重放、批量重放、标记忽略」四种操作，并记录操作人与时间。
## 四、延迟消息
### RocketMQ：原生延迟级别
```go
msg := primitive.NewMessage("mall.order.delay.v1", body)
msg.WithDelayTimeLevel(16) // 固定档位，4.x 共 18 级（1s ~ 2h）
_, err := p.SendSync(ctx, msg)
```
消费时务必二次校验订单状态：延迟消息只保证「大约 30 分钟后投递」，期间订单可能已支付。
### Kafka：定时扫表（最稳）
```sql
-- 必须有 (status, expire_at) 联合索引
SELECT id FROM orders
WHERE status = 'PENDING' AND expire_at < NOW()
ORDER BY id
LIMIT 200;
```
```go
func CancelExpiredOrders(ctx context.Context, db *gorm.DB, rdb redis.UniversalClient) error {
	var orders []Order
	if err := db.WithContext(ctx).
		Where("status = ? AND expire_at < ?", StatusPending, time.Now()).
		Order("id").Limit(200).Find(&orders).Error; err != nil {
		return err
	}
	for _, o := range orders {
		res := db.WithContext(ctx).Model(&Order{}).
			Where("id = ? AND status = ?", o.ID, StatusPending).
			Updates(map[string]any{"status": StatusCancelled, "cancel_reason": "timeout"})
		if res.Error != nil {
			return res.Error
		}
		if res.RowsAffected == 0 {
			continue // 已支付/已取消，幂等跳过
		}
		_ = rdb.IncrBy(ctx, stockKey(o.SkuID), int64(o.Qty)).Err() // 回补预扣库存
		_ = publishOrderCancelled(ctx, o.ID)
	}
	return nil
}
```
扫表方案的优点：实现简单、状态以 DB 为准、天然幂等；缺点：有扫描周期延迟（秒级）、订单量大时要分片扫描。用 `LIMIT + 主键游标` 避免深分页。
### Kafka：延迟 Topic（低延迟场景）
把消息按延迟档位分桶（1s/5s/30s/1m/5m/15m），消费到未到期的消息时转发到下一档，避免阻塞当前分区：
```go
type DelayEnvelope struct {
	EventID   string `json:"event_id"`
	DeliverAt int64  `json:"deliver_at"` // Unix 毫秒
	Target    string `json:"target"`     // 到期后投递的目标 Topic
	Key       string `json:"key"`
	Payload   []byte `json:"payload"`
}
```
不要用 `time.Sleep` 在消费线程里等：会阻塞整个分区，且进程重启后消息重复。更稳的是「时间轮/Redis ZSet + 定时拉取」，或直接回到扫表方案。
## 五、监控指标与告警
| 指标 | 采集方式 | 告警建议 |
| --- | --- | --- |
| 消费 lag | Kafka 消费组命令 / Reader Stats | 持续 5 分钟 > 1 万告警 |
| 堆积量 | Broker 端 `MessagesInPerSec` 与 lag 趋势 | 环比突增 5 倍关注 |
| 消费耗时 P99 | 应用埋点 | > 1s 关注，> 3s 告警 |
| 处理失败率 | 失败数 / 消费数 | > 1% 告警 |
| 死信数量 | DLQ Topic/Queue 消息数 | > 0 即告警 |
| rebalance 次数 | 客户端日志/指标 | 每小时 > 3 次排查 |
| 消费线程池饱和度 | 队列长度/worker 占用 | 持续 > 80% 扩容 |
```bash
kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 \
  --describe --group mall-stock-consumer
```
```powershell
kafka-consumer-groups.sh --bootstrap-server 127.0.0.1:9092 --describe --group mall-stock-consumer
```
```go
// kafka-go 直接暴露 lag 快照，定期采集即可
st := r.Stats()
log.Printf("topic=%s partition=%d lag=%d offset=%d errors=%d",
	st.Topic, st.Partition, st.Lag, st.Offset, st.Errors)
```
告警要带上下文：Topic、消费组、分区、当前 lag、消费速率、最近错误，否则值班同学只能从头查。
## 六、消息治理规范
| 项 | 规范 |
| --- | --- |
| 命名 | `mall.<domain>.<entity>.<event>.v<major>`，如 `mall.order.order.paid.v1` |
| 事件 ID | 每条消息带全局唯一 `event_id`，用于幂等与追踪 |
| 时间字段 | `occurred_at` 用 RFC3339，禁止本地时间字符串 |
| 版本演进 | 只加可选字段、不复用字段编号、不改变字段语义；Protobuf 用 reserved |
| 消息大小 | 建议 < 256KB，硬上限 1MB；大对象传 OSS 地址 |
| 链路追踪 | Header 注入 `trace_id`/`span_id`，消费端续接 trace |
| 保留策略 | 按业务定 `retention.ms`，事件总线建议 3~7 天 |
| 权限 | 生产/消费分账号，禁止跨业务直连 Topic |
```go
// 生产者注入 trace 上下文
headers := []kafka.Header{{Key: "trace_id", Value: []byte(traceID)}}
w.WriteMessages(ctx, kafka.Message{Key: []byte(orderID), Value: body, Headers: headers})
```
Schema 演进失败是线上事故高发区：新增字段必须可缺省，消费端对未知字段要忽略而不是报错；删除字段前先确认所有消费者已升级。
## 常见坑
1. **积压就加消费者**：分区只有 3 个，加到 10 个实例也没用，先看分区数。
2. **追积压时跳过失败消息**：lag 降下来了，数据却永久缺失。
3. **延迟消息用 `time.Sleep` 阻塞消费线程**：整个分区停摆，重启后重复消费。
4. **扫表 SQL 没有 `(status, expire_at)` 索引**：定时任务全表扫描，把 DB 拖慢。
5. **取消订单不回补库存**：订单取消了，Redis 预扣库存却永久少一件。
6. **只看 lag 不看消费耗时**：lag 低但 P99 已经 3 秒，下一次洪峰立刻积压。
7. **死信无告警**：消息进了 DLQ 无人知晓，几天后对账才发现少数据。
8. **消息体无版本号**：字段含义变更后老消费者解析出错误业务值。
## 小结
- 积压先看生产/消费速率，再看分区与耗时；扩容只对「分区够、资源未满」有效
- 死信是数据不是垃圾：必须告警、可查看、可重放
- 延迟消息优先 RocketMQ 延迟级别；Kafka 场景用定时扫表或延迟 Topic，别 sleep
- 监控四件套：lag、消费耗时、失败率、死信量
- 治理从命名、event_id、schema 兼容、trace 透传开始，而不是出事后补
