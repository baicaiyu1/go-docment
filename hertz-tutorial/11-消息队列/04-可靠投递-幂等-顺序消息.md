# 04-可靠投递-幂等-顺序消息
> 一句话定位：把「不丢、不重、不乱」拆成生产端、消费端、顺序三件事，并承认业务幂等才是最后一道防线。
## 本篇目标
- 看清 at-least-once 与 exactly-once 的真实边界
- 用本地消息表（Outbox）+ 定时补偿实现生产端可靠投递
- 掌握唯一键、去重表、Redis SETNX、状态机条件更新四种消费幂等手段
- 用「同 key 同分区 + 单分区串行」实现业务顺序，并知道乱序后的补救
- 设计重试与死信策略，避免毒消息拖垮消费组

- 已读 [12-微服务与Kitex/08](../12-微服务与Kitex/08-分布式事务与最终一致性.md)（建议对照阅读）

## 一、先破除幻想：没有免费的 exactly-once
| 语义 | 含义 | 实现成本 |
| --- | --- | --- |
| at-most-once | 最多一次，可能丢 | 最低，先提交后处理 |
| at-least-once | 至少一次，可能重 | 低，先处理后提交 |
| exactly-once | 恰好一次 | 极高，通常只在「流处理内部」成立 |
Kafka 的事务（EOS）能保证「读 Kafka → 处理 → 写 Kafka」的原子性，但一旦副作用落到 MySQL、Redis、第三方支付，就必须靠业务幂等。RocketMQ 事务消息保证的是「本地事务与消息发送」的一致，同样不保证消费只执行一次。**结论：工程上做 at-least-once + 幂等消费，对外表现为「效果恰好一次」。**
## 二、生产端可靠：本地消息表 + 补偿
核心思路：业务数据与消息记录写在同一个本地事务里，再由独立协程投递，失败就重试。
```sql
CREATE TABLE outbox_event (
  id            BIGINT AUTO_INCREMENT PRIMARY KEY,
  event_id      CHAR(36)     NOT NULL UNIQUE,
  topic         VARCHAR(64)  NOT NULL,
  msg_key       VARCHAR(64)  NOT NULL,
  payload       JSON         NOT NULL,
  status        TINYINT      NOT NULL DEFAULT 0, -- 0 待投递 1 已投递 2 已废弃
  retry_count   INT          NOT NULL DEFAULT 0,
  next_retry_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  created_at    DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  KEY idx_status_next (status, next_retry_at)
);
```
投递协程按 `status + next_retry_at` 扫描，指数退避重试：
```go
func backoff(retry int) time.Duration {
	d := time.Duration(1<<min(retry, 8)) * time.Second
	if d > 5*time.Minute {
		d = 5 * time.Minute
	}
	return d
}

// 扫描时用 SKIP LOCKED，多实例部署也不会重复抢同一批
db.Clauses(clause.Locking{Strength: "UPDATE", Options: "SKIP LOCKED"}).
	Where("status = 0 AND next_retry_at <= NOW()").
	Order("id").Limit(100).Find(&events)
```
| 方案 | 与本地事务原子 | 实现复杂度 | 补偿能力 | 适用 |
| --- | --- | --- | --- | --- |
| 先写库再发消息 | 否，中间失败会丢 | 低 | 无 | 可丢消息 |
| Outbox + 定时补偿 | 是 | 中 | 强，可重放 | 订单、支付、库存 |
| RocketMQ 事务消息 | 是（半消息 + 回查） | 中 | 依赖 Broker 回查 | 已用 RocketMQ |
| CDC（Debezium/Canal） | 是（读 binlog） | 高 | 强 | 平台化团队 |
Outbox 的代价：消息可能重复投递（发出成功但状态更新失败），消费端必须幂等；扫表有延迟（通常百毫秒级），不适合强实时场景。
## 三、消费端幂等：四板斧
### 1. 数据库唯一键（最简单）
```sql
CREATE TABLE consumed_message (
  id             BIGINT AUTO_INCREMENT PRIMARY KEY,
  consumer_group VARCHAR(64) NOT NULL,
  msg_id         VARCHAR(64) NOT NULL,
  created_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY uk_group_msg (consumer_group, msg_id)
);
```
```go
func ConsumeStockEvent(ctx context.Context, db *gorm.DB, msgID string, ev StockEvent) error {
	return db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		err := tx.Create(&ConsumedMessage{ConsumerGroup: "mall-stock-consumer", MsgID: msgID}).Error
		if errors.Is(err, gorm.ErrDuplicatedKey) {
			return nil // 已消费过，直接确认
		}
		if err != nil {
			return err
		}
		return tx.Model(&Stock{}).Where("sku_id = ?", ev.SkuID).
			Update("available", gorm.Expr("available - ?", ev.Qty)).Error
	})
}
```
去重记录与业务更新必须在同一事务，否则「记了去重但业务没成功」会导致漏处理。GORM 需开启 `gorm.Config{TranslateError: true}` 才能用 `ErrDuplicatedKey` 判断。
### 2. 状态机条件更新（订单最常用）
```sql
UPDATE orders
SET status = 'PAID', paid_at = NOW()
WHERE id = ? AND status = 'PENDING';
```
```go
res := tx.Model(&Order{}).Where("id = ? AND status = ?", ev.OrderID, StatusPending).
	Updates(map[string]any{"status": StatusPaid, "paid_at": time.Now()})
if res.Error != nil {
	return res.Error
}
if res.RowsAffected == 0 {
	return nil // 已支付或状态非法，本次视为成功
}
```
把「幂等」交给状态迁移规则：重复支付回调不会再次扣款，非法状态流转被 SQL 拒绝。
### 3. Redis SETNX（适合通知类）
```go
key := "mall:mq:dedup:notify:" + msgID
ok, err := rdb.SetNX(ctx, key, 1, 72*time.Hour).Result()
if err != nil {
	return err // 不能当成功处理，交给 MQ 重试
}
if !ok {
	return nil
}
if err := sendSMS(ctx, ev); err != nil {
	_ = rdb.Del(ctx, key).Err() // 失败要释放，否则用户永远收不到
	return err
}
```
风险：SETNX 成功后进程崩溃，消息重投时会因去重键存在而跳过，导致业务未执行。因此 Redis 去重只用于「重复无害、漏发可接受」的通知，金额相关一律用 DB 去重。
### 4. 业务天然幂等
| 操作 | 是否天然幂等 | 说明 |
| --- | --- | --- |
| `SET status = 'PAID'` | 是 | 重复执行结果相同 |
| `balance = balance - 100` | 否 | 必须加唯一流水号 |
| `INSERT` 带唯一键 | 是（冲突即忽略） | 推荐 |
| 调用支付退款 | 否 | 用退款单号做幂等键 |
## 四、顺序消息
顺序成立的两个条件：**同 key 同分区** + **同分区同一时刻只有一个消费者串行处理**。
```go
// 生产端：订单 ID 作为 key，Hash 分区
w.WriteMessages(ctx, kafka.Message{Key: []byte(orderID), Value: body})
// 消费端：一个分区一个 goroutine 串行处理，处理完再提交该分区 offset
```
常见破坏顺序的写法：
- key 为空或每次随机，同一订单落到不同分区
- 拉取线程把消息丢进共享线程池，多线程并发处理同一分区
- 失败后立即重试当前消息，但后续消息已被处理（乱序重试）
RocketMQ 的顺序消费开启 `WithConsumerOrder(true)`，同队列加锁串行，吞吐会下降。
如果业务对顺序要求不强，更稳的做法是**用版本号兜底**：
```sql
UPDATE order_status
SET status = ?, version = ?
WHERE order_id = ? AND version < ?;
```
乱序到达时旧版本被 SQL 拒绝，最终状态仍然收敛。
## 五、重试与死信
| MQ | 重试机制 | 死信 |
| --- | --- | --- |
| Kafka | 无原生重试；消费端不提交 + 退避，或转「重试 Topic」 | 自建死信 Topic |
| RocketMQ | 消费失败自动重试（默认 16 次，间隔递增） | `%DLQ%<group>` |
| RabbitMQ | `Nack(requeue=true)` 或 TTL + DLX | 死信交换机 |
设计原则：
- 区分「可重试错误」（超时、锁冲突）与「不可重试错误」（参数非法、数据不存在），后者直接进死信并告警
- 重试要有上限与退避，避免毒消息打满 CPU
- 死信必须有人看：接告警、提供重放入口，否则等于黑洞
## 六、和分布式事务章节的关系
本文的 Outbox、幂等消费、状态机，正是 [12-微服务与Kitex/08](../12-微服务与Kitex/08-分布式事务与最终一致性.md) 中「最终一致性」的落地手段：TCC/Saga 解决跨服务流程，消息 + 幂等解决跨服务通知。两者不要混用：下单扣库存用 Saga/TCC，订单支付成功后的积分、通知用消息。
## 常见坑
1. **以为 Kafka 事务消息能保证 MySQL 只写一次**：EOS 只在 Kafka 内部成立，外部副作用仍需幂等。
2. **去重表与业务更新不在同一事务**：记了去重但业务失败，消息被永久跳过。
3. **Redis 去重键先设后处理且失败不释放**：用户收不到通知，排查时还以为已发送。
4. **用 `Nack(requeue=true)` 处理参数错误**：毒消息无限循环，CPU 打满。
5. **消费端线程池并发处理同一分区**：顺序保证被自己破坏。
6. **重试无上限**：一条坏消息阻塞整个分区，lag 持续上涨。
7. **死信队列无人消费**：消息静默堆积，直到磁盘写满才发现。
## 小结
- 生产端可靠 = 本地事务 + Outbox + 定时补偿（或事务消息）
- 消费端幂等 = 唯一键/去重表/状态机/Redis SETNX，按数据重要性选
- exactly-once 是营销词，工程上做 at-least-once + 幂等
- 顺序 = 同 key 同分区 + 单分区串行；顺序要求不强时用版本号兜底
- 重试要有上限与退避，死信必须可观测、可重放
## 练习
1. 为订单支付回调实现「去重表 + 状态机」双重幂等，并用重复消息验证只生效一次。
2. 给 Outbox dispatcher 加上指数退避与最大重试次数，超过后标记为废弃并告警。
3. 用 10 个线程并发消费同一分区，观察乱序；再改回单分区串行验证顺序恢复。
4. 设计一个「重试 Topic + 死信 Topic」方案，画出消息流转图并说明各级 TTL。
