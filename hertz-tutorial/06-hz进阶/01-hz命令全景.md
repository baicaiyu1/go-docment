# hz 命令全景
> 一句话定位：把 `hz new / update / model / client` 的参数、目录约束与生成规则一次讲清，并能安全地增量改 IDL。
## 本篇目标
- 装好 hz 并确认版本与 Hertz 匹配
- 掌握四个子命令的职责与常用参数
- 理解 `.hz` 标记文件、目录约束与生成规则
- 能在已有项目中安全地增量生成，不被覆盖
- 掌握 Windows 下的 symlink、protoc、路径与编码注意点

## 一、安装与版本
```bash
# 通用方式（Linux / macOS / Windows PowerShell 均可）
go install github.com/cloudwego/hertz/cmd/hz@latest
hz -v
```

```powershell
# Windows 确认 GOPATH\bin 在 PATH 中
$env:Path -split ';' | Select-String "go\\bin"
hz -v
```

版本匹配原则：

| 组件 | 教程基线 | 说明 |
| --- | --- | --- |
| Hertz | v0.10.6 | 运行时框架 |
| hz | v0.9.8 | 代码生成工具 |
| Go | 1.25 | 语言版本 |

hz 生成的 `go.mod` 会写入它认为合适的 hertz 版本。若与团队基线不一致，生成后手动对齐并 `go mod tidy`。
## 二、四个子命令
| 命令 | 作用 | 典型场景 |
| --- | --- | --- |
| `hz new` | 创建全新项目脚手架 | 从零开始 |
| `hz update` | 基于 IDL 增量更新已有项目 | IDL 加了接口/字段 |
| `hz model` | 只生成 model | 只想更新数据结构 |
| `hz client` | 基于 IDL 生成 HTTP 客户端 | 调用方 SDK |

全局参数只有三个：`--verbose`、`--help`、`--version`。
## 三、`hz new` 参数
```bash
hz new --help
```

| 参数 | 说明 | 建议 |
| --- | --- | --- |
| `--idl` | IDL 文件路径，可多个（`.thrift` / `.proto`） | 必填（纯脚手架可省略） |
| `--module` / `--mod` | Go module 名 | 非 GOPATH 下必填 |
| `--service` | 服务名，为服务发现预留 | 与注册中心服务名一致 |
| `--out_dir` | 项目生成目录 | 默认当前目录 |
| `--handler_dir` | handler 相对路径 | 默认 `biz/handler` |
| `--model_dir` | model 相对路径 | 默认 `biz/model` |
| `--router_dir` | router 相对路径 | 默认 `biz/router` |
| `--client_dir` | client 生成路径 | 不指定则不生成 |
| `--use` | handler 引用已有 model 包 | 先有 model 再生成 handler 时用 |
| `--proto_path` / `-I` | proto 搜索路径 | 有 import 时必填 |
| `--thriftgo` / `-t` | 透传 thriftgo 参数 | 高级用法 |
| `--protoc` / `-p` | 透传 protoc 参数 | 高级用法 |
| `--force` / `-f` | 覆盖已生成文件 | 危险，慎用 |
| `--sort_router` | 路由注册排序 | 减少无意义 diff，推荐 |
| `--handler_by_method` | 每个方法单独 handler 文件 | 方法多时更清晰 |
| `--exclude_file` / `-E` | 不更新的文件 | 保护手工文件 |
| `--json_enumstr` | Thrift 枚举用字符串 | 前后端联调更友好 |
| `--unset_omitempty` | 去掉 omitempty | 需要区分零值时用 |
| `--snake_tag` | tag 用 snake_case | 与前端约定一致时用 |
| `--rm_tag` | 移除默认 json/query/form tag | 需要完全自定义时用 |

示例：

```bash
hz new -module example.com/order -idl idl/order.thrift --sort_router
```

```powershell
hz new -module example.com/order -idl idl/order.thrift --sort_router
```
## 四、`hz update` 参数
`hz update` 与 `new` 大部分参数相同，但没有 `--force`，并且**不会保存项目创建时的路径配置**：

- `--handler_dir`、`--model_dir`、`--client_dir` 必须与 `new` 时一致
- 不一致会在新路径下再生成一份，导致重复代码与引用错乱

```bash
hz update -idl idl/order.thrift
```

Protobuf 特别注意：`update` 时需要把**所有依赖的 proto 文件**都列出来（或通过 `-I` 能解析到），因为 protobuf 的依赖不会自动更新。Thrift 则只需指定主 IDL，依赖会自动生成。
## 五、`hz model` 与 `hz client`
只更新模型：

```bash
hz model -idl idl/order.thrift -model_dir biz/model
```

生成客户端：

```bash
hz client -idl idl/order.proto \
  -module example.com/order \
  -client_dir biz/client \
  --force_client_dir
```

`hz client` 的额外参数：

| 参数 | 说明 |
| --- | --- |
| `--base_domain` | 请求域名（也可在 IDL 用 `api.base_domain`） |
| `--force_client` | 强制更新 `hertz_client.go` |
| `--force_client_dir` | client 目录不按 namespace 分子路径 |
## 六、目录约束与 `.hz` 标记
hz 判断“当前目录是不是 Hertz 项目”的依据是 `.hz` 文件：

- 存在 `.hz`：`hz new` 直接报错
- 不存在 `.hz`：`hz update` 直接报错

典型项目结构（Thrift）：

```text
order/
├── .hz
├── go.mod
├── main.go
├── idl/
│   └── order.thrift
├── biz/
│   ├── handler/order/example/order_service.go
│   ├── model/order/example/...
│   └── router/
│       ├── register.go
│       └── order/example/
│           ├── order.go        # 每次重新生成，不要改
│           └── middleware.go   # 追加，不要删已有内容
└── router_gen.go               # 生成，不要改
```

规则：

1. `.hz`、`router_gen.go`、`biz/router/{namespace}/{idl}.go` 都是生成物，**不要手改**
2. `biz/handler/**` 首次生成后归你，`update` 只在文件末尾追加新方法
3. `biz/model/**` 会按 IDL 重新生成，业务逻辑不要写在这里
4. 自定义代码放 `pkg/`、`internal/`，或独立的 service 层
## 七、增量生成的正确姿势
推荐流程：

1. 改 IDL（新增字段用新编号，不删不改已有编号）
2. `hz update -idl ...`（参数与 new 完全一致）
3. 检查 diff：只应出现新增 handler、model 字段、路由
4. 在新增 handler 里补业务逻辑
5. `go build ./...` + 跑测试
6. 提交 IDL 与生成代码（团队约定允许提交生成物时）

如果 IDL 改坏了：

```bash
# 先看会改哪些文件（养成看 diff 的习惯）
git diff --stat
git checkout -- biz/model biz/router router_gen.go
```

不要在 `--force` 下盲目重跑 `hz new`，它会覆盖 handler 里的业务代码。
## 八、Windows 注意点
| 问题 | 原因 | 解决 |
| --- | --- | --- |
| `symlink ... privilege` | Windows 默认不允许普通用户创建符号链接 | 开启“开发者模式”，或以管理员运行终端 |
| `protoc not found` | protobuf IDL 需要外部 protoc | 下载 release 并把 `bin` 加入 PATH |
| `google/protobuf/*.proto not found` | 未配置 include 路径 | 把 protoc 压缩包的 `include` 目录内容放到 protoc 同级 |
| 路径反斜杠报错 | IDL 中的 import 必须用 `/` | 统一写 `idl/order.proto` |
| 中文路径失败 | 部分工具链对非 ASCII 路径支持差 | 项目放到纯英文路径 |
| 生成文件 CRLF 导致 diff 噪音 | Git 自动换行 | 配置 `.gitattributes` 统一 LF |

PowerShell 示例：

```powershell
# 检查 protoc
protoc --version
# 生成（注意参数顺序，路径用正斜杠更稳）
hz new -module example.com/order -I idl -idl idl/order.proto
```

Linux/macOS：

```bash
protoc --version
hz new -module example.com/order -I idl -idl idl/order.proto
```
## 九、生成规则速查
| IDL 元素 | 生成结果 |
| --- | --- |
| Thrift `namespace go a.b` | model/handler/router 都在 `a/b` 子目录下 |
| Proto `go_package` | 决定 model 路径，取最后一级决定 handler/router 目录 |
| 每个 service | 生成一个 handler 文件，包含该 service 的所有方法 |
| 每个 method 注解 | 生成一条路由注册 |
| 新增 method | 在对应 handler 文件末尾追加函数 |
| 新增 service | 新增 handler 文件 + 路由注册 |
| 新增 IDL 文件 | `biz/router/register.go` 插入新的注册调用 |
## 常见坑
1. **在已有项目里执行 `hz new -f`**：handler 业务代码被模板覆盖，只能靠 Git 恢复。
2. **`update` 时 `--model_dir` 与 `new` 不一致**：两套 model 并存，handler 引用混乱。
3. **手动改 `router_gen.go` 或 `biz/router/{ns}/{idl}.go`**：下次 update 直接丢失。
4. **只改生成代码不改 IDL**：下次生成全部回退，且团队其他人拿到的是旧接口。
5. **proto 只更新主文件**：依赖的 message 没重新生成，编译报字段不存在。
6. **Windows 没开开发者模式**：`hz new` 卡在创建 symlink。
7. **模块名与目录不一致**：`go.mod` 的 module 与 `-module` 不同，import 全红。
8. **把 `.hz` 提交到错误目录**：在子目录执行 hz 会误判项目根。
## 小结
- `new` 建项目、`update` 增量、`model` 只更模型、`client` 生成 SDK
- 路径类参数在 new/update 之间必须保持一致
- `.hz` 决定 hz 认为“项目在哪”，生成物与手工代码要严格分区
- Windows 的核心是三件事：symlink、protoc、纯英文路径
- 增量生成的底线是：IDL 先行、看 diff、不手改生成物
## 练习
1. 用 Thrift IDL 执行一次 `hz new`，再新增一个 method 执行 `hz update`，观察 diff。
2. 故意把 `--model_dir` 改成 `my_model` 执行 update，复现重复代码并清理。
3. 在 Windows 上不开启开发者模式执行 `hz new`，记录报错并修复。
4. 用 `hz client` 生成客户端，调用自己服务的接口验证可用。
