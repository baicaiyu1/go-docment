# 01-项目全景与架构设计

> 一句话定位：先把 mall-lite 的需求、限界上下文、目录端口、契约与 SLO 钉死，再动手写代码——本篇交付一张能落地的架构图，后面六篇只是往里填实现。

## 本篇目标

- 用需求表锁定用户、商品、库存、订单、支付五个域，明确"不做"清单
- 按限界上下文切出三个 Kratos 服务 + 一个 Gin BFF，说清谁拥有哪张表
- 冻结目录、端口、统一响应、错误码与 REST/gRPC 契约，让服务并行开发
- 把 SLO 换算成超时预算、副本数与连接池，而不是口号

## 一、业务需求：五块闭环

| 域 | 需求 | 优先级 | 关键工程点 |
| --- | --- | --- | --- |
| 用户 | 注册、密码登录、刷新令牌、查本人资料 | P0 | bcrypt cost 12、JWT 双令牌、Redis 消费 jti |
| 商品 | 列表、详情、价格 | P0 | Cache-Aside + singleflight + 空值缓存 |
| 库存 | 查库存、预扣、回补 | P0 | 条件更新防超卖、幂等流水、Redis 预扣削峰 |
| 订单 | 下单、查单、取消 | P0 | 状态机、幂等键、本地事务 + Outbox |
| 支付 | 模拟回调（**占位**，只做状态迁移） | P1 | 回调幂等、按 event_id 去重 |

支付只占位：收到成功通知就把订单从「待支付」推到「已支付」，不接真实渠道。先跑通状态机 + 幂等 + 最终一致主线，接渠道只是换验签实现。

## 二、限界上下文

| 上下文 | 聚合根 | 独占数据 | 对外契约 |
| --- | --- | --- | --- |
| 用户 | User | `mall_user.users` | `user.v1.UserService` |
| 商品 | Product | `mall_goods.products` | `product.v1.ProductService` |
| 库存 | Stock | `mall_goods.stocks`、`stock_logs` | 同一服务的库存方法 |
| 订单 | Order | `mall_order.orders`、`order_items`、`outbox_events` | `order.v1.OrderService` |
| 支付（占位） | Payment | 不落库 | 订阅 `order.created`，发布 `order.paid` |

规则：**跨上下文只走 Proto 或 Kafka 事件，不共享表、不跨库 join**。商品与库存同属 product-service，但读模型与并发模型完全不同，所以逻辑上拆开。依赖方向：order → product，payment ← order。

## 三、完整架构图

```text
Web/App ──HTTPS──▶ APISIX 3.11 :9080（jwt-auth · limit-req · cors · otel · 灰度）
                          │ HTTP（upstream 固定指向 gateway）
                          ▼
              gateway（Gin BFF）:8080（鉴权 · 校验 · 聚合 · 错误映射 · SSE）
        ┌─────────────────┼──────────────────┐ gRPC
        ▼ :9001           ▼ :9002            ▼ :9003
  user-service      product-service     order-service        （Kratos v2.8）
        │                 │                  │
  MySQL mall_user   MySQL mall_goods    MySQL mall_order ──▶ Kafka :9092
  横切：etcd:2379 / Consul:8500 注册 · Sentinel 限流熔断 · OTel:4317 → Jaeger:16686
```

APISIX 上游**永远指向 Gin 网关**，前端不直连 gRPC；注册中心只服务 `Gin → Kratos` 这一段，APISIX 用固定 upstream 或 K8s Service；Sentinel 保护服务内部临界资源（DB 连接、下游 RPC），入口洪水由 APISIX 挡，两者不是二选一。Prometheus:9090 抓各服务 :9101-9103 指标并接 Grafana。

## 四、技术栈与版本基线

| 层 | 选型 | 版本基线 | 职责 | 明确不做 |
| --- | --- | --- | --- | --- |
| 入口 | APISIX | 3.11 | 路由、JWT、限流、灰度 | 不写业务 |
| BFF | Gin | v1.10.x | HTTP/JSON、校验、聚合、SSE | 不直连 MySQL |
| 微服务 | Kratos | v2.8.x | Proto、gRPC、注册发现、中间件 | 不做前端适配 |
| ORM | GORM | v1.25.x（MySQL 8.4） | 单服务事务、乐观锁、软删除 | 跨库 join |
| 缓存 | go-redis v9 | v9.7（Redis 7.4） | 详情缓存、幂等键、预扣 | 当事实来源 |
| 消息 | Kafka + sarama | 3.8 | 领域事件、最终一致 | 当 RPC 用 |
| 防护 | Sentinel Go | v1.0.4 | 限流、熔断、热点参数 | 替代入口限流 |
| 配置日志 | Viper / zap | v1.20 / v1.27 | yaml + 环境变量；结构化日志 | 密钥入库 |

可观测用 OTel + Jaeger + Prometheus + Grafana（最新稳定组合）。版本按「教程基线」，落地以官方最新稳定版为准。

## 六、核心数据模型

```sql
-- deploy/mysql/init.sql（每服务独立库，只列关键表）
CREATE TABLE users (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT,
    email VARCHAR(128) NOT NULL, password_hash VARCHAR(72) NOT NULL,
    nickname VARCHAR(32) NOT NULL DEFAULT '', status TINYINT NOT NULL DEFAULT 1,
    UNIQUE KEY uk_email (email)
);
CREATE TABLE products (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT, title VARCHAR(128) NOT NULL,
    price_cent INT NOT NULL, version BIGINT NOT NULL DEFAULT 0, status TINYINT NOT NULL DEFAULT 1
);
CREATE TABLE stocks (
    sku_id BIGINT UNSIGNED PRIMARY KEY, product_id BIGINT UNSIGNED NOT NULL,
    available INT NOT NULL DEFAULT 0, locked INT NOT NULL DEFAULT 0,
    KEY idx_product (product_id), CONSTRAINT ck_available CHECK (available >= 0)
);
CREATE TABLE orders (
    id BIGINT UNSIGNED PRIMARY KEY AUTO_INCREMENT, order_no VARCHAR(32) NOT NULL,
    user_id BIGINT UNSIGNED NOT NULL, status TINYINT NOT NULL COMMENT '10待支付 20已支付 30已取消',
    total_cent INT NOT NULL, idempotency_key VARCHAR(64) NOT NULL, expire_at DATETIME(3) NOT NULL,
    UNIQUE KEY uk_order_no (order_no), UNIQUE KEY uk_user_idem (user_id, idempotency_key)
);
-- order_items、outbox_events 的完整 DDL 见 04-订单服务与下单主链路
```

口径：`available + locked = 总库存`；`order_items` 存标题与价格快照，改价不影响历史订单；`outbox_events` 与订单同库同事务，见 [04-订单服务与下单主链路](04-订单服务与下单主链路.md)。

## 七、API 清单：REST 对外、gRPC 对内

| 方法 | 路径 | 说明 | 鉴权 |
| --- | --- | --- | --- |
| POST | `/api/v1/auth/register` | 注册 | 否 |
| POST | `/api/v1/auth/login` | 登录，返回 access + refresh | 否 |
| POST | `/api/v1/auth/refresh` | 刷新令牌（轮换） | 否 |
| GET | `/api/v1/users/me` | 查本人资料 | 是 |
| GET | `/api/v1/products` `/products/:id` | 列表 / 详情 | 否 |
| POST | `/api/v1/orders` | 下单，必带 `Idempotency-Key` | 是 |
| GET | `/api/v1/orders/:order_no` | 订单详情 | 是 |
| POST | `/api/v1/orders/:order_no/cancel` | 取消未支付订单 | 是 |
| POST | `/api/v1/payments/callback` | 支付回调（占位） | 签名 |

```proto
// api/{user,product,order}/v1/*.proto 节选
service UserService {
    rpc Register(RegisterRequest) returns (RegisterReply);
    rpc Login(LoginRequest) returns (LoginReply);
    rpc RefreshToken(RefreshTokenRequest) returns (LoginReply);
} // 另有 GetUser(GetUserRequest) returns (User)
service ProductService {
    rpc GetProduct(GetProductRequest) returns (Product);
    rpc DeductStock(DeductStockRequest) returns (DeductStockReply);
    rpc RestoreStock(RestoreStockRequest) returns (RestoreStockReply);
}
service OrderService {
    rpc CreateOrder(CreateOrderRequest) returns (CreateOrderReply);
    rpc GetOrder(GetOrderRequest) returns (Order);
    rpc CancelOrder(CancelOrderRequest) returns (CancelOrderReply);
    rpc MarkPaid(MarkPaidRequest) returns (MarkPaidReply);
}
```

gateway 调全部三个服务；order-service 只调 product-service（扣减/回补），用户信息由网关透传 `user_id`；支付回调走 gateway → `MarkPaid`。gRPC 只在内网暴露，客户端启动时建一次连接并复用。

## 八、非功能需求：SLO、超时、幂等、安全

| 项 | 目标 | 落地 |
| --- | --- | --- |
| 可用性 | 99.95%，月停机 ≤ 21.6 min | 三副本 + 滚动发布 + 探针 |
| 延迟 | 网关 P99 50ms、详情 30ms、下单 300ms | Histogram 分位告警 |
| 容量 | 读 2000 QPS、写 200 QPS（10:1） | 利特尔法则：`2000×30ms=60` 并发 |
| 一致性 | 不超卖、不重复下单 | 条件更新 + 唯一索引 + 对账 |
| 安全 | 不泄露内部细节 | 只暴露 8080；密钥走 Secret；bcrypt 12 |

超时预算逐跳递减：`APISIX 3s → Gin http.Server 2.5s → CreateOrder 800ms → DeductStock 300ms → 单条 SQL 100ms`。上游超时小于下游，等于让下游白干且连接不释放。幂等三处：下单 `Idempotency-Key` → `uk_user_idem`；库存 `(request_id, type)` 唯一键；支付回调按 `event_id` 去重。

## 完整示例

文件 `pkg/errs/response.go`——统一信封 + gRPC 错误映射，业务码落 4xx/5xx 区间：

```go
package errs

import (
    "net/http"

    "github.com/gin-gonic/gin"
    kerrors "github.com/go-kratos/kratos/v2/errors"
)

func OK(c *gin.Context, data any) {
    c.JSON(http.StatusOK, gin.H{"code": 0, "message": "ok", "data": data, "request_id": c.GetString("request_id")})
}

// Fail 只输出可读信息：堆栈、下游服务名、SQL 一律不出网
func Fail(c *gin.Context, err error) {
    e := kerrors.FromError(err)
    status, msg := http.StatusInternalServerError, "internal server error"
    if e.Code >= 400 && e.Code < 500 {
        status, msg = int(e.Code), e.Message
    }
    c.AbortWithStatusJSON(status, gin.H{"code": status*100 + 1, "message": msg, "request_id": c.GetString("request_id")})
}
```

文件 `app/gateway/internal/middleware/idempotency.go`——网关只做快速去重，真正幂等在下单服务：

```go
package middleware

import (
    "net/http"
    "time"

    "github.com/gin-gonic/gin"
    "github.com/redis/go-redis/v9"
)

func Idempotency(rdb *redis.Client) gin.HandlerFunc {
    return func(c *gin.Context) {
        key := c.GetHeader("Idempotency-Key")
        if c.Request.Method != http.MethodPost || key == "" {
            c.AbortWithStatusJSON(http.StatusBadRequest, gin.H{"code": 40002, "message": "Idempotency-Key required"})
            return
        }
        if ok, err := rdb.SetNX(c.Request.Context(), "idem:gw:"+key, 1, 10*time.Minute).Result(); err == nil && !ok {
            c.AbortWithStatusJSON(http.StatusConflict, gin.H{"code": 40902, "message": "duplicate request"})
            return
        }
        c.Next() // Redis 故障时放行，由下游唯一索引兜底
    }
}
```

## 常见坑

1. **先写代码再定契约**：三个服务字段名各叫一套，最后只能 DTO 硬转；先冻结 `api/*/v1/*.proto`。
2. **把 QPS 当 TPS**：一次下单 = 3 次 RPC + 2 次 DB + 1 次 Kafka，容量会算小一半。
3. **前端直连 gRPC 服务**：鉴权、限流、错误码要在每个服务重写，且无法统一灰度。
4. **错误码只有 200/500**：前端分不清"库存不足"和"系统错误"，只能弹通用文案。
5. **时区不统一**：容器、MySQL、Go 进程时区不同会让 30 分钟超时判定漂移；统一 `TZ=Asia/Shanghai`。
6. **网关里塞业务**：BFF 一旦写状态机就退化成胖服务；聚合可以做，业务归 Kratos。

## 小结

- 范围锁定「浏览 → 登录 → 下单 → 查单 → 取消」，支付只占位
- APISIX 挡流量、Gin 做 BFF、Kratos 管契约治理、GORM 管单服务数据、Sentinel 护临界资源
- 非功能指标必须能换算成副本数、超时预算与连接池，否则只是口号
- 统一信封 + 分段错误码是网关、可观测性与排障的共同语言
