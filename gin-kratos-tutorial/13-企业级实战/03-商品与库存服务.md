# 03-商品与库存服务

> 一句话定位：商品读走缓存，库存写走「条件更新 + 流水」，把「不超卖」变成一条 SQL 和一张可对账的事实表。

## 本篇目标

- 设计 products / stocks / stock_logs 三张表，固定 `available + locked` 口径
- `product.proto` 定义 GetProduct / DeductStock / RestoreStock / GetStock
- 商品详情缓存解决穿透、击穿、雪崩，库存数字只用于展示
- 用 `UPDATE ... WHERE available >= n` 防超卖，事务内同时写库存与流水，`request_id` 保证幂等

## 一、三张表定口径

```sql
-- deploy/mysql/init.sql（节选）
CREATE TABLE products (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(128) NOT NULL,
    price_cent INT NOT NULL COMMENT '单位分',
    version BIGINT NOT NULL DEFAULT 0,
    status TINYINT NOT NULL DEFAULT 1 COMMENT '1 上架 0 下架'
);
CREATE TABLE stocks (
    sku_id BIGINT UNSIGNED PRIMARY KEY,
    product_id BIGINT UNSIGNED NOT NULL,
    available INT NOT NULL DEFAULT 0,
    locked INT NOT NULL DEFAULT 0,
    version BIGINT NOT NULL DEFAULT 0,
    KEY idx_product (product_id), CONSTRAINT ck_available CHECK (available >= 0)
);
CREATE TABLE stock_logs (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    request_id VARCHAR(64) NOT NULL,
    sku_id BIGINT UNSIGNED NOT NULL,
    delta INT NOT NULL COMMENT '扣减为负，回补为正',
    type VARCHAR(16) NOT NULL COMMENT 'init/deduct/restore',
    UNIQUE KEY uk_request (request_id, type)
);
```

口径只有一句：`available + locked = 总库存`。下单把 available 挪进 locked，支付后扣 locked，取消反向回补；每次变更都写一条流水，期初建仓也要写 `init`，否则对账全是误差。

## 二、product.proto

```proto
// api/product/v1/product.proto
syntax = "proto3";
package product.v1;
option go_package = "mall-lite/api/product/v1;v1";

service ProductService {
    rpc GetProduct(GetProductRequest) returns (Product);
    rpc GetStock(GetStockRequest) returns (Stock);
    rpc DeductStock(DeductStockRequest) returns (DeductStockReply);
    rpc RestoreStock(RestoreStockRequest) returns (RestoreStockReply);
}
message Product { int64 id = 1; string title = 2; int64 price_cent = 3; int64 version = 4; int32 available = 5; }
message Stock { int64 sku_id = 1; int32 available = 2; int32 locked = 3; }
message GetProductRequest { int64 product_id = 1; }
message GetStockRequest { int64 sku_id = 1; }
message DeductStockRequest { string request_id = 1; int64 sku_id = 2; int32 qty = 3; }
message DeductStockReply { bool success = 1; }
message RestoreStockRequest { string request_id = 1; int64 sku_id = 2; int32 qty = 3; }
message RestoreStockReply { bool success = 1; }
```

`request_id` 由 order-service 生成并贯穿全链路；`RestoreStock` 用「原 request_id + restore」做幂等，超时重试与取消关单重复调用都只回补一次。

## 三、商品详情缓存

Cache-Aside 读缓存；repo 注入 `singleflight.Group`，配合空值缓存防穿透、随机 TTL 防雪崩：

```go
// app/product-service/internal/data/product.go
func (r *productRepo) GetProduct(ctx context.Context, id int64) (*biz.Product, error) {
    key := fmt.Sprintf("product:detail:%d", id)
    if b, err := r.rdb.Get(ctx, key).Bytes(); err == nil {
        if string(b) == emptyMark {
            return nil, kerrors.NotFound("PRODUCT_NOT_FOUND", "product not found")
        }
        var p biz.Product
        if json.Unmarshal(b, &p) == nil {
            return &p, nil
        }
    }
    v, err, _ := r.sf.Do(key, func() (any, error) { // 并发回源只放行一个
        p, err := r.findFromDB(ctx, id)
        if err != nil {
            return nil, err
        }
        if p == nil {
            r.rdb.Set(ctx, key, emptyMark, time.Minute) // 空值，60s 后再试
            return nil, kerrors.NotFound("PRODUCT_NOT_FOUND", "product not found")
        }
        b, _ := json.Marshal(p)
        r.rdb.Set(ctx, key, b, 10*time.Minute+time.Duration(rand.IntN(120))*time.Second)
        return p, nil
    })
    if err != nil {
        return nil, err
    }
    return v.(*biz.Product), nil
}
```

详情页的「剩余库存」单独读 `stock:{sku_id}`，TTL 3~5 秒，允许展示滞后；**扣减永远走 DB，不能信缓存数字**。改价或下架时删除 `product:detail:{id}`（先改库再删缓存），不要直接 set 新值。

## 四、防超卖：条件更新就是锁

```go
// app/product-service/internal/data/stock.go
func (r *stockRepo) Lock(ctx context.Context, tx *gorm.DB, skuID int64, qty int32) error {
    res := tx.WithContext(ctx).Model(&StockModel{}).
        Where("sku_id = ? AND available >= ?", skuID, qty).
        UpdateColumns(map[string]any{
            "available": gorm.Expr("available - ?", qty),
            "locked":    gorm.Expr("locked + ?", qty),
        })
    if res.Error != nil {
        return res.Error
    }
    if res.RowsAffected == 0 { // 扣不到就是不够，不要再查一次
        return kerrors.Conflict("STOCK_NOT_ENOUGH", "stock not enough")
    }
    return nil
}
```

`UPDATE ... WHERE available >= n` 在 InnoDB 行锁内完成读改写，同一 SKU 天然串行。禁止「先 SELECT 判断再 UPDATE」——两把锁之间就是超卖窗口。`stocks.version` 不用于扣减（条件本身已是锁，加版本只会放大重试）；它留给商品编辑：改价用 `WHERE id = ? AND version = ?` 配合 `version = version + 1`，影响行数为 0 就返回 `PRODUCT_VERSION_CONFLICT` 让运营重试。

## 五、DeductStock：一个事务，三件事

扣库存、写流水必须同生共死；流水唯一键让重复请求变成幂等成功，而不是报错。

```go
// app/product-service/internal/biz/stock.go
func (uc *StockUsecase) Deduct(ctx context.Context, requestID string, skuID int64, qty int32) error {
    return uc.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := uc.repo.Lock(ctx, tx, skuID, qty); err != nil {
            return err
        }
        log := &StockLog{RequestID: requestID, SkuID: skuID, Delta: -qty, Type: "deduct"}
        if err := tx.WithContext(ctx).Create(log).Error; err != nil {
            if errors.Is(err, gorm.ErrDuplicatedKey) {
                return nil // 同 request_id 已扣过，按成功返回
            }
            return err
        }
        return nil
    })
}
```

回补方向相反，并额外要求 `locked >= qty`，防止把 `locked` 扣成负数；流水表用「原 request_id + restore」唯一键去重，重复回补只成功一次：

```go
res := tx.WithContext(ctx).Model(&StockModel{}).Where("sku_id = ? AND locked >= ?", skuID, qty).
    UpdateColumns(map[string]any{
        "available": gorm.Expr("available + ?", qty),
        "locked":    gorm.Expr("locked - ?", qty),
    })
```

高并发热点 SKU 可在 DB 前加一层 Redis Lua 预扣（`GET` 判断 + `DECRBY` 原子），把流量挡在数据库外；它只决定「谁先抢到」，DB 条件更新才是事实来源，事务失败必须 `INCRBY` 回补，回补失败进补偿任务。

## 六、压测关注点

- **同一 SKU 行锁**：并发全打一个 SKU 时 DB 串行化，TPS 上限取决于单行更新耗时；用库存分桶或 Redis 预扣削峰
- **Redis 热 key 与连接池**：盯 `redis_cmd_duration` 与慢查询，单 key 写有上限；`MaxOpenConns` 要与 DB CPU 一起看
- **正确性**：压测后校验 `available + locked = 初始库存`、流水求和一致、无负库存

## 完整示例

```sql
-- deploy/mysql/check_stock.sql：按 SKU 对账，有结果即告警并冻结该 SKU 自动扣减
SELECT s.sku_id, s.available, s.locked, COALESCE(SUM(l.delta), 0) AS log_balance
FROM stocks s LEFT JOIN stock_logs l ON l.sku_id = s.sku_id
GROUP BY s.sku_id, s.available, s.locked
HAVING s.available + s.locked <> COALESCE(SUM(l.delta), 0);
```

## 常见坑

1. **先查后改**：`SELECT available` 再 `UPDATE` 在并发下必然超卖；只认带条件的 `UPDATE`。
2. **Redis 扣了 DB 没扣**：异常路径忘记回补，缓存与 DB 永久偏差；补偿任务按 `request_id` 可重放。
3. **幂等键放内存**：多实例部署后本地 map 失效，重复请求直接穿透；幂等必须落 Redis 或 DB 唯一键。
4. **缓存库存用于下单**：页面数字滞后几秒可以接受，扣减依据必须是 DB。
5. **回补无上限**：重复回补把库存刷高；`RestoreStock` 要校验 `locked >= qty` 并靠 `(request_id, type)` 唯一键去重。

## 小结

- 库存口径固定为 `available + locked`，任何变更都留流水，期初也要留
- 防超卖靠 `UPDATE ... WHERE available >= n`，影响行数为 0 即失败；乐观锁只用于商品改价
- 缓存只服务展示，热点用 Redis 预扣削峰；幂等靠 `request_id` 唯一键 + 事务内流水
