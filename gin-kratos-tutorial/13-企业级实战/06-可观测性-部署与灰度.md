# 06-可观测性、部署与灰度

> 一句话定位：指标回答「坏没坏」、日志回答「为什么坏」、链路回答「坏在哪一跳」——三者共用 `trace_id`/`request_id`，再用探针、优雅退出与金丝雀把发布变成可回滚的流程。

## 本篇目标

- 定义 SLO 与可行动告警，接上日志采集，做到「一个 `trace_id` 捞全链路」
- 用滚动更新 + 金丝雀（APISIX `traffic-split` 或 Argo Rollouts）发布，指标门禁不达标自动回滚
- 用 k6/ghz 压测与故障演练验证：发布不掉容量，依赖故障不雪崩

## 三、Grafana：RED 与四黄金信号

```text
sum(rate(http_server_requests_total[1m])) by (service)                                   # Rate
sum(rate(http_server_requests_total{status=~"5.."}[5m])) by (service) / sum(rate(http_server_requests_total[5m])) by (service)  # Errors
histogram_quantile(0.99, sum(rate(http_server_request_duration_seconds_bucket[5m])) by (le, service))  # Duration
sum(rate(sentinel_block_total[5m])) by (resource, reason)                                 # 限流/熔断
```

每个服务固定四块：流量、错误、延迟、饱和度；顶部放 SLO 摘要。标签只用 `service/method/route/status` 这类低基数维度，`uid`、订单号、真实路径一律禁止——一条序列就是一份存储成本。四黄金信号里的「饱和度」看连接池等待、Goroutine 数、Kafka lag。

## 四、Jaeger：一条链路串三服务

```go
// pkg/tracing/provider.go
func NewProvider(ctx context.Context, cfg Config) (*sdktrace.TracerProvider, error) {
    exp, err := otlptracegrpc.New(ctx, otlptracegrpc.WithEndpoint(cfg.Endpoint), otlptracegrpc.WithInsecure())
    if err != nil {
        return nil, err
    }
    tp := sdktrace.NewTracerProvider(sdktrace.WithBatcher(exp),
        sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(cfg.SampleRatio))))
    otel.SetTracerProvider(tp)
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(propagation.TraceContext{}, propagation.Baggage{}))
    return tp, nil
}
```

`resource` 里必须带 `service.name` 与 `deployment.environment`，否则 Jaeger 无法按服务检索。Gin 中间件顺序必须是 `requestid.New()` → `otelgin.Middleware("gateway")` → 访问日志 → 指标；`otelgin` 放后面，日志里的 `trace_id` 全空。Kratos 侧加 `tracing.Server()`/`tracing.Client()`，GORM 与 go-redis 只要 `WithContext(ctx)` 就能续上父子 span。Kafka 跨进程不共享 ctx，生产端要手工 `Inject` 到消息头，消费端先 `Extract` 再起 consumer span。

## 五、SLO 与告警

SLO 用「可用性 + 延迟」两条就够：`99.9%` 的请求非 5xx、P99 < 300ms。99.9% 对应每月约 43 分钟错误预算，烧完就冻结功能发布，只允许修缺陷。QPS 跌零比 P99 升高更危险：多半是流量根本没进来（证书过期、Endpoint 被摘空、DNS 故障）。

```yaml
# deploy/prometheus/rules/mall-slo.yaml
groups:
    - name: mall-slo
      rules:
          - alert: GatewayHighErrorRate
            expr: sum(rate(http_server_requests_total{status=~"5.."}[5m])) by (service) / sum(rate(http_server_requests_total[5m])) by (service) > 0.01
            for: 5m
            labels: { severity: critical }
            annotations: { summary: "{{ $labels.service }} 5xx 比例 > 1%", runbook: "https://wiki/mall/runbook/5xx" }
          - alert: GatewaySlowP99
            expr: histogram_quantile(0.99, sum(rate(http_server_request_duration_seconds_bucket[5m])) by (le, service)) > 0.3
            for: 10m
            labels: { severity: warning }
          - alert: TrafficDrop
            expr: sum(rate(http_server_requests_total[5m])) < 1 and sum(rate(http_server_requests_total[5m] offset 1h)) > 50
            for: 5m
            labels: { severity: critical }
          - alert: KafkaConsumerLag
            expr: sum(kafka_consumer_lag) by (group) > 10000
            for: 10m
            labels: { severity: warning }
```

QPS 跌零的告警不能省；每条告警都必须带 runbook 与值班人，否则就是噪音。熔断打开用 `sentinel_block_total{reason="circuit_breaker"} > 0` 单独建规则。

## 六、日志采集

容器只写 stdout + JSON（zap），由节点上的 Fluent Bit DaemonSet 采集并打上 `namespace/pod/container` 标签后送 Loki 或 ES。统一字段：`service/env/request_id/trace_id/user_id/latency_ms/http.method/http.path/http.status`。禁止打印 body、`Authorization`、完整手机号；`trace_id` 是日志与链路的跳转键，缺了就只能按时间盲搜。

## 七、滚动更新

```yaml
# deploy/k8s/gateway.yaml
apiVersion: apps/v1
kind: Deployment
metadata: { name: gateway, labels: { app: gateway } }
spec:
    replicas: 3
    strategy: { rollingUpdate: { maxUnavailable: 0, maxSurge: 1 } }
    selector: { matchLabels: { app: gateway } }
    template:
        metadata: { labels: { app: gateway } }
        spec:
            terminationGracePeriodSeconds: 40
            containers:
                - name: gateway
                  image: registry.example.com/mall/gateway:${GIT_SHA}
                  resources: { requests: { cpu: 300m, memory: 256Mi }, limits: { cpu: "1", memory: 512Mi } }
                  envFrom: [{ secretRef: { name: mall-secret } }, { configMapRef: { name: mall-config } }]
                  startupProbe: { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 2, failureThreshold: 30 }
                  readinessProbe: { httpGet: { path: /readyz, port: 8080 }, periodSeconds: 5 }
                  livenessProbe: { httpGet: { path: /healthz, port: 8080 }, periodSeconds: 10 }
                  lifecycle: { preStop: { httpGet: { path: /drain, port: 8080 } } }
```

`/healthz` 只证明进程活着，不查 DB——否则一次 DB 抖动会重启全部 Pod；`/readyz` 查 DB ping 与注册中心，失败即摘流量。distroless 没有 shell，preStop 必须用 HTTP `/drain`，别写 `sleep`；`terminationGracePeriodSeconds`（40s）要大于 `Shutdown` 超时（20s）。退出顺序：摘流量 → 停收新请求 → 等存量 → 关连接池 → 冲刷 span。

## 八、金丝雀与自动回滚

网关层用 APISIX `traffic-split` 按权重放量；需要按步骤暂停、自动分析就用 Argo Rollouts。判定只看指标，不看人肉日志：对比 v1/v2 的 5xx 比例、P99、`sentinel_block_total`、Kafka 积压。

```yaml
# deploy/k8s/rollout-order.yaml（需安装 argo-rollouts 与 APISIX 流量路由）
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: order-service }
spec:
    replicas: 6
    strategy:
        canary:
            trafficRouting: { apisix: { route: order-route } }
            steps: [{ setWeight: 10, pause: { duration: 10m } }, { setWeight: 50, pause: { duration: 30m } }]
```

门禁脚本查不到数据时按失败处理，别让「没指标」变成放行理由。

```bash
# deploy/scripts/canary-gate.sh
ratio=$(curl -sG http://127.0.0.1:9090/api/v1/query --data-urlencode \
    'query=sum(rate(http_server_requests_total{version="v2",status=~"5.."}[5m]))/sum(rate(http_server_requests_total{version="v2"}[5m]))' \
    | jq -r '.data.result[0].value[1] // "1"')
if awk "BEGIN{exit !($ratio > 0.01)}"; then
    kubectl argo rollouts abort order-service
    exit 1
fi
```

回滚三级：配置开关关功能 → 灰度权重归零（秒级）→ `kubectl rollout undo`。数据库变更永远「先加后删」，保证新旧版本并存时可读写。

## 九、压测与故障演练

```bash
TOKEN=$(curl -s -X POST http://127.0.0.1:8080/api/v1/auth/login -H "Content-Type: application/json" \
    -d '{"username":"demo","password":"demo"}' | jq -r .data.access_token)
k6 run -e BASE=http://127.0.0.1:9080 -e TOKEN="$TOKEN" deploy/k6/order.js
ghz --insecure --proto api/order/v1/order.proto --call order.v1.OrderService/CreateOrder \
    -d '{"user_id":1,"sku_id":1001,"qty":1}' -n 20000 -c 50 127.0.0.1:9003
```

压测要跑出拐点：吞吐上升而 P99 突然拐头的位置就是容量上限，之后加并发只加延迟和错误。故障演练每季度至少一轮：

| 演练 | 注入方式 | 预期 | 观察指标 |
| --- | --- | --- | --- |
| 实例下线 | 删除一个 order Pod | 流量自动切走，无 5xx | readiness、错误率 |
| 注册中心不可用 | 停 etcd 一个节点 / 全停 | 存量连接继续服务 | 路由数、gRPC 失败率 |
| Kafka 积压 | 停消费者 10 分钟 | 告警触发，恢复后追平 | consumer lag、P99 |
| Redis 故障 | 主节点 kill / 切主 | 降级读 DB，不雪崩 | 缓存命中率、DB QPS |

## 发布 checklist

1. CI 全绿：`go vet`、`golangci-lint`、`go test -race`、镜像漏洞扫描
2. 变更评审：SQL 是否走索引、是否兼容旧版本、配置是否有默认值
3. 灰度前：数据库迁移已「先加后删」、Feature Flag 默认关闭
4. 灰度 10%：观察 5xx、P99、限流触发、Kafka lag 至少 10 分钟
5. 放量 50% → 100%：每档留观察窗口，指标门禁自动判定
6. 回滚演练 + 发布后 24h：确认权重归零与 `rollout undo` 一分钟内完成，对比 SLO 与错误预算消耗

## 常见坑

1. **otelgin 排在日志之后**：日志里 `trace_id` 全空；把 tracing 中间件放最前。
2. **指标用真实路径或 uid**：序列数爆炸；用 `c.FullPath()` 与低基数标签。
3. **liveness 查 DB**：DB 抖动导致全部 Pod 重启，故障放大；存活与就绪必须分开。
4. **preStop 用 `sleep`**：distroless 没有 shell，命令直接失败；改成 HTTP `/drain`。
5. **门禁在无数据时放行 / 只扩 Pod 不扩连接池**：`jq` 取到 `null` 要当失败；副本翻倍后 DB 连接按「实例 × 池大小」一起算。

## 小结

- 三根支柱靠 `trace_id`/`request_id` 互跳，缺一层就是盲人摸象；Gin 用 otelgin、Kratos 用 tracing，MySQL/Redis 靠 ctx 续链，Kafka 手工 Inject
- 告警只留可行动规则并绑定 runbook；SLO 决定什么时候停止发布
- 探针分离 + 优雅退出 + 金丝雀 + 指标门禁，是 K8s 上稳定发布的四件套
