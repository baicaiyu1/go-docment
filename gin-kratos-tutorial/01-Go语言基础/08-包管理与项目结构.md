## 一、包：Go 的组织单元

Go 的包由**目录**决定：一个目录下的所有 `.go` 文件属于同一个包，包名必须一致。

```text
go-lab/
├── go.mod
├── main.go              // package main
├── internal/
│   └── user/
│       ├── service.go   // package user
│       └── repo.go      // package user
└── pkg/
    └── response/
        └── response.go  // package response
```

导入路径 = **模块路径 + 目录相对路径**。模块是 `go-lab` 时：

```go
import (
	"go-lab/internal/user"
	"go-lab/pkg/response"
)
```

三个规则：同目录下不能有两个包名（`user` 与 `user_test` 除外）；包名可以与目录名不同，但**强烈建议一致**；导入路径最后一段是目录名，实际使用的标识符前缀是**包名**。

## 二、包命名规范

- 全小写，短，不要下划线或驼峰：`user`、`httpx`、`config`
- 不要用 `util`、`common`、`base` 这种无意义名字，它们最终会变成垃圾场
- 包名不要与标准库冲突：`http`、`json`、`context` 都不行
- 导出标识符用注释说明，注释以标识符名开头：

```go
// User 表示系统中的用户。
type User struct {
	ID   int64
	Name string
}

// NewService 创建用户服务。
func NewService(repo Repository) *Service {
	return &Service{repo: repo}
}
```

包名是调用方代码的一部分：`user.NewService(...)` 读起来要像一句话。写成 `userutil.NewUserServiceUtil(...)`，说明命名失败了。

## 三、推荐的目录结构

```text
go-lab/
├── go.mod
├── cmd/
│   └── server/
│       └── main.go          # 程序入口，只做装配与启动
├── internal/
│   ├── user/
│   │   ├── handler.go       # HTTP 处理
│   │   ├── service.go       # 业务逻辑
│   │   └── repo.go          # 数据访问
│   └── platform/
│       ├── logger/
│       └── config/
├── pkg/
│   └── response/
└── configs/
    └── config.yaml
```

| 目录 | 职责 | 能否被外部导入 |
| --- | --- | --- |
| `cmd/` | 可执行程序入口，每个子目录一个二进制 | 不对外 |
| `internal/` | 私有实现，禁止外部模块导入 | 否 |
| `pkg/` | 可被外部复用的公共库 | 是 |

**为什么入口要放 `cmd/server/main.go`？** 一个项目可能有多个二进制（server、cli、migrate）。`main.go` 只负责「读配置、构造依赖、启动」，业务逻辑全部在 `internal`，这样入口很薄，测试也容易。这是 Gin 社区常见 layout 的简化版，后续 [02-Gin入门/04-项目结构与分层布局](../02-Gin入门/04-项目结构与分层布局.md) 会看到更完整的分层结构。

## 四、internal：编译器的可见性强制

`internal` 是 Go 的特殊目录名：**只有以 `internal` 的父目录为根的子包才能导入它**。另一个模块 `example.com/other` 试图 `import "go-lab/internal/user"` 时，编译直接失败：

```text
use of internal package go-lab/internal/user not allowed
```

这解决了「文档写着别用，但没人遵守」的问题——**用编译器强制约束**。业务实现、领域模型、不想承诺兼容性的工具包都该放这里。

`pkg/` 用于「确实要被外部项目 import」的库；如果只是本项目的其他包用，放 `internal` 即可，不要滥用 `pkg`。

## 五、循环依赖：原因与解法

Go **禁止包级循环依赖**，编译报错 `import cycle not allowed`。常见成因：两个包互相引用对方的模型；Service 直接 import Repo，Repo 又为了返回类型 import Service；工具函数互相引用。

解法一：**接口下沉**，在调用方定义接口，实现方只依赖自己的包：

```go
// internal/user/service.go
package user

import "context"

type Repository interface {
	FindByID(ctx context.Context, id int64) (*User, error)
}

type Service struct {
	repo Repository
}

func NewService(repo Repository) *Service {
	return &Service{repo: repo}
}
```

如果数据库实现放在另一个包 `internal/user/mysql`，它 import `user`（拿模型和接口），而 `user` 不 import `mysql`——依赖方向单一，不会成环。

解法二：**抽取共享类型到独立的 model 包**，让 `user`、`order` 都 import 它。解法三：**重新划分包边界**——循环依赖往往是「包切得太细或职责不清」的信号，把强关联的代码合并，或按领域而不是按技术分层。

## 六、init 函数

每个包可以有多个 `init`，在包被导入时自动执行：

```go
package config

var defaults map[string]string

func init() {
	defaults = map[string]string{"port": "8080", "env": "dev"}
}
```

执行顺序：先初始化被导入的包（递归）→ 再初始化本包的包级变量 → 再执行本包的 `init` → 最后执行 `main`。

**为什么要慎用 `init`？** 它隐式执行，读者不知道何时跑了什么；无法返回错误，失败只能 panic；难以测试，导入包就会触发副作用。推荐用显式的 `NewXxx` 构造函数替代，把初始化错误返回给调用方。`init` 真正合理的场景：注册驱动、注册编解码器（如 `database/sql` 驱动）。

## 七、构建标签与 go.work

构建标签让同一个包在不同平台编译不同文件，`//go:build` 必须在文件最顶部，与包声明之间空一行：

```go
//go:build linux

package main

func platformName() string { return "linux" }
```

常用标签：`linux`、`windows`、`darwin`、`amd64`、`arm64`、`ignore`，也支持自定义标签，编译时用 `-tags` 指定：

```text
go build -tags=integration ./...
```

常见用途：集成测试文件加 `//go:build integration`，默认 `go test` 不跑，CI 里单独跑。

一个仓库有多个独立模块（例如 `app` 与 `shared` 分别发版）时，用 `go.work` 在本地把它们连起来：

```text
go work init ./app ./shared
go work use ./app
```

注意：`go.work` 是**本地开发**工具，通常不提交（或团队约定用于 monorepo）；CI 构建时应显式设置 `GOWORK=off`，确保用的是各模块自己的 `go.mod`；能用单模块解决就不要上多模块。

## 常见坑

1. **包名与目录名不一致**：`import "x/user"` 却要写 `account.New()`，读者会困惑，保持同名。
2. **把业务代码放 `cmd`**：入口会越来越厚，无法复用与测试，`cmd` 只做装配。
3. **滥用 `pkg`**：`pkg` 是公共 API 承诺，本项目内部用的放 `internal`。
4. **用 `init` 做重活**：失败只能 panic，测试也会被牵连，改用构造函数。
5. **循环依赖时直接合并包**：先尝试接口下沉或抽 model，合并只是掩盖设计问题。
6. **构建标签位置写错**：`//go:build` 前有注释或空行都会失效。
7. **提交 `go.work` 导致 CI 行为不一致**：CI 用 `GOWORK=off`，或团队明确约定提交。

## 小结

包是 Go 的模块边界：目录即包，`internal` 用编译器强制私有，`cmd/internal/pkg` 划分职责，循环依赖靠接口下沉解决。下一篇 [09-标准库net-http入门](09-标准库net-http入门.md) 会把前面所有知识组装成一个真正的 HTTP 服务。
