# 跨服务链路追踪与日志串联

> 一句话定位：一次下单在 Gin 网关、order-service、product-service、MySQL 与 Kafka 之间共用一个 `trace_id`，日志、指标、追踪用同一组字段串起来，才能回答「慢在哪一跳」。

## 本篇目标

- 初始化 OTel SDK（OTLP/gRPC + W3C TraceContext + 采样），进程退出前 `Shutdown` 刷盘
- Gin 用 `otelgin`、Kratos 用 `tracing.Server()` / `tracing.Client()`，服务端客户端两侧都不漏
- trace 贯穿 GORM 与 Kafka，异步消息靠消息头续接
- 讲清 request_id 与 trace_id 的分工、metadata 透传、zap 字段、采集到 Loki/ELK 与 Jaeger 排查

## 一、两个 ID 的分工

| 维度 | trace_id | request_id |
| --- | --- | --- |
| 生成位置 | 入口 span（网关或第一个服务） | 网关中间件，必生成 |
| 生命周期 | 整条调用链，可跨进程与消息 | 单次 HTTP 请求 |
| 是否可能丢失 | 会被采样丢弃 | 永不丢弃，必须回写响应头与日志 |

两者不要合并：采样率调到 1% 时，用户报障给的 trace_id 很可能查不到，但 request_id 一定能在日志里找到。request_id 通过 metadata 逐跳透传，服务端日志、下游 RPC、异步消息都带上。

## 二、初始化 OTel SDK

```go
// pkg/tracing/tracer.go
func Init(ctx context.Context, cfg *config.Config) (func(context.Context) error, error) {
    exp, err := otlptracegrpc.New(ctx,
        otlptracegrpc.WithEndpoint(cfg.Trace.Endpoint), // otel-collector:4317
        otlptracegrpc.WithInsecure(),
    )
    if err != nil {
        return nil, err
    }
    res, err := resource.Merge(resource.Default(), resource.NewWithAttributes(
        semconv.SchemaURL,
        semconv.ServiceName(cfg.App.Name),
        attribute.String("deployment.environment", cfg.App.Env),
    ))
    if err != nil {
        return nil, err
    }
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exp),
        sdktrace.WithResource(res),
        sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(cfg.Trace.Ratio))),
    )
    otel.SetTracerProvider(tp)
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{}, propagation.Baggage{},
    ))
    return tp.Shutdown, nil
}
```

全局只初始化一次；`propagation.TraceContext` 就是 W3C `traceparent`；`ParentBased` 保证上游不采样时下游也不采样，避免半条链路。`tp.Shutdown` 必须带 5s 超时调用，否则 batcher 里最后一批 span 直接丢。

## 三、Gin 网关：otelgin + request_id

```go
// app/gateway/internal/router/router.go
func NewRouter(h *handler.OrderHandler, tp trace.TracerProvider) *gin.Engine {
    r := gin.New()
    r.Use(gin.Recovery(), requestid.New())
    r.Use(otelgin.Middleware("gateway", otelgin.WithTracerProvider(tp)))
    api := r.Group("/api/v1")
    api.Use(func(c *gin.Context) {
        if sc := trace.SpanContextFromContext(c.Request.Context()); sc.IsValid() {
            c.Header("X-Trace-ID", sc.TraceID().String())
        }
        c.Header("X-Request-ID", requestid.Get(c))
        c.Next()
    })
    api.POST("/orders", h.CreateOrder)
    return r
}
```

`otelgin` 要在业务 handler 之前注册，它会自动从请求头提取 `traceparent` 并写入 `c.Request.Context()`。下游一律传这个 context，不要在 goroutine 里直接引用 `*gin.Context`（请求结束后会被复用）。响应头回写 `X-Trace-ID` 是排障刚需：用户截图报障时，凭它直接跳 Jaeger。

## 四、Kratos：Server 与 Client 成对出现

```go
// app/order-service/cmd/main.go（节选）
grpcSrv := kgrpc.NewServer(kgrpc.Address(":9003"),
    kgrpc.Middleware(recovery.Recovery(), tracing.Server(), logging.Server(logger)))
v1.RegisterOrderServiceServer(grpcSrv, svc)

productConn, err := kgrpc.DialInsecure(ctx,
    kgrpc.WithEndpoint("discovery:///product-service"),
    kgrpc.WithDiscovery(reg.Discovery),
    kgrpc.WithMiddleware(tracing.Client(), recovery.Recovery()),
)
```

只加 `tracing.Server()` 的典型症状是：order-service 入口有 span，调 product-service 的那一段消失，最后把锅甩给 product。同一进程既当服务端又当客户端，两个中间件都要加。`tracing.Client()` 会把 span 上下文写进 gRPC metadata，服务端 `tracing.Server()` 再提取，形成父子关系。

## 五、W3C TraceContext 在三种协议里的传播

| 协议 | 载体 | 谁负责 |
| --- | --- | --- |
| HTTP | `traceparent` / `tracestate` 请求头 | `otelgin` + 全局 propagator |
| gRPC | metadata 键 `traceparent` | Kratos `tracing` 中间件 |
| Kafka | 消息头（headers） | 业务代码手动注入/提取 |

```go
// pkg/mq/trace.go
var tp = otel.GetTextMapPropagator()

func InjectTrace(ctx context.Context, headers []sarama.RecordHeader) []sarama.RecordHeader {
    carrier := propagation.MapCarrier{}
    tp.Inject(ctx, carrier)
    for k, v := range carrier {
        headers = append(headers, sarama.RecordHeader{Key: []byte(k), Value: []byte(v)})
    }
    return headers
}

func ExtractTrace(ctx context.Context, headers []sarama.RecordHeader) context.Context {
    carrier := propagation.MapCarrier{}
    for _, h := range headers {
        carrier[string(h.Key)] = string(h.Value)
    }
    return tp.Extract(ctx, carrier)
}
```

生产端用 `InjectTrace`，消费端把 `ExtractTrace` 的结果作为消费 span 的父 context，异步链路才不会断。批量消费时逐条提取，不要拿一条消息的 context 复用给整批。

## 六、metadata 透传业务字段

```go
// app/gateway/internal/handler/order.go（节选）
ctx := metadata.AppendToClientContext(c.Request.Context(),
    "x-request-id", requestid.Get(c), "x-tenant-id", c.GetString("tenant"))
resp, err := h.orderClient.CreateOrder(ctx, req)
```

服务端用 `metadata.FromServerContext(ctx)` 取；key 全小写，只透传 trace、request_id、tenant 这类白名单字段。`user_id` 必须由服务端从 JWT 解析后写入，不能信客户端直传；metadata 不放大对象，也别塞手机号、身份证等 PII。

## 七、日志串联与采集

```go
// pkg/logger/logger.go
func WithTrace(ctx context.Context, l *zap.Logger) *zap.Logger {
    sc := trace.SpanContextFromContext(ctx)
    if !sc.IsValid() {
        return l
    }
    return l.With(
        zap.String("trace_id", sc.TraceID().String()),
        zap.String("span_id", sc.SpanID().String()),
    )
}
```

日志统一 stdout JSON，字段固定 `ts / level / service / env / trace_id / span_id / request_id / msg`，由采集器收走，不在容器里写文件。Promtail 采集示例：

```yaml
# deploy/otel/promtail.yaml
server:
    http_listen_port: 9080
clients:
    - url: http://loki:3100/loki/api/v1/push
scrape_configs:
    - job_name: mall
      docker_sd_configs:
          - host: unix:///var/run/docker.sock
      relabel_configs:
          - source_labels: ['__meta_docker_container_name']
            target_label: service
      pipeline_stages:
          - json:
                expressions:
                    level: level
                    trace_id: trace_id
          - labels:
                level:
```

Loki 只给 `service / env / level` 建标签，**trace_id 不做标签**（高基数列会拖垮索引），查询时用 `|= "trace_id"` 过滤。ELK 方案同理：`trace_id` 做普通字段而非 keyword 聚合键。

## 八、Jaeger 查询与火焰图

```bash
docker run -d --name jaeger -p 16686:16686 -p 4317:4317 jaegertracing/all-in-one:1.62
```

浏览器打开 `http://127.0.0.1:16686`，按 service + operation 查，或粘贴响应头里的 `X-Trace-ID`。火焰图看的是 span 的父子与耗时占比：先找耗时最长且「自身耗时」高的 span，再对比同 operation 的 P99；跨服务断链时，缺失的那一段就是没加 Client 中间件或没传 context。System Architecture 页用来看依赖与错误率。

## 九、采样策略与成本

- 开发环境 100%，预发 20%，生产头部 5% + 错误全留；所有服务采样率必须一致，靠 `ParentBased` 跟随上游。
- 更省钱的做法是 Collector 尾部采样：`status_code = ERROR` 全留、`duration > 500ms` 全留、其余 1%。
- 估算：1000 QPS × 5% = 50 trace/s，每 trace 约 10 span、每 span 约 1KB，约 43GB/天；降到 1% 加尾部采样通常足够。trace 可以采样，日志不能按同一比例丢：错误日志 100% 保留，成功日志按比例。

## 常见坑

1. **用 `context.Background()` 调下游**：新开一条链，父子关系全丢；一律传请求 context。
2. **只加 Server 不加 Client**：调下游那段没有 span，误判性能瓶颈。
3. **GORM 不用 `WithContext`**：SQL span 不挂到 trace 上；所有查询传 ctx。
4. **Kafka 不注入消息头**：异步链路断在消息边界；生产注入、消费提取。
5. **自己在业务里生成 trace_id 写日志**：与 OTel 的 ID 对不上；用 `tracing.TraceID()` / `SpanContextFromContext`。
6. **忘记 `tp.Shutdown`**：最后一批 span 丢失；各服务采样率不同还会让链路拼不起来，统一配置并用 ParentBased。

## 小结

- trace_id 跨进程、可被采样；request_id 单请求、永不丢，两者都写日志
- Gin 用 `otelgin`、Kratos 用 `tracing.Server()` + `tracing.Client()`，GORM 与 Kafka 手动接
- 日志走 stdout JSON，Loki/ELK 只给低基数字段建标签，trace_id 做过滤字段
- 采样按环境分级，错误与慢请求全留；`Shutdown` 必须调用

## 练习

1. 给 gateway → order → product 全链路加追踪，在 Jaeger 里确认是一条完整 trace。
2. 停掉 order-service 的 `tracing.Client()` 观察火焰图断在哪一段，再把生产采样率从 5% 改到 1% 对比数据量。
