# 分布式事务与最终一致性

> 一句话定位：mall-lite 不追求跨服务强一致，而是「同步预扣库存 + 本地事务写订单与 Outbox + Kafka 至少一次投递 + 消费端幂等 + 超时取消补偿 + 每日对账」，把一致性做成可重放、可修复的工程问题。

## 本篇目标

- 用 CAP/BASE 说清为什么下单选 AP + 最终一致，2PC/XA 为什么不落地
- 分清 TCC、Saga、Outbox、RocketMQ 事务消息、最大努力通知的适用边界
- 跑通「下单 → 预扣库存 → 支付 → 发货」，给出表结构、状态机与关键代码，并讲透空补偿、悬挂、重复、丢失的防法

## 一、CAP、BASE 与 2PC 的局限

库存与订单分库后，跨服务写无法同时满足 C 与 A：网络分区时只能二选一。下单必须可用（A）且容忍分区（P），所以放弃强一致（C），换成 BASE：基本可用、软状态（订单 `CREATED`、库存 `locked`）、最终一致。代价是中间态可见、必须做幂等与对账；收益是下单不被全局锁拖死。

2PC/XA 在 prepare 阶段就锁住资源直到 commit，协调者单点、同步阻塞、跨 MQ 不适用，云上数据库与中间件支持参差。结论：只在单个数据库内用本地事务，跨服务不用 XA；要「冻结」语义就用 TCC 的业务锁，而不是数据库锁。

## 二、方案谱系与选择

| 方案 | 一致性 | 侵入性 | 适用 |
| --- | --- | --- | --- |
| TCC | 最终一致 | 高，要写 Try/Confirm/Cancel | 资金、库存等需精确冻结 |
| Saga | 最终一致 | 中，每步要有补偿 | 长流程、跨多个服务 |
| 本地消息表 / Outbox | 最终一致 | 低，业务表旁加 outbox | 绝大多数业务事件 |
| RocketMQ 事务消息 | 最终一致 | 中，依赖 MQ 回查 | 已用 RocketMQ、不想维护 outbox |
| 最大努力通知 | 不保证 | 低 | 通知第三方、回调 |

选择顺序：能合服务就合 → 能「本地事务 + 异步事件」就 Outbox → 需精确冻结用 TCC → 长流程用 Saga（简单流程编排，跨团队协同）→ 有 RocketMQ 可用事务消息 → 对外系统用最大努力通知 + 对账。

## 三、端到端链路

```text
POST /api/v1/orders（Idempotency-Key）
  └─ order: Redis 幂等 → product.LockStock(同步) → 本地事务(orders + outbox order.created)
       └─ relay → Kafka order.created → 积分 / 通知 / 搜索（幂等消费）
  └─ 支付回调 → Kafka payment.succeeded → order 消费：CREATED→PAID + outbox stock.confirm
       └─ product 消费 stock.confirm：locked→sold，发 order.paid → shipping 消费后 SHIPPED
  └─ 超时：cancel job 扫 expire_at → CREATED→CANCELLED + outbox order.cancelled → product 释放锁定
```

## 四、表结构与状态机

```sql
-- deploy/sql/order.sql
CREATE TABLE orders (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, order_no CHAR(32) NOT NULL, user_id BIGINT UNSIGNED NOT NULL,
    sku_id BIGINT UNSIGNED NOT NULL, quantity INT NOT NULL, amount DECIMAL(10,2) NOT NULL,
    status VARCHAR(16) NOT NULL DEFAULT 'CREATED', expire_at DATETIME(3) NOT NULL, version INT NOT NULL DEFAULT 0,
    UNIQUE KEY uk_order_no (order_no), KEY idx_status_expire (status, expire_at)
) ENGINE=InnoDB;
CREATE TABLE stock (
    sku_id BIGINT UNSIGNED PRIMARY KEY, available INT NOT NULL, locked INT NOT NULL DEFAULT 0, sold INT NOT NULL DEFAULT 0
) ENGINE=InnoDB;
CREATE TABLE stock_lock (
    order_no CHAR(32) NOT NULL, sku_id BIGINT UNSIGNED NOT NULL, quantity INT NOT NULL,
    state TINYINT NOT NULL DEFAULT 0, PRIMARY KEY (order_no, sku_id) -- 0 锁定 1 确认 2 释放
) ENGINE=InnoDB;
CREATE TABLE order_outbox (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY, event_id CHAR(36) NOT NULL,
    topic VARCHAR(64) NOT NULL, payload JSON NOT NULL,
    status TINYINT NOT NULL DEFAULT 0, UNIQUE KEY uk_event_id (event_id), KEY idx_status (status, id) -- 0 待投递 1 已投递
) ENGINE=InnoDB;
CREATE TABLE consumed_event (consumer VARCHAR(64) NOT NULL, event_id CHAR(36) NOT NULL, PRIMARY KEY (consumer, event_id)) ENGINE=InnoDB;
```

```text
CREATED ──PAID──> PAID ──SHIP──> SHIPPED ──CONFIRM──> COMPLETED；超时 / 取消 ──> CANCELLED；推进一律 WHERE status = 旧值，RowsAffected = 0 视为幂等成功
```

## 五、下单：同步预扣 + 本地事务 Outbox

```go
// app/order-service/internal/biz/order.go
func (uc *OrderUsecase) Create(ctx context.Context, req *v1.CreateOrderRequest) (*v1.Order, error) {
    if !uc.idem.SetNX(ctx, "order:"+req.IdempotencyKey, 1, 24*time.Hour) {
        return nil, v1.ErrorDuplicateOrder("重复提交")
    }
    if _, err := uc.stock.LockStock(ctx, &productv1.LockStockRequest{
        OrderNo: req.OrderNo, SkuId: req.SkuId, Quantity: req.Quantity,
    }); err != nil {
        return nil, err // 预扣失败直接返回，不落订单
    }
    o := Order{OrderNo: req.OrderNo, UserID: req.UserID, SkuID: req.SkuId, Quantity: req.Quantity,
        Amount: req.Amount, Status: StatusCreated, ExpireAt: time.Now().Add(15 * time.Minute)}
    if err := uc.db.Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(&o).Error; err != nil {
            return err
        }
        return uc.outbox.Append(tx, "order.created", o.OrderNo, OrderCreated{OrderNo: o.OrderNo})
    }); err != nil {
        _ = uc.stock.Release(context.WithoutCancel(ctx), req.OrderNo)
        return nil, err
    }
    return toProto(&o), nil
}
```

`LockStock` 用 `UPDATE stock SET available = available - ?, locked = locked + ? WHERE sku_id = ? AND available >= ?` 并写 `stock_lock(state=0)`，影响行数为 0 就是超卖。本地事务只包订单与 outbox，不包 RPC；relay 用 `WHERE status=0 ORDER BY id LIMIT 200 FOR UPDATE SKIP LOCKED` 扫表，以 `event_id` 作分区键，发送成功再置 1。

## 六、支付回调：幂等消费与状态推进

```go
// app/order-service/internal/consumer/payment.go
func (c *PaymentConsumer) OnPaid(ctx context.Context, evt PaymentSucceeded) error {
    return c.db.Transaction(func(tx *gorm.DB) error {
        err := tx.Create(&ConsumedEvent{Consumer: "order-paid", EventID: evt.EventID}).Error
        if err != nil && !errors.Is(err, gorm.ErrDuplicatedKey) {
            return err // 唯一键冲突 = 重复消息，继续往下走
        }
        res := tx.Model(&Order{}).Where("order_no = ? AND status = ?", evt.OrderNo, StatusCreated).
            Updates(map[string]any{"status": StatusPaid, "version": gorm.Expr("version + 1")})
        if res.Error != nil || res.RowsAffected == 0 {
            return res.Error // 已取消 / 已支付：幂等结束，不再发确认
        }
        return c.outbox.Append(tx, "stock.confirm", evt.OrderNo, StockConfirm{OrderNo: evt.OrderNo})
    })
}
```

`consumed_event` 的唯一键是最后一道幂等闸门；GORM 需开 `TranslateError: true` 才能把 MySQL 1062 映射成 `gorm.ErrDuplicatedKey`。只在内存去重，重启或扩容后必然重复。

## 七、库存确认 / 释放：状态位挡空补偿

```go
// app/product-service/internal/consumer/stock.go
func (c *StockConsumer) handle(ctx context.Context, evt StockEvent, target uint8) error {
    return c.db.Transaction(func(tx *gorm.DB) error {
        err := tx.Create(&ConsumedEvent{Consumer: "stock-" + evt.Type, EventID: evt.EventID}).Error
        if err != nil && !errors.Is(err, gorm.ErrDuplicatedKey) {
            return err
        }
        res := tx.Model(&StockLock{}).Where("order_no = ? AND sku_id = ? AND state = 0", evt.OrderNo, evt.SkuID).
            Update("state", target) // 1 确认出库，2 释放
        if res.Error != nil || res.RowsAffected == 0 {
            return res.Error // 空补偿 / 已处理：什么都不做
        }
        delta := map[string]any{"locked": gorm.Expr("locked - ?", evt.Quantity)}
        if target == 2 {
            delta["available"] = gorm.Expr("available + ?", evt.Quantity)
        } else {
            delta["sold"] = gorm.Expr("sold + ?", evt.Quantity)
        }
        return tx.Model(&Stock{}).Where("sku_id = ?", evt.SkuID).Updates(delta).Error
    })
}
```

状态位 `state = 0` 让同一 `order_no + sku_id` 的确认与释放互斥：重复的释放消息自然变成空操作，**空补偿**（补偿先于原操作）与**悬挂**（原操作后到）都被这个条件连同唯一键挡住。

## 八、超时取消与补偿

```go
// app/order-service/internal/job/cancel.go
func (j *CancelJob) Run(ctx context.Context) {
    var rows []Order
    j.db.WithContext(ctx).Where("status = ? AND expire_at < ?", StatusCreated, time.Now()).
        Order("id").Limit(200).Find(&rows)
    for _, o := range rows {
        _ = j.db.Transaction(func(tx *gorm.DB) error {
            res := tx.Model(&Order{}).Where("order_no = ? AND status = ?", o.OrderNo, StatusCreated).
                Update("status", StatusCancelled)
            if res.RowsAffected == 0 {
                return nil // 已被支付推进，放弃取消（防悬挂）
            }
            return j.outbox.Append(tx, "order.cancelled", o.OrderNo, OrderCancelled{OrderNo: o.OrderNo})
        })
    }
}
```

取消与支付竞态：谁先条件更新成功谁赢，输的一方 `RowsAffected = 0` 安静退出。任务按 `idx_status_expire` 走索引、每批 200 条、可重跑；补偿消息同样走 outbox，不能直接调 RPC。

## 九、RocketMQ 事务消息（Outbox 的替代）

```go
// app/order-service/internal/mq/tx.go
func (l *txListener) ExecuteLocalTransaction(msg *primitive.Message) primitive.LocalTransactionState {
    if err := l.repo.CreateIdempotent(context.Background(), msg.Body); err != nil {
        return primitive.RollbackMessage
    }
    return primitive.CommitMessage
}
func (l *txListener) CheckLocalTransaction(msg *primitive.MessageExt) primitive.LocalTransactionState {
    ok, err := l.repo.ExistsByOrderNo(context.Background(), msg.GetKeys())
    if err != nil {
        return primitive.UnknowState // 查不到就回查，不能猜
    }
    if ok {
        return primitive.CommitMessage
    }
    return primitive.RollbackMessage
}
// p, _ := rocketmq.NewTransactionProducer(listener, producer.WithNameServer(ns)); p.SendMessageInTransaction(ctx, &primitive.Message{Topic: "order-tx", Body: body}, nil)
```

半消息成功后执行本地事务；进程崩溃时 broker 回查，本地事务必须能用 `order_no` 查到结果。它省掉 outbox 表，但换 Kafka 就得改回 Outbox。

## 十、对账与最大努力通知

每日对账：`PAID` 但 `stock_lock.state != 1`、`CANCELLED` 但 `state != 2`、`available + locked + sold` 与初始库存不符，全部生成差异单修复。对第三方（支付、短信、物流）用最大努力通知：本地记录任务、指数退避、有上限、失败进人工队列，并以对方账单为准对账。

## 常见坑

1. **空补偿与悬挂**：取消先于锁定到达会释放不存在的记录，支付成功后又有迟到的取消；用 `state`、`status` 条件更新 + 唯一键一起挡。
2. **重复消费**：没有 `consumed_event` 唯一键，只在内存去重，重启后重复发货。
3. **消息丢失**：先发消息再提交本地事务，事务回滚了消息却已发出；必须 outbox 同事务写入。
4. **先 SELECT 再 UPDATE**：并发下覆盖别人状态；用条件更新看 `RowsAffected`，relay 还要 `SKIP LOCKED`。
5. **只补偿不对账**：补偿失败没人发现；差异必须每日对账兜底。另外 MQ 保留期有限，历史状态以库为准。

## 小结

- 跨服务放弃强一致：本地事务 + Outbox + 至少一次投递 + 幂等消费 + 补偿 + 对账
- TCC 适合精确冻结，Saga 适合长流程，Outbox 是默认解，RocketMQ 事务消息是替代品
- 状态推进只做条件更新；空补偿、悬挂、重复、丢失四类问题都被「唯一键 + 状态位 + 同事务 outbox」覆盖

## 练习

1. 用 `consumed_event` 唯一键改造一个消费者，重放同一批消息验证不会重复扣库存。
2. 把取消任务与支付回调同时触发，观察谁赢，检查库存最终是否守恒；再给 relay 加 `SKIP LOCKED` 验证不重复发送。
