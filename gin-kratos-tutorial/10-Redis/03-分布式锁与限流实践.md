# 03-分布式锁与限流实践

> 一句话定位：锁用 `SET NX PX` + 唯一 token + Lua 释放，语义只是「尽力互斥」，最终防线是幂等；限流用 Redis + Lua 做集群配额，网关与 Kratos 各守一层。

## 本篇目标

- 写完整的加锁、释放、续期，并说清每一步防的是什么
- 讲清主从切换丢锁与 Redlock 争议，给出可落地的工程结论
- 用 Lua 实现令牌桶与滑动窗口，接入 Gin 与 Kratos，并用预扣 + DB 幂等防超卖

## 一、最小可用锁：三个要素

```go
// app/order-service/internal/data/lock.go
type Lock struct {
    rdb           redis.UniversalClient
    key, token    string
    ttl           time.Duration
}

func TryLock(ctx context.Context, rdb redis.UniversalClient, key string, ttl time.Duration) (*Lock, bool, error) {
    token := uuid.NewString() // 每次加锁唯一，用于归属校验
    ok, err := rdb.SetNX(ctx, key, token, ttl).Result()
    if err != nil || !ok { // 取锁失败或已被占用
        return nil, false, err
    }
    return &Lock{rdb: rdb, key: key, token: token, ttl: ttl}, true, nil
}
```

`SetNX(key, val, ttl)` 底层就是 `SET key val NX PX ttl`，一条命令完成「不存在才写 + 设过期」。

| 要素 | 作用 | 写错的后果 |
| --- | --- | --- |
| `NX` | 只有 key 不存在才成功 | 后到者覆盖先到者，锁形同虚设 |
| `PX` | 进程崩溃后自动释放 | 一次 panic 锁死整个商品 |
| 唯一 token | 释放时校验归属 | 业务超时后删掉别人的锁 |

锁粒度取「最小可串行单元」`lock:order:{orderID}`，TTL 取业务 P99 的 2~3 倍并加上下游超时预算。

## 二、安全释放：必须用 Lua

```go
var releaseScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0
`)

func (l *Lock) Unlock(ctx context.Context) (bool, error) {
    n, err := releaseScript.Run(ctx, l.rdb, []string{l.key}, l.token).Int64()
    return n == 1, err // 删除成功才说明锁还属于自己
}
```

不要写成「先 GET 比较、再 DEL」两条命令：中间锁可能过期并被别人持有；Lua 单线程执行，比较与删除不可分割。

## 三、续期与看门狗

```go
var renewScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("PEXPIRE", KEYS[1], ARGV[2])
end
return 0
`)

func (l *Lock) keepAlive(ctx context.Context) {
    ticker := time.NewTicker(l.ttl / 3)
    defer ticker.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-ticker.C:
            n, _ := renewScript.Run(ctx, l.rdb, []string{l.key}, l.token, l.ttl.Milliseconds()).Int64()
            if n == 0 {
                return // 锁已过期或被抢走，立即停止续期
            }
        }
    }
}
```

## 四、丢锁与 Redlock

看门狗只解决「进程活着但业务慢」；进程被 `kill -9` 时续期协程一起消失，只能靠 TTL 兜底，它还会掩盖业务卡死。

主从是**异步复制**：A 在主节点加锁成功，主节点没同步给从节点就宕机，哨兵提升从节点为主，B 立刻能拿到同一把锁。单 Redis 锁的准确语义是「尽力而为的互斥」。

| 做法 | 说明 | 代价 |
| --- | --- | --- |
| 业务幂等 + 唯一约束 | 唯一键/状态机保证重复执行无副作用 | 最推荐，成本最低 |
| fencing token | 加锁返回单调递增序号，下游拒绝旧序号写 | 需要下游配合 |
| Redlock | 向 N 个独立实例过半加锁 | 部署复杂，仍有争议 |

Redlock 的争议来自 Kleppmann《How to do distributed locking》与 antirez 的回应：GC 停顿、时钟漂移下，客户端可能在锁失效后仍以为自己持有锁。**务实结论**：普通业务用单实例锁 + 幂等；只有「误判代价极高且无法幂等」才考虑 Redlock，并写明其假设。

## 五、redsync：多节点锁的现成实现

先 `go get github.com/go-redsync/redsync/v4@latest`（PowerShell 相同），核心用法：

```go
import "github.com/go-redsync/redsync/v4"
import goredis "github.com/go-redsync/redsync/v4/redis/goredis/v9"

rs := redsync.New(goredis.NewPool(rdb))
mutex := rs.NewMutex("mall:lock:order:1001", redsync.WithExpiry(8*time.Second), redsync.WithTries(3))
if err := mutex.LockContext(ctx); err != nil {
    return fmt.Errorf("acquire lock: %w", err)
}
defer func() { _, _ = mutex.UnlockContext(ctx) }() // 临界区：创建订单、扣库存
```

redsync 已实现唯一值、Lua 释放与自动续期；但它同样解决不了主从切换语义，别当强一致锁用。

## 六、限流算法怎么选

| 算法 | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 固定窗口 | `INCR` + `EXPIRE` | 最简单、成本最低 | 窗口边界可双倍放量 | 粗粒度兜底 |
| 滑动窗口 | ZSet 或分桶计数 | 精确、无边界突刺 | 内存随请求增长 | 第三方配额 |
| 令牌桶 | 令牌 + 按时间补充 | 允许容量内突发 | 参数需调 | 网关按用户 |
| 漏桶 | 队列 + 恒定出速 | 输出绝对平滑 | 排队增加延迟 | 下游保护 |

## 七、令牌桶：Redis + Lua 原子实现

```lua
-- KEYS[1]=桶 key  ARGV[1]=rate(个/秒)  ARGV[2]=capacity  ARGV[3]=ttl_ms
local rate, cap, ttl = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3])
local t = redis.call('TIME')
local now = tonumber(t[1]) + tonumber(t[2]) / 1000000
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens')) or cap
local ts = tonumber(redis.call('HGET', KEYS[1], 'ts')) or now
tokens = math.min(cap, tokens + math.max(0, now - ts) * rate)
local allowed = 0
if tokens >= 1 then tokens = tokens - 1; allowed = 1 end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], ttl)
return allowed
```

```go
var tokenBucket = redis.NewScript(tokenBucketLua) // tokenBucketLua 定义在 scripts.go，内容同上

func Allow(ctx context.Context, rdb redis.UniversalClient, key string, rate, burst float64) (bool, error) {
    n, err := tokenBucket.Run(ctx, rdb, []string{key}, rate, burst, 60_000).Int64()
    return n == 1, err
}
```

时间取 Redis 的 `TIME` 而不是客户端时钟，避免多实例时钟漂移导致限流抖动。key 粒度建议 `mall:gw:rate:uid:<uid>`，不要全局一个桶。

## 八、滑动窗口：精确配额

```lua
-- KEYS[1]=窗口 key  ARGV[1]=limit  ARGV[2]=window_ms  ARGV[3]=唯一成员
local limit, window = tonumber(ARGV[1]), tonumber(ARGV[2])
local t = redis.call('TIME')
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now - window)
if redis.call('ZCARD', KEYS[1]) >= limit then return 0 end
redis.call('ZADD', KEYS[1], now, ARGV[3])
redis.call('PEXPIRE', KEYS[1], window)
return 1
```

ZSet 内存随请求数增长，只适合中小流量；百万 QPS 优先令牌桶，或本地限流 + 集群配额。Go 侧同样用 `redis.NewScript` 包装，成员传 `uuid.NewString()`。

## 九、接入 Gin 与 Kratos

```go
func RedisRateLimit(rdb redis.UniversalClient, rate, burst float64) gin.HandlerFunc {
    return func(c *gin.Context) {
        uid := c.GetString("uid")
        ok, err := limiter.Allow(c.Request.Context(), rdb, "mall:gw:rate:uid:"+uid, rate, burst)
        if err != nil {
            return // 依赖不可用：fail-open，同时打点告警
        }
        if !ok {
            c.AbortWithStatusJSON(http.StatusTooManyRequests, gin.H{"code": 42901, "message": "too many requests"})
        }
    }
}
```

Kratos 侧在 `grpc.NewServer(..., grpc.Middleware(recovery.Recovery(), logging.Server(logger), sentinelGRPC()))` 里注入：`sentinelGRPC()` 用 `sentinel.Entry("grpc:"+info.Operation(), sentinel.WithTrafficType(base.Inbound))` + `defer e.Exit()`，被限流返回 `kerrors.New(429, "RATE_LIMITED", ...)`。分层原则：APISIX 做入口级 `limit-count`/`limit-req`（见 [13-企业级实战/05-APISIX网关鉴权与限流](../13-企业级实战/05-APISIX网关鉴权与限流.md)），Gin 做用户级配额，Kratos Sentinel 做实例级兜底，三层阈值从外到内递减。

## 十、幂等与预扣库存

预扣脚本与第 01 篇第五节 `stockScript` 相同，`Run` 返回 `-1`（未预热）、`0`（不足）、剩余库存。预扣成功后立即落库，`Create` 失败必须 `INCRBY` 回补，否则 Redis 与 DB 永久对不上。配套：订单号建唯一索引，消费者重复扣 DB 库存时被幂等拦截（见 [13-企业级实战/04-订单服务与下单主链路](../13-企业级实战/04-订单服务与下单主链路.md)）；定时对账比对 Redis 预扣、DB 库存与订单；Redis 丢失后从 DB 重建库存 key。

## 常见坑

1. **释放时删了别人的锁**：token 用固定值或 `time.Now()`，必须每次 `uuid.NewString()`。
2. **只 `SETNX` 不设过期**：进程 crash 后锁永久存在，只能人工删 key。
3. **锁 TTL 短于业务耗时**：两个请求同时进临界区，看门狗没开或已退出。
4. **把 Redis 锁当强一致**：主从切换窗口内可能双持有，核心交易必须有 DB 幂等兜底。
5. **限流 key 全局一个**：一个用户打满全站不可用，必须按 uid/IP/租户分桶；依赖故障时应 fail-open 并告警。

## 小结

- 锁 = `SET NX PX` + 唯一 token + Lua 释放；续期只解决业务慢，不解决进程死
- 单实例锁是「尽力互斥」，幂等与唯一约束才是最终防线，Redlock 谨慎使用
- 令牌桶适合网关按用户限流，滑动窗口适合精确配额；库存用 Lua 预扣换性能，用 DB + 唯一键 + 对账换正确性

## 练习

1. 用 `SET NX PX` 写带看门狗的锁，要求 ctx 取消时续期协程退出，并用并发测试验证互斥。
2. 给 Gin 加按 IP 限流的中间件，断开 Redis 后验证请求仍能通过（fail-open）。
3. 200 个并发请求抢 10 件库存，验证只有 10 单成功，并补上落库失败的回补逻辑。
