# 02-缓存模式与三大经典问题

> 一句话定位：Cache-Aside 是默认解；穿透用空值 + 布隆、击穿用 singleflight / 逻辑过期、雪崩用 TTL 抖动 + 多级 + 限流，一致性用「先更库再删缓存」。

## 本篇目标

- 分别给出穿透、击穿、雪崩的可落地方案，并能讲出各自的成本

- 掌握「先更库再删缓存 → 延迟双删 → binlog 订阅」的取舍，并做预热与降级

## 一、四种缓存模式

| 模式 | 读路径 | 写路径 | 优点 | 代价 | 适用 |
| --- | --- | --- | --- | --- | --- |
| Cache-Aside | 先查缓存，未命中回源并回填 | 更新 DB 后删缓存 | 简单、可控 | 应用自己管一致性 | 90% 业务 |
| Read-Through | 缓存层代理回源 | 同上 | 业务代码干净 | 需要缓存框架支持 | 中间件封装完善时 |
| Write-Through | 先查缓存，未命中回源 | 同步写缓存与 DB | 缓存始终较新 | 写延迟高、写放大 | 读多写少且强依赖缓存 |
| Write-Behind | 先查缓存，未命中回源 | 只写缓存，异步刷 DB | 写极快、可合并 | 宕机丢数据、实现复杂 | 计数、点赞、浏览数 |

Go 没有统一的 Read-Through 框架，实际做法是 data 层封装 `GetOrLoad(ctx, key, loader)`；Write-Behind 一般借 Kafka 异步落库（见 [11-消息队列/04-可靠投递-幂等-顺序消息](../11-消息队列/04-可靠投递-幂等-顺序消息.md)）。Cache-Aside 的要点只有两句：**读回填带 TTL，写只删缓存不改缓存**。

## 二、TTL 必须加随机抖动

10 万个商品在 0 点统一预热、统一 30 分钟过期，30 分钟后会在同一秒集体失效，DB 瞬间被打穿。

```go
func jitterTTL(base time.Duration) time.Duration {
    delta := base / 5 // 在 [base, base*1.2) 内随机
    return base + time.Duration(rand.Int63n(int64(delta)))
}
```

| 场景 | 建议 TTL |
| --- | --- |
| 商品详情（变化慢） | 10~30 分钟 + 抖动 |
| 库存展示（变化快） | 5~30 秒，或只缓存「有货/无货」 |
| 空值标记 | 30~60 秒，防止新上架商品长期不可见 |
| 用户会话 | 与 token 有效期一致 |

## 三、缓存穿透：查不存在的数据

攻击者用 `id=-1`、随机 UUID 疯狂请求，缓存永远不命中，全部打到 MySQL。

```go
func (r *productRepo) loadAndFill(ctx context.Context, id int64, key string) (*biz.Product, error) {
    var row model.Product
    switch err := r.data.db.WithContext(ctx).First(&row, id).Error; {
    case errors.Is(err, gorm.ErrRecordNotFound):
        _ = r.data.rdb.Set(ctx, key, nullMark, 60*time.Second).Err() // 空值短缓存
        return nil, biz.ErrProductNotFound
    case err != nil:
        return nil, err
    }
    p := toBiz(&row)
    body, _ := json.Marshal(p)
    _ = r.data.rdb.Set(ctx, key, body, jitterTTL(30*time.Minute)).Err()
    return p, nil
}
```

**布隆过滤器前置拦截**（需要 RedisBloom，Redis Stack 自带）：

```go
func (r *productRepo) warmBloom(ctx context.Context, ids []int64) error {
    if err := r.data.rdb.BFReserve(ctx, "mall:prod:bloom", 0.01, 10_000_000).Err(); err != nil {
        return err
    }
    for _, id := range ids {
        _ = r.data.rdb.BFAdd(ctx, "mall:prod:bloom", strconv.FormatInt(id, 10)).Err()
    }
    return nil
}

func (r *productRepo) mayExist(ctx context.Context, id int64) bool {
    ok, err := r.data.rdb.BFExists(ctx, "mall:prod:bloom", strconv.FormatInt(id, 10)).Result()
    return err != nil || ok // 布隆不可用时放行，交给缓存与 DB
}
```

判定「不存在」直接返回 404；判定「存在」仍有误判率，要继续查缓存/DB。布隆不支持删除，用定期重建解决。

## 四、缓存击穿：单个热点 key 失效

爆款商品缓存过期的瞬间，上万请求同时回源。三种解法：

- **singleflight**：同进程内同一 key 只有一个请求真正回源，其余等待结果（完整代码见下）
- **逻辑过期**：value 里存 `expireAt`，物理 TTL 很长；读到逻辑过期先返回旧值，由抢到 `SetNX(key+":rebuild")` 的协程异步重建，牺牲新鲜度换稳定
- **分布式互斥重建**：跨实例用 `SET NX PX` 锁控制回源，见 [03-分布式锁与限流实践](03-分布式锁与限流实践.md)

代价对比：singleflight 实现最轻但不跨进程；逻辑过期无阻塞、容忍旧值；互斥锁最严格，但要处理锁超时与误删。

## 五、缓存雪崩：大面积同时失效

| 手段 | 说明 | 代价 |
| --- | --- | --- |
| TTL 抖动 | 避免同时过期 | 几乎为零 |
| 多级缓存 | 进程内 bigcache/ristretto + Redis | 一致性窗口变长 |
| 熔断降级 | Redis 错误率高时切「直查 DB + 限流」 | 需要降级开关 |
| 回源限流 | 并发信号量保护 DB | 部分请求拿到兜底页 |

```go
var dbGuard = make(chan struct{}, 50) // 单实例最多 50 个并发回源

func (r *productRepo) loadWithGuard(ctx context.Context, id int64) (*biz.Product, error) {
    select {
    case dbGuard <- struct{}{}:
        defer func() { <-dbGuard }()
    case <-ctx.Done():
        return nil, ctx.Err()
    }
    return r.loadAndFill(ctx, id, productKey(id))
}
```

## 六、缓存与 MySQL 的一致性

结论：**缓存与数据库不追求强一致，只追求「最终一致 + 不一致窗口足够短」**。订单、库存以 DB 为准，不拿缓存当账本。

```go
func (r *productRepo) UpdatePrice(ctx context.Context, id, price int64) error {
    if err := r.data.db.WithContext(ctx).Model(&model.Product{}).
        Where("id = ?", id).Update("price", price).Error; err != nil {
        return err
    }
    return r.data.rdb.Del(ctx, productKey(id)).Err() // 删，不改
}
```

演进路径按需选一种：

1. **先更库再删缓存**：成本最低，并发窗口极小，90% 场景够用
2. **延迟双删**：更新 DB → 删缓存 → 500ms 后再删一次，清理「更新前读旧值、更新后回填」的脏数据；延迟要大于一次「读 DB + 回填」，只能降低概率
3. **binlog 订阅**：Canal / Debezium 订阅 MySQL binlog，投递 Kafka 后由消费者删缓存；业务零侵入、顺序可靠，代价是多一套组件与几十到几百毫秒延迟

## 七、预热与降级

```go
func (r *productRepo) WarmUp(ctx context.Context, topN int) error {
    ids, err := r.topHotIDs(ctx, topN)
    if err != nil {
        return err
    }
    for _, id := range ids {
        if _, err := r.Detail(context.WithoutCancel(ctx), id); err != nil {
            r.data.log.Warn("warmup failed", zap.Int64("id", id), zap.Error(err))
        }
    }
    return nil
}
```

降级写进代码而不是应急预案：Redis 超时直查 DB 并上报 `cache_error_total`；DB 压力过大时返回本地旧值或「稍后再试」；详情页允许价格短暂延迟时要在产品上明示。

## 完整示例

`app/product-service/internal/data/product_cache.go`：空值缓存 + TTL 抖动 + singleflight + 故障降级。

```go
// app/product-service/internal/data/product_cache.go
const nullMark = "1"

type productCache struct {
    data *Data
    sf   singleflight.Group
}

func (c *productCache) GetDetail(ctx context.Context, id int64) (*biz.Product, error) {
    key := productKey(id)
    raw, err := c.data.rdb.Get(ctx, key).Bytes()
    switch {
    case err == nil && string(raw) == nullMark:
        return nil, biz.ErrProductNotFound
    case err == nil:
        return decodeProduct(raw)
    case !errors.Is(err, redis.Nil):
        c.data.cacheErrors.Inc() // Redis 故障：降级直查 DB
        return c.fromDB(ctx, id)
    }
    ch := c.sf.DoChan(key, func() (any, error) {
        loadCtx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 2*time.Second)
        defer cancel()
        return c.loadAndStore(loadCtx, id, key)
    })
    select {
    case <-ctx.Done():
        return nil, ctx.Err()
    case res := <-ch:
        if res.Err != nil {
            return nil, res.Err
        }
        return res.Val.(*biz.Product), nil
    }
}
```
`loadAndStore` 就是第三节的 `loadAndFill`：未命中缓存空值 60 秒，命中则 JSON 序列化后写入 `jitterTTL(30*time.Minute)`。两个细节决定它能不能上线：

- 用 `DoChan` + `select` 才尊重请求超时，直接 `Do` 会被慢请求拖住
- 回源用 `context.WithoutCancel` 并重新设超时，避免首个请求取消导致所有等待者失败；空值标记用不会与 JSON 冲突的字符串，且必须短 TTL

## 常见坑

1. **更新时改缓存而不是删缓存**：并发写把旧值写回，问题极难复现。
2. **先删缓存再更新 DB**：删除后、更新前的读请求会把旧值回填，脏窗口更长。
3. **空值不设短 TTL**：一次误缓存「不存在」让新上架商品一小时不可见。
4. **所有 key 同一 TTL、同一时刻预热**：整点集体失效，DB 直接被雪崩。
5. **用 `singleflight.Do` 不处理 context**：首请求取消，所有等待者一起失败。

## 小结

- Cache-Aside 是默认解：读回填、写删缓存、TTL 加抖动
- 穿透靠布隆 + 空值短缓存，击穿靠 singleflight / 逻辑过期，雪崩靠抖动 + 多级 + 限流
- 一致性优先「先更库再删缓存」，再上 binlog；缓存不是账本，交易链路以 MySQL 为准
