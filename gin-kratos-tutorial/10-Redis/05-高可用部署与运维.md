# 05-高可用部署与运维

> 一句话定位：主从解决副本、哨兵解决自动切换、Cluster 解决容量；高可用真正落地靠「指标 + 容量规划 + 演练过的备份」。

## 本篇目标

- 说清主从、哨兵、Cluster 的原理、切换代价与选型边界
- 掌握 Cluster 的 slot 机制与多 key / 事务 / Lua 限制
- 在 RDB 与 AOF 之间取舍，会看命中率、内存、连接、淘汰、主从延迟，能完成扩容、备份恢复与演练

## 前置知识

- 已读 [01-go-redis 接入与连接池](01-go-redis接入与连接池.md)，了解 Redis 单机启动与 `redis.conf`，会用 Docker 与 `redis-cli`

## 一、三种形态怎么选

| 形态 | 解决什么 | 容量上限 | 切换 | 适用 |
| --- | --- | --- | --- | --- |
| 主从 | 读扩展、数据副本 | 单机内存 | 手动 | 读多写少、能接受人工切 |
| 哨兵 | 自动故障转移 | 单机内存 | 秒级自动 | 中小规模、单点容量够 |
| Cluster | 分片扩容 | 多机内存之和 | 秒级自动 | 数据量大、QPS 高 |

三者都不保证强一致：异步复制下切换必然可能丢最后一段写，核心数据仍以 MySQL 为准。

## 二、主从复制

从节点只需 `replicaof 10.0.0.10 6379` + `masterauth`，再设 `repl-backlog-size 64mb`、`min-replicas-to-write 1`、`min-replicas-max-lag 10`。从节点先全量同步（`PSYNC` → `BGSAVE` 生成 RDB + 缓冲增量），之后持续接收命令流。`master_repl_offset - slave_repl_offset` 就是从节点落后的字节数。`min-replicas-to-write` 让主节点在副本失联时拒绝写入，用可用性换更低丢数据风险；强一致读仍走主节点。

## 三、Sentinel：自动故障转移

`sentinel.conf` 关键项：`sentinel monitor mallmaster <ip> 6379 2`、`down-after-milliseconds 5000`、`failover-timeout 60000`，3 个节点各一份。哨兵负责监控、主观/客观下线、选主与通知客户端。客户端按模式创建：

```go
// app/product-service/internal/data/redis.go
func NewRedis(cfg config.RedisConfig) redis.UniversalClient {
    switch cfg.Mode {
    case "cluster":
        return redis.NewClusterClient(&redis.ClusterOptions{
            Addrs: cfg.ClusterAddrs, Password: cfg.Password,
            PoolSize: cfg.PoolSize / len(cfg.ClusterAddrs), ReadTimeout: cfg.ReadTimeout, RouteByLatency: true,
        })
    case "sentinel":
        return redis.NewFailoverClient(&redis.FailoverOptions{
            MasterName: cfg.MasterName, SentinelAddrs: cfg.SentinelAddrs,
            Password: cfg.Password, DB: cfg.DB, PoolSize: cfg.PoolSize,
        })
    default:
        return redis.NewClient(&redis.Options{Addr: cfg.Addr, Password: cfg.Password, DB: cfg.DB})
    }
}
```

哨兵数量 ≥3 且为奇数，`quorum` 取 `n/2+1`。切换期间有秒级不可用，客户端必须配超时与重试，K8s 探针不要因此直接重启 Pod。

## 四、Cluster：分片与限制

Cluster 把 key 按 `CRC16(key) % 16384` 映射到 16384 个 slot，每个主节点负责一部分，从节点做副本，最少 3 主。

```bash
redis-cli --cluster create 10.0.1.1:6379 10.0.1.2:6379 10.0.1.3:6379 \
  10.0.1.4:6379 10.0.1.5:6379 10.0.1.6:6379 --cluster-replicas 1
```

| 限制 | 表现 | 应对 |
| --- | --- | --- |
| 多 key 跨 slot | `CROSSSLOT Keys in request don't hash to the same slot` | 用 hash tag `{sku:1001}:stock` |
| 事务 / Lua 跨 slot | `EXECABORT` / 脚本报错 | 所有 key 同 tag |
| 不支持 `SELECT DB` | 只能 DB 0 | 用 key 前缀隔离环境 |
| 扩容迁移 slot | 期间出现 `MOVED`/`ASK` | go-redis 已内置重定向处理 |

## 五、持久化：RDB 与 AOF

| 方案 | 原理 | 优点 | 缺点 | 丢失窗口 |
| --- | --- | --- | --- | --- |
| RDB | 定时 fork 生成快照 | 文件小、恢复快 | 崩溃丢最后一次快照后的数据 | 取决于 `save`，可能几分钟 |
| AOF | 追加写命令日志 | 丢数据少、可读 | 文件大、恢复慢、写放大 | `everysec` 约 1 秒 |
| 混合 | AOF 重写时用 RDB 前导 | 恢复快且丢得少 | 配置稍复杂 | 约 1 秒 |

纯缓存可以只开 RDB；「丢了要赔钱」的数据开 AOF `everysec`（`appendfsync everysec` + `aof-use-rdb-preamble yes`）+ 主从 + 定期备份，关键数据仍以 MySQL 为准。`appendfsync always` 会把写性能打到地板上，只在极端场景用。

## 六、内存与淘汰

```bash
redis-cli CONFIG SET maxmemory 8gb
redis-cli CONFIG SET maxmemory-policy allkeys-lfu
```

淘汰策略的行为与适用场景见 [04-数据结构选型与热点Key治理](04-数据结构选型与热点Key治理.md) 第十一节。`maxmemory` 设为物理内存 70% 左右，且必须小于容器 limit；fork 做 RDB/AOF 重写时 RSS 可能接近 2 倍，预留不足会触发 OOM Killer。

## 七、监控：慢查询、连接、命中率

| 指标 | 来源 | 告警建议 |
| --- | --- | --- |
| 命中率 | `keyspace_hits/(hits+misses)` | <80% 关注，<60% 告警 |
| 内存使用 | `used_memory / maxmemory` | >80% 预警 |
| 连接数 | `connected_clients` | 超过 `maxclients` 80% 告警 |
| 淘汰 key | `evicted_keys` | 持续增长说明容量不足 |
| 慢日志 | `SLOWLOG GET 10` | 阈值 `slowlog-log-slower-than 10000` |
| 主从延迟 | `master_repl_offset` 差值 | 超几 MB 或 `master_link_status:down` |

生产接 `redis_exporter` + Prometheus + Grafana（见 [08-部署与运维/05-可观测运维与告警](../08-部署与运维/05-可观测运维与告警.md)），`INFO memory` / `INFO stats` / `INFO replication` / `SLOWLOG GET 10` 是排查入口；Gateway 的 `/readyz` 只做轻量 `Ping`：

```go
func RedisReady(rdb redis.UniversalClient) gin.HandlerFunc {
    return func(c *gin.Context) {
        ctx, cancel := context.WithTimeout(c.Request.Context(), 300*time.Millisecond)
        defer cancel()
        if err := rdb.Ping(ctx).Err(); err != nil {
            c.JSON(http.StatusServiceUnavailable, gin.H{"code": 50302, "message": "redis unavailable"})
            return
        }
        c.JSON(http.StatusOK, gin.H{"code": 0, "message": "ok"})
    }
}
```

## 八、扩容与槽迁移

```bash
redis-cli --cluster add-node 10.0.1.7:6379 10.0.1.1:6379
redis-cli --cluster add-node 10.0.1.8:6379 10.0.1.1:6379 --cluster-slave --cluster-master-id <new-master-id>
redis-cli --cluster reshard 10.0.1.1:6379 --cluster-from <src-id> --cluster-to <new-master-id> \
  --cluster-slots 1000 --cluster-yes
redis-cli --cluster check 10.0.1.1:6379
```

迁移期间单 key 有很短阻塞，务必低峰执行并观察 P99；`cluster-node-timeout` 太小会误判下线，太大则切换慢，通常 10~15 秒。

## 九、备份与恢复

```bash
redis-cli -h 10.0.0.10 -p 6379 BGSAVE
redis-cli -h 10.0.0.10 -p 6379 --rdb ./backup-20261125.rdb
redis-cli -h 10.0.0.10 -p 6379 CONFIG GET dir
```

```go
func TriggerBackup(ctx context.Context, rdb redis.UniversalClient) (int64, error) {
    if err := rdb.BGSave(ctx).Err(); err != nil {
        return 0, err
    }
    return rdb.LastSave(ctx).Result() // 上一次成功落盘的时间戳
}
```

恢复流程：停目标实例并确认 `dir`/`dbfilename` → 替换 `dump.rdb`（开 AOF 时同步处理 `appendonly.aof` 与 manifest）→ 启动后 `DBSIZE` + 抽样校验 → 业务验收（详情可读、库存 key 存在、锁 key 无脏值）。没有演练过的备份等于没有备份，至少每季度从备份拉起一次实例。

## 十、安全：ACL、TLS 与危险命令

```bash
redis-cli ACL SETUSER mall_app on '>StrongPassw0rd' '~mall:*' '+@read' '+@write' '-@dangerous'
```

```text
# redis.conf
tls-port 6380
tls-cert-file /etc/redis/tls/redis.crt
tls-key-file /etc/redis/tls/redis.key
rename-command FLUSHALL ""
rename-command CONFIG ""
```

应用账号只授权业务前缀，禁 `FLUSHALL`、`KEYS`、`CONFIG`、`DEBUG`；`rename-command` 需重启生效，能用 ACL 就用 ACL。跨网络访问必开 TLS，go-redis 用 `TLSConfig` 配置，密码与证书走 Secret 注入。

## 十一、K8s 与云托管注意点

- 用 StatefulSet + headless Service + PVC，禁止 `emptyDir` 存数据
- Pod 反亲和打散主从；readiness 用 `redis-cli ping`，liveness 不要太激进
- Cluster 的 `cluster-announce-ip` 必须是可达地址，否则客户端拿到不可达 IP
- 云托管注意「代理模式 vs 直连模式」：代理模式不支持部分多 key 命令与事务
- 不要与业务 Pod 混部抢 CPU，fork 期间 CPU 抖动会放大延迟

## 十二、故障演练

演练项：主节点 `kill -9` 观察哨兵切换耗时与客户端报错；切断主从网络制造脑裂；打满磁盘让 `BGSAVE` 失败；灌数据触发 `evicted_keys`；低峰做一次 slot 迁移。

```go
// cmd/redis-probe/main.go：切换后验证可写，并打印 Cluster 拓扑
func WaitWritable(ctx context.Context, rdb redis.UniversalClient, timeout time.Duration) error {
    deadline := time.Now().Add(timeout)
    for {
        cctx, cancel := context.WithTimeout(ctx, 500*time.Millisecond)
        err := rdb.Set(cctx, "mall:ops:probe", time.Now().Unix(), 30*time.Second).Err()
        cancel()
        if err == nil {
            return nil
        }
        if time.Now().After(deadline) {
            return fmt.Errorf("redis not writable: %w", err)
        }
        time.Sleep(500 * time.Millisecond)
    }
}
```

## 常见坑

1. **以为主从切换不丢数据**：异步复制下最后一段写必然可能丢，核心数据以 MySQL 为准。
2. **Cluster 里 `MGET` 不带 hash tag**：线上直接 `CROSSSLOT`。
3. **AOF `appendfsync no` 却宣称不丢数据**：OS 缓冲可能丢 30 秒。
4. **`maxmemory` 不设或等于物理内存**：触发 OOM Killer，Redis 被系统杀掉。
5. **只看 `used_memory` 不看 `evicted_keys`**：缓存已被大面积淘汰，命中率暴跌却无人知。
6. **哨兵只部署一个**：主节点挂了没人投票，自动切换形同虚设。
7. **备份不校验**：文件损坏或 AOF 不完整，故障时才发现恢复不了。

## 小结

- 主从解决副本、哨兵解决切换、Cluster 解决容量，都不保证强一致
- Cluster 的一切限制都源自 slot：多 key、事务、Lua 必须同 tag
- 纯缓存可只开 RDB，关键数据 AOF `everysec` + 备份；运维核心是「指标 + 演练」
