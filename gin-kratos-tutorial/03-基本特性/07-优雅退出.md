# 优雅退出

> 一句话定位：优雅退出 = 摘流 → 停止接收新请求 → 排空在途请求 → 按序释放资源；Gin 不处理信号，标准做法是 `signal.NotifyContext` + `http.Server.Shutdown` + 超时兜底。

## 本篇目标

- 理解直接 kill 进程与优雅退出的差别，明确要解决的三件事。
- 用 `signal.NotifyContext` 接管 `SIGINT` / `SIGTERM`，不手写 signal channel。
- 用 `http.Server.Shutdown(ctx)` 排空在途请求，超时后 `Close()` 兜底。
- 按序停止 Kafka 消费者、关闭 Redis 与数据库，并让 `/readyz`、`preStop`、宽限期互相配合。

## 一、优雅退出要解决什么

直接终止进程会导致：在途请求被切断、事务提交一半、日志与 Trace 丢失、注册中心还没摘除实例。所以要同时做到：

1. 停止接收新连接与新请求。
2. 给在途请求留出完成时间。
3. 按依赖顺序释放资源。

容器里还有一个前提：PID 1 必须能收到信号。Dockerfile 用 exec 形式启动，别用 `sh -c` 包一层，否则 `SIGTERM` 可能被吞掉。

## 二、signal.NotifyContext：一行接管信号

```go
// app/gateway/cmd/main.go（片段）
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()
<-ctx.Done() // 信号到达后 ctx 取消，继续走退出流程
```

- Windows 下 `Ctrl+C` 发的是 `os.Interrupt`；`syscall.SIGTERM` 在 Windows 无效但可编译。
- 不要在多个 goroutine 里各自 `signal.Notify`，重复触发会让退出流程执行多次；`SIGHUP` 留给配置热更新。

## 三、Shutdown：排空请求与超时兜底

`http.Server.Shutdown(ctx)` 会关闭监听套接字、等待活跃连接空闲，但**不会**关闭 hijack 的连接（WebSocket 等），这部分要业务自己通知断开。

- `ListenAndServe` 正常关闭返回 `http.ErrServerClosed`，必须用 `errors.Is` 排除；Shutdown 的 `ctx` 要重新创建，不能复用已取消的信号 `ctx`。
- `Shutdown(ctx)` 超时仍报错时用 `srv.Close()` 兜底，避免进程卡死；完整接线见下方「完整示例」。

### 在途请求与健康检查配合

`/healthz`（liveness）只表示进程活着，退出期间仍返回 200，否则容器会被重启；`/readyz`（readiness）读 `atomic.Bool`，收到信号后立即返回 503，让 Service 摘流（实现见下方完整示例）。

不要用 liveness 检查数据库：数据库抖动会让容器反复重启，放大故障。依赖检查放 readiness。

## 四、资源释放顺序

顺序错了比不退出更糟：先关 DB，在途请求会成批 500。推荐顺序：

```text
摘流（not ready）→ Shutdown 排空在途 → 停 Kafka → flush 日志/Trace → 关 Redis/DB → 退出
```

Kafka 消费者必须显式关闭：sarama 的 `ConsumerGroup.Close()` 会触发 rebalance 并阻塞到当前消息处理完，不关就退出会重复消费：

```go
// app/gateway/internal/lifecycle/close.go
type Consumer interface{ Close() error }

func CloseAll(consumer Consumer, rdb *redis.Client, db *sql.DB) {
    if consumer != nil {
        if err := consumer.Close(); err != nil {
            log.Printf("close kafka consumer: %v", err)
        }
    }
    if rdb != nil {
        _ = rdb.Close()
    }
    if db != nil {
        _ = db.Close() // 等待使用中的连接归还，必须在请求排空之后
    }
}
```

## 五、K8s 的 preStop 与宽限期

删除 Pod 的顺序：进入 `Terminating` → 从 Endpoints 摘除（异步）→ 执行 `preStop` → 发 `SIGTERM` → 等待 `terminationGracePeriodSeconds` → `SIGKILL`。

```yaml
# deploy/k8s/gateway-deployment.yaml
spec:
  terminationGracePeriodSeconds: 40 # preStop 5s + Shutdown 20s + 收尾 5s + 缓冲 10s
  containers:
    - name: gateway
      readinessProbe:
        httpGet: { path: /readyz, port: 8080 }
      lifecycle:
        preStop:
          exec:
            command: ["/bin/sh", "-c", "sleep 5"] # 等 kube-proxy/Ingress 停止转发
```

## 完整示例

`app/gateway/cmd/main.go`（`CloseAll` 见上节；真实项目传入已初始化的实例）：

```go
package main

import (
    "context"
    "errors"
    "log"
    "net/http"
    "os/signal"
    "sync/atomic"
    "syscall"
    "time"

    "github.com/gin-gonic/gin"
    "mall-lite/app/gateway/internal/lifecycle"
)

func main() {
    r := gin.New()
    r.Use(gin.Logger(), gin.Recovery())

    var ready atomic.Bool
    ready.Store(true)
    r.GET("/healthz", func(c *gin.Context) { c.String(http.StatusOK, "ok") })
    r.GET("/readyz", readiness(&ready))
    r.GET("/slow", func(c *gin.Context) {
        time.Sleep(3 * time.Second) // 模拟慢请求，验证退出时会被等待
        c.JSON(http.StatusOK, gin.H{"code": 0})
    })

    srv := &http.Server{Addr: ":8080", Handler: r, ReadHeaderTimeout: 5 * time.Second}
    go func() {
        if err := srv.ListenAndServe(); err != nil && !errors.Is(err, http.ErrServerClosed) {
            log.Fatalf("listen: %v", err)
        }
    }()

    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()
    <-ctx.Done()
    ready.Store(false) // 先摘流

    shutCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutCtx); err != nil {
        log.Printf("shutdown timeout: %v", err)
        _ = srv.Close()
    }

    lifecycle.CloseAll(nil, nil, nil) // 换成 consumer / redis / sql.DB
    log.Println("exit cleanly")
}

func readiness(ready *atomic.Bool) gin.HandlerFunc {
    return func(c *gin.Context) {
        if !ready.Load() {
            c.String(http.StatusServiceUnavailable, "draining")
            return
        }
        c.String(http.StatusOK, "ready")
    }
}
```

验证：先启动服务，另开终端请求 `/slow`，再 `Ctrl+C`；应看到 `/slow` 正常返回 200，随后日志打印 `exit cleanly`。

```powershell
go run ./app/gateway/cmd
curl.exe -i http://127.0.0.1:8080/slow   # 另一个窗口
```

```bash
go run ./app/gateway/cmd
curl -i http://127.0.0.1:8080/slow &
kill -TERM <服务PID>
```

## 常见坑

1. **用 `r.Run()` 就以为有优雅退出**：`r.Run` 内部直接 `ListenAndServe`，被杀即断；必须自己管 `http.Server`。
2. **Shutdown 复用了已取消的信号 ctx**：秒超时，等于直接关闭；要新建 `context.WithTimeout`。
3. **不判断 `http.ErrServerClosed`**：正常退出被当成启动失败，告警误报。
4. **先关 DB/Redis 再 Shutdown**：在途请求全部 500；顺序必须反过来。
5. **宽限期小于总预算**：还没排空就 `SIGKILL`，优雅退出形同虚设。
6. **没有 `preStop`**：Endpoints 摘除有延迟，退出瞬间仍有新流量打进来。
7. **`Close()` 无限阻塞**：消费者 rebalance 卡住会拖死退出；每个步骤都要有上限。
8. **liveness 在退出期间失败**：容器被重启，退出流程前功尽弃；摘流只改 readiness。

## 小结

- 优雅退出 = 摘流 → 排空 → 停消费者 → 关缓存/数据库，Gin 需要自己接管 `http.Server`。
- `signal.NotifyContext` 接管信号，`Shutdown(ctx)` 排空，超时后 `Close()` 兜底。
- readiness 收到信号后立刻失败，liveness 保持健康。
- `terminationGracePeriodSeconds` 必须覆盖 `preStop + Shutdown + 收尾`。
