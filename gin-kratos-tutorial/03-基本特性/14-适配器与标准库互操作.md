# 适配器与标准库互操作

> 一句话定位：Gin 的 `*gin.Engine` 本身就是 `http.Handler`，所以「Gin 挂到老 mux 下」和「标准库 handler 挂进 Gin」都是一行代码的事；真正要小心的是中间件语义、`ResponseWriter` 能力与 `Abort` 屏障。

## 本篇目标

- 说清 `gin.Engine`、`gin.Context`、`http.Handler` 三者的关系。
- 会把 Gin 服务挂到已有 `http.ServeMux` 下，实现渐进迁移或共存。
- 会用 `gin.WrapH` / `gin.WrapF` 把标准库 handler 与中间件接入 Gin。
- 掌握两种适配方向的边界：中间件顺序、`Abort`、`Flusher`/`Hijacker`。
- 知道 SSE、WebSocket 这类需要 `Hijack`/`Flush` 的场景如何落地。

- [Engine 详解与启动参数](../02-Gin入门/05-Engine详解与启动参数.md)

## 一、三者的关系

```text
http.Handler           接口：ServeHTTP(ResponseWriter, *Request)
  └── *gin.Engine       实现该接口 → 可以当 http.Server.Handler、可以注册进 ServeMux
        └── *gin.Context 每个请求一个（池化），包装了 Writer + Request + Params + 中间件索引
```

`gin.Context` 不是 `http.Handler`，也不能脱离 Gin 使用；它只是「一次请求的执行上下文」。所以适配方向只有两个：

- 外 → 内：`gin.WrapH(h)`，把一个 `http.Handler` 变成 `gin.HandlerFunc`。
- 内 → 外：`*gin.Engine` 直接当 `http.Handler` 用，`mux.Handle("/api/", r)`。

## 二、把 Gin 挂到 http.ServeMux 下

老项目已经有一个 `ServeMux`（可能挂着 pprof、metrics、静态页），想逐步把接口迁到 Gin：

```go
// cmd/legacy/main.go
mux := http.NewServeMux()
mux.HandleFunc("/healthz", func(w http.ResponseWriter, r *http.Request) {
    w.Write([]byte("ok"))
})
mux.Handle("/debug/pprof/", http.DefaultServeMux) // 复用标准库 pprof

r := gin.New()
r.Use(gin.Recovery())
r.GET("/v1/users/:id", func(c *gin.Context) {
    c.JSON(http.StatusOK, gin.H{"code": 0, "data": c.Param("id")})
})
mux.Handle("/api/", http.StripPrefix("/api", r)) // 关键：剥掉前缀再交给 Gin

srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 3 * time.Second}
log.Fatal(srv.ListenAndServe())
```

注意 `http.StripPrefix`：Gin 路由里写的是 `/v1/users/:id`，若不加 StripPrefix，请求路径仍带 `/api`，会 404。也可以不用 StripPrefix，把 Gin 的路由都写成 `/api/v1/...`。

如果整个服务都归 Gin 管，但想保留若干标准库路径，用 `NoRoute` 兜底更顺：

```go
r := gin.New()
r.GET("/v1/ping", func(c *gin.Context) { c.String(http.StatusOK, "pong") })

legacy := http.NewServeMux()
legacy.HandleFunc("/legacy/report", reportHandler)
r.NoRoute(gin.WrapH(legacy)) // 未命中 Gin 路由时交给老 mux
```

## 三、把标准库 handler 挂进 Gin

`gin.WrapH` 用于 `http.Handler`，`gin.WrapF` 用于 `func(http.ResponseWriter, *http.Request)`：

```go
r := gin.New()

// 静态文件：标准库 FileServer
r.Any("/static/*filepath", gin.WrapH(http.FileServer(http.Dir("./public"))))

// 单个函数
r.GET("/metrics", gin.WrapF(func(w http.ResponseWriter, req *http.Request) {
    w.Header().Set("Content-Type", "text/plain; version=0.0.4")
    promhttp.Handler().ServeHTTP(w, req)
}))

// 整个第三方 handler（含它自己的中间件）
r.Any("/admin/*any", gin.WrapH(adminMux))
```

`WrapH` 保证了 `c.Writer` 被当作 `http.ResponseWriter` 传给内部 handler，因此内部 handler 写出的状态码、Header、Body 都能正常回给客户端；Gin 侧中间件（鉴权、日志）依然生效。

## 四、复用标准库中间件

标准库中间件签名是 `func(http.Handler) http.Handler`，Gin 中间件是 `func(*gin.Context)`，二者不能直接互换。三种正确姿势：

**1）整层包裹（推荐）**：标准库中间件放在最外层，包住整个 Engine。

```go
func withRecover(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

srv := &http.Server{Addr: ":8080", Handler: withRecover(r)}
```

**2）按路由包裹**：只对某些路由生效时，把「中间件 + 末端 handler」整体交给 `gin.WrapH`：

```go
limited := rateLimitMiddleware(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
    w.Write([]byte("ok"))
}))
r.GET("/limited", gin.WrapH(limited))
```

**3）Gin 中间件想给标准库 handler 用**：不推荐硬转。做法是「先让 Gin 执行中间件，再调用标准库 handler」，用 `c.Next()` 控制顺序：

```go
r.GET("/mixed", AuthRequired(), gin.WrapH(legacyHandler))
// AuthRequired 内部 c.Abort() 后，WrapH 不会执行，效果等同标准库中间件链
```

## 五、边界：三个必须知道的差异

| 维度 | 标准库 | Gin | 适配注意 |
| --- | --- | --- | --- |
| 中间件顺序 | 显式 `mw(h)` 嵌套 | `Use` 注册顺序 + `c.Next()` | 外层标准库中间件永远先于 Gin 中间件 |
| 中断请求 | 直接 `return` 不调用 `next` | 必须 `c.Abort()`，且注意引擎最外层已 `c.Next()` | 忘记 `Abort` 会让后续 handler 继续跑 |
| ResponseWriter 能力 | 原样实现 `Flusher`/`Hijacker` | `gin.ResponseWriter` 也实现了，但被包装过 | `Hijack` 后不能再走 Gin 的响应流程 |

`gin.ResponseWriter` 接口包含 `http.Flusher`、`http.Hijacker`、`http.CloseNotifier`（已废弃），所以 `c.Writer` 可以安全地传给需要 `Flush`/`Hijack` 的库。但 `Hijack` 之后连接归你管，Gin 不能再去写响应头。

## 六、SSE 与 WebSocket

- **SSE**：用 `c.SSEvent` / `c.Stream`（见 [SSE 与流式响应](15-SSE与流式响应.md)），或 `gin.WrapH` 挂一个标准库 SSE handler，后者需要自己设置 `Content-Type: text/event-stream` 并 `Flush`。
- **WebSocket**：推荐 `github.com/gorilla/websocket` 的 `Upgrader.Upgrade(c.Writer, c.Request, nil)`，依赖 `Hijacker`；如果用的是标准库封装的 WebSocket handler，直接 `r.GET("/ws", gin.WrapH(wsHandler))`。
- 两者都要求 `http.Server.WriteTimeout = 0`，否则长连接会被定时切断。

## 完整示例

```go
// cmd/hybrid/main.go：一个进程里共存 Gin 路由、标准库 handler 与老 mux
package main

import (
    "log"
    "net/http"
    "time"

    "github.com/gin-gonic/gin"
)

func main() {
    gin.SetMode(gin.ReleaseMode)
    r := gin.New()
    r.Use(gin.Logger(), gin.Recovery())

    r.GET("/api/v1/ping", func(c *gin.Context) { c.String(http.StatusOK, "pong") })

    legacy := http.NewServeMux()
    legacy.HandleFunc("/legacy/version", func(w http.ResponseWriter, _ *http.Request) {
        w.Write([]byte(`{"version":"v1.0.0"}`))
    })
    r.Any("/legacy/*path", gin.WrapH(legacy))

    root := http.NewServeMux()
    root.Handle("/", r)                                // Gin 接管其余全部路径
    root.Handle("/files/", http.StripPrefix("/files/", http.FileServer(http.Dir("./public"))))

    srv := &http.Server{Addr: ":8080", Handler: root, ReadHeaderTimeout: 3 * time.Second}
    log.Fatal(srv.ListenAndServe())
}
```

验证：

```powershell
# PowerShell
curl.exe -i http://127.0.0.1:8080/api/v1/ping
curl.exe -i http://127.0.0.1:8080/legacy/version
```

```bash
# bash

curl -i http://127.0.0.1:8080/legacy/version
```

## 常见坑

1. **`mux.Handle("/api/", r)` 后 Gin 路由 404**：路径前缀没剥，用 `http.StripPrefix` 或让 Gin 路由带上 `/api`。
2. **`ServeMux` 模式缺少结尾斜杠**：`/api` 只精确匹配，`/api/v1` 不命中；子树匹配必须写 `/api/`。
3. **Gin 中间件里 `return` 而不 `Abort`**：因为引擎最外层已调用 `c.Next()`，后续 handler 仍会执行，造成越权。
4. **在标准库 handler 里读 `c.Param`**：`gin.WrapH` 之后拿不到 `*gin.Context`，路径参数只能从 `r.URL.Path` 或 `r.PathValue` 取。
5. **把标准库 gzip 中间件包在 Engine 上又用 `c.DataFromReader`**：包装层的 `Content-Length` 与实际不一致，响应被截断；要么全用 Gin 中间件，要么外层统一压缩。
6. **`Hijack` 后继续 `c.JSON`**：连接已被接管，Gin 写响应会返回错误或产生告警日志。
7. **同时注册 `r.NoRoute` 和 `mux.Handle("/")`**：优先级容易混乱，只保留一处兜底。
8. **想直接复用 `http.Handler` 中间件给 Gin 的 `r.Use`**：类型不兼容，只能整层包裹或按路由 `WrapH`。

## 小结

- `*gin.Engine` 实现了 `http.Handler`，因此可以与任何标准库基础设施共存。
- 外→内用 `gin.WrapH` / `gin.WrapF`；内→外用 `mux.Handle` + `http.StripPrefix`。
- 标准库中间件建议整层包裹 Engine，或在路由级与 handler 一起 `WrapH`。
- 适配的核心风险在 `Abort` 语义与 `ResponseWriter` 能力，SSE/WebSocket 需 `WriteTimeout=0`。
