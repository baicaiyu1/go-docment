# 项目结构与分层布局

> 一句话定位：mall-lite 用 `api / app / pkg / configs / deploy` 五段式布局分离「契约、服务、通用库、配置、部署」；网关内部按 `cmd + internal/{router,handler,middleware,client}` 分层，依赖只能单向向内。

## 本篇目标

- 说清五个顶层目录的职责与依赖方向。
- 搭出 gateway 的 `cmd + internal` 骨架，明确每层边界。
- 理解「proto 契约先行」：`api` 是唯一事实来源，并能指出典型分层违规。

## 前置知识

- 已了解 Gin 引擎与中间件，见 [Engine 详解与启动参数](./05-Engine详解与启动参数.md)。
- 已搭好工具链，见 [Gin 工程化脚手架与代码生成](./03-Gin工程化脚手架与代码生成.md)；建议先读 [项目分层与目录规范](../07-工程化与测试/01-项目分层与目录规范.md)。

## 一、整体布局

```text
mall-lite/
├── api/{user,product,order}/v1/*.proto   # 契约，唯一事实来源
├── app/
│   ├── gateway/                          # Gin BFF：cmd + internal/{router,handler,middleware,client,server}
│   ├── user-service/                     # Kratos：biz/data/service/server/conf
│   ├── product-service/  order-service/
├── pkg/                                  # config/logger/errs/tracing/sentinel/discovery
├── configs/                              # gateway.yaml、user-service.yaml
├── deploy/                               # apisix/docker/k8s/prometheus/grafana/otel
└── go.mod                                # 单 go.mod，module = mall-lite
```

单 `go.mod` 的理由：内部服务共享 `api` 与 `pkg`，多模块会引入 `replace` 与版本地狱；代价是依赖升级要整体回归，所以只允许引入少量高质量依赖。

## 二、逐目录职责与依赖方向

| 目录 | 职责 | 允许依赖 | 明确禁止 |
| --- | --- | --- | --- |
| `api/` | proto 与生成代码 | 无业务依赖 | 手写业务、手改生成文件 |
| `app/gateway/cmd/` | 进程入口：配置、装配、启动、退出 | `internal/*` | 业务逻辑、SQL |
| `internal/router/` | 路由与中间件装配 | handler、middleware | 直接 new 数据库或 gRPC 连接 |
| `internal/handler/` | 解析请求、调用 client、写响应 | client、pkg/errs | 直接访问 MySQL/Redis |
| `internal/client/` | gRPC 调用与错误转换 | api、kratos grpc | 感知 `*gin.Context` |
| `internal/middleware/` | 横切逻辑 | gin、pkg | 业务判断、查库 |
| `pkg/` | 通用库 | 标准库、三方库 | 反向依赖 `app/` |
```text
cmd ──→ router ──→ handler ──→ client ──→ (gRPC) ──→ 下游服务
                       ├──→ pkg/errs（错误码映射）
                       └──→ api（生成的结构体）
pkg ←── 任何层可依赖；pkg 不能反向 import app
```

三条铁律：依赖只能从外向内；`internal` 只能被同服务子树引用（Go 语言规则）；`pkg` 必须能独立编译。

## 三、gateway 的 cmd + internal

入口只做装配与生命周期，不出现路由细节：

```go
// app/gateway/cmd/main.go
package main

import (
    "log/slog"
    "net/http"
    "time"

    "github.com/gin-gonic/gin"

    "mall-lite/app/gateway/internal/router"
)

func main() {
    gin.SetMode(gin.ReleaseMode)
    // 完整超时与优雅退出见 05 篇；handler 依赖生产由 wire 注入
    srv := &http.Server{Addr: ":8080", Handler: router.New(nil), ReadHeaderTimeout: 5 * time.Second}
    if err := srv.ListenAndServe(); err != nil {
        slog.Error("gateway exited", "err", err)
    }
}
```

路由层是唯一装配点，依赖通过参数传入，禁止在这里 `New`：

```go
// app/gateway/internal/router/router.go
package router

import (
    "github.com/gin-gonic/gin"

    "mall-lite/app/gateway/internal/handler"
    "mall-lite/app/gateway/internal/middleware"
)

func New(userHandler *handler.UserHandler) *gin.Engine {
    r := gin.New()
    r.Use(gin.Recovery(), middleware.RequestID(), middleware.Logging())
    _ = r.SetTrustedProxies(nil)
    v1 := r.Group("/api/v1")
    v1.GET("/users/:id", userHandler.Get)
    return r
}
```

handler 只做「解析 → 调用 → 输出」，下游协议藏在 client 后面：

```go
// app/gateway/internal/handler/user.go
package handler

import (
    "strconv"

    "github.com/gin-gonic/gin"

    "mall-lite/app/gateway/internal/client"
)

type UserHandler struct{ users client.UserClient }

func NewUserHandler(users client.UserClient) *UserHandler { return &UserHandler{users: users} }

func (h *UserHandler) Get(c *gin.Context) {
    id, err := strconv.ParseInt(c.Param("id"), 10, 64)
    if err != nil {
        c.JSON(400, gin.H{"code": 40001, "message": "invalid user id"})
        return
    }
    // 必须透传请求 context，才能带上超时与 trace
    user, err := h.users.GetUser(c.Request.Context(), id)
    if err != nil {
        c.JSON(502, gin.H{"code": 50201, "message": "user service unavailable"})
        return
    }
    c.JSON(200, gin.H{"code": 0, "message": "ok", "data": user})
}
```

client 封装连接与错误映射，连接在启动时建一次：

```go
// app/gateway/internal/client/user.go
package client

import (
    "context"

    "github.com/go-kratos/kratos/v2/transport/grpc"

    userv1 "mall-lite/api/user/v1"
)

// UserClient 用接口暴露，方便 handler 单测 mock
type UserClient interface {
    GetUser(ctx context.Context, id int64) (*userv1.User, error)
}

type userClient struct{ cli userv1.UserServiceClient }

// NewUserClient 由 wire 调用一次，进程内复用同一个连接
func NewUserClient(conn *grpc.ClientConn) UserClient {
    return &userClient{cli: userv1.NewUserServiceClient(conn)}
}

func (u *userClient) GetUser(ctx context.Context, id int64) (*userv1.User, error) {
    return u.cli.GetUser(ctx, &userv1.GetUserRequest{Id: id})
}
```

## 四、proto 契约先行

先改 proto，再生成，最后写实现；`go_package` 必须与模块路径一致：

```text
// api/user/v1/user.proto
syntax = "proto3";
package user.v1;
option go_package = "mall-lite/api/user/v1;v1";

service UserService {
  rpc GetUser(GetUserRequest) returns (User);
}
message GetUserRequest { int64 id = 1; }
message User { int64 id = 1; string name = 2; string email = 3; }
```

```bash
protoc --go_out=. --go-grpc_out=. api/user/v1/user.proto   # 等价 kratos proto client
```

网关与 user-service 引用**同一个** `userv1.User`，字段不可能漂移；proto 字段编号不复用就天然向后兼容。CI 里 `git diff --exit-code api/` 能拦住「改了 proto 却没提交生成代码」。

## 完整示例

一次 `GET /api/v1/users/42` 的路径：

```text
请求 → Recovery → RequestID → Logging（c.Next 前）
     → handler.Get：c.Param 解析 → client.GetUser(ctx, 42) → gRPC user-service:9001
     → c.JSON(200) → Logging 后置记录 status 与 latency
```

落地顺序建议：`api` 写 proto 并生成 → 实现 RPC → `client` 包一层 → `handler` 调用 → `router` 注册 → `cmd` 启动。反向插入（先写 handler 再补契约）必然导致 DTO 双份。

## 常见坑

1. **handler 里直接 `db.Query`**：HTTP 层与存储耦合，数据访问应放 Kratos 的 `data` 层。
2. **`pkg` 反向 import `app`**：无法复用且易成环，通用能力只依赖标准库与三方库。
3. **跨服务引用别人 `internal`**：Go 编译器直接报错，共享代码放 `api` 或 `pkg`。
4. **proto 与手写 DTO 双份**：字段改一处漏一处，直接用生成结构体。
5. **在 `router` 里 new 依赖**：无法替换、无法 mock，依赖从 `cmd`/wire 注入。
6. **每个请求 `grpc.Dial`**：握手成本极高，启动时建一次并复用。

## 小结

- 五段式布局的核心是「契约、实现、通用库」互不污染。
- `cmd → router → handler → client` 单向依赖，任何反向 import 都是设计事故。
- proto 先行让 BFF 与微服务共享同一份类型，分层换来可测试、可替换、可并行开发。
