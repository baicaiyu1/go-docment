# 04-可靠投递-幂等-顺序消息

> 一句话定位：把「不丢、不重、不乱」拆成生产端 Outbox、消费端幂等、顺序三件事，并承认业务幂等才是最后一道防线。

## 本篇目标
- 看清 at-least-once 与 exactly-once 的真实边界
- 用本地消息表（Outbox）+ 定时补偿实现生产端可靠投递
- 掌握唯一键、去重表、Redis SETNX、状态机条件更新四种幂等手段
- 用「同 key 同分区 + 单分区串行」实现业务顺序，并知道乱序如何兜底
- 能按现象排查重复、丢失、乱序，并设计对账补偿

## 一、先把语义定清楚
投递语义与三种 MQ 的边界见 [01-消息队列选型对比](01-消息队列选型对比.md) 第四节，结论只有一句：Kafka 的 EOS 只在 Kafka 内部成立，RocketMQ 事务消息只保证「本地事务与消息发送」一致；**副作用一旦落到 MySQL、Redis、支付网关，就必须靠业务幂等。** 工程上全线做 at-least-once + 幂等消费，对外表现为「效果恰好一次」。

## 二、生产端可靠：本地消息表
```sql
CREATE TABLE outbox_event (
  id            BIGINT      NOT NULL AUTO_INCREMENT,
  event_id      CHAR(36)    NOT NULL,
  topic         VARCHAR(64) NOT NULL,
  msg_key       VARCHAR(64) NOT NULL,
  payload       JSON        NOT NULL,
  status        TINYINT     NOT NULL DEFAULT 0 COMMENT '0待投递 1已投递 2已废弃',
  retry_count   INT         NOT NULL DEFAULT 0,
  next_retry_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  created_at    DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_event_id (event_id),
  KEY idx_status_next (status, next_retry_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
```go
// internal/data/outbox.go
func (d *Dispatcher) dispatch(ctx context.Context) error {
    var events []OutboxEvent
    if err := d.db.WithContext(ctx).
        Clauses(clause.Locking{Strength: "UPDATE", Options: "SKIP LOCKED"}).
        Where("status = ? AND next_retry_at <= ?", 0, time.Now()).
        Order("id").Limit(100).Find(&events).Error; err != nil {
        return err
    }
    for _, e := range events {
        _, _, err := d.producer.SendMessage(&sarama.ProducerMessage{
            Topic: e.Topic,
            Key:   sarama.StringEncoder(e.MsgKey),
            Value: sarama.ByteEncoder(e.Payload),
        })
        if err != nil {
            d.log.Warn("outbox send failed", zap.Int64("id", e.ID), zap.Error(err))
            _ = d.db.WithContext(ctx).Model(&OutboxEvent{}).Where("id = ?", e.ID).
                Updates(map[string]any{
                    "retry_count":   gorm.Expr("retry_count + 1"),
                    "next_retry_at": time.Now().Add(time.Duration(e.RetryCount+1) * 10 * time.Second),
                }).Error
            continue
        }
        _ = d.db.WithContext(ctx).Model(&OutboxEvent{}).Where("id = ?", e.ID).
            Update("status", 1).Error
    }
    return nil
}
```
`SKIP LOCKED` 保证多实例不抢同一批，`unique(event_id)` 防止业务重复写入。代价是**至少一次**：Kafka 已写入但状态更新失败会重复投递，靠下一节幂等吸收。生产端还有两条路：RocketMQ 事务消息（半消息 + 回查）、CDC 读 binlog（Debezium/Canal，成本最高）。

## 三、消费端幂等四板斧
```sql
CREATE TABLE consumed_message (
  id             BIGINT      NOT NULL AUTO_INCREMENT,
  consumer_group VARCHAR(64) NOT NULL,
  msg_id         VARCHAR(64) NOT NULL,
  created_at     DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  UNIQUE KEY uk_group_msg (consumer_group, msg_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```
```go
// internal/data/stock_consumer.go
func (c *StockConsumer) Handle(ctx context.Context, msg *sarama.ConsumerMessage) error {
    var ev biz.OrderPaid
    if err := json.Unmarshal(msg.Value, &ev); err != nil {
        return err // 坏消息转死信，不要无限重试
    }
    return c.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        rec := ConsumedMessage{ConsumerGroup: "stock-service", MsgID: ev.EventID}
        if err := tx.Create(&rec).Error; err != nil {
            if errors.Is(err, gorm.ErrDuplicatedKey) {
                return nil // 已消费过
            }
            return err
        }
        res := tx.Model(&OrderStock{}).
            Where("order_id = ? AND status = ?", ev.OrderID, "PENDING").
            Update("status", "DEDUCTED")
        if res.Error != nil || res.RowsAffected == 0 {
            return res.Error // 状态非法说明已处理，幂等跳过
        }
        return tx.Model(&Stock{}).
            Where("sku_id = ? AND available >= ?", ev.SKUID, ev.Qty).
            UpdateColumn("available", gorm.Expr("available - ?", ev.Qty)).Error
    })
}
```
去重记录与业务更新**必须同一事务**；GORM 要开 `gorm.Config{TranslateError: true}` 才能用 `ErrDuplicatedKey`；`WHERE available >= ?` 兼作防超卖校验。另外两板斧：Redis SETNX 适合「重复无害、漏发可接受」的通知（键带 eventID、TTL 72h，发送失败必须 `DEL` 释放）；状态机把幂等写进 SQL，例如 `UPDATE orders SET status='PAID' WHERE id=? AND status='PENDING'`，`RowsAffected=0` 直接返回成功。

## 四、顺序消息
顺序成立需要**同 key 同分区** + **同分区同一时刻只有一个处理者**：

```go
producer.SendMessage(&sarama.ProducerMessage{ // 分区键必须是业务主键
    Topic: topic, Key: sarama.StringEncoder(orderID), Value: sarama.ByteEncoder(body),
})
for msg := range claim.Messages() { // 一个分区一条 goroutine，串行处理
    _ = handle(msg)
    sess.MarkMessage(msg, "")
}
```
破坏顺序的常见写法：key 为空、拉取后丢进共享线程池、失败立即重试而后续消息已处理。顺序要求不强时用版本号兜底：

```sql
UPDATE order_status SET status = ?, version = ?
WHERE order_id = ? AND version < ?;
```
旧版本到达会被 SQL 拒绝，最终状态仍然收敛。

## 五、故障排查
| 现象 | 高概率原因 | 排查手段 |
| --- | --- | --- |
| 消息重复 | 消费成功但提交失败；rebalance；Outbox 重投 | 对比去重表与业务表，查位点跳变 |
| 消息丢失 | 先提交后处理；自动 ack；Nack 后无死信 | 检查 ack 模式、DLQ、broker 保留期 |
| 顺序错乱 | key 不稳定；消费并发；重试插队 | 打印 partition/offset，验证同 key 同分区 |
| lag 上涨 | 消费变慢或分区不足 | 见 05 篇处置表 |

## 六、对账与补偿
消息保证「最终」不保证「一定」，每天跑对账把长期不一致的订单捞出来补偿：

```go
// internal/job/reconcile.go
func Reconcile(ctx context.Context, db *gorm.DB) error {
    var rows []Order
    err := db.WithContext(ctx).Raw(`
        SELECT o.id, o.sku_id, o.qty FROM orders o
        LEFT JOIN order_stock s ON s.order_id = o.id
        WHERE o.status = 'PAID' AND s.order_id IS NULL
        LIMIT 200`).Scan(&rows).Error
    if err != nil {
        return err
    }
    for _, o := range rows {
        if err := deductStock(ctx, o.ID, o.SKUID, o.Qty); err != nil { // 幂等重放
            db.WithContext(ctx).Create(&ReconcileDiff{OrderID: o.ID, Reason: err.Error()})
        }
    }
    return nil
}
```
对账放在独立任务里，用 zap 记录扫描量、补偿量、失败明细；建议「单轮失败 > 10 条」告警，避免噪声。

## 完整示例：下单 → 扣库存 → 通知
```sql
CREATE TABLE orders (
  id        VARCHAR(32) PRIMARY KEY,
  user_id   BIGINT      NOT NULL,
  sku_id    BIGINT      NOT NULL,
  qty       INT         NOT NULL,
  status    VARCHAR(16) NOT NULL DEFAULT 'PENDING',
  expire_at DATETIME(3) NOT NULL,
  version   INT         NOT NULL DEFAULT 0,
  KEY idx_status_expire (status, expire_at)
);

CREATE TABLE order_stock (
  order_id   VARCHAR(32) PRIMARY KEY,
  sku_id     BIGINT      NOT NULL,
  qty        INT         NOT NULL,
  status     VARCHAR(16) NOT NULL DEFAULT 'PENDING',
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3)
);
```
```go
// internal/biz/order.go：下单只做本地事务，消息进 Outbox
func (uc *OrderUsecase) Create(ctx context.Context, req *CreateOrderReq) (*Order, error) {
    o := &Order{ID: newID(), UserID: req.UserID, SKUID: req.SKUID, Qty: req.Qty, Status: "PENDING", ExpireAt: time.Now().Add(30 * time.Minute)}
    ev := &OutboxEvent{EventID: newID(), Topic: "mall.order.event.v1", MsgKey: o.ID, Payload: mustJSON(biz.OrderCreated{OrderID: o.ID, SKUID: o.SKUID, Qty: o.Qty})}
    err := uc.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(o).Error; err != nil {
            return err
        }
        return tx.Create(ev).Error
    })
    return o, err
}
```
后续链路：dispatcher 投递 `OrderCreated` → 库存服务去重表 + 状态机扣减 → 发 `OrderStockDeducted` → 通知服务 Redis SETNX 去重发短信。每一跳都可能重复，每一跳都必须幂等。

## 常见坑
1. **以为 Kafka 事务能保证 MySQL 只写一次**：EOS 只在 Kafka 内部成立，外部副作用仍需幂等。
2. **去重表与业务更新不在同一事务**：记了去重但业务失败，消息被永久跳过。
3. **Redis 去重键失败不释放**：用户收不到通知，排查时还以为已发送。
4. **用 `Nack(requeue=true)` 处理参数错误**：毒消息无限循环，CPU 打满。
5. **消费线程池并发处理同一分区**：顺序保证被自己破坏。
6. **重试无上限**：一条坏消息阻塞整个分区，lag 持续上涨。
7. **死信无人消费或只靠 MQ 不跑对账**：消息静默堆积、数据长期漂移，直到财务结账才发现。

## 小结
- 生产端可靠 = 本地事务 + Outbox + 定时补偿，或直接用 RocketMQ 事务消息。
- 消费端幂等 = 唯一键 / 去重表 / 状态机 / Redis SETNX，按数据重要性选择。
- exactly-once 是营销词，工程上做 at-least-once + 幂等。
- 顺序 = 同 key 同分区 + 单分区串行；要求不强时用版本号兜底。

## 练习
1. 为支付回调实现「去重表 + 状态机」双重幂等，用重复消息验证只生效一次。
2. 给 Outbox dispatcher 加最大重试次数，超过后标记废弃并告警。
