# 01-消息队列选型对比

> 一句话定位：先用「能否丢、要不要顺序、谁来运维」三条硬约束筛掉候选，再看功能矩阵与压测数据，而不是背参数表。

## 本篇目标
- 从吞吐、延迟、顺序、事务、延迟消息、运维、生态七个维度对比 Kafka / RocketMQ / RabbitMQ / Pulsar
- 讲清 Topic / Partition / Queue / Exchange / ConsumerGroup 这些模型概念分别在哪个 MQ 里成立
- 分清 at-most-once / at-least-once / exactly-once 的真实边界，不被营销词带偏
- 拿到一棵可执行的选型决策树
- 说明 mall-lite 为什么用 Kafka 做订单事件总线，以及什么情况下应当换掉

## 前置知识
- 已读 [10-Redis/05](../10-Redis/05-高可用部署与运维.md)，理解中间件的可用性代价
- 已读 [12-微服务与Kratos/08](../12-微服务与Kratos/08-分布式事务与最终一致性.md)，知道最终一致性要解决什么
- 本机有 Docker，能拉起单节点 Kafka

## 一、先回答三个问题
选型前先把业务约束写进设计文档，再去比性能数字：

1. **消息能不能丢？** 订单、支付、库存不能丢；日志、埋点、推荐特征可以丢。
2. **要不要顺序？** 同一订单的状态变更必须有序；通知、积分可以乱序。
3. **谁来运维？** 有没有专职中间件团队，直接决定能不能上 Pulsar 这类存算分离的重组件。

## 二、七维对比
| 维度 | Kafka 3.8 | RocketMQ 5.3 | RabbitMQ 3.13 | Pulsar |
| --- | --- | --- | --- | --- |
| 吞吐 | 极高，十万~百万级/s | 高，十万级/s | 中，万级/s | 高，分层存储可更大 |
| 延迟 | 毫秒~几十毫秒（受批量影响） | 毫秒级 | 微秒~毫秒级 | 毫秒级 |
| 顺序 | 分区内有序 | 队列内有序，可全局顺序 | 单队列有序 | 分区有序 |
| 事务 | 事务写（EOS 仅在 Kafka 内部） | 半消息 + 回查，原生事务消息 | 不支持，需业务补偿 | 支持 |
| 延迟消息 | 不自带，需扫表 / 延迟 Topic | 原生延迟级别，5.x 支持定时消息 | TTL + 死信交换机 | 支持 |
| 运维 | 中（KRaft 去掉 ZooKeeper 后更低） | 中高（NameServer + Broker + 主从） | 低 | 高（Broker + BookKeeper） |
| 生态 | 最大，流处理与 CDC 事实标准 | 国内交易场景最活跃 | 老牌稳定，插件丰富 | 云原生多租户 |
| 典型场景 | 事件总线、日志、实时数仓 | 电商交易、订单支付 | 任务分发、复杂路由 | 多租户平台、海量留存 |

> 表里的吞吐是数量级感受。真实值取决于分区数、批量、压缩、磁盘与网络，**必须用自己 1KB 左右的真实消息体压测**后再定分区数。

## 三、消息模型对照
| 概念 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 逻辑分类 | Topic | Topic（+ Tag 二级过滤） | Exchange + RoutingKey |
| 物理分片 | Partition | Queue | Queue |
| 顺序粒度 | 分区内 | 队列内 | 单队列 |
| 消费位点 | offset，可任意回溯 | offset / 时间回溯 | 消费即删，无位点 |
| 扇出方式 | 多个 ConsumerGroup 各自消费全量 | 多个 ConsumerGroup | 一个 Exchange 绑多个 Queue |
| 消费模型 | 拉（长轮询） | 推为主，也支持拉 | 推（prefetch 流控） |

**ConsumerGroup 最容易被误解**：Kafka 组内分摊分区、组间互不影响，所以「库存组」「通知组」各拿一份全量事件；RabbitMQ 靠「一个 Exchange 绑多个 Queue」扇出，一个 Queue 的消息只会被组内一个消费者拿走。设计扇出前先确认自己用的是哪种语义。

## 四、投递语义的真实边界
| 语义 | 含义 | 实现方式 | 代价 |
| --- | --- | --- | --- |
| at-most-once | 最多一次，可能丢 | 先提交位点再处理 / 自动 ack | 最低，宕机即丢 |
| at-least-once | 至少一次，可能重 | 先处理再提交 / 手动 ack | 低，需要幂等 |
| exactly-once | 恰好一次 | Kafka 事务（读 → 处理 → 写 Kafka） | 极高，跨系统不成立 |

必须记住三条边界：
- **Kafka 的 EOS 只覆盖「消费 Kafka → 处理 → 再写 Kafka」**。副作用一旦落到 MySQL、Redis 或第三方支付，就不在事务范围内。
- **RocketMQ 事务消息保证「本地事务与消息发送」的原子性**，并不保证消费只执行一次。
- **RabbitMQ 的 publisher confirm + 手动 ack 只保证不丢**，重复照样发生。

工程结论：全线做 at-least-once + 消费端幂等，对外表现为「效果恰好一次」。第 04 篇给出完整实现。

## 五、Go 客户端生态
| MQ | 推荐库 | 说明 |
| --- | --- | --- |
| Kafka | `github.com/IBM/sarama` | 功能最全，支持幂等生产者、事务、消费组；mall-lite 使用 |
| Kafka | `github.com/segmentio/kafka-go` | API 简单，但不暴露 `enable.idempotence` |
| Kafka | `github.com/confluentinc/confluent-kafka-go` | 基于 librdkafka，性能最好，需要 cgo |
| RocketMQ | `github.com/apache/rocketmq-client-go/v2` | 官方维护，事务 / 顺序 / 延迟都有 |
| RabbitMQ | `github.com/rabbitmq/amqp091-go` | 官方维护，替代已归档的 streadway/amqp |
| Pulsar | `github.com/apache/pulsar-client-go` | 官方纯 Go 客户端 |

选库原则：官方或官方推荐、近一年有提交、**确认目标语言支持你要的特性**（不少特性只有 Java 客户端有），不要只看 star 数。

## 六、选型决策树
```text
消息能不能丢？
├─ 能丢（日志/埋点） → Kafka（吞吐与成本优先）
└─ 不能丢
   ├─ 需要事务消息 / 延迟消息 / 严格顺序 → RocketMQ
   ├─ 需要复杂路由 / 低延迟任务分发 → RabbitMQ
   ├─ 数据量极大且要长期留存 / 多租户 → Pulsar（有平台团队时）
   └─ 团队已有 Kafka → 继续用 Kafka + Outbox + 定时扫表
```
补充规则：
- **少引入一套中间件比「功能更贴合」更重要**。已有 Kafka 的团队，业务消息也走 Kafka，用 Outbox 补事务、用扫表补延迟。
- 消息体超过 1MB 不要塞 MQ，改传对象存储地址 + 元数据。
- 消费跟不上时，先看分区数，再看消费者并发，最后才考虑换 MQ。

## 七、mall-lite 的选择与例外
| 需求 | 是否满足 | 说明 |
| --- | --- | --- |
| 订单事件扇出到库存、通知、积分 | 满足 | 三个 ConsumerGroup 各消费全量 |
| 大促峰值写入 | 满足 | 批量 + Snappy 压缩 + 多分区 |
| 故障后回放事件重建读模型 | 满足 | 按 offset 回溯 |
| 30 分钟未支付自动取消 | 不满足 | 用 `(status, expire_at)` 扫表，见 05 篇 |
| 本地事务与消息同时成功 | 不满足 | 用 Outbox，见 04 篇 |
| 精确到秒的延迟投递 | 不满足 | 必要时引入 RocketMQ |

**例外**：团队本身是 RocketMQ 交易体系，或业务大量依赖「延迟取消 + 事务消息」时，把事件总线换成 RocketMQ 更省事，第 03 篇给出对应代码。反过来，几万 QPS 的订单事件用 Kafka 单栈完全够。

```go
// internal/biz/event.go

import "context"

type OrderEvent struct {
    EventID   string `json:"event_id"`
    OrderID   string `json:"order_id"`

    OccurredAt int64 `json:"occurred_at"`
}

// OrderEventPublisher 是端口，Kafka/RocketMQ 都是它的实现。
type OrderEventPublisher interface {
    Publish(ctx context.Context, ev OrderEvent) error
}
```

## 常见坑
1. **只看吞吐不看延迟**：批量参数调大后吞吐上升、P99 也上升，交易链路无法接受。
2. **以为 Kafka 有延迟消息**：原生不支持，必须扫表或延迟 Topic。
3. **忽略 Go 客户端能力差异**：某些特性只有 Java 客户端支持，选型要按语言验证。
4. **小团队上 Pulsar**：BookKeeper + Broker 的运维成本远超收益。
5. **用 RabbitMQ 堆百万消息**：堆积后内存与磁盘告警，消费速度进一步下降。
6. **不压测就定分区数**：分区只能增不能减，后期扩容会打乱 key 路由。
7. **把 MQ 当 RPC**：发消息等回复，超时与错误处理极其别扭；同步调用请用 gRPC。
8. **没有死信与监控就上线**：消息静默丢失，只能靠用户投诉发现。

## 小结
- 先按「能否丢、要不要顺序、谁运维」筛候选，再看功能矩阵与压测。
- Kafka 强在吞吐与回溯，RocketMQ 强在业务消息能力，RabbitMQ 强在路由，Pulsar 强在存算分离。
- Go 生态最稳的是 sarama、rocketmq-client-go/v2、amqp091-go。
- mall-lite 用 Kafka 做事件总线，用 Outbox 与定时扫表补足事务与延迟能力。
- MQ 不是 RPC，也不是数据库，更不是任务调度器。
