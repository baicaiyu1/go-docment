## 一、积压：先定位再动手
| 根因 | 现象 | 判断方法 |
| --- | --- | --- |
| 流量突增 | 生产速率远大于消费速率 | 两条 TPS 曲线对比 |
| 消费变慢 | 单条耗时上升 | 处理耗时 P99、下游 RT |
| 分区太少 | 加消费者后 lag 不降 | 消费者数 > 分区数，多出的空闲 |
| 下游抖动 | DB / Redis / HTTP 超时增多 | 下游错误率、连接池等待 |
| 毒消息 | 同一 offset 反复重试 | 日志中同一 msgID 循环 |
| rebalance 频繁 | 消费周期性暂停 | 组状态日志、rebalance 计数 |

## 二、处置手段与副作用
| 手段 | 操作 | 适用 | 副作用 |
| --- | --- | --- | --- |
| 扩消费者 | 实例数不超过分区数 | CPU / IO 未打满 | 超过分区数无效 |
| 扩分区 | 增加 Partition | 长期容量不足 | 同 key 路由变化，顺序受影响 |
| 批量消费 | 一次拉多条、批量写库 | DB 往返是瓶颈 | 单条失败回滚成本高 |
| 降级非核心 | 暂停通知 / 积分消费 | 大促洪峰 | 功能暂时不可用 |
| 生产端限流 | 网关限流、暂停低优 Topic | 源头失控 | 影响业务写入 |
| 转异步 | 消费线程只入队，后台池处理 | 单条耗时长且可并行 | 位点管理变复杂 |

追积压时必须保持幂等：**宁可把失败消息转死信并记录，也不要静默丢弃**。

## 三、死信队列与重放
```text
消费失败 → 有限重试（退避）→ 仍失败 → 死信 → 告警 → 人工/工具重放
```
- Kafka：无原生死信，消费端把「不可重试错误」投到 `mall.dlq.<topic>`，附带原 topic/partition/offset/异常。
- RocketMQ：返回 `ConsumeRetryLater`，默认重试 16 次后进入 `%DLQ%<group>`。
- RabbitMQ：`Nack(requeue=false)` + 队列配置 `x-dead-letter-exchange`。

```go
// internal/job/dlq_replay.go
func ReplayDLQ(ctx context.Context, db *gorm.DB, pub biz.OrderEventPublisher, limit int) (int, error) {
    var rows []DLQMessage
    if err := db.WithContext(ctx).Where("status = ? AND retry_count < ?", 0, 5).
        Order("id").Limit(limit).Find(&rows).Error; err != nil {
        return 0, err
    }
    n := 0
    for _, r := range rows {
        if err := pub.Publish(ctx, r.ToEvent()); err != nil {
            db.WithContext(ctx).Model(&DLQMessage{}).Where("id = ?", r.ID).
                Update("retry_count", gorm.Expr("retry_count + 1"))
            continue
        }
        db.WithContext(ctx).Model(&DLQMessage{}).Where("id = ?", r.ID).
            Updates(map[string]any{"status": 1, "replayed_at": time.Now()})
        n++
    }
    return n, nil
}
```
重放前先确认根因已修复，否则只是把毒消息再灌一遍。

## 四、延迟消息的三条路
**Kafka 不自带延迟消息**，按可靠性排序有三种做法。

1）**定时扫表（最稳）**：状态以 DB 为准，天然幂等，缺点是秒级延迟与扫描压力。

```go
// internal/job/order_timeout.go
func CancelExpiredOrders(ctx context.Context, db *gorm.DB, rdb redis.UniversalClient, log *zap.Logger) error {
    var orders []Order
    if err := db.WithContext(ctx).Where("status = ? AND expire_at < ?", "PENDING", time.Now()).
        Order("id").Limit(200).Find(&orders).Error; err != nil {
        return err
    }
    for _, o := range orders {
        res := db.WithContext(ctx).Model(&Order{}).
            Where("id = ? AND status = ?", o.ID, "PENDING").
            Updates(map[string]any{"status": "CANCELLED", "cancel_reason": "timeout"})
        if res.Error != nil || res.RowsAffected == 0 {
            continue // 已支付或已取消，幂等跳过
        }
        if err := rdb.IncrBy(ctx, stockKey(o.SKUID), int64(o.Qty)).Err(); err != nil {
            log.Error("rollback stock", zap.String("order_id", o.ID), zap.Error(err))
        }
        publishOrderCancelled(ctx, o)
    }
    return nil
}
```
必须有 `(status, expire_at)` 联合索引，并用主键游标而不是深分页。

2）**延迟 Topic 分级**：按 1s / 30s / 1m / 5m 分桶，未到期转发下一档。

```go
// internal/worker/delay.go
type DelayEnvelope struct {
    DeliverAt int64           `json:"deliver_at"` // Unix 毫秒
    Target    string          `json:"target"`
    Key       string          `json:"key"`
    Payload   json.RawMessage `json:"payload"`
}

func (w *DelayWorker) ConsumeClaim(sess sarama.ConsumerGroupSession, claim sarama.ConsumerGroupClaim) error {
    for msg := range claim.Messages() {
        var env DelayEnvelope
        if err := json.Unmarshal(msg.Value, &env); err != nil {
            sess.MarkMessage(msg, "")
            continue
        }
        if time.Until(time.UnixMilli(env.DeliverAt)) > time.Minute {
            w.forward(sess.Context(), env) // 转下一档 Topic，绝不 sleep
        } else {
            w.publishTarget(sess.Context(), env)
        }
        sess.MarkMessage(msg, "")
    }
    return nil
}
```
进程内时间轮只适合可丢、短延迟场景，重启即丢，不能承载订单超时。

3）**RocketMQ 原生延迟**：固定档位，最省事，`WithDelayTimeLevel(16)` 的用法见 [03-RocketMQ与RabbitMQ实践](03-RocketMQ与RabbitMQ实践.md) 第四节。

无论哪种方案，消费时都要二次校验订单状态，避免「已支付却被取消」。

## 五、监控指标与告警
| 指标 | 来源 | 告警建议 |
| --- | --- | --- |
| 消费 lag | kafka_exporter | 持续 5 分钟 > 1 万 |
| 消费速率 | 应用埋点或 exporter | 环比掉 50% 且 lag 上升 |
| 处理耗时 P99 | 应用 Histogram | > 1s 关注，> 3s 告警 |
| 失败率 | 失败数 / 消费数 | > 1% 告警 |
| 重试次数 | 重试计数器 | 突增 3 倍排查下游 |
| 死信数量 | DLQ Topic / Queue | > 0 即告警 |

```go
// internal/metrics/mq.go
var (
    handleSeconds = promauto.NewHistogramVec(prometheus.HistogramOpts{
        Namespace: "mall", Subsystem: "mq", Name: "handle_duration_seconds",
        Buckets: []float64{.005, .02, .05, .1, .5, 1, 3}}, []string{"topic"})
    handleFailed = promauto.NewCounterVec(prometheus.CounterOpts{
        Namespace: "mall", Subsystem: "mq", Name: "handle_failed_total"}, []string{"topic", "reason"})
)
```
```yaml
# deploy/prometheus/rules/mq.yml
groups:
  - name: mall-mq
    rules:
      - alert: KafkaConsumerLagHigh
        expr: sum by (consumergroup, topic) (kafka_consumergroup_lag) > 10000
        for: 5m
        labels: { severity: warning }
        annotations: { summary: "消费组 {{ $labels.consumergroup }} 在 {{ $labels.topic }} 积压超 1 万" }
      - alert: KafkaConsumerStalled
        expr: sum by (consumergroup) (rate(kafka_consumergroup_current_offset[5m])) == 0
          and sum by (consumergroup) (kafka_consumergroup_lag) > 0
        for: 10m
        labels: { severity: critical }
        annotations: { summary: "消费组 {{ $labels.consumergroup }} 十分钟无进度" }
      - alert: MQHandleFailureRateHigh
        expr: sum(rate(mall_mq_handle_failed_total[5m])) / sum(rate(mall_mq_consumed_total[5m])) > 0.01
        for: 5m
        labels: { severity: warning }
```
Grafana 固定三块面板：总量（生产/消费 TPS + lag）、质量（失败率、重试、死信）、延迟（处理 P99 与端到端延迟）。手工核对用 `kafka-consumer-groups.sh --describe --group order-service`。

## 常见坑
1. **积压就加消费者**：分区只有 3 个，加到 10 个实例也没用。
2. **追积压时跳过失败消息**：lag 降了，数据永久缺失。
3. **延迟消息用 `time.Sleep` 阻塞消费线程**：整个分区停摆，重启后重复消费。
4. **扫表 SQL 没 `(status, expire_at)` 索引**：全表扫描拖慢 DB。
5. **取消订单不回补库存**：Redis 预扣库存永久少一件。
6. **只看 lag 不看耗时**：lag 低但 P99 已 3 秒，下次洪峰立刻积压。

## 小结
- 积压先看速率差，再看耗时，最后看分区与 rebalance；扩容只对「分区够、资源未满」有效。
- 死信是数据不是垃圾：必须告警、可查看、可重放，重放前先修根因。
- 延迟消息优先扫表或 RocketMQ 延迟级别；Kafka 用分级延迟 Topic，禁止 sleep。
- 监控四件套：lag、消费速率、失败率、死信量，配合 Grafana 三块固定面板。
