# 03-技术选型与版本基线

> 一句话定位：给出本教程一套可锁定、可复现的版本基线，并用对比矩阵回答「为什么是 Gin + Kratos」「什么时候根本不需要微服务」。

## 本篇目标

- 拿到一张可直接写进 `go.mod` 与部署清单的版本基线表。
- 完成 HTTP 框架、微服务框架、注册中心、消息队列、ORM 五组选型对比。
- 能判断什么场景不该上微服务，避免为架构而架构。

## 前置知识

- 已读 [Gin + Kratos 的微服务架构](../12-微服务与Kratos/01-Gin加Kratos的微服务架构.md)，并了解语义化版本与 Go Modules（[Go Module 与国内代理](../00-开始之前/03-Go-Module与国内代理.md)）。

## 一、教程版本基线

| 能力 | 选型 | 基线 | 说明 |
| --- | --- | --- | --- |
| 语言 | Go | 1.25 | 与 CI 镜像、`go.mod` 的 `go` 指令一致 |
| HTTP 框架 | Gin | v1.10.x | 网关 BFF 与对外 HTTP 接口 |
| 微服务框架 | Kratos | v2.8.x | 内部 gRPC 服务与治理 |
| RPC / 契约 | gRPC + Protobuf | grpc-go 1.6x / protobuf 1.3x | proto 是唯一契约来源 |
| 注册中心 | etcd / Consul | 3.5 / 1.20 | 教程以 etcd 为主线，Consul 做对照 |
| 网关 | Apache APISIX | 3.11 | 鉴权、限流、路由、可观测插件 |
| 限流熔断 | Sentinel Go | v1.0.4 | 资源级流控与熔断 |
| ORM / 数据库 | GORM / MySQL | v1.25.x / 8.4 | 事务、乐观锁、软删除 |
| 配置 | Viper | v1.20 | 本地 YAML + 环境变量覆盖 |
| 日志 | zap | v1.27 | JSON 输出，lumberjack 轮转 |
| 缓存 | go-redis v9 / Redis | v9.7 / 7.4 | 连接池、分布式锁、限流 |
| 消息队列 | Kafka / RocketMQ / RabbitMQ | 3.8 / 5.3 / 3.13 | 主线 Kafka（sarama），需事务或延迟消息时换 RocketMQ |
| 可观测性 | OTel + Jaeger | 最新稳定组合 | 链路追踪，OTLP 导出 |
| 指标 | Prometheus + Grafana | 2.x / 11.x | RED 指标与告警 |
| 部署 | Docker + Kubernetes | 27.x / 1.31 | 多阶段构建、探针、HPA |

这是「一组能互相兼容的版本」，不是各自最新；新项目以官方最新稳定版为准，并自行验证兼容性。

## 二、为什么是 Gin + Kratos

- **接入层用 Gin**：生态最大，中间件、SSE、文件上传、Swagger、OTel 埋点都有成熟方案，团队上手成本最低。
- **服务层用 Kratos**：proto 优先，内置 transport/registry/config/log/tracing，etcd、Consul、zap 的适配都在 contrib 里，不用自己拼治理框架。
- **职责清晰**：Gin 做鉴权、聚合、限流与协议转换，Kratos 只做领域逻辑；gRPC 契约固定，前后端解耦。
- **代价要认**：多一层网关、多一条 proto 生成链路，还要维护 etcd 与可观测性；没有这些预算就别拆。

## 三、HTTP 框架：Gin vs Echo vs Fiber vs net/http

| 维度 | Gin | Echo | Fiber | net/http |
| --- | --- | --- | --- | --- |
| 生态 | 最大，教程与三方库最多 | 较多 | 中等 | 官方全集，需自己组合 |
| 性能模型 | `net/http`，goroutine-per-conn | 同左 | fasthttp，不兼容 `http.Handler` | 同左 |
| 适合场景 | 通用业务、BFF、团队协作 | 想要内置能力与性能 | 极致吞吐、能接受生态限制 | 标准库优先、依赖最少 |

结论：要高生态与可维护性选 Gin；Fiber 的高吞吐换来标准库生态不可用，治理组件基本要重写。

## 四、微服务框架：Kratos vs go-zero vs 纯 grpc-go

| 维度 | Kratos | go-zero | 纯 grpc-go |
| --- | --- | --- | --- |
| 定位 | proto 驱动的微服务框架 | 代码生成 + 内置中间件 | 只有 RPC 能力 |
| 治理与上手 | 注册/配置/日志/链路齐全，需理解 DDD 分层 | 限流熔断缓存内置，生成即用 | 全部自建，成本最高 |
| 适合场景 | 中大型 gRPC 微服务 | 快速交付的 API 服务 | 已有基础设施、只要 RPC |

结论：Kratos 的价值是「约定 + 组件齐全」，代价是分层约束；只要 RPC 时直接用 grpc-go 更轻。

## 五、注册中心：etcd vs Consul vs K8s Service

| 维度 | etcd | Consul | K8s Service |
| --- | --- | --- | --- |
| 核心能力 | 强一致 KV（Raft）+ 租约 | 注册发现 + 健康检查 + KV + ACL | DNS + kube-proxy 负载均衡 |
| 健康检查 | 租约 TTL 续约 | 主动探测，支持脚本 | 依赖 readinessProbe |
| 适合场景 | K8s 内外统一注册中心 | 多语言、多数据中心 | 纯 K8s 部署、无跨集群需求 |

结论：教程用 etcd 讲清租约与 Watch，因为它在 K8s 内外都能用；全量上 K8s 的团队可以先只依赖 Service。

## 六、消息队列：Kafka vs RocketMQ vs RabbitMQ

| 维度 | Kafka | RocketMQ | RabbitMQ |
| --- | --- | --- | --- |
| 吞吐与模型 | 最高，分区日志拉模式 | 高，主题队列推拉结合 | 中，AMQP 推模式 |
| 事务 / 延迟消息 | 需自行设计 | 原生事务、延迟、顺序消息 | 延迟靠插件 |
| 适合场景 | 日志、埋点、大流量异步化 | 电商交易、订单状态流转 | 业务解耦、复杂路由 |

结论：教程用 Kafka 讲「分区有序 + 消费组 + 幂等」，它的模型最能暴露可靠投递问题；交易类业务可平移到 RocketMQ。

## 七、ORM：GORM vs ent vs sqlx

| 维度 | GORM | ent | sqlx |
| --- | --- | --- | --- |
| 抽象层级 | 高，约定优先 | 高，Schema as Code | 低，SQL 薄封装 |
| 学习成本 | 低 | 中 | 低（会 SQL 即可） |
| 适合场景 | 业务 CRUD、快速迭代 | 关系复杂、强类型团队 | 复杂查询、性能敏感 |

结论：GORM 赢在覆盖率与上手速度；复杂报表与批量任务直接写 SQL，别硬套 ORM。

## 八、什么时候不需要微服务

- 团队小于 5 人、单体 QPS 低于 1k：模块化单体足够，拆分只增加网络调用与故障面。
- 没有独立发布与独立扩容需求：拆服务收益接近零。
- 没有 etcd/K8s/监控值班：注册中心与可观测性是前置条件，缺一个都会放大故障。
- 跨服务强一致场景多：先做单库事务，Saga/Outbox 的成本远高于收益。
- 只对外提供少量接口：APISIX + 单体即可，不必引入 gRPC。

## 九、版本锁定与升级

基线要落到 `go.mod`：锁定补丁版本，`go mod tidy` 后才可复现；升级按「改版本 → tidy → 编译 → 单测 → 回归 → 灰度」执行。生成器（`protoc-gen-go`、`buf`、Kratos CLI）同样要锁版本。

## 完整示例：可复现的版本基线

```text
module mall-lite

go 1.25

require (
	github.com/gin-gonic/gin v1.10.0
	github.com/go-kratos/kratos/v2 v2.8.4
	github.com/redis/go-redis/v9 v9.7.0
	github.com/spf13/viper v1.20.1
	go.uber.org/zap v1.27.0
	gorm.io/gorm v1.25.12
	google.golang.org/grpc v1.67.1
)
```

```bash
# Windows PowerShell 下命令完全相同
go get github.com/gin-gonic/gin@v1.10.0
go get github.com/go-kratos/kratos/v2@v2.8.4
go mod tidy
go build ./... && go vet ./... && go test ./... -race
```

## 常见坑

1. **只锁大版本**：写 `v1.10` 而不是 `v1.10.0`，不同机器 `go mod tidy` 可能解析出不同补丁版本。
2. **生成器用 `@latest`**：`protoc-gen-go`、`buf`、Kratos CLI 版本漂移会让 proto 生成物不一致，统一写进 `tools.go`。
3. **主框架升级不带 contrib**：etcd/consul/zap 适配是独立模块，版本错配会编译失败或运行时异常。
4. **只看 benchmark 选型**：基准测试不衡量运维成本与团队熟悉度，高吞吐但没人会维护等于负债。
5. **生产用 `AutoMigrate`**：它会静默改表删列，生产必须用版本化 SQL 迁移，并先在灰度环境跑。

## 小结

- 版本基线是一组「能一起工作」的版本，锁定补丁版本才算锁定。
- Gin 负责接入与聚合，Kratos 负责服务治理与契约，分工比强行统一一个框架更省心。
- 选型先看团队与运维能力，再看性能数字；微服务解决的是组织与部署问题，不是性能银弹。

## 练习

1. 把本篇基线表写进自己项目的 `go.mod`，用示例程序打印版本，确认与表格一致。
2. 用表格对比你所在团队现有技术栈与教程基线，列出三处差异及升级风险。
3. 假设「内部工具 + 200 QPS」的场景，写出不上微服务的理由与替代架构。
