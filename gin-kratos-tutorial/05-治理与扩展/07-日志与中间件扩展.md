# 日志与中间件扩展

> 一句话定位：zap 的扩展点是 Core / WriteSyncer / Sampler，Gin 的扩展点是中间件顺序与 `ResponseWriter` 包装；本篇把脱敏、异步不阻塞、请求响应体日志、trace_id 串联与 stdout 采集串成一条可上生产的链路。

## 本篇目标

- 写出脱敏 Core 与异步 Writer，理解采样与丢日志的边界。
- 定死 Gin 中间件顺序，实现受控的请求 / 响应体日志，并用 Kratos 中间件补齐 `trace_id`。

## 前置知识

- 已读 [日志体系 zap](../04-可观测性/01-日志体系zap.md)，会用 `zap.NewProduction` 与字段化日志。
- 已读 [中间件](../03-基本特性/05-中间件.md)，理解 `c.Next()` 与 `c.Abort()`。

## 一、zap 的扩展模型

`Encoder` 改字段名与时间格式；`Core` 负责过滤、采样、脱敏、分流；`WriteSyncer` 负责异步、轮转、多路复用；`Sampler` 按「每秒前 N 条 + 之后每 M 条」抽样。关键认知：`Logger` 只是 `Core` 的壳，要加能力就包 Core，不要在外面包「业务日志函数」，否则 `AddCaller` 的行号全指到包装层。

## 二、自定义 Core：脱敏 + 采样

```go
// pkg/logger/logger.go
package logger

import (
    "strings"

    "go.uber.org/zap/zapcore"
)

type maskCore struct{ zapcore.Core; keys []string }

// With 必须重写，否则 logger.With 出来的字段绕过脱敏
func (c maskCore) With(f []zapcore.Field) zapcore.Core { return maskCore{c.Core.With(f), c.keys} }

func (c maskCore) Check(e zapcore.Entry, ce *zapcore.CheckedEntry) *zapcore.CheckedEntry {
    if c.Enabled(e.Level) {
        return ce.AddCore(e, c)
    }
    return ce
}

func (c maskCore) Write(e zapcore.Entry, fs []zapcore.Field) error {
    for i := range fs {
        if fs[i].Type != zapcore.StringType {
            continue
        }
        for _, k := range c.keys {
            if !strings.EqualFold(fs[i].Key, k) {
                continue
            }
            s := fs[i].String
            if len(s) <= 6 {
                fs[i].String = "***"
            } else {
                fs[i].String = s[:3] + "***" + s[len(s)-3:]
            }
        }
    }
    return c.Core.Write(e, fs)
}
```

组装方式：`zapcore.NewCore(JSONEncoder, AddSync(w), level)` → 套 `maskCore{keys: []string{"password", "token"}}` → 再套 `zapcore.NewSamplerWithOptions(core, time.Second, 100, 100)`（同秒前 100 条全留，之后每 100 条留 1 条），最后 `zap.New(core, zap.AddCaller(), zap.AddCallerSkip(1))`。脱敏只处理 `StringType`，`[]byte` 与嵌套对象要自己处理，通常约定「敏感字段一律用 `zap.String` 打」。

## 三、异步 Writer：满了就丢

```go
// pkg/logger/async.go
package logger

import (
    "io"
    "sync/atomic"
)

// ch 满即丢，dropped 用 atomic 记录丢弃条数
type AsyncWriter struct{ ch chan []byte; out io.Writer; dropped uint64 }

func NewAsyncWriter(out io.Writer, buffer int) *AsyncWriter {
    w := &AsyncWriter{ch: make(chan []byte, buffer), out: out}
    go func() {
        for b := range w.ch {
            _, _ = w.out.Write(b) // 单 goroutine 串行写，避免多写者交错
        }
    }()
    return w
}

func (w *AsyncWriter) Write(p []byte) (int, error) {
    select {
    case w.ch <- append([]byte(nil), p...):
        return len(p), nil
    default:
        atomic.AddUint64(&w.dropped, 1) // 队列满就丢，坚决不阻塞业务
        return len(p), nil
    }
}

func (w *AsyncWriter) Dropped() uint64 { return atomic.LoadUint64(&w.dropped) }
```

`Dropped() > 0` 要打进指标并告警；如果日志是审计凭证就不能丢，改同步写，宁可慢。

## 四、Gin 中间件顺序与装配

顺序由「谁需要看到全部请求」决定：`RequestID`（最先，后续日志都要带 `request_id`）→ `Recovery`（兜 panic，必须在业务之前）→ `AccessLog`（耗时与状态码）→ `CORS`（预检要在鉴权之前返回）→ 指标（要包含被限流 / 鉴权的请求）→ Sentinel（限流）→ JWT（鉴权）。body 日志只挂在需要审计的单个路由上：`r.POST("/api/v1/orders", middleware.BodyLog(log), orderHandler.Create)`。顺序错了代价很实在：AccessLog 在 Recovery 内层，panic 请求就没有访问日志；CORS 在鉴权内层，预检 `OPTIONS` 被 401；指标在限流内层，429 不计入 QPS。

## 五、请求 / 响应体日志

```go
// app/gateway/internal/middleware/bodylog.go
package middleware

import (
    "bytes"
    "io"
    "net/http"
    "strings"

    "github.com/gin-gonic/gin"
    "go.uber.org/zap"
)

type bodyWriter struct{ gin.ResponseWriter; buf *bytes.Buffer }

func (w *bodyWriter) Write(b []byte) (int, error) {
    if w.buf.Len() < 8<<10 {
        w.buf.Write(b)
    }
    return w.ResponseWriter.Write(b) // 必须透传，否则客户端收不到响应
}

func BodyLog(log *zap.Logger) gin.HandlerFunc {
    return func(c *gin.Context) {
        if strings.HasPrefix(c.ContentType(), "multipart/form-data") ||
            strings.Contains(c.GetHeader("Accept"), "text/event-stream") {
            c.Next() // 上传与 SSE 必须跳过：读下去不是内存爆就是连接卡死
            return
        }
        raw, _ := io.ReadAll(http.MaxBytesReader(c.Writer, c.Request.Body, 8<<10))
        c.Request.Body = io.NopCloser(bytes.NewReader(raw))

        bw := &bodyWriter{ResponseWriter: c.Writer, buf: bytes.NewBuffer(nil)}
        c.Writer = bw
        c.Next()

        log.Info("http body",
            zap.String("request_id", c.GetString("request_id")),
            zap.ByteString("req", maskAndCut(raw)),
            zap.ByteString("resp", maskAndCut(bw.buf.Bytes())),
        )
    }
}
```

三条硬约束：**限长**（`MaxBytesReader` 防大包进内存）、**跳过**（上传与流式响应会毁性能）、**脱敏**（`maskAndCut` 替换敏感键并截断）。生产更推荐只记 `path`、`status`、`latency` 与错误摘要，body 日志默认关闭、按路由开启。

## 六、Kratos logging.Server 与自定义字段

```go
// app/user-service/internal/server/middleware/logging.go
package middleware

import (
    "context"
    "time"

    "github.com/go-kratos/kratos/v2/log"
    "github.com/go-kratos/kratos/v2/middleware"
    "github.com/go-kratos/kratos/v2/transport"
    "go.opentelemetry.io/otel/trace"
)

func Logging(logger log.Logger) middleware.Middleware {
    return func(handler middleware.Handler) middleware.Handler {
        return func(ctx context.Context, req any) (any, error) {
            operation := "unknown"
            if info, ok := transport.FromServerContext(ctx); ok {
                operation = info.Operation()
            }
            start := time.Now()
            reply, err := handler(ctx, req)
            helper := log.NewHelper(log.With(logger, "operation", operation,
                "trace_id", trace.SpanContextFromContext(ctx).TraceID().String(), // 与 Gin 侧同一个 TraceID
                "latency_ms", time.Since(start).Milliseconds()))
            if err != nil {
                helper.WithContext(ctx).Error("msg", "rpc failed", "err", err)
                return nil, err
            }
            helper.WithContext(ctx).Info("msg", "rpc ok")
            return reply, nil
        }
    }
}
```

内置 `logging.Server(klog)` 只给「方法名 + 耗时 + 错误」，缺业务维度；要补 `trace_id` 就换成上面这个中间件，两者二选一，叠加会打两条日志。`request_id` 串「单次请求」，`trace_id` 串「跨服务链路」，各取各的，别混用。

## 七、采集：stdout JSON → Loki / ELK

容器里只写 stdout，落盘、轮转、采集交给平台：promtail 用 `kubernetes_sd_configs` 发现 Pod，`pipeline_stages` 里 `json` 解析 `level`、`service`、`trace_id` 后转成标签；ELK 同理，Filebeat 用 `decode_json_fields`。单行 JSON 是硬要求（多行堆栈用 Encoder 的 `StackKey` 收进一个字段），否则采集侧按行切分会把一条日志拆成几十条。Grafana 里按 `trace_id` 跳 Jaeger、按 `service` + `level` 过滤，是排障最快的两条路径。

## 常见坑

1. **`fmt.Println` 混进业务日志**：没有级别、没有字段、无法采集；全项目只允许 `*zap.Logger`。
2. **中间件里无脑读 body**：上传接口读 100MB 文件，内存与耗时双爆。
3. **包装 Writer 后不透传**：不调用 `w.ResponseWriter.Write`，客户端收不到响应。
4. **Error 级别也被采样**：出故障时最需要的日志恰好被丢；采样只对 Debug / Info 生效。
5. **同步写远端（HTTP / ES）**：日志后端一抖动，整个服务 P99 飙升；远端投递必须异步批量。
6. **把 `X-Request-ID` 当 `trace_id` 用**：语义不同，混用后 Jaeger 查不到链路。

## 小结

- 加能力包 Core（脱敏、采样），加落盘能力包 WriteSyncer（异步、轮转），不要包 Logger。
- 异步日志必然要面对丢日志，丢多少要能被观测到；审计场景不能丢。
- Gin 顺序：RequestID → Recovery → 日志 → CORS → 指标 → 限流 → 鉴权；body 日志默认关闭、按需开启。
