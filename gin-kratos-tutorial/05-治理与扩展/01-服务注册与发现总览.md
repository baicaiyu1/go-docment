# 服务注册与发现总览

> 一句话定位：Kratos 把服务发现收敛成 `registry.Registrar` / `registry.Discovery` 两个接口，加一套 `discovery:///服务名` 的端点语法；etcd 与 Consul 是同一抽象下的两个实现，真正决定可用性的是健康检查与优雅上下线。

## 本篇目标

- 说清「注册、发现、健康检查、负载均衡」四步各自由谁负责。
- 读懂 `Registrar`、`Discovery`、`ServiceInstance` 三个类型，知道权重为什么放在 `Metadata` 里。
- 会用 `discovery:///user-service` + `WithDiscovery` 建 gRPC 连接，理解实例列表如何刷新。
- 能对照 etcd 与 Consul 选型，并判断 K8s 场景下是否需要独立注册中心。
- 写出健康检查端点与「摘除 → 等待 → 退出」的下线顺序。

## 一、地址硬编码的问题

网关调用户服务，第一版通常长这样：

```go
// app/gateway/internal/client/user.go（反例：不要这么写）
resp, err := http.Get("http://10.0.0.12:8080/api/v1/users/" + id)
if err != nil {
    return nil, err
}
defer resp.Body.Close()
```

| 问题 | 后果 |
| --- | --- |
| 地址硬编码 | 扩缩容、迁机房都要改代码发版 |
| 无法感知宕机 | 坏节点继续收流量，5xx 一直冒 |
| 无法加权 | 新机器不能小流量爬坡，发布即全量 |
| 没有元数据 | 做不到按版本、机房、租户灰度 |

注册中心把「一份写死的地址」变成「一份会变化的服务目录」：

```text
┌──────────────┐  1. 注册（TTL 续约）  ┌────────────────┐
│ user-service │ ────────────────────▶ │  etcd / Consul │
│  :9001       │ ◀── 4. Watch 推送 ──── └───────┬────────┘
└──────┬───────┘                               │ 2. 订阅
       │ 5. gRPC 调用                           │
       ▼                                       ▼
┌─────────────────────────────────────────────────────┐
│ gateway：Discovery(拉实例) → 负载均衡(选一个) → 调用 │
└─────────────────────────────────────────────────────┘
```

## 二、Kratos 只定义两个接口

Kratos 不发明注册中心，只规定「注册」和「发现」必须长什么样：

```go
// 参考 go-kratos/kratos/v2/registry/registry.go（节选，勿复制进项目）
type Registrar interface {
    Register(ctx context.Context, svc *ServiceInstance) error
    Deregister(ctx context.Context, svc *ServiceInstance) error
}

type Discovery interface {
    GetService(ctx context.Context, serviceName string) ([]*ServiceInstance, error)
    Watch(ctx context.Context, serviceName string) (Watcher, error)
}

type ServiceInstance struct {
    ID        string            // 建议 服务名-IP-端口
    Name      string            // 服务名，必须全局统一
    Version   string            // 服务版本，便于灰度
    Metadata  map[string]string // 权重、机房、灰度标签
    Endpoints []string          // 如 ["grpc://10.0.0.12:9001"]
}
```

三个容易忽略的点：

1. **没有 `Weight` 字段**。权重、`zone`、`version` 全走 `Metadata`，由客户端节点过滤器读取，注册中心不参与加权决策。
2. **`Watch` 是发现的核心**。`GetService` 只用于首次全量拉取，之后靠 `Watcher.Next()` 推送变更，客户端才能秒级感知上下线。
3. **`Endpoints` 带协议前缀**。`grpc://` 与 `http://` 混在同一服务名下时，客户端按前缀过滤，不会把 HTTP 端口当 gRPC 端口拨。

## 三、`discovery:///` 与负载均衡

客户端不需要知道 etcd 地址，只需要「一个服务名 + 一个 Discovery 实现」：

```go
// app/gateway/internal/client/client.go
func NewUserClient(ctx context.Context, reg registry.Discovery) (v1.UserServiceClient, error) {
    conn, err := kratosgrpc.DialInsecure(ctx,
        kratosgrpc.WithEndpoint("discovery:///user-service"), // 服务名，不是 IP
        kratosgrpc.WithDiscovery(reg),                        // 从配置构造，禁止硬编码
        kratosgrpc.WithTimeout(2*time.Second),
        kratosgrpc.WithNodeFilter(func(_ context.Context, ins *registry.ServiceInstance) bool {
            return ins.Metadata["version"] != "canary-blocked"
        }),
    )
    if err != nil {
        return nil, err
    }
    return v1.NewUserServiceClient(conn), nil
}
```

| 端点写法 | 含义 | 适用 |
| --- | --- | --- |
| `discovery:///user-service` | 用注入的 `Discovery` 解析服务名 | 生产 |
| `dns:///user-service:9001` | 走 DNS（K8s Service 名） | 部署在 K8s |
| `10.0.0.12:9001` | 直连单实例 | 本地调试 |

负载均衡由客户端 selector 决定，与注册中心无关：Kratos 默认 `wrr`（加权轮询），还内置 `p2c`（随机选两个比负载，绕开慢节点）与 `random`；用 `selector.SetGlobalSelector(p2c.NewBuilder())` 进程级切换，权重和机房从 `Metadata` 读取。

## 四、etcd 与 Consul 的差异

| 维度 | etcd 3.5 | Consul 1.20 |
| --- | --- | --- |
| 一致性 | Raft，强一致 | Raft，强一致 |
| 存活机制 | Lease 租约，到期 key 自动删除 | 注册 + 健康检查（HTTP/TCP/TTL/gRPC） |
| 健康语义 | 只代表「客户端还在续约」 | 能主动探测端口，失败被标 critical |
| 运维成本 | 轻量，无 UI，靠 etcdctl | 组件多、自带 UI，学习成本更高 |
| KV/配置 | 原生 KV，适合做配置中心 | KV + UI，配置能力较弱 |
| Kratos 实现 | `contrib/registry/etcd/v2` | `contrib/registry/consul/v2` |
| 适合场景 | 已有 K8s/etcd，追求轻量 | 需要可视化、主动健康检查、多机房 |

结论先给：**已有 etcd 就直接用 etcd**，少运维一套组件；**需要「进程活着但业务不可用」也被摘除**，选 Consul，它的 HTTP 检查能打到 `/readyz`。etcd 的租约只证明进程还在续约，进程卡死但 lease 未过期时实例仍在列表里。

## 五、健康检查与优雅下线

| 模式 | 原理 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 客户端续约 | 实例定期续 TTL | 简单，Kratos 内置 | 进程卡死时仍可能被判存活 |
| 主动探测 | 注册中心请求 `/readyz` | 能验证依赖是否就绪 | 需暴露端口、控制探测频率 |
| 被动摘除 | 调用失败后熔断 | 兜底 | 已经产生错误请求 |

存活探针只证明进程在，就绪探针要证明能干活，两者必须分开：

```go
// app/gateway/internal/router/health.go
func RegisterHealth(r *gin.Engine, db *gorm.DB) {
    r.GET("/healthz", func(c *gin.Context) {
        c.String(http.StatusOK, "ok") // 不在这里查 DB
    })
    r.GET("/readyz", func(c *gin.Context) {
        sqlDB, err := db.DB()
        if err != nil || sqlDB.PingContext(c.Request.Context()) != nil {
            c.String(http.StatusServiceUnavailable, "mysql not ready")
            return
        }
        c.String(http.StatusOK, "ready")
    })
}
```

优雅下线四步都不能省：① 收到 `SIGTERM` 先 `Deregister`（`app.Stop(ctx)` 内部会做）；② 等一个发现刷新周期（5~10 秒）让调用方 Watch 到新列表；③ 停止接收新连接、等存量请求跑完；④ 进程退出，租约到期 / 检查转 critical 做双重兜底。只做第 ③ 步，就是发布期 5xx 尖峰的最常见原因。

## 六、K8s 场景还要不要注册中心

K8s 已经给了三件事：`Service` + `kube-proxy` 做四层转发，`CoreDNS` 提供 `user-service.default.svc.cluster.local` 解析，`readinessProbe` 失败会把 Pod 从 Endpoints 摘掉。

仍然需要客户端发现的场景：

- **gRPC 长连接 + 多副本**：`Service` 是 L4 转发，一条长连接会一直落在同一个 Pod，负载严重倾斜。要么客户端发现做 per-RPC 负载均衡，要么上 service mesh。
- **多集群 / 混合云**：跨集群实例不在同一个 K8s API 里，需要外部注册中心。
- **按版本、机房精细灰度**：`Metadata` 比两套 Deployment 更灵活。

结论：**单集群纯 K8s，优先用 Service + DNS（`dns:///user-service:9001`）+ readinessProbe**；出现长连接倾斜、跨集群或精细灰度再引入 etcd/Consul。别为「架构完整」硬加一层需要高可用保障的中间件。

## 完整示例

服务端把 `Registrar` 交给 `kratos.New` 托管注册与注销；客户端按第三节一次性 `Dial` 后注入 handler，不要在 handler 里建连：

```go
// app/user-service/cmd/main.go（片段）
func newApp(logger log.Logger, gs *grpc.Server, reg *etcdreg.Registry, svc *server.UserService) *kratos.App {
    v1.RegisterUserServiceServer(gs, svc)
    return kratos.New(
        kratos.Name("user-service"),
        kratos.Version("v1.0.0"),
        kratos.Logger(logger),
        kratos.Server(gs),
        kratos.Registrar(reg), // 来自配置
    )
}
```

## 常见坑

1. **注册了 `127.0.0.1`**：本机自测通过，跨节点必然失败。注册地址必须取网卡可达 IP 或 Pod IP。
2. **服务名不统一**：注册 `user-service`、发现 `userservice`，实例在线却查不到。服务名收敛成常量。
3. **认为注册成功就代表可用**：注册只代表地址写进去了。业务依赖没起来要靠 `/readyz` + Consul HTTP 检查或就绪探针摘除；注册中心短时不可用时 resolver 会用本地缓存继续解析，但缓存不会剔除坏实例，熔断与健康检查不能省。
4. **用 `GetService` 轮询代替 `Watch`**：注册中心压力翻倍，变更延迟等于轮询间隔。直接用 `WithDiscovery`。
5. **`Metadata` 里塞大对象**：etcd、Consul 都有 value 上限，写失败。只放版本、机房、权重这类短标签。
6. **发布直接 kill 进程**：没有摘除等待期，调用方拿旧列表打过来，叠加超时重试就是雪崩。用 `signal.NotifyContext` + `app.Stop`，并给下游设超时预算。
7. **K8s 里既用 Service 又用 etcd 注册**：两套发现并存，实例列表不一致。选一套，另一套明确不用。

## 小结

- Kratos 的 registry 抽象只有 `Registrar` 与 `Discovery`，权重与灰度标签放在 `Metadata`，负载均衡由客户端完成。
- `discovery:///服务名` + `WithDiscovery` 是标准接法，服务名与注册中心地址都来自配置。
- etcd 胜在轻量与已有基础设施，Consul 胜在主动健康检查与可视化；单集群 K8s 优先 Service + DNS，长连接倾斜、跨集群、精细灰度才引入注册中心。
- 可用性取决于「摘除 → 等待 → 优雅退出」与就绪探针，不是取决于选了哪个注册中心。
