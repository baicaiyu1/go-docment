> 一句话定位：先把 SQL 看明白，再谈优化；索引、EXPLAIN、慢日志和 N+1，是数据层性能的四把手术刀。

## 一、B+ 树与两种索引

InnoDB 主键索引是**聚簇索引**，叶子节点直接存整行；二级索引叶子存“索引列 + 主键”，查非索引列要**回表**。

- 所有数据在叶子节点且按 key 有序，范围查询与排序友好
- 树高通常 3~4 层，一次查询 3~4 次页读取
- 联合索引按定义顺序逐列排序，所以有**最左前缀**限制
- 索引不是越多越好：每个索引都增加写放大、磁盘与优化器选择成本

## 二、联合索引、最左前缀与覆盖索引

订单列表按“用户 + 状态 + 时间”查询，索引列顺序必须匹配查询模式；把 `order_no` 放进索引尾部即可覆盖查询列，省掉回表。

```sql
ALTER TABLE orders
  ADD INDEX idx_orders_user_status_created (user_id, status, created_at, order_no);

-- 覆盖索引：Extra 出现 Using index
EXPLAIN SELECT user_id, status, order_no FROM orders
 WHERE user_id = 42 AND status = 1 AND created_at >= '2026-01-01'
 ORDER BY created_at DESC LIMIT 20;

-- 只查 status：缺少最左列 user_id，用不上该索引
EXPLAIN SELECT id FROM orders WHERE status = 1;
```

同一个查询在 GORM 中写成 `Where("user_id = ? AND status = ?", uid, 1).Order("created_at DESC").Limit(20).Find(&pos)`，生成 SQL 与上面一致；**用 `Select` 明确列出字段**才能保住覆盖索引，`SELECT *` 会直接把它破坏。

## 三、索引失效的常见写法

```sql
-- 失效：对索引列做函数
SELECT * FROM orders WHERE DATE(created_at) = '2026-01-01';
SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2026-01-02';

-- 失效：隐式类型转换（phone 为 varchar）
SELECT * FROM users WHERE phone = 13800138000;
SELECT * FROM users WHERE phone = '13800138000';

-- 前导模糊必然全表扫描，搜索需求交给全文索引/ES
SELECT * FROM products WHERE name LIKE '%耳机%';
SELECT * FROM products WHERE name LIKE '耳机%';
```

其他高频原因：`OR` 连接无索引列、`!=`/`NOT IN`、联合索引跳过最左列、`ORDER BY` 与索引顺序不一致、JOIN 两表字符集/排序规则不一致、对索引列做 `+ - * /`。

## 四、EXPLAIN 与慢查询日志

`EXPLAIN` 关注四列：`type`（`const` > `eq_ref` > `ref` > `range` > `index` > `ALL`）、`key`（`NULL` 即未走索引）、`rows`（预估扫描行数）、`Extra`（`Using index` 覆盖、`Using filesort`/`Using temporary` 需警惕）。MySQL 8 可用 `EXPLAIN ANALYZE` 看真实耗时与循环次数。

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 0.2;   -- 200ms
SET PERSIST slow_query_log = ON;    -- 重启后仍生效
SHOW VARIABLES LIKE 'slow_query_log_file';
```

```bash
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query_log_file';"
pt-query-digest /var/lib/mysql/mysql-slow.log > slow_report.txt
```

```powershell
mysql -uroot -p -e "SHOW VARIABLES LIKE 'slow_query_log_file';"
pt-query-digest C:\mysql\data\mysql-slow.log > slow_report.txt
```

报告重点：**总耗时占比、执行次数、平均/最大耗时、扫描行数**。次数多且单次不慢的 SQL，往往比偶发超慢 SQL 更值得优化。

## 五、N+1 的识别与修复

反例是 1 + N 条 SQL；下面三种正解分别适合取聚合根、ID 列表已知、用子表条件筛父表。上线前用 GORM 日志确认实际 SQL 条数。

```go
func (r *orderRepo) listBad(ctx context.Context, uid uint64) []OrderPO {
    var pos []OrderPO
    r.data.db.WithContext(ctx).Where("user_id = ?", uid).Find(&pos)
    for i := range pos { // N+1：100 个订单 = 101 条 SQL
        r.data.db.WithContext(ctx).Where("order_id = ?", pos[i].ID).Find(&pos[i].Items)
    }
    return pos
}

func (r *orderRepo) listGood(ctx context.Context, uid uint64, orderIDs []uint64) ([]OrderPO, error) {
    var pos []OrderPO
    // 1) Preload：订单 + 明细，共 2 条 SQL
    if err := r.data.db.WithContext(ctx).Preload("Items").
        Where("user_id = ?", uid).Find(&pos).Error; err != nil {
        return nil, err
    }
    // 2) 批量 IN：先收集主键，一次查回
    var items []OrderItemPO
    if err := r.data.db.WithContext(ctx).Where("order_id IN ?", orderIDs).Find(&items).Error; err != nil {
        return nil, err
    }
    // 3) Joins + Select：只取需要的列
    var rows []OrderRow
    err := r.data.db.WithContext(ctx).Table("orders").
        Select("orders.order_no, users.nickname").
        Joins("JOIN users ON users.id = orders.user_id").
        Where("orders.status = ?", 1).Scan(&rows).Error
    return pos, err
}
```

`Preload` 支持条件 `Preload("Items", "status = ?", 1)`，嵌套用 `Preload("Items.Product")`。

## 六、深分页与 count

`OFFSET 1000000` 要先扫描并丢弃 100 万行，越翻越慢。改用游标：用上一页最后一个主键做条件；不便改游标时用延迟关联（先只查主键，再按主键回表取整行），两者都能避免大偏移扫描。排序字段必须有索引且唯一，按 `created_at` 翻页时要加 `id` 作为第二排序键避免重复。

```go
func (r *orderRepo) PageByCursor(ctx context.Context, uid, lastID uint64, size int) ([]OrderPO, error) {
    var pos []OrderPO
    err := r.data.db.WithContext(ctx).
        Where("user_id = ? AND id < ?", uid, lastID). // lastID=0 时返回第一页
        Order("id DESC").Limit(size).Find(&pos).Error
    return pos, err
}
```

`COUNT(*)` 在 InnoDB 要扫描最小的二级索引，大表仍可能慢。手段：缩小 `WHERE`、覆盖索引、维护计数表、接受估算值；**不要**对多表 JOIN 结果直接 `COUNT(*)`，先聚合再计数。

## 七、大表 DDL 与慢 SQL 治理流程

大表加索引/改列一律用 `gh-ost` 或 `pt-online-schema-change`，避开业务高峰并监控主从延迟；MySQL 8 的 `ALGORITHM=INSTANT` 只支持部分变更（如末尾加列），不满足会直接报错而不是偷偷锁表。

```bash
gh-ost --host=127.0.0.1 --database=mall --table=orders \
  --alter="ADD INDEX idx_orders_status_created (status, created_at)" \
  --allow-on-master --execute
```

治理流程固定为：慢日志/APM 发现 → `EXPLAIN` 定位 → 加索引或改写 SQL → 压测验证 → SQL 审核与慢查询告警防回归。大字段（商品详情、富文本）拆纵表；千万级订单按时间归档到 `orders_history`。

## 完整示例

订单列表 Repository：游标分页 + Preload，对应上面的联合索引；接口层只暴露 DTO，`OrderPO` 不出 data 包。

```go
// app/order-service/internal/data/order.go
type orderRepo struct{ data *Data }

func NewOrderRepo(d *Data) biz.OrderRepo { return &orderRepo{data: d} }

func (r *orderRepo) ListByUser(ctx context.Context, uid, cursor uint64, size int) ([]*biz.Order, error) {
    if size <= 0 || size > 100 {
        size = 20
    }
    q := r.data.db.WithContext(ctx).Where("user_id = ?", uid)
    if cursor > 0 {
        q = q.Where("id < ?", cursor) // 深分页改用游标
    }
    var pos []OrderPO
    if err := q.Preload("Items").Order("id DESC").Limit(size).Find(&pos).Error; err != nil {
        return nil, err
    }
    out := make([]*biz.Order, 0, len(pos))
    for i := range pos {
        out = append(out, pos[i].ToBiz())
    }
    return out, nil
}
```

## 常见坑

1. **联合索引按“区分度最高”排序**：忽略查询模式，最左前缀永远用不上。
2. **对索引列做函数或运算**：`DATE(created_at)`、`price * 2` 都让索引失效。
3. **隐式类型转换**：`varchar` 列用数字比较，既全表扫描又可能查出错误结果。
4. **`LIKE '%关键词'`**：前导模糊必然全表扫描，搜索应交给全文索引或 ES。
5. **`SELECT *`**：破坏覆盖索引，还把大字段一起读回内存。
6. **大 `OFFSET` 深分页**：页数越深越慢，必须改游标。
7. **只看 `key` 不看 `rows`/`Extra`**：走了索引但扫描百万行，依然是慢 SQL。
8. **盲目加索引**：写放大、锁范围变大、优化器选错索引，删除通常比新增更安全。

## 小结

- 联合索引按查询模式设计并遵守最左前缀，覆盖索引能省掉回表
- 索引失效多来自函数、隐式转换、前导模糊与联合索引跳列
- `EXPLAIN` 看 `type/key/rows/Extra`，慢日志按总耗时占比排优先级
- N+1 用 Preload、批量 IN、Joins + Select 三种方式解决
- 深分页用游标，count 用计数表或缩小范围，大表 DDL 用在线工具
