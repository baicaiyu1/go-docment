# 05-连接池与数据库性能调优

> 一句话定位：数据库性能的上限，往往不是 SQL 慢，而是连接池配错、超时没预算、读写分离读到了旧数据。

## 本篇目标

- 搞懂 `sql.DB` 四个参数，并按 QPS 与 MySQL 容量算出合理值
- 识别连接池耗尽与连接泄漏，用 `db.Stats`、Prometheus、pprof 定位
- 把 `context` 超时从 Gin 网关经 Kratos 服务一路传到 GORM
- 掌握 dbresolver 读写分离、批量写入、PrepareStmt 与事务大小控制

## 一、`sql.DB` 与四个参数

GORM 的 `*gorm.DB` 底层是一个 `*sql.DB` **连接池**，不是单连接。四个参数在 `data.NewDB` 里设置一次，所有 Repository 共享。

```go
// app/order-service/internal/data/data.go
func NewDB(dsn string) (*gorm.DB, func(), error) {
    db, err := gorm.Open(mysql.Open(dsn), &gorm.Config{PrepareStmt: true})
    if err != nil {
        return nil, nil, err
    }
    sqlDB, err := db.DB()
    if err != nil {
        return nil, nil, err
    }
    sqlDB.SetMaxOpenConns(100)                 // 并发上限（使用中 + 空闲）
    sqlDB.SetMaxIdleConns(20)                  // 热连接保留，默认只有 2
    sqlDB.SetConnMaxLifetime(30 * time.Minute) // 必须短于 wait_timeout/代理空闲断连
    sqlDB.SetConnMaxIdleTime(5 * time.Minute)  // 空闲多久后关闭
    return db, func() { _ = sqlDB.Close() }, nil
}
```

| 参数 | 作用 | 配错的后果 |
| --- | --- | --- |
| `MaxOpenConns` | 并发上限 | 太小请求排队；太大打爆 MySQL |
| `MaxIdleConns` | 保留热连接 | 太小频繁建连/断连，握手开销高 |
| `ConnMaxLifetime` | 强制换连接 | 为 0 时连接永久存活，主从切换/重启后报 `invalid connection` |
| `ConnMaxIdleTime` | 回收空闲连接 | 空闲连接长期占用 MySQL 名额 |

`MaxIdleConns` 建议等于或略小于 `MaxOpenConns`，避免“用一下关一下”的抖动。

## 二、按 QPS 与 MySQL 容量估算

```text
单实例并发 ≈ 峰值 QPS × 平均 DB 耗时(s)
maxOpen   ≈ 并发 × 2（突发余量）
总连接     = 副本数 × maxOpen + 其他服务连接 + 运维预留
约束       : 总连接 ≤ max_connections × 0.8
           : ConnMaxLifetime < wait_timeout 与代理/LB 的空闲断连时间
```

示例：单实例 2000 QPS、平均 DB 耗时 5ms → 并发约 10，`maxOpen=20`；8 副本共 160，MySQL `max_connections=1000` 时余量充足。若 500 QPS、平均 50ms → 并发 25，`maxOpen` 至少 50。

```sql
SHOW VARIABLES LIKE 'max_connections';
SHOW VARIABLES LIKE 'wait_timeout';
SHOW STATUS LIKE 'Threads_connected';
SHOW STATUS LIKE 'Threads_running';
```

扩容副本前先做乘法：副本翻倍，数据库连接数也翻倍，这是“扩容把数据库打挂”的最常见原因。

## 三、连接池耗尽与泄漏排查

典型现象：接口 P99 抬升、日志出现 `context deadline exceeded`、`SHOW PROCESSLIST` 大量 `Sleep`、MySQL 报 `Too many connections`、pprof 里 goroutine 大量卡在 `database/sql.(*DB).conn`。先看池内指标，再谈加连接。

```go
func ReportPool(sqlDB *sql.DB, log *zap.Logger) {
    s := sqlDB.Stats()
    log.Info("mysql pool",
        zap.Int("open", s.OpenConnections),
        zap.Int("in_use", s.InUse),
        zap.Int("idle", s.Idle),
        zap.Int64("wait_count", s.WaitCount),
        zap.Duration("wait_duration", s.WaitDuration),
        zap.Int("max_open", s.MaxOpenConnections),
    )
}

// 交给 Prometheus 持续观测，告警看 wait_count 增速与 in_use/max_open
prometheus.MustRegister(collectors.NewDBStatsCollector(sqlDB, "mysql_master"))
```

`WaitCount` 持续增长、`WaitDuration` 变大，说明请求在等连接，而不是 SQL 慢。抓 goroutine 栈确认：

```bash
go tool pprof -http=:8080 "http://127.0.0.1:9103/debug/pprof/goroutine?debug=1"
```

```powershell
go tool pprof -http=:8080 "http://127.0.0.1:9103/debug/pprof/goroutine?debug=1"
```

常见根因：事务里做 RPC/发 MQ、N+1、`MaxOpenConns` 小于实际并发、慢 SQL 占住连接。**连接泄漏**多来自手写 `sql.Rows` 未 `Close`、事务未 `Commit/Rollback`；GORM 链式调用会自己释放，手动 `db.Raw(...).Rows()` 必须 `defer rows.Close()`。

## 四、超时预算：从网关传到 GORM

超时必须逐层递减，下游超时后上游不再傻等。`WithContext` 把取消信号传给驱动，查询被 cancel 后连接尽快归还。

```go
// app/order-service/internal/service/order.go
func (s *OrderService) GetOrder(ctx context.Context, req *v1.GetOrderRequest) (*v1.OrderReply, error) {
    ctx, cancel := context.WithTimeout(ctx, 200*time.Millisecond) // 单次查询预算
    defer cancel()
    o, err := s.repo.Get(ctx, req.Id) // data 层统一 WithContext(ctx)
    if err != nil {
        return nil, errors.From(err, "ORDER_QUERY_FAILED")
    }
    return toReply(o), nil
}
```

| 层级 | 预算 | 说明 |
| --- | --- | --- |
| Gin 网关 | 800ms | 对外承诺的 P99 |
| Kratos gRPC | 400ms | 网关到 order-service |
| MySQL 查询 | 200ms | 单次查询上限 |
| Redis | 50ms | 缓存读写 |

每层预留 10%~20% 余量，不要全部设成一样长。重试只用于**幂等读**，最多 2~3 次并加抖动退避；写操作与事务内禁止盲目重试。

## 五、读写分离：dbresolver 与主从延迟

```go
db.Use(dbresolver.Register(dbresolver.Config{
    Sources:  []gorm.Dialector{mysql.Open(masterDSN)},
    Replicas: []gorm.Dialector{mysql.Open(replicaDSN)},
    Policy:   dbresolver.RandomPolicy{},
}).SetMaxOpenConns(100).SetMaxIdleConns(20).SetConnMaxIdleTime(5 * time.Minute))

// 写后立即读：强制走主库
db.Clauses(dbresolver.Write).WithContext(ctx).Where("id = ?", orderID).Take(&po)
```

默认读走从库、写走主库；也可以 `gorm.Open` 两个 `*gorm.DB` 在 Repository 里手动路由，但事务跨库时无法保证一致性，优先用 dbresolver。主从延迟的应对：下单后跳详情强制读主库或读缓存；延迟敏感的列表页才走从库；监控 `Seconds_Behind_Source`，超阈值自动切主；强一致事务绝不拆到从库。

## 六、批量写入、PrepareStmt 与事务时长

```go
func (r *orderRepo) SaveBatch(ctx context.Context, pos []OrderPO) error {
    // 每批 500~1000 行，避免单条 SQL 过大和长事务
    return r.data.db.WithContext(ctx).CreateInBatches(&pos, 500).Error
}

func (r *productRepo) Upsert(ctx context.Context, po *ProductPO) error {
    return r.data.db.WithContext(ctx).Clauses(clause.OnConflict{
        Columns:   []clause.Column{{Name: "sku"}},
        DoUpdates: clause.AssignmentColumns([]string{"price", "updated_at"}),
    }).Create(po).Error
}
```

`PrepareStmt: true` 复用预编译语句、降低解析开销，但 DDL 变更后应滚动重启。单事务控制在 500~1000 行或 1~2 秒内提交；超大事务会导致 undo/binlog 膨胀、锁等待与主从延迟，批量任务拆小事务并记录断点。

## 七、监控、容量与压测方法

监控四类指标：池（`wait_count`、`in_use/max_open`）、MySQL（`Threads_running`、`Innodb_row_lock_waits`）、SQL（慢查询数、P99）、业务（下单成功率）。容量按“峰值 QPS × 平均耗时”推并发，每季度用压测复核。

压测步骤：固定数据集与索引 → k6 阶梯加压到目标 QPS 的 1.5 倍 → 同时观察网关 P99、`WaitDuration`、`Threads_running` → 找到拐点后按 0.7 倍定容量。工具见 [08-部署与运维/04-性能调优与压测](../08-部署与运维/04-性能调优与压测.md)。

## 完整示例

```go
// app/order-service/internal/data/data.go
package data

import (
    "time"

    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/collectors"
    "gorm.io/driver/mysql"
    "gorm.io/gorm"
)

type MySQLConfig struct {
    DSN             string        `mapstructure:"dsn"`
    MaxOpenConns    int           `mapstructure:"max_open_conns"`
    MaxIdleConns    int           `mapstructure:"max_idle_conns"`
    ConnMaxLifetime time.Duration `mapstructure:"conn_max_lifetime"`
    ConnMaxIdleTime time.Duration `mapstructure:"conn_max_idle_time"`
    PrepareStmt     bool          `mapstructure:"prepare_stmt"`
}

func NewDB(cfg MySQLConfig, reg prometheus.Registerer) (*gorm.DB, func(), error) {
    db, err := gorm.Open(mysql.Open(cfg.DSN), &gorm.Config{PrepareStmt: cfg.PrepareStmt})
    if err != nil {
        return nil, nil, err
    }
    sqlDB, err := db.DB()
    if err != nil {
        return nil, nil, err
    }
    sqlDB.SetMaxOpenConns(cfg.MaxOpenConns)
    sqlDB.SetMaxIdleConns(cfg.MaxIdleConns)
    sqlDB.SetConnMaxLifetime(cfg.ConnMaxLifetime)
    sqlDB.SetConnMaxIdleTime(cfg.ConnMaxIdleTime)
    reg.MustRegister(collectors.NewDBStatsCollector(sqlDB, "mysql_master"))
    return db, func() { _ = sqlDB.Close() }, nil
}
```

Viper 配置（环境变量 `MALL_MYSQL_DSN` 可覆盖，见 [05-治理与扩展/03-配置管理Viper](../05-治理与扩展/03-配置管理Viper.md)）：

```yaml
mysql:
  dsn: "root:root@tcp(127.0.0.1:3306)/mall?charset=utf8mb4&parseTime=True&loc=Local"
  max_open_conns: 100
  max_idle_conns: 20
  conn_max_lifetime: 30m
  conn_max_idle_time: 5m
  prepare_stmt: true
```

## 常见坑

1. **只设 `MaxOpenConns` 不设 `MaxIdleConns`**：默认空闲只有 2，流量抖动时反复建连。
2. **`ConnMaxLifetime=0`**：连接永久存活，MySQL 重启、主从切换、代理断连后报 `invalid connection`。
3. **连接数不乘副本数**：扩容后总连接超过 `max_connections`，新 Pod 全部启动失败。
4. **事务里做 RPC/MQ 或循环查库**：连接被长期占用，池很快耗尽。
5. **忘记 `WithContext`**：客户端断开后查询继续跑，白白占用连接与 CPU。
6. **读写分离后写后立即读**：从库延迟导致“刚下的单查不到”，必须强制读主库或读缓存。
7. **把连接池当限流**：入口不限流，池满后所有请求一起超时，故障面更大。
8. **手动 `sql.Rows` 不 `Close`**：连接永不归还，表现为 `InUse` 持续上涨，是典型连接泄漏。

## 小结

- `sql.DB` 是连接池，四个参数要按 QPS、副本数与 MySQL 容量一起算
- 池耗尽先看 `WaitCount/WaitDuration` 与 goroutine 栈，再谈加连接
- 超时预算从网关到 DB 逐层递减，`WithContext` 必须贯穿全链路
- 读写分离要处理主从延迟，强一致读显式走主库
- 批量写分批、事务短小、PrepareStmt 按需开启并配合滚动重启

## 练习

1. 按你的服务 QPS 与平均 DB 耗时计算 `maxOpen`，再乘副本数校验是否超过 MySQL 容量。
2. 用 `go tool pprof` 抓一次高并发下的 goroutine 栈，找出等待连接的位置。
3. 为订单详情接口配置 dbresolver，并实现“下单后 3 秒内强制读主库”的策略。
