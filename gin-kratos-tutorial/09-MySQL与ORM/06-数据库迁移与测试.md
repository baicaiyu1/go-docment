# 06-数据库迁移与测试

> 一句话定位：迁移脚本是数据库的代码，必须版本化、可回滚，并在 CI 里和业务代码一起验证。

## 本篇目标

- 明确 `AutoMigrate` 的适用边界，生产只认版本化迁移
- 对比 golang-migrate、goose、atlas 的取舍，建立 up/down 目录规范
- 掌握生产变更原则：只做加法、双写回填、在线 DDL、按灰度发布
- 用 testcontainers 写真实 MySQL 测试，每用例事务回滚保证隔离
- 在 CI 中先迁移再跑测试，避免 SQLite 与 MySQL 的行为差异

## 一、AutoMigrate 的适用边界

`AutoMigrate` 只做“加法”：建表、补列、补索引；**不删多余列、不安全改类型、不回填数据、没有 down 脚本**，多副本同时执行还会互相阻塞。它只适合本地开发与一次性脚本；生产环境由独立的迁移 Job/InitContainer 执行版本化 SQL，Kratos 服务启动时**不要**调用它。

## 二、迁移工具对比

| 工具 | 工作方式 | 优点 | 边界 |
| --- | --- | --- | --- |
| golang-migrate | 版本化 SQL，up/down 文件 | 简单、语言无关、CI 友好 | MySQL DDL 隐式提交，失败需人工修复 |
| goose | 版本化 SQL/Go，注释分隔 | 支持 Go 迁移、可嵌入二进制 | 复杂场景仍需自己写 SQL |
| atlas | 声明式 diff + 版本化 | 能生成迁移、lint、检测漂移 | 需要 dev 数据库，学习成本高 |
| GORM AutoMigrate | 结构体 diff | 开发期零成本 | 不删列、不改类型、无 down、大表风险 |

结论：开发可用 `AutoMigrate` 或 atlas diff 提速，**生产只认版本化迁移**，两者不要同时改同一张表。

## 三、版本化目录与 up/down

```text
migrations/
  000001_create_users.up.sql
  000001_create_users.down.sql
  000002_create_products.up.sql
  000002_create_products.down.sql
```

编号连续、描述用动词开头；**已执行的迁移文件永远不再修改**，需要变更就新增一版。

```sql
-- migrations/000001_create_users.up.sql
CREATE TABLE `users` (
  `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
  `email` VARCHAR(128) NOT NULL COMMENT '邮箱',
  `password` CHAR(60) NOT NULL COMMENT 'bcrypt 哈希',
  `nickname` VARCHAR(64) NOT NULL DEFAULT '' COMMENT '昵称',
  `status` TINYINT NOT NULL DEFAULT 1 COMMENT '1正常 0禁用',
  `created_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  `updated_at` DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
  `deleted_at` DATETIME(3) NULL DEFAULT NULL COMMENT '软删除时间',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_users_email` (`email`),
  KEY `idx_users_status_created` (`status`, `created_at`),
  KEY `idx_users_deleted_at` (`deleted_at`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci COMMENT='用户表';
```

```sql
-- migrations/000001_create_users.down.sql
DROP TABLE IF EXISTS `users`;
```

`down` 必须真能回滚：删表、删索引、删列写全；数据回填类迁移的 down 通常只回滚结构，数据无法自动还原，要在注释里写清楚。

## 四、执行迁移

```bash
migrate -path ./migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" up
migrate -path ./migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" down 1
migrate -path ./migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" version
```

```powershell
migrate -path .\migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" up
migrate -path .\migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" down 1
migrate -path .\migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall" version
```

`force` 只用于修复 `dirty` 状态：先人工确认库结构与版本号一致，再强制设置版本，绝不能拿它跳过失败的迁移。goose 用 `-- +goose Up/Down` 注释分隔，格式与 golang-migrate 不同，不要在同一目录混用。

## 五、生产变更：双写、回填、回滚

- **只做加法**：先加可空列或带默认值的列，再回填，最后加非空约束
- **Expand-Contract**：加新列 → 双写 → 回填 → 切读 → 观察 → 删旧列，每步可独立回滚
- **数据迁移双写**：代码同时写新旧字段，回填脚本按主键分批（每批 1000~5000 行）并记录断点
- **大表在线 DDL**：用 `gh-ost`/`pt-online-schema-change`，避开高峰，监控主从延迟与锁等待
- **先发 schema 再发代码**；删列/改语义必须等旧代码全部下线
- **回滚优先向前修复**：生产数据回滚风险高，准备补偿 SQL 比执行 down 更现实

```sql
-- 加列：可空 + INSTANT，避免大表重建与长时间 MDL 等待
ALTER TABLE orders ADD COLUMN remark VARCHAR(255) NULL COMMENT '备注',
  ALGORITHM=INSTANT;
```

上线 checklist：确认备份与恢复演练 → 低峰执行并设置 `lock_wait_timeout` → 观察 MDL 等待与主从延迟 → 先灰度一个实例验证 → 失败立即停并向前修复。

## 六、测试：testcontainers 与 sqlmock

集成测试用真实 MySQL（testcontainers），不要用 SQLite：自增、`ON UPDATE CURRENT_TIMESTAMP`、`FOR UPDATE`、唯一索引 NULL 语义全都不同。单元测试可用 sqlmock 隔离 SQL 生成逻辑。

```go
// app/order-service/internal/data/testhelper_test.go
func setupDB(t *testing.T) *gorm.DB {
    t.Helper()
    if testing.Short() {
        t.Skip("skip db test in -short mode")
    }
    ctx := context.Background()
    ctr, err := mysql.Run(ctx, "mysql:8.4",
        mysql.WithDatabase("mall_test"), mysql.WithUsername("root"), mysql.WithPassword("root"))
    if err != nil {
        t.Fatal(err)
    }
    t.Cleanup(func() { _ = ctr.Terminate(ctx) })
    dsn, err := ctr.ConnectionString(ctx, "parseTime=true&loc=Local&charset=utf8mb4")
    if err != nil {
        t.Fatal(err)
    }
    db, err := gorm.Open(gormmysql.Open(dsn), &gorm.Config{})
    if err != nil {
        t.Fatal(err)
    }
    if err := runMigrations(dsn); err != nil { // 跑真实迁移脚本，而不是 AutoMigrate
        t.Fatal(err)
    }
    return db
}
```

```go
func TestGetUserNotFound(t *testing.T) {
    sqlDB, mock, _ := sqlmock.New()
    db, _ := gorm.Open(gormmysql.New(gormmysql.Config{
        Conn: sqlDB, SkipInitializeWithVersion: true,
    }), &gorm.Config{})
    mock.ExpectQuery("SELECT \\* FROM `users`").
        WillReturnRows(sqlmock.NewRows([]string{"id", "email"}))
    var po UserPO
    err := db.WithContext(context.Background()).Take(&po, 1).Error
    if !errors.Is(err, gorm.ErrRecordNotFound) {
        t.Fatalf("want not found, got %v", err)
    }
}
```

## 七、CI 中跑迁移

```yaml
services:
  mysql:
    image: mysql:8.4
    env:
      MYSQL_ROOT_PASSWORD: root
      MYSQL_DATABASE: mall_test
    ports: ["3306:3306"]
    options: >-
      --health-cmd "mysqladmin ping -h 127.0.0.1 -proot"
      --health-interval 3s --health-timeout 3s --health-retries 20
steps:
  - run: migrate -path ./migrations -database "mysql://root:root@tcp(127.0.0.1:3306)/mall_test" up
  - run: go test ./... -race -count=1
```

CI 必须等 MySQL healthy 再迁移；迁移失败立即中止，不要带着半套 schema 跑测试。

## 完整示例

每个用例包一层事务，结束后回滚，保证用例互不影响；被测代码必须接收 `tx`，不能自己另开连接。

```go
// app/order-service/internal/data/order_repo_test.go
func withRollback(t *testing.T, ctx context.Context, db *gorm.DB, fn func(tx *gorm.DB)) {
    t.Helper()
    tx := db.WithContext(ctx).Begin()
    if tx.Error != nil {
        t.Fatal(tx.Error)
    }
    defer tx.Rollback()
    fn(tx)
}

func TestSubmitOrder(t *testing.T) {
    db := setupDB(t)
    ctx := context.Background()
    withRollback(t, ctx, db, func(tx *gorm.DB) {
        seedStock(t, tx, 1, 100)
        repo := NewOrderRepo(NewData(tx))
        o, err := repo.Submit(ctx, &biz.SubmitOrder{
            UserID: 1, IdempotencyKey: "req-001",
            Items: []biz.OrderItem{{ProductID: 1, Quantity: 1, Price: 19900}},
        })
        if err != nil {
            t.Fatal(err)
        }
        if o.Amount != 19900 {
            t.Fatalf("amount = %d, want 19900", o.Amount)
        }
        var stock StockPO
        if err := tx.WithContext(ctx).Where("product_id = ?", 1).Take(&stock).Error; err != nil {
            t.Fatal(err)
        }
        if stock.Available != 99 {
            t.Fatalf("available = %d, want 99", stock.Available)
        }
    })
}
```

## 常见坑

1. **修改已执行的迁移文件**：本地能过，其他环境版本号相同但结构不同，排查极难。
2. **down 缺失或写错**：回滚时删错表/索引，事故比不回滚更大。
3. **`AutoMigrate` 与迁移文件混用**：同一张表两套 schema 来源，最终没人知道线上结构。
4. **大表直接 `ALTER` 加索引**：锁表、主从延迟、业务超时；必须用在线 DDL 工具并控峰。
5. **测试用 SQLite**：自增、时间戳默认值、`FOR UPDATE`、唯一索引 NULL 规则全不同。
6. **用例回滚失效**：被测代码用了全局 `db` 或新连接，数据残留导致后续用例随机失败。
7. **CI 未等 MySQL 就绪**：迁移报连接拒绝，流水线偶发红。
8. **代码与 schema 发布顺序颠倒**：先删列后发代码，旧实例直接报 `Unknown column`。

## 小结

- 生产只认版本化迁移，工具首选 golang-migrate 或 goose，atlas 适合声明式管理
- 目录编号连续、up/down 成对，已执行文件不改，只新增版本
- 变更遵循“只做加法 + Expand-Contract”，大表用在线 DDL 并准备回滚
- 测试用真实 MySQL，每用例事务回滚并显式 seed，被测代码接收 `tx`
- CI 先迁移、等健康检查，再跑 `-race` 测试
