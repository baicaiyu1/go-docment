# 03-事务-乐观锁-软删除

> 一句话定位：事务管边界、锁管并发、软删除管历史，三者错一个，订单和库存就会对不上。

## 本篇目标

- 掌握 `db.Transaction`、嵌套事务（SavePoint）与手动回滚的边界
- 明确事务内不能做 RPC/HTTP/MQ，改用 outbox + Kafka 异步补偿
- 用 `version` 乐观锁与 `clause.Locking` 悲观锁解决库存并发
- 理解隔离级别、死锁排查路径与软删除的唯一索引冲突
- 用幂等键保证重复请求不会生成重复订单

## 前置知识

- 已读 [09-MySQL与ORM/02-GORM核心用法与模型设计](02-GORM核心用法与模型设计.md)
- 了解 ACID、行锁、间隙锁与 MVCC 的基本概念
- 知道 gRPC 是同步调用、Kafka 是异步消息（见 [12-微服务与Kratos/08-分布式事务与最终一致性](../12-微服务与Kratos/08-分布式事务与最终一致性.md)）

## 一、事务的三种写法

**推荐：`db.Transaction`**。回调返回 error 自动回滚，返回 nil 自动提交，不必手写 defer。

```go
// app/order-service/internal/data/order.go
func (r *orderRepo) CreateOrder(ctx context.Context, o *biz.Order) error {
    payload, err := json.Marshal(o)
    if err != nil {
        return err
    }
    return r.data.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(toOrderPO(o)).Error; err != nil {
            return err
        }
        if err := tx.CreateInBatches(toItemPOs(o), 100).Error; err != nil {
            return err
        }
        // 本地事务只写业务表 + outbox，提交后由消费者投递 Kafka
        return tx.Create(&OutboxPO{
            EventType: "order.created",
            Payload:   string(payload),
            Status:    0,
        }).Error
    })
}
```

**嵌套事务**：GORM 在已有事务上再调用 `Transaction` 会用 `SAVEPOINT` 实现，内层失败只回滚到保存点，外层可决定降级或继续。

```go
func (r *orderRepo) CreateWithAudit(ctx context.Context, o *biz.Order) error {
    return r.data.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        if err := tx.Create(toOrderPO(o)).Error; err != nil {
            return err
        }
        // 审计失败只回滚到 SAVEPOINT，不影响主流程
        if err := tx.Transaction(func(tx2 *gorm.DB) error {
            return tx2.Create(&AuditPO{OrderID: o.ID, Action: "create"}).Error
        }); err != nil {
            r.log.Warn("audit degraded", zap.Error(err))
        }
        return nil
    })
}
```

要“全有或全无”时把内层 err 继续向上返回；不需要 SavePoint 语义时用 `Session(&gorm.Session{DisableNestedTransaction: true})`。**不要在事务里启动 goroutine 复用 `tx`**，`*gorm.DB` 不是并发安全的。

## 二、事务边界：只包本地数据库操作

下面这些必须放到事务外：调用 product-service 预扣库存、发送 Kafka 事件、调用支付/短信/对象存储、读写 Redis（除同一语义的锁）。原因是网络耗时不可控，事务会长时间持有行锁与连接，轻则池耗尽，重则锁等待雪崩。正确模式是**本地事务 + outbox 表**，由独立消费者投递并做补偿，详见 [11-消息队列/04-可靠投递-幂等-顺序消息](../11-消息队列/04-可靠投递-幂等-顺序消息.md)。

## 三、隔离级别与死锁

InnoDB 默认 `REPEATABLE READ`（RR）。RR 下普通 `SELECT` 是快照读，`SELECT ... FOR UPDATE` 与 `UPDATE` 是当前读；当前读会加锁，RR 还有间隙锁，死锁概率高于 RC。高并发扣减可在确认 `binlog_format=ROW` 后评估 `READ COMMITTED`：`db.Transaction(fn, &sql.TxOptions{Isolation: sql.LevelReadCommitted})`。

```sql
SELECT @@transaction_isolation;
SHOW VARIABLES LIKE 'innodb_lock_wait_timeout';
SHOW ENGINE INNODB STATUS\G          -- 看 LATEST DETECTED DEADLOCK
SET PERSIST innodb_print_all_deadlocks = ON;
```

治理思路：**固定加锁顺序**（都按 `product_id` 升序）、缩短事务、确保 `WHERE` 走索引（否则锁大量间隙）、对错误码 `1213` 做有限重试。

## 四、乐观锁：version 字段

适合冲突不频繁的库存扣减。核心是 `UPDATE ... WHERE id=? AND version=?`，用 `RowsAffected` 判断是否抢到。

```go
func (r *stockRepo) Deduct(ctx context.Context, productID uint64, qty int64) error {
    for i := 0; i < 3; i++ { // 冲突重试，需上限 + 退避
        var po StockPO
        if err := r.data.db.WithContext(ctx).
            Where("product_id = ?", productID).Take(&po).Error; err != nil {
            return err
        }
        if po.Available < qty {
            return biz.ErrStockNotEnough
        }
        res := r.data.db.WithContext(ctx).Model(&StockPO{}).
            Where("product_id = ? AND version = ? AND available >= ?", productID, po.Version, qty).
            Updates(map[string]any{
                "available": gorm.Expr("available - ?", qty),
                "version":   gorm.Expr("version + 1"),
            })
        if res.Error != nil {
            return res.Error
        }
        if res.RowsAffected == 1 {
            return nil
        }
        // RowsAffected=0：版本冲突或库存不足，重新读取后再区分
    }
    return biz.ErrConflict
}
```

只检查 `res.Error` 不检查 `RowsAffected` 是最常见的 bug：冲突被当成成功，库存少扣。

## 五、悲观锁：SELECT ... FOR UPDATE

适合冲突频繁、必须一次成功的场景（如同一订单的重复支付回调）。`clause.Locking{Strength: "UPDATE"}` 会生成 `FOR UPDATE`。

```go
func (r *stockRepo) DeductForUpdate(ctx context.Context, productID uint64, qty int64) error {
    return r.data.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        var po StockPO
        if err := tx.Clauses(clause.Locking{Strength: "UPDATE"}).
            Where("product_id = ?", productID).Take(&po).Error; err != nil {
            return err
        }
        if po.Available < qty {
            return biz.ErrStockNotEnough
        }
        return tx.Model(&StockPO{}).Where("id = ?", po.ID).
            Update("available", gorm.Expr("available - ?", qty)).Error
    }, &sql.TxOptions{Isolation: sql.LevelReadCommitted})
}
```

`FOR UPDATE` 必须满足：条件列有索引、事务尽量短、加锁顺序一致。并发极高时优先 Redis 预扣，不要把数据库行锁当万能锁。

## 六、软删除与唯一索引冲突

`gorm.DeletedAt` 会让查询自动追加 `deleted_at IS NULL`，但 `users.email` 若是普通唯一索引，软删除后该行仍在表里，**同邮箱无法重新注册**。方案：`deleted_at` 改为 `BIGINT NOT NULL DEFAULT 0`，与业务键组成复合唯一索引。

```sql
ALTER TABLE users
  MODIFY deleted_at BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '0未删除，其余为删除时间戳(ms)',
  DROP INDEX uk_users_email,
  ADD UNIQUE KEY uk_users_email_del (email, deleted_at);
```

```go
import "gorm.io/plugin/soft_delete"

type UserPO struct {
    ID        uint64                `gorm:"primaryKey"`
    Email     string                `gorm:"uniqueIndex:uk_users_email_del,priority:1"`
    DeletedAt soft_delete.DeletedAt `gorm:"softDelete:milli;uniqueIndex:uk_users_email_del,priority:2"`
}
```

迁移前先把历史 `DATETIME` 转为毫秒时间戳，否则改类型会截断数据。**不要**直接给 `gorm.DeletedAt` 加 `(email, deleted_at)` 复合唯一索引：MySQL 把多个 `NULL` 视为互不相等，两条活跃行仍能插入。恢复删除用 `db.WithContext(ctx).Unscoped().Model(&po).Update("deleted_at", 0)`。

## 七、幂等键

客户端每次提交带一个 `idempotency_key`，服务端建唯一索引；插入冲突说明重复请求，直接返回上次结果或 `ErrDuplicateRequest`。它和事务必须在同一个本地事务里，避免“键写成功、订单失败”。

## 完整示例

下单主链路：幂等键 → 条件更新扣库存（防超卖）→ 写订单与明细，全部在一个事务内；扣减按 `product_id` 升序，避免交叉死锁。

```go
// app/order-service/internal/data/order.go
func (r *orderRepo) Submit(ctx context.Context, req *biz.SubmitOrder) (*biz.Order, error) {
    var created *biz.Order
    err := r.data.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        res := tx.Clauses(clause.OnConflict{DoNothing: true}).
            Create(&IdempotencyPO{Key: req.IdempotencyKey, UserID: req.UserID})
        if res.Error != nil {
            return res.Error
        }
        if res.RowsAffected == 0 {
            return biz.ErrDuplicateRequest
        }
        for _, it := range req.SortedItems() { // 固定按 product_id 升序
            r2 := tx.Model(&StockPO{}).
                Where("product_id = ? AND available >= ?", it.ProductID, it.Quantity).
                Updates(map[string]any{
                    "available": gorm.Expr("available - ?", it.Quantity),
                    "version":   gorm.Expr("version + 1"),
                })
            if r2.Error != nil {
                return r2.Error
            }
            if r2.RowsAffected == 0 {
                return biz.ErrStockNotEnough
            }
        }
        po := toOrderPO(req.Order)
        if err := tx.Create(po).Error; err != nil {
            return err
        }
        if err := tx.CreateInBatches(toItemPOs(po.ID, req.Items), 100).Error; err != nil {
            return err
        }
        created = po.ToBiz()
        return nil
    })
    return created, err
}
```

## 常见坑

1. **`defer tx.Rollback()` 无条件执行**：Commit 后返回 `sql.ErrTxDone`，日志全是噪音，应按命名 `err` 判断。
2. **事务内调 gRPC/Kafka**：下游抖动把数据库连接和行锁一起拖死，故障扩散到整条链路。
3. **RR 下读不到刚提交的数据**：先快照读再判断，看到旧版本，误以为丢更新。
4. **乐观锁只看 `Error` 不看 `RowsAffected`**：冲突被当成成功，库存少扣。
5. **软删除 + 普通唯一索引**：删除后无法重建同邮箱用户；复合索引含 `NULL` 又不起作用。
6. **大事务批量更新**：一次改几十万行，binlog 膨胀、主从延迟、锁等待超时。
7. **在 goroutine 里复用 `tx`**：`*gorm.DB` 非并发安全，随机报错或串事务。

## 小结

- 优先 `db.Transaction`；嵌套事务默认 SavePoint 语义，想清内层失败是否拖垮外层
- 事务只包本地数据库操作，跨服务用 outbox + 异步补偿
- 冲突少用乐观锁并检查 `RowsAffected`，冲突多用悲观锁但必须短事务
- 软删除要配复合唯一索引或归档表，别让 `NULL` 骗了你
- 幂等键唯一索引与业务写在同一事务，重复请求直接短路
