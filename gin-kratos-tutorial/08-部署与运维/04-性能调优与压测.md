# 性能调优与压测

> 一句话定位：先定 SLO，再用 k6/ghz 拿到可复现的 QPS、P99、错误率，然后用 pprof 找到热点，最后一次只改一个变量复压验证。

## 本篇目标

- 设计压测场景与指标口径，保证结果可复现、可对比
- 用 k6 压 HTTP、ghz 压 Kratos gRPC，并把阈值接进流水线
- 掌握 pprof 五类 profile、`runtime/trace` 与 benchmark 的正确用法
- 按容器 limit 调 `GOGC`/`GOMEMLIMIT`/`GOMAXPROCS`，定位 DB/Redis 瓶颈

## 一、指标口径与压测场景

| 指标 | 口径 | 示例目标 |
| --- | --- | --- |
| QPS | 成功请求速率（2xx 或 `code=0`） | 按容量规划 |
| P99 | 服务端处理耗时直方图 | HTTP < 100ms，gRPC < 50ms |
| 错误率 | 5xx / 总请求 | < 0.1% |
| 饱和度 | CPU、内存、连接池、goroutine | < 70% limit |

场景至少四种：**基准**（单接口单实例）、**全链路**（APISIX → gateway → gRPC）、**120% 峰值持续 30 分钟**（暴露泄漏与 GC 抖动）、**尖刺**（10 秒内翻 5 倍，验证限流与扩容）。只压 1 分钟的数据没有参考价值。

## 二、工具与脚本

| 工具 | 协议 | 适用 |
| --- | --- | --- |
| k6 | HTTP/WebSocket | 主选，脚本化、带 thresholds、CI 友好 |
| ghz | gRPC | 直读 proto，支持并发与固定 RPS |
| wrk | HTTP | 压极限 QPS，客户端开销最低 |

```text
// deploy/k6/user.js
import http from 'k6/http';
import { check } from 'k6';

export const options = {
    stages: [
        { duration: '30s', target: 200 }, // 预热，排除冷启动
        { duration: '5m', target: 400 },  // 稳态
        { duration: '30s', target: 0 },
    ],
    thresholds: {
        http_req_failed: ['rate<0.001'],
        http_req_duration: ['p(99)<100'],
    },
};

export default function () {
    const res = http.get(`${__ENV.BASE_URL}/api/v1/users/1`, {
        headers: { Authorization: `Bearer ${__ENV.TOKEN}`, 'X-Request-Id': `k6-${__VU}-${__ITER}` },
    });
    check(res, { 'status is 200': (r) => r.status === 200 });
}
```

```bash
BASE_URL=http://127.0.0.1:8080 TOKEN=dev-token \
  k6 run --summary-export=report.json deploy/k6/user.js
```

```powershell
$env:BASE_URL = "http://127.0.0.1:8080"; $env:TOKEN = "dev-token"
k6 run --summary-export=report.json deploy/k6/user.js
```

```bash
ghz --insecure --proto api/user/v1/user.proto --call user.v1.UserService.GetUser \
  -d '{"id":1}' -c 50 --rps 2000 --duration 60s 127.0.0.1:9001
```

阈值不达标时 k6 以非 0 退出，可直接做流水线门禁。先直压 user-service:9001 拿到能力上限，再压网关全链路，差值就是网关与序列化成本。

## 三、pprof 与 trace：先拿证据

```go
// app/gateway/internal/router/debug.go（只挂管理端口 9101，绝不暴露公网）
package router

import (
    "net/http"
    _ "net/http/pprof"
)

func NewDebugMux() *http.ServeMux {
    mux := http.NewServeMux()
    mux.Handle("/debug/pprof/", http.DefaultServeMux)
    return mux
}
```

```bash
go tool pprof -http=:8081 "http://127.0.0.1:9101/debug/pprof/profile?seconds=30"  # CPU
go tool pprof -http=:8081 "http://127.0.0.1:9101/debug/pprof/heap"               # 内存
go tool pprof -http=:8081 "http://127.0.0.1:9101/debug/pprof/goroutine?debug=1"  # 协程
go tool trace "http://127.0.0.1:9101/debug/pprof/trace?seconds=5"
```

CPU 看 `flat`（自身耗时）与 `cum`（含调用链），`list 函数名` 定位到行；heap 的 `inuse_space` 是当前占用、`alloc_space` 是累计分配；goroutine 持续上涨通常是连接、channel 或锁没释放；block/mutex 需先用 `SetBlockProfileRate` 开采样，仅排障期间开启。

## 四、benchmark：锁定单点开销

```go
// app/gateway/internal/handler/user_bench_test.go
package handler

import (
    "net/http"
    "net/http/httptest"
    "testing"

    "github.com/gin-gonic/gin"
)

func BenchmarkGetUser(b *testing.B) {
    gin.SetMode(gin.TestMode)
    r := gin.New()
    r.GET("/api/v1/users/:id", func(c *gin.Context) {
        c.JSON(http.StatusOK, gin.H{"code": 0, "data": c.Param("id")})
    })
    req := httptest.NewRequest(http.MethodGet, "/api/v1/users/1", nil)
    b.ReportAllocs()
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        r.ServeHTTP(httptest.NewRecorder(), req)
    }
}
```

```bash
go test -run '^$' -bench BenchmarkGetUser -benchmem -count 5 ./app/gateway/internal/handler/ | tee bench.txt
benchstat bench.txt
```

benchmark 验证「单点改动是否更快」，压测验证「系统吞吐是否提升」；JSON 序列化、正则预编译、middleware 里多余的 `Set/Get` 都适合先用 benchmark 验证。

## 五、GC 与运行时参数

```bash
GOGC=200 GOMEMLIMIT=400MiB GOMAXPROCS=2 ./bin/gateway
```

- `GOGC=100` 为默认，调到 200 减少 GC 次数但堆更大，延迟敏感服务小步试（150 → 200）并复压对比
- `GOMEMLIMIT` 是软上限，设为容器内存 limit 的 70%~80%，能防 OOM 但不能替代限流
- Go 1.25 会读取 cgroup CPU 限额，仍要核对 `GOMAXPROCS` 与 `limits.cpu` 一致
- 在线服务禁用 `GOGC=off`

## 六、连接池与超时

```go
// app/gateway/cmd/main.go 片段
srv := &http.Server{Addr: ":8080", Handler: r, ReadHeaderTimeout: 3 * time.Second,
    ReadTimeout: 5 * time.Second, WriteTimeout: 10 * time.Second, IdleTimeout: 60 * time.Second}
transport := &http.Transport{MaxIdleConns: 200, MaxIdleConnsPerHost: 200,
    IdleConnTimeout: 60 * time.Second, ResponseHeaderTimeout: 2 * time.Second,
    DialContext: (&net.Dialer{Timeout: 500 * time.Millisecond}).DialContext}
sqlDB.SetMaxOpenConns(50)
sqlDB.SetMaxIdleConns(20)
sqlDB.SetConnMaxLifetime(30 * time.Minute)
```

起始公式：`maxOpen ≈ QPS × 平均耗时(s) × 2`，并满足「副本数 × maxOpen < MySQL `max_connections` × 0.8」；Redis 同理设 `PoolSize` 与 `ReadTimeout`。所有超时必须显式设置，`0` 表示无限等待，会成为故障放大器。

## 七、瓶颈定位与火焰图

| 现象 | 先看哪里 | 常见原因 |
| --- | --- | --- |
| P99 高、CPU 不满 | 下游耗时、锁等待、连接池排队 | 慢 SQL、大 key、池过小 |
| CPU 打满 | CPU 火焰图 | 序列化、正则、日志、无缓存计算 |
| 内存持续上涨 | heap `inuse_space`、goroutine 数 | 泄漏、缓存无上限 |
| QPS 上不去且错误率高 | 客户端端口/fd、限流、DB 连接 | 压测机瓶颈、Sentinel 规则过紧 |

```bash
go tool pprof -top -cum "http://127.0.0.1:9101/debug/pprof/profile?seconds=30"
```

MySQL 看 `SHOW PROCESSLIST` 与慢查询日志，Redis 看 `SLOWLOG GET 10` 与 `INFO commandstats`；DB 指标正常但应用延迟高时，问题通常在连接池或超时。

## 八、容量规划与报告

```text
副本数 = ceil(峰值QPS × 冗余系数 / (单实例QPS × 目标利用率))
例：单实例 3000 QPS，峰值 20000，冗余 1.3，利用率 0.6 → ceil(20000×1.3/(3000×0.6)) = 15
```

```text
压测报告模板
1. 结论：X 副本可稳定承载 Y QPS，P99 = Z ms，错误率 W%
2. 环境：镜像 digest、节点规格、副本数、依赖版本、数据量
3. 场景与数据：基准/全链路/120% 峰值/尖刺，各持续时长与 P50/P95/P99
4. 瓶颈证据与调优前后对比表（每次只改一个变量）、扩容阈值、回滚条件
```

## 常见坑

1. **压测机与被测服务同机**：CPU 互相抢，数据完全失真；还要检查客户端 fd 与端口是否耗尽。
2. **只看平均延迟**：平均 20ms、P99 800ms，用户照样超时；一律以 P99 为准。
3. **不预热、不固定版本**：冷启动与依赖缓存差异让两轮结果不可比。
4. **用 `-race` 构建做压测**：性能下降数倍，测出的上限毫无意义。
5. **pprof 暴露公网**：泄露内存内容，还可能被恶意触发高开销采样。
6. **`GOMAXPROCS` 按物理核设置**：容器限 2 核却开 16 个 P，调度开销反而变大。
7. **不压 120%**：只压 60% 利用率永远发现不了连接泄漏与扩容缺口。

## 小结

- 先定 SLO 与场景，再取数；预热、多轮、固定版本是结果可信的前提
- k6 压 HTTP、ghz 压 gRPC，先单服务后全链路，差值就是框架与网关成本
- pprof 定位热点、benchmark 验证单点、trace 看调度阻塞，改完必须复压
