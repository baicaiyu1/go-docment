> 一句话定位：指标负责发现、日志与链路负责定位、runbook 负责处置——SLO 算清楚、每条告警挂处置文档，值班同学凌晨三点也知道先做什么。

## 一、SLI、SLO 与错误预算

| SLI | 计算方式 | SLO（30 天） | 错误预算 |
| --- | --- | --- | --- |
| 可用性 | 非 5xx 请求 / 总请求 | 99.9% | 43m12s 不可用 |
| 延迟 | `≤200ms` 请求的比例 | 99% | 1% 请求可超时 |
| 消费时效 | 订单消息 1 分钟内消费的比例 | 99.5% | 0.5% 可延迟 |

```yaml
# deploy/prometheus/rules/slo.yml：先落 recording rule，再谈告警
groups:
  - name: slo
    rules:
      - record: sli:http_success_ratio:5m
        expr: |
          sum(rate(http_server_requests_total{job="gateway",code!~"5.."}[5m]))
          / sum(rate(http_server_requests_total{job="gateway"}[5m]))
      - record: slo:http_error_budget_remaining:30d
        expr: |
          1 - (1 - (sum(rate(http_server_requests_total{job="gateway",code!~"5.."}[30d]))
                    / sum(rate(http_server_requests_total{job="gateway"}[30d])))) / 0.001
```

错误预算驱动**决策**：充足时正常迭代，消耗过半冻结非必要发布，耗尽后只允许修复类变更；没有这条规则，SLO 只是看板上的数字。

## 二、指标口径与抓取

| 信号 | 指标 | 说明 |
| --- | --- | --- |
| 流量 | `http_server_requests_total{service,method,route,code}` | 路由用模板 `/users/:id` |
| 延迟 | `http_server_request_duration_seconds_bucket` | 直方图，用于算 P99 |
| 错误 | 同上，`code=~"5.."` | 4xx 不计入错误率 |
| 饱和度 | `go_goroutines`、`process_resident_memory_bytes` | 对照请求量看水位 |

```yaml
# deploy/prometheus/prometheus.yml
global: {scrape_interval: 15s, evaluation_interval: 30s}
rule_files: ["rules/*.yml"]
alerting: {alertmanagers: [{static_configs: [{targets: ["alertmanager:9093"]}]}]}
scrape_configs:
  - job_name: gateway
    kubernetes_sd_configs: [{role: pod}]
    relabel_configs:
      - {source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape], action: keep, regex: "true"}
      - {source_labels: [__meta_kubernetes_pod_label_app], target_label: service}
```

`user_id`、`order_id`、原始 URL 一律不做 label；指标端口（9101/9102/9103）与业务端口分离，只在内网暴露。

## 三、告警规则

```yaml
# deploy/prometheus/rules/mall.yml
groups:
  - name: mall
    rules:
      - alert: GatewayHigh5xxRatio
        expr: sum(rate(http_server_requests_total{job="gateway",code=~"5.."}[5m])) / sum(rate(http_server_requests_total{job="gateway"}[5m])) > 0.01
        for: 5m
        labels: {severity: critical, team: platform}
        annotations: {summary: "网关 5xx 比例 > 1%", runbook_url: "https://wiki.mall.local/runbook/gateway-5xx"}
      - alert: GatewayP99LatencyHigh
        expr: histogram_quantile(0.99, sum by (le) (rate(http_server_request_duration_seconds_bucket{job="gateway"}[5m]))) > 0.5
        for: 10m
        labels: {severity: warning, team: platform}
        annotations: {summary: "网关 P99 > 500ms", runbook_url: "https://wiki.mall.local/runbook/gateway-latency"}
      - alert: GatewayQPSDropToZero
        expr: sum(rate(http_server_requests_total{job="gateway"}[5m])) == 0
        for: 3m
        labels: {severity: critical, team: platform}
        annotations: {summary: "QPS 归零，疑似入口或摘流异常", runbook_url: "https://wiki.mall.local/runbook/qps-zero"}
      - alert: ServiceInstanceDown
        expr: absent(up{job="gateway"} == 1)
        for: 2m
        labels: {severity: critical, team: platform}
        annotations: {summary: "gateway 抓取目标全部消失", runbook_url: "https://wiki.mall.local/runbook/instance-down"}
      - alert: CircuitBreakerOpen
        expr: max by (resource) (mall_circuit_breaker_open{state="open"}) == 1
        for: 1m
        labels: {severity: critical, team: platform}
        annotations: {summary: "熔断打开 {{ $labels.resource }}", runbook_url: "https://wiki.mall.local/runbook/breaker-open"}
      - alert: KafkaConsumerLagHigh
        expr: sum by (group, topic) (kafka_consumergroup_lag) > 10000
        for: 10m
        labels: {severity: warning, team: order}
        annotations: {summary: "消费积压 {{ $labels.group }}/{{ $labels.topic }}", runbook_url: "https://wiki.mall.local/runbook/kafka-lag"}
```

错误率用比例不用绝对值（低流量绝对值必然误报）；`for` 是最低成本的防抖；实例下线必须用 `absent()`，因为目标被移除后 `up` 序列会消失。熔断状态由 Sentinel Go 埋点为 0/1 指标，不要用日志做告警源。

## 四、Alertmanager 路由与抑制

```yaml
# deploy/prometheus/alertmanager.yml
route:
  receiver: oncall-default
  group_by: [alertname, service]
  repeat_interval: 4h
  routes:
    - {matchers: ['severity="critical"'], receiver: oncall-phone, continue: true}
    - {matchers: ['team="platform"'], receiver: platform-im}
inhibit_rules:
  - source_matchers: ['alertname="GatewayQPSDropToZero"']
    target_matchers: ['alertname=~"GatewayHigh5xxRatio|GatewayP99LatencyHigh"']
    equal: [service]
receivers:
  - {name: oncall-default, webhook_configs: [{url: "http://im-webhook:8060/alert"}]}
  - {name: oncall-phone, webhook_configs: [{url: "http://phone-gateway:8080/call", send_resolved: true}]}
  - {name: platform-im, webhook_configs: [{url: "http://im-webhook:8060/platform"}]}
```

抑制解决「一次故障刷屏」：入口挂了必然同时触发 5xx 与延迟，只保留根因那条。`repeat_interval` 太短会被屏蔽、太长会漏掉未恢复的故障，4h 是常见起点。

## 五、Grafana 看板

看板按 **RED + 四黄金信号** 分层：Rate/Errors/Duration → 依赖（下游延迟、熔断、连接池、Kafka lag）→ 运行时（goroutine、GC、内存/limit）→ 业务（下单成功率）。关键 PromQL：

```text
sum by (route) (rate(http_server_requests_total{job="gateway",code=~"5.."}[5m]))
  / sum by (route) (rate(http_server_requests_total{job="gateway"}[5m]))
histogram_quantile(0.99, sum by (le, route) (rate(http_server_request_duration_seconds_bucket{job="gateway"}[5m])))
```

每个面板必须带单位与阈值线（如 P99 画 100ms/500ms），否则值班判断全靠猜。

## 六、日志：stdout JSON → Loki

```yaml
# deploy/loki/promtail.yml
server: {http_listen_port: 9080, grpc_listen_port: 0}
clients: [{url: "http://loki:3100/loki/api/v1/push"}]
scrape_configs:
  - job_name: pods
    kubernetes_sd_configs: [{role: pod}]
    pipeline_stages:
      - {json: {expressions: {level: level, service: service, trace_id: trace_id}}}
      - {labels: {level: level, service: service}}
```

```text
{"level":"error","ts":"2026-11-25T10:00:00.123+08:00","service":"gateway","request_id":"3f9c","trace_id":"4b1e...","http.method":"GET","http.path":"/api/v1/users/1","http.status":500,"latency_ms":812,"msg":"upstream error"}
```

容器只写 stdout，采集器负责落盘与轮转。Loki 索引 label，适合按 `trace_id/service/level` 查；需要复杂全文检索与审计时用 ELK（Filebeat → Elasticsearch）。共同要求：JSON 结构化、带 `trace_id`、敏感字段脱敏、30 天以上降采样。

## 七、链路采样与存储

```yaml
# deploy/otel/collector.yaml
receivers:
  otlp: {protocols: {grpc: {endpoint: 0.0.0.0:4317}, http: {endpoint: 0.0.0.0:4318}}}
processors:
  tail_sampling:
    policies:
      - {name: errors, type: status_code, status_code: {status_codes: [ERROR]}}
      - {name: slow, type: latency, latency: {threshold_ms: 500}}
      - {name: baseline, type: probabilistic, probabilistic: {sampling_percentage: 5}}
exporters:
  otlp/jaeger: {endpoint: "jaeger:4317", tls: {insecure: true}}
service:
  pipelines: {traces: {receivers: [otlp], processors: [tail_sampling], exporters: [otlp/jaeger]}}
```

头部采样省资源但会丢错误链路；**尾部采样**等整条 trace 结束再决策，错误与慢请求 100% 保留、正常请求 5%。Jaeger 存储按天清理，生产保留 7~14 天。

## 八、值班 runbook 与复盘

| 级别 | 判定 | 首次响应 | 通报 |
| --- | --- | --- | --- |
| P0 | 全站不可用、资损、数据错误扩散 | 5 分钟 | 拉群 + 电话 |
| P1 | 核心链路错误率 > 5% 或 P99 > 1s | 15 分钟 | 值班群 + 负责人 |
| P2/P3 | 非核心降级、单实例异常、告警抖动 | 30 分钟 | 值班群 / 工单 |

处置顺序固定：**确认影响面（看板）→ 止血（回滚/扩容/限流/熔断）→ 定位（trace + 日志）→ 记录时间线 → 复盘**。每条告警的 `runbook_url` 至少包含：含义与阈值、影响面判断、三种常见原因、止血命令、升级联系人。

```text
故障复盘模板
1. 概要：发生/发现/恢复时间、影响用户数、资损估算、定级
2. 时间线：分钟粒度，记录谁做了什么、看到什么结果
3. 根因：直接原因 + 根本原因（设计/流程/容量），附监控与 trace 证据
4. 改进项与检测能力：每条带负责人与截止时间，区分立即修复/短期/长期；新增的告警、看板、演练项
```

## 常见坑

1. **告警没有 `for`**：一次抖动打爆电话，几天后所有人开始屏蔽告警。
2. **用 4xx 算错误率**：用户输错密码触发 P0，真正的 5xx 被稀释。
3. **label 放高基数**：Prometheus 内存暴涨、查询超时；路由必须模板化。
4. **实例下线只看 `up == 0`**：目标被移除时序列消失，永远不触发；必须补 `absent()`。
5. **日志没有 trace_id**：指标发现异常后无法定位具体请求，只能靠时间点猜。
6. **告警阈值照抄别家**：流量与依赖不同，阈值必须由压测与历史数据推出。

## 小结

- 先用 SLI/SLO 定义「健康」，错误预算驱动发布与冻结决策
- 六类告警覆盖大部分事故，全部挂 runbook 并配 `for` 防抖
- Alertmanager 抑制压噪、Grafana 按 RED/四黄金信号分层，日志与 trace 用同一个 id 串联
